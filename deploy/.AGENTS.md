# Directory: deploy/

## Purpose
Артефакты развёртывания Control Plane по `docs/architectures/deployment.md`: Compose стенда и
разработки, конфигурация nginx (C-09), секреты, скрипты. Ноды (Xray + node-agent) ставятся на
удалённые VPS задачей 001.61 — здесь их нет.

## Files

### [README.md]
- Карта каталогов и запуск стенда одной командой.

### [compose/docker-compose.yml]
- Стенд (§10.1): `postgres` 18.6 (`archive_mode=on`, локальный архив WAL на томе до 001.67),
  `redis` 8.10 (`appendonly yes`, `noeviction`), `nginx` 1.30, роли приложения `api`,
  `worker-critical`, `worker-background`, `scheduler` из одного образа `control-plane/app:dev`
  (переменная `APP_ROLE`). Секреты — `secrets:` из файлов `compose/secrets/`, монтируются в
  `/run/host-secrets` (точка входа копирует их в `/run/secrets` пользователю `app`; `/run/secrets` —
  tmpfs у всех ролей приложения, копии не ложатся в записываемый слой контейнера, 001.25). Роли базы:
  приложение — `app_rw` (`pg_app_rw_password`), миграции `api` — `app_migrate`
  (`pg_app_migrate_password`), копии — `app_backup` (`pg_app_backup_password`); суперпользователь
  `postgres` (`pg_password`) — только bootstrap ролей при инициализации кластера.
  Архив WAL на томе ограничен 3 сутками. Порты nginx — `BIND_ADDR`, `HTTP_PORT`, `HTTPS_PORT`,
  `AGENT_PORT`, `ENROLL_PORT`.
- Якоря YAML: `x-app-env` — общее окружение ролей, `x-app` — общая часть служб приложения.

  `driver_opts` `device`, `env_file`, `develop.watch`, контексты и секреты сборки); путь с

  драйвера и `external`, секреты только литеральным `file`, `env_file` — только `.env`; новый
  механизм сначала пересматривается и вносится в список.

### [nginx/nginx.conf]
- Три `server`: публичный (80/443), агентский (8443, `ssl_verify_client on`, глубина 0 — лист,
  подписанный CA напрямую, `X-Client-Cert` из `$ssl_client_escaped_cert` — сертификат целиком,
  отпечаток SHA-256 считает C-01 (001.25); `$ssl_client_fingerprint` (SHA-1) не используется нигде),
  enrollment (8444, только `/agent/v1/enroll`); `X-Client-Cert` очищается на публичном и enrollment
  (правило границы 1). `ssl_crl` нет: отзыв identity действует в C-01 (401 со следующего запроса),
  отказ отозванному сертификату на прокси — 001.66. Н-25: `$loggable` из четырёх map — по
  нормализованному `$uri`, по признаку «`$uri` — служебный путь перехода `rewrite` своего server»
  (карта по `$server_port`: у публичного server служебных путей нет — раунд 9), по пути в сырой
  строке `$request` до «?» и «#» (читается только у служебного `$uri`: на 8443/8444 запрос,
  переведённый в служебный location, несёт к журналу служебный путь — 001.25, раунд 6; у остальных
  сырой ключ не читается — в раунде 8 суффикс `#/s/` прятал любой запрос из журнала целиком; косая
  вокруг «s» — и `%2F`) и по признаку «отвергнут до разбора URI» (пустой `$uri` при любом статусе:
  400 — негодный процент, 408 — строка не пришла за `client_header_timeout`, 414 — строка длиннее
  буфера, 505 — HTTP/2.0 поверх HTTP/1; `$request` тогда несёт сырые байты с токеном — строка
  пишется форматом `unparsed` без `$request`; раунд 9 знал только 400) — и `access_log off` в
  `location ^~ /s/`, там же `error_log /dev/null` (строка error.log любого уровня несёт строку
  запроса; остаток — строки до выбора location, в журнале уровня http), без временных файлов
  ответа и тела,
  `Referrer-Policy: no-referrer`; путь `/s/` на 8443/8444 до апстрима не доходит; referer с `/s/` в
  журнале заменяется на `-` — в любом написании, тем же шаблоном, что сырой ключ (регистр,
  `%73`/`%53`, косая `%2F`; 001.25, раунд 7). `access_log` — только на уровне http (ниже — только
  `off`: строка уровня server заменила бы пару с фильтром), `error_log` — не мягче `warn` (строки
  пределов с путём запроса — на `notice`), у переменной map писатель один — сама map (ни `set`, ни
  второй `map`/`geo`, ни именованной группы регулярного выражения; имя в кавычках — то же имя:
  стражи читают файл словами, как nginx), `command`/`entrypoint` в Compose — только у postgres и
  redis (001.25, раунд 7); `$remote_addr` — адрес соединения: realip (`set_real_ip_from`,
  `real_ip_header`) и `proxy_protocol` запрещены — `enrolled_from` и пределы по адресу иначе брали
  бы адрес из заголовка (раунд 8). `$uri` меняют только шесть переходов `rewrite` 8443/8444 в
  служебные location: `error_page` — только в именованный location, `try_files` — проба
  `/nonexistent` и код, каждый location решает сам (`proxy_pass`, `return`, `try_files`) — отдачи
  файлов и `index` нет, `proxy_ignore_headers X-Accel-Redirect` на уровне http (ниже — ни
  одного), модулей скриптов нет: внутренний переход увёл бы запрос подписки из `location /s/` на
  путь, который журнал пишет (стенд: `error_page 50x` на `/50x.html` при лежащем api — токен в
  access.log и error.log; роаст 001.25, раунд 9). Публичный `server` отдаёт 404 на `/agent…` и на `/metrics`
  (метрики снимает C-10 внутри сети с `api:8000`, 001.10). Первое правило каждого server — путь с
  управляющими символами (map `$uri_has_control` по декодированному `$uri`, класс
  `[\x00-\x1f\x7f]`): публичный — `return 404`, 8443 и 8444 — `rewrite ^ /__not_found last` в
  служебный `location` без предела тела с `try_files /nonexistent =404` (после пределов); без него
  `%0A` в конце пути доходил до `api` (`$` в шаблоне маршрута Starlette совпадает перед завершающим
  `\n`) — `/metrics%0A` отдавал метрики наружу (роаст 001.25, раунд 5); второй слой — промежуточный
  слой `api` (`app/errors.py`). Пределы агентского `server` (001.33): тела без известной длины
  (chunked, поток HTTP/2 без content-length) на агентском и enrollment-server не принимаются — map
  `$body_without_length` на уровне http, `if … rewrite ^ /__length_required last` в служебный
  `location` с `try_files /nonexistent =411` и `error_page 411 = @length_required` на уровне обоих
  server (411 в едином формате без `Retry-After`; `Content-Length` обязателен по контракту;
  отсутствие длины — у любого метода, кроме GET и HEAD; служебный `location` не `internal` —
  внешнему запросу к `internal` nginx отвечает 404 в фазе FIND_CONFIG, до пределов; внешний запрос
  туда получает 404 в `@length_required`); 404 — `try_files /nonexistent =404`, 5xx апстрима — через
  именованные `location` единого формата (`error_page 404 = @not_found`, `error_page 502 503 504 =
  @upstream_unavailable`): `return` вне именованных `location` исполняется в фазе (SERVER_)REWRITE
  до пределов PREACCESS, и `error_page` после него пределов не даёт (стенд: 30 × 411 и 404 без 429 —
  роаст 001.25, раунд 3), а `try_files` решает после них; `client_header_timeout 5s` и
  `reset_timedout_connection on` на уровне http — полуоткрытое соединение не держит слот worker'а
  минуту: без таких тел нет ни временных файлов тел, ни сырого потока с обрамлением без верхней
  границы; тело — 64 КиБ на уровне server с буфером 64 КиБ (тело читается до отказа по версии и
  identity; буфер равен пределу — во временный файл не пишется) и 1 МиБ только в `location =
  /agent/v1/reports` с буфером 1 МиБ (предел выведен из пределов модели одной части отчёта — 500
  строк / 2 500 адресов из бюджета Н-4 по `urt` при двух одновременных: самое большое допустимое
  тело 457 369 Б помещается, полоса выброшенного разбора — не шире 1 МиБ); временные файлы прокси —
  `client_body_temp_path` и `proxy_temp_path` под `/var/cache/nginx`, смонтированным в Compose как
  tmpfs 64 МиБ (mode 0711 — рабочему процессу nginx нужен проход в подкаталоги) под потолком памяти
  — тела пишет туда только публичный server телами больше буфера 16k (пределы — 001.66), ответы
  апстрима сверх буферов — до `proxy_max_temp_file_size` 8 МиБ на ответ (запрет файлов держал бы
  апстрим на скорости клиента); `proxy_request_buffering on` и `proxy_buffering on` объявлены явно
  (на них трактовка Н-4 по `urt`), `proxy_connect_timeout 2s`, `proxy_send_timeout 10s`,
  `proxy_read_timeout 10s` в location отчётов; `client_body_timeout 10s` на уровне обоих server;
  `ssl_verify_depth 0` (только листы, подписанные CA напрямую: в OpenSSL глубина считает
  промежуточных CA, 001.25); отказы 404, 411 и 413 на 8443/8444 — `try_files` после пределов (путь с
  управляющими символами, тело без длины и тело длиннее предела location — переход `rewrite … last`
  в служебные `location = /__not_found`, `= /__length_required` и `= /__too_large`; длину сверяют
  карты по `Content-Length` на уровне http с порогами `client_max_body_size` каждого location, путь
  в шаблонах карт закреплён `\z` — `$` в PCRE, как и в Python, совпадает перед завершающим `\n`; у
  служебных 404 и 413 предела тела нет; прямой запрос к `/__too_large` без признака длины — 404
  единого формата в `@too_large` по карте `$too_large_requested_directly` от
  `"$agent_body_too_large:$uri"`), `return` — только в именованных location (и первое правило
  публичного server), `rewrite` — только эти три перехода, `internal` нет, у prefix-location с
  `proxy_pass` на «/» — точный сосед без косой черты (иначе auto_redirect — 301 в FIND_CONFIG, до
  пределов); отказы, которые nginx выносит при разборе заголовков (400 — разбор, негодный Host,
  `Content-Length` с `Transfer-Encoding`, сбой или отсутствие клиентского сертификата, HTTP без TLS;
  405 `TRACE` и `CONNECT`; 408 — заголовки не дошли за `client_header_timeout`; 414; 494; 501 —
  неизвестный `Transfer-Encoding`), пределов не знают — журнал от анонимного залпа пределы не
  защищают (001.66); `ssl_trusted_certificate` и `ssl_conf_command` на уровне http и на агентском
  server запрещены — второй якорь клиента; одновременность и частота по серийному номеру клиентского
  сертификата (`$ssl_client_serial`, внутри подписанного тела: у близнеца листа по податливости
  ECDSA отпечаток другой, номер тот же — 001.25, проверено на стенде) — зоны `agent_conn` (8 на ноду
  на весь server, повторено в `location` отчётов: location со своим `limit_conn` не наследует
  server), `agent_report_conn` (1 отчёт на ноду — части идут последовательно), `agent_report_rate`
  (2 в секунду, очередь 10, без nodelay), `agent_rate` (5 в секунду, очередь 20) и общие потолки
  парка с постоянным ключом `"agent"` — `agent_report_total` (2 отчёта на парк — бюджет Н-4;
  пропускная способность парка 2 / (заливка + разбор) ≈ 17 частей в секунду) и `agent_fleet_rate`
  (15 в секунду на парк, очередь 200 — самый дорогой путь отказа 64-КиБ тела после проверки формы по
  байтам 2 мс по p95, доля цикла в гейте; очередь сливается за 14 с — таймаут остальных операций у
  агента ≥ 30 с, long-poll ≥ 60 с) на остальные операции в `location ^~ /agent/v1/`;
  enrollment-server — пределы по адресу источника (`$binary_remote_addr`: `enroll_addr_rate` 1 в
  секунду с очередью 5, `enroll_conn_addr` 4 — один адрес не выбирает enrollment всему парку) и
  общий потолок `enroll_fleet_rate` (2 в секунду, очередь 10, ключ `"enroll"`), буфер 64 КиБ, те же
  `@rate_limited` и `@length_required`; запрос в очереди `limit_req` слота `limit_conn` не держит
  (проверено на стенде); сверх — 429 в едином формате ошибки с `Retry-After: 1` (`error_page 429 =
  @rate_limited` на обоих server); отказы и задержки пределов не пишутся в error.log уровня warn
  (`limit_req_log_level` и `limit_conn_log_level notice`), `resolver_timeout 5s`; `include` кроме
  таблицы MIME запрещён; `log_format` несёт `rt=$request_time urt=$upstream_response_time` (Н-4 по
  `urt` измерим на стенде); в Compose — у `api` `mem_limit` = `memswap_limit` 1g, у `nginx` 256m
  (без swap — cgroup `memory.swap.max` 0; вывод из замеров контейнеров на стенде и худших тел, не
  измерение под нагрузкой — 001.73 меряет; политика перезапуска после OOM — 001.66), `cpus` (nginx
  1.0, api 2.0) и `pids_limit` (nginx 256, api 512), tmpfs `/var/cache/nginx` 64 МиБ с правами 0711
  (рабочему процессу nginx нужен проход в подкаталоги), журналы всех служб `json-file` 10 МиБ × 3
  (`x-logging`). После правки `nginx.conf` контейнер пересоздаётся (`up -d --force-recreate nginx`):
  файл смонтирован как bind mount, и после rsync `nginx -s reload` читает прежний inode. Страж всего
  перечисленного — `control-plane/tests/unit/test_proxy_contract.py` (список файлов Compose — из
  команды запуска в шапке `docker-compose.yml`, сверенной с `deploy/README.md`; любой другой
  `*.y*ml` в каталоге, `include:` и `extends:` — отказ; каждый проксирующий `location` обоих server
  Node API обязан нести зону по своему ключу и зону парка; `ports` — список разрешений
  `ALLOWED_PORTS`: четыре порта nginx на `${BIND_ADDR:-0.0.0.0}`, postgres и redis — только на
  литеральном `127.0.0.1` (адрес переменной открывал их среде запуска — стенд с `0.0.0.0`, роаст
  001.25, раунд 6), у `api` и прочих служб портов нет — иначе опубликованный `api:8000` обходил бы
  прокси целиком, раунд 5). Заголовки прокси `X-Forwarded-For`/`X-Real-IP`/`X-Forwarded-Proto`
  **перезаписываются** (`$remote_addr`, `$scheme`/`https`), не дополняются: uvicorn запущен с
  `--forwarded-allow-ips '*'` и берёт крайний левый элемент цепочки — дополнение дало бы клиенту
  подделку адреса; контракт закреплён `control-plane/tests/unit/test_proxy_contract.py`. Служебный
  `server` 127.0.0.1:8081 `/-/health` — для healthcheck Compose. Апстрим `api` резолвится через
  `resolver 127.0.0.11` (переменная `$api`).

### [scripts/dev-secrets.sh]
- Генерация секретов и dev CA/сертификатов (`tls/agent`, `tls/public`, клиентский
  `dev/dev-node` для проверки mTLS). Идемпотентен; `--force` пересоздаёт.

### [compose/postgres/entrypoint.sh]
- Обёртка точки входа образа postgres: копирует секреты паролей ролей в `/run/pg-secrets`
  пользователю `postgres` (скрипты initdb.d выполняются не от root), затем штатный
  `docker-entrypoint.sh`.

### [compose/postgres/initdb.d/10-roles.sh]
- Создание ролей при инициализации кластера: `psql -f /opt/control-plane/roles.sql`
  (`control-plane/migrations/bootstrap/roles.sql`) с паролями из `/run/pg-secrets`. Выполняется
  только на пустом томе; на существующем — тот же SQL вручную (secrets/README.md).

### [scripts/vm-sync.sh]
- rsync рабочего дерева на VM стенда (`VM_HOST`, `VM_DIR`; `--dry-run`), без `.env`, секретов,
  `.venv`, `node_modules`, `.bin`, каталогов фреймворка. См. `skills/vm-deploy/SKILL.md`.

### [scripts/stand-tunnel.sh]
- `start|status|stop` — туннель ssh (`VM_HOST`, управляющий сокет в `$TMPDIR`) к PostgreSQL и
  Redis стенда: они опубликованы только на `127.0.0.1` VM, туннель отдаёт те же порты
  (`PG_HOST_PORT`, `REDIS_HOST_PORT`, по умолчанию 15432 и 16379) на `127.0.0.1` рабочей машины
  (001.25, раунд 6).

## Conventions
- Версии образов закреплены точно (`postgres:18.6`, `redis:8.10`, `nginx:1.30`,
  `python:3.14-slim`) и совпадают с `docs/architectures/stack.md`.
- `docker compose` вызывается с `--env-file deploy/compose/.env` и обоими `-f` из корня
  репозитория; Docker на рабочей машине не устанавливается — стенд на VM
  (`skills/vm-deploy/SKILL.md`).
- `proxy_set_header` в nginx повторяется целиком в каждом `server` (не наследуется частично).
