# Directory: deploy/

## Purpose
Артефакты развёртывания Control Plane по `docs/architectures/deployment.md`: Compose стенда и
разработки, конфигурация nginx (C-09), секреты, скрипты. Ноды (Xray + node-agent) ставятся на
удалённые VPS задачей 001.61 — здесь их нет.

## Files

### [README.md]
- Карта каталогов и запуск стенда одной командой.

### [compose/docker-compose.yml]
- Стенд (§10.1): `postgres` 18.6 (`archive_mode=on`, локальный архив WAL на томе до 001.67),
  `redis` 8.10 (`appendonly yes`, `noeviction`), `nginx` 1.30, роли приложения `api`,
  `worker-critical`, `worker-background`, `scheduler` из одного образа `control-plane/app:dev`
  (переменная `APP_ROLE`). Секреты — `secrets:` из файлов `compose/secrets/`, монтируются в
  `/run/host-secrets` (точка входа копирует их в `/run/secrets` пользователю `app`). Роли базы:
  приложение — `app_rw` (`pg_app_rw_password`), миграции `api` — `app_migrate`
  (`pg_app_migrate_password`), копии — `app_backup` (`pg_app_backup_password`); суперпользователь
  `postgres` (`pg_password`) — только bootstrap ролей при инициализации кластера.
  Архив WAL на томе ограничен 3 сутками. Порты nginx — `BIND_ADDR`, `HTTP_PORT`, `HTTPS_PORT`,
  `AGENT_PORT`, `ENROLL_PORT`.
- Якоря YAML: `x-app-env` — общее окружение ролей, `x-app` — общая часть служб приложения.

### [compose/docker-compose.dev.yml]
- Разработка: публикация PostgreSQL/Redis на `DEV_BIND_ADDR:PG_HOST_PORT|REDIS_HOST_PORT`,
  монтирование `control-plane/app` в контейнеры, `APP_RELOAD=1` для `api`.

### [compose/.env.example]
- Переменные без секретов: домены, режимы, порты, `PG_ARCHIVE_COMMAND`. Копируется в `.env`.

### [compose/secrets/README.md]
- Перечень Docker secrets (`pg_password`, `pg_app_rw_password`, `pg_app_migrate_password`,
  `app_encryption_key`, `ca_key`, `smtp_password`, `pgbackrest_key`) и сертификатов `tls/`
  (серверные) и `dev/` (клиентский тестовый) с командами создания. Сами файлы — вне репозитория.

### [nginx/nginx.conf]
- Три `server`: публичный (80/443), агентский (8443, `ssl_verify_client on`,
  `X-Client-Fingerprint` из `$ssl_client_fingerprint`), enrollment (8444, только
  `/agent/v1/enroll`). Н-25: `$loggable` из трёх map — по нормализованному `$uri`, по пути в
  сырой строке `$request` до «?» (строка запроса журнал не глушит — иначе любой клиент прятал
  бы себя суффиксом `?/s/`) и по признаку «отвергнут до разбора URI» (запрос с негодным
  процентом в пути отвергается с пустым `$uri`, а `$request` несёт токен — такая строка
  пишется форматом `unparsed` без `$request`) — и `access_log off` в `location ^~
  /s/`, там же `error_log … crit` и `Referrer-Policy: no-referrer`; referer с `/s/` в журнале
  заменяется на `-`. Публичный `server` отдаёт 404 на `/agent…` и на
  `/metrics` (метрики снимает C-10 внутри сети с `api:8000`, 001.10). Пределы агентского
  `server` (001.33): тела без известной длины (chunked, поток HTTP/2 без content-length) на
  агентском и enrollment-server не принимаются — map `$body_without_length` на уровне http,
  `if … return 411` и `error_page 411 = @length_required` на уровне обоих server (411 в едином
  формате без `Retry-After`; `Content-Length` обязателен по контракту; отсутствие длины — у
  любого метода, кроме GET и HEAD); 404 и 5xx апстрима — тоже через именованные `location`
  единого формата (`error_page 404 = @not_found`, `error_page 502 503 504 =
  @upstream_unavailable`): `return` прямо в `location` исполняется в фазе REWRITE до пределов
  PREACCESS, внутренний редирект проходит их заново; `client_header_timeout 5s` и
  `reset_timedout_connection on` на уровне http — полуоткрытое соединение не держит слот
  worker'а минуту: без таких тел нет ни
  временных файлов тел, ни сырого потока с обрамлением без верхней границы; тело — 64 КиБ на
  уровне server с буфером 64 КиБ (тело читается до отказа по версии и identity; буфер равен
  пределу — во временный файл не пишется) и 1 МиБ только в `location = /agent/v1/reports` с
  буфером 1 МиБ (предел выведен из пределов модели одной части отчёта — 500 строк / 2 500
  адресов из бюджета Н-4 по `urt` при двух одновременных: самое большое допустимое тело
  457 369 Б помещается, полоса выброшенного разбора — не шире 1 МиБ); временные файлы
  прокси — `client_body_temp_path` и `proxy_temp_path` под `/var/cache/nginx`, смонтированным
  в Compose как tmpfs 64 МиБ (mode 0711 — рабочему процессу nginx нужен проход в подкаталоги)
  под потолком памяти — тела пишет туда только публичный server телами больше буфера 16k
  (пределы — 001.66), ответы апстрима сверх буферов — до `proxy_max_temp_file_size` 8 МиБ на
  ответ (запрет файлов держал бы апстрим на скорости клиента); `proxy_request_buffering on` и
  `proxy_buffering on` объявлены явно (на них трактовка Н-4 по `urt`), `proxy_connect_timeout
  2s`, `proxy_send_timeout 10s`, `proxy_read_timeout 10s` в location отчётов; `client_body_timeout 10s` на уровне обоих server; `ssl_verify_depth 1` (только
  листы CA);
  одновременность и частота по отпечатку клиентского сертификата — зоны `agent_conn` (8 на
  ноду на весь server, повторено в `location` отчётов: location со своим `limit_conn` не
  наследует server), `agent_report_conn` (1 отчёт на ноду — части идут последовательно),
  `agent_report_rate` (2 в секунду, очередь 10, без nodelay), `agent_rate` (5 в секунду,
  очередь 20) и общие потолки парка с постоянным ключом `"agent"` — `agent_report_total` (2
  отчёта на парк — бюджет Н-4; пропускная способность парка 2 / (заливка + разбор) ≈ 17
  частей в секунду) и `agent_fleet_rate` (15 в секунду на парк, очередь 200 — самый дорогой путь
  отказа 64-КиБ тела после проверки формы по байтам 2 мс по p95, доля цикла в гейте; очередь
  сливается за 14 с — таймаут
  остальных операций у агента ≥ 30 с, long-poll ≥ 60 с) на остальные операции в `location ^~
  /agent/v1/`; enrollment-server — пределы по адресу источника (`$binary_remote_addr`:
  `enroll_addr_rate` 1 в секунду с очередью 5, `enroll_conn_addr` 4 — один адрес не выбирает
  enrollment всему парку) и общий потолок `enroll_fleet_rate` (2 в секунду, очередь 10, ключ
  `"enroll"`), буфер 64 КиБ, те же `@rate_limited` и `@length_required`; запрос в очереди
  `limit_req` слота `limit_conn` не держит (проверено на стенде); сверх — 429 в едином
  формате ошибки с `Retry-After: 1` (`error_page 429 = @rate_limited` на обоих server);
  отказы и задержки пределов не пишутся в error.log уровня warn (`limit_req_log_level` и
  `limit_conn_log_level notice`), `resolver_timeout 5s`; `include` кроме таблицы MIME запрещён;
  `log_format` несёт `rt=$request_time urt=$upstream_response_time` (Н-4 по `urt` измерим на
  стенде); в Compose — у `api` `mem_limit` = `memswap_limit` 1g, у `nginx` 256m (без swap —
  cgroup `memory.swap.max` 0; вывод из замеров контейнеров на стенде и худших тел, не измерение
  под нагрузкой — 001.73 меряет; политика перезапуска после OOM — 001.66), `cpus` (nginx 1.0,
  api 2.0) и `pids_limit` (nginx 256, api 512), tmpfs `/var/cache/nginx` 64 МиБ с правами 0711
  (рабочему процессу nginx нужен проход в подкаталоги), журналы всех служб `json-file`
  10 МиБ × 3 (`x-logging`). После правки `nginx.conf` контейнер
  пересоздаётся (`up -d --force-recreate nginx`): файл смонтирован как bind mount, и после
  rsync `nginx -s reload` читает прежний inode.
  Страж всего перечисленного — `control-plane/tests/unit/test_proxy_contract.py` (список файлов
  Compose — из команды запуска в шапке `docker-compose.yml`, сверенной с `deploy/README.md`;
  любой другой `*.y*ml` в каталоге, `include:` и `extends:` — отказ; каждый проксирующий
  `location` обоих server Node API обязан нести зону по своему ключу и зону парка). Заголовки прокси
  `X-Forwarded-For`/`X-Real-IP`/`X-Forwarded-Proto` **перезаписываются** (`$remote_addr`,
  `$scheme`/`https`), не дополняются: uvicorn запущен с `--forwarded-allow-ips '*'` и берёт
  крайний левый элемент цепочки — дополнение дало бы клиенту подделку адреса; контракт закреплён
  `control-plane/tests/unit/test_proxy_contract.py`. Служебный `server`
  127.0.0.1:8081 `/-/health` — для healthcheck Compose. Апстрим `api` резолвится через
  `resolver 127.0.0.11` (переменная `$api`).

### [scripts/dev-secrets.sh]
- Генерация секретов и dev CA/сертификатов (`tls/agent`, `tls/public`, клиентский
  `dev/dev-node` для проверки mTLS). Идемпотентен; `--force` пересоздаёт.

### [compose/postgres/entrypoint.sh]
- Обёртка точки входа образа postgres: копирует секреты паролей ролей в `/run/pg-secrets`
  пользователю `postgres` (скрипты initdb.d выполняются не от root), затем штатный
  `docker-entrypoint.sh`.

### [compose/postgres/initdb.d/10-roles.sh]
- Создание ролей при инициализации кластера: `psql -f /opt/control-plane/roles.sql`
  (`control-plane/migrations/bootstrap/roles.sql`) с паролями из `/run/pg-secrets`. Выполняется
  только на пустом томе; на существующем — тот же SQL вручную (secrets/README.md).

### [scripts/vm-sync.sh]
- rsync рабочего дерева на VM стенда (`VM_HOST`, `VM_DIR`; `--dry-run`), без `.env`, секретов,
  `.venv`, `node_modules`, `.bin`, каталогов фреймворка. См. `skills/vm-deploy/SKILL.md`.

## Conventions
- Версии образов закреплены точно (`postgres:18.6`, `redis:8.10`, `nginx:1.30`,
  `python:3.14-slim`) и совпадают с `docs/architectures/stack.md`.
- `docker compose` вызывается с `--env-file deploy/compose/.env` и обоими `-f` из корня
  репозитория; Docker на рабочей машине не устанавливается — стенд на VM
  (`skills/vm-deploy/SKILL.md`).
- `proxy_set_header` в nginx повторяется целиком в каждом `server` (не наследуется частично).
