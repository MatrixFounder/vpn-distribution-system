## Infra & VM ops (dev/test)

Docker на рабочей машине не устанавливается. Стенд Control Plane (Compose из `deploy/compose/`)
живёт в Parallels-VM Ubuntu — доступ **`ssh vm`** (IP не хардкодить). Для любой операции с VM,
Docker или стендом следуй скиллу **`vm-deploy`** (`skills/vm-deploy/SKILL.md`): репозиторий —
источник истины, на VM только `deploy/scripts/vm-sync.sh`; деструктивные действия (`down -v`,
`prune`, чужие контейнеры) — только с явного подтверждения. VPN-ноды на VM не ставятся —
только на удалённые VPS.

## Статусы задач в плане

`docs/PLAN.md` хранит статус каждой задачи в строке `Статус:` её записи (`принята — коммит <hash>
(<дата>)`, `в работе (с <дата>)`, `не начата`). После приёмки задачи: обновить эту строку и
выполнить `python3 docs/scripts/plan_graph.py --write` — он пересобирает раздел «Состояние
выполнения и граф зависимостей» (таблица, готовые к началу, критический путь, диаграмма Mermaid)
и отмечает пункты чек-листа RTM; `make lint-plan` (часть `make lint`) падает, если блок отстал.
Следующая задача выбирается из списка «Готовы к началу», а не по номеру.

## Развёртка устаревших чисел

Когда предел, частота или правило задачи меняются, прежние значения остаются в других документах
числом, словом или производной фразой. Шаблоны задачи — `docs/sweeps/<задача>.json` (старое
значение, текущее, формы); прогон — `python3 docs/scripts/sweep_stale.py --patterns
docs/sweeps/<задача>.json --since <базовый коммит>` после каждой смены предела и перед роастом.
Скрипт ищет без учёта регистра, разворачивает числа в словесные формы и отделяет подписанную
историю («в раунде 7», исторические разделы отчёта); совпадения вне истории либо исправляются,
либо объясняются в разделе «Регрессия» отчёта задачи. `make test-scripts` (часть `make test`)
проверяет сам скрипт.

## Цикл задачи

Правила приняты заказчиком 2026-10-21 по WI-35 (`docs/backlog/wi-35-task-cycle-speedup.md`) и
уточняют для этого проекта `vdd-03-develop` и `developer-guidelines` §6.3 п. 8.

1. **«Решить здесь» — до кода.** До первого шага сборщика (Step 2.1) каждый пункт «решить здесь»
   файла задачи разбирается. Решённое принятой задачей, архитектурой, контрактом или кодом
   вносится в тело задачи (цель, изменения, тесты, критерии приёмки) со ссылкой на источник.
   Техническая заметка, не меняющая поведения, тоже вносится в тело. Выбор поведения (что
   списывается, какой статус, какой предел, кто владелец, что видит пользователь) уходит
   заказчику вопросом с вариантами и рекомендацией. Реализация начинается после ответов; ответ
   записывается в тело задачи с датой, пункт «решить здесь» снимается. Правила одной операции
   до кода проходят общий сценарий (отказ, повтор, деление, поздняя часть) с конкретными числами.
2. **Посадка — на подмножестве.** Посадка мерится прогоном тестов, достигающих изменённого кода:
   файлы её ожидаемых тестов и тестовые файлы, импортирующие посаженный модуль (для миграции —
   тесты схемы и миграций её группы). Прогон — без `-x` и `--maxfail`; команда подмножества
   пишется в строку посадки. Посадка, зелёная на подмножестве, перемеряется полным набором до
   вывода «страж не работает». Полный набор (`make check`) — прогон окончательного дерева перед
   каждым роастом и перед коммитом.
3. **Между раундами перемеряются только затронутые посадки** — те, у которых изменился образец,
   код вокруг образца (функция или блок, где он стоит) или ожидаемые тесты. Остальные проходят
   сухую проверку: образец совпадает с деревом ровно один раз. Отчёт задачи перечисляет
   перемеренные посадки с причиной и число сухих.
4. **Крупная задача делится до старта.** Задача, объединяющая несколько независимых правил
   поведения (масштаб 001.34: идемпотентность, допуск времени, интервалы частей, потолки, якорь,
   порог, метрика), делится в плане на задачи, каждая из которых принимается отдельно со своими
   стражами и посадками. Ориентир — оценка до 4 ч и до трёх независимых правил на задачу.
