# Контракт Node API `/agent/v1`

Зафиксированные запросы и ответы раздела `/agent/v1` (`docs/architectures/interfaces.md` §5.2).
Каталог общий для двух сторон обмена: Control Plane воспроизводит фикстуры в
`control-plane/tests/contract/test_agent_v1.py` — это и есть стадия «Контракты» конвейера
(`docs/architectures/deployment.md` §10.2), цель `make test-contract`. Сторона агента
(`node-agent/internal/contracts/contracts_test.go`, задача 001.53) читает те же файлы; пока её
нет, стадия проверяет одну сторону.

Файлы правятся людьми. Изменение контракта обязано быть видно в diff — тесты фикстуры только
читают и никогда не перезаписывают. Ответы сняты с заглушек задачи 001.28: значения
фиксированные, но форма ответа — настоящая.

## Формат файла

```json
{
  "operation": "state",
  "summary": "одна строка о том, какой случай зафиксирован",
  "given": {"node_status": "active"},
  "request": {
    "method": "GET",
    "path": "/agent/v1/state",
    "query": {"config_version": "0"},
    "headers": {"X-Agent-Version": "0.1.0"},
    "body": null
  },
  "response": {"status": 200, "headers": {"Cache-Control": "no-store"}, "body": {}}
}
```

- `given` — предусловие на стороне Control Plane. Статус ноды (§4.6) живёт на сервере, а не в
  запросе, но определяет ответ целиком: без него фикстура не воспроизводима. Значение — из
  перечисления `node_status`.
- `query` — параметры строки запроса как текст: клиент собирает URL из них без преобразований.
- `headers` — заголовки запроса как он уходит в фикстуре. В бою нода шлёт `X-Agent-Version` и
  `X-Node-Identity`; `X-Client-Fingerprint` ставит прокси из клиентского сертификата (§7.1) и
  переписывает безусловно — агент его не отправляет. В фикстурах он приведён, чтобы запрос
  воспроизводился без mTLS.
- `body: null` — тела нет: в запросе GET, в ответе 204.
- `response.headers` — подмножество заголовков, которые обязаны присутствовать, а не все. В нём
  `Content-Type`, `Cache-Control` (ответ состояния везёт credentials и не кэшируется) и
  `Retry-After` (единственный рычаг, которым сервер управляет частотой опроса: 3600 с после 426 —
  обновление парка делает администратор, 300 с после 403 — подтверждение ноды тоже, 1 с после
  409 — снапшот нода берёт сама).
- Ответ сверяется по разобранному JSON, а не побайтно: порядок ключей и пробелы значения не имеют.
- Секретов в фикстурах нет. `bootstrap_token` и `identity_token` — заведомо распознаваемые
  строки-заглушки, а `vless_uuid` и `trojan_password` выведены детерминированно из пары
  «нода × пользователь» и публичны. В бою и то и другое — только CSPRNG (§7.2): схему выведения
  переносить в генератор credentials (001.29) нельзя.
- Сроки в фикстурах не протухают: команда канала объявлена с заведомо дальним `expires_at`,
  потому что агент обязан сверять его перед исполнением, и команда, устаревшая от одного лишь
  течения времени, дала бы красный контрактный тест на верной реализации агента.

## Полнота состава

`users.full` — разрешение удалить: приняв ответ с `true`, нода удаляет из inbound всех, кого в
нём нет (`data-model.md` §4.2.3). `false` стоит у дельты и у любого урезанного ответа — в том
числе у снапшота, запрошенного нодой в статусе, где вентиль §4.6 скрывает часть состава, и у
ответа, урезанного будущим пределом размера выборки. Правило одно: удалять можно только по
ответу, который объявил себя полным. Обычная дельта тоже приходит с `full: false` — и с
`resync_required: false`: неполнота дельты нормальна, пересинхронизации она не требует.

`users.seq` продвигается по выборке **до** фильтра по статусу: строки, скрытые вентилем, нода
добирает снапшотом, а не повторной дельтой, иначе она застревала бы на каждом изменении, которое
вентиль не пропустил.

Курсор больше выданного Control Plane — отказ 409 `cursor_ahead` на **дельту**, а не 204: после
восстановления сервера из копии нода обязана взять снапшот, а не считать себя актуальной. Запрос
`full=1` при этом обслуживается: снапшот присланный курсор игнорирует и сам ставит `users.seq`
по состоянию сервера — это и есть выход из положения «нода впереди».

### Когда пересинхронизироваться и когда остановиться

- `resync_required: true` — нода не синхронизирована: она обязана запросить `full=1`.
- Ответ с `users.full: true` — пересинхронизация выполнена; в нём `resync_required` уже `false`.
  Это и есть условие остановки, и оно наблюдаемо: своего статуса нода не знает.
- Ответ на `full=1`, пришедший с `users.full: false`, означает, что полный состав сейчас выдать
  нельзя — вентиль по статусу его урезал (§4.6, «Только отзывы»). Повторять снапшот немедленно
  бесполезно: ответ не изменится, пока администратор не снимет статус. Агент обязан отступать с
  выдержкой, а не опрашивать в цикле.

### Ключи в потоке состава

`credentials` несёт только строка, выдающая доступ (`state: "active"`): ключ нужен, чтобы
добавить пользователя в inbound. Отзыв, приостановка и удаление применяются по тегу
`xray_email`, поэтому такие строки идут без ключей — и отключённая нода живых ключей не
получает вовсе.

## Контрольная сумма конфигурации

`config.checksum` — SHA-256 канонической записи `config.json` в шестнадцатеричном виде, нижним
регистром. Каноническая запись: ключи объектов отсортированы, разделители без пробелов (`,` и
`:`), не-ASCII символы не экранируются, кодировка UTF-8. Сериализация самого ответа при этом может
отличаться — нода считает сумму от разобранного документа, а не от полученных байтов.

- Python: `json.dumps(document, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`
  (`control-plane/app/domain/composition.py::config_checksum`).
- Go: `json.Encoder` с `SetEscapeHTML(false)` — ключи `map[string]any` он сортирует сам, пробелов
  не добавляет; завершающий перевод строки, который дописывает `Encode`, в сумму не входит.

Чтобы обе записи совпадали, документ конфигурации ограничен — генератор (001.26, 001.27) обязан
это соблюдать:

- числа — только целые в диапазоне ±2⁵³ и без экспоненты. `1.0` Python пишет как `1.0`, а Go
  через `map[string]any` — как `1`; за пределами ±2⁵³ Go искажает значение, а от 1e21 переходит
  на экспоненту;
- строки не содержат U+2028 и U+2029: `encoding/json` экранирует их всегда, независимо от
  `SetEscapeHTML(false)`, а Python с `ensure_ascii=False` — нет;
- строки не содержат управляющих символов: Python пишет U+0008 и U+000C как `\b` и `\f`, Go — как
  `\u0008` и `\u000c`.

Метки времени в ответе сериализует pydantic: UTC записывается с `Z` (`2026-09-01T00:00:00Z`), а не
с `+00:00`. Обе записи — валидный RFC 3339, но в фикстурах встречается только первая.
