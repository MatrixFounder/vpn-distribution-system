# Задача 001.20: Redeem- и Promo-коды: генерация, экспорт, активация, учёт использования

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-02 Регистрация и активация подписки Redeem-кодом
- UC-06 Продление и смена тарифа
- UC-09 Управление тарифами, группами и кодами

Требования RTM: R-08, R-31, R-32, R-33.

<!-- contract:goal -->

## Цель задачи

Реализовать `CodeService`: партии кодов с шифрованием для экспорта, ограничения использования,
погашение через `SubscriptionService` одной транзакцией по правилам «состояние подписки × вид кода
× тариф кода» и регистрацию по приглашению Redeem-кодом. Генерация и контрольная сумма — 001.18.

- Изменение принятого кода (отступление от 001.18): валидатор `CodeSpec` — Redeem-код (`kind = redeem`) без `plan_id` отклоняется, 422 `validation_error`; у Promo-кода `plan_id` необязателен и означает ограничение «только для подписки этого тарифа» (решение заказчика 2026-10-25, В-22); тесты 001.18, создающие Redeem-код без тарифа, получают тариф
- `redeem(user_id, code, *, conn=None)`: проверка суммы до базы, срока, `max_uses`, `max_uses_per_user`, затем правило погашения по таблице ниже; вызов `SubscriptionService.activate|renew|extend|add_traffic`; запись `code_redemptions`; при переданном `conn` — в транзакции вызывающего (регистрация по приглашению, `app/domain/users.py`); лимит частоты — `ratelimit.redeem_account(user_id)` и `ratelimit.redeem_ip(ip)`: каждая попытка, в том числе с неверной суммой, считается в обоих счётчиках
- правило погашения (решение заказчика 2026-10-25, В-22, В-23, В-24) — по состоянию текущей подписки под блокировкой строки `subscriptions`; «нет подписки» — строки `subscriptions` нет или `state = 'none'`; `active` и `suspended_quota` с `period_end <= now()` (планировщик 001.83 ещё не перевёл) — как `expired`; при отказе код не расходуется, `code_redemptions` и `uses_count` не меняются:

  | Состояние подписки | Redeem-код | Promo-код |
  | :--- | :--- | :--- |
  | `suspended_admin` | 409 `subscription_blocked` | 409 `subscription_blocked` |
  | нет подписки | `activate` тарифа кода | 409 `no_active_subscription` |
  | `expired` | тариф кода равен тарифу подписки — `renew`; иначе 409 `code_plan_mismatch` | 409 `no_active_subscription` |
  | `active`, `suspended_quota` | тариф кода равен тарифу подписки — `renew`; иначе 409 `code_plan_mismatch` | `plan_id` кода задан и не равен тарифу подписки — 409 `code_plan_mismatch`; иначе бонусы к текущему периоду |

- бонус дней (`duration_bonus_days` = N > 0; В-23): Promo-код — `extend(user_id, N, conn=...)`: `period_end` текущего периода + N дней на месте, лимит, израсходованное и состояние не меняются (`suspended_quota` остаётся); Redeem-код — тот же `extend` над периодом, который открыл `activate` или `renew` этого погашения: срок нового периода — срок тарифа + N дней
- `activate(user_id, plan_id, source, *, source_id=...)` и `renew(..., *, source_id=...)` получают `source_id` = `codes.id` (колонка `subscription_periods.source_id`) и возвращают `PeriodId` нового периода: бонус того же погашения пишется в `balance_entries` этого периода без запроса `subscriptions.current_period_id`
- бонус трафика — `add_traffic(user_id, bytes, actor, reason, *, ref_key=...)` (001.22) к периоду погашения (Redeem-код — к новому периоду, Promo-код — к текущему): отрицательная дельта журнала баланса, а не правка лимита, 001.20 ничего не считает сама; `actor` не передаётся (`None`: иначе запись уйдёт как `adjustment` и потребует причины, `CHECK (source <> 'adjustment' OR reason IS NOT NULL)` §4.2.4), `reason` необязателен, `ref_key` = `redemption:{code_redemptions.id}`
- повтор погашения отсекают блокировка строки кода и проверка `max_uses`/`max_uses_per_user` в одной транзакции (`balance_entries.ref_key` не уникален)
- после активации или продления — `emit(conn, subscription_activated, user_id=..., dedup_key=subscription_activated:{user_id}:{period_id})` (001.51) в той же транзакции; бонус дней Promo-кода нового периода не открывает и события не порождает
- `export`: расшифровка `code_enc` — строки CSV всех кодов партии; разрешение `codes.export` у маршрута и вызов `audit.record` — 001.46, проверка строки `audit_log` — 001.48

### Интеграция компонентов

Погашение — одна транзакция: блокировка строк кода и подписки, проверки, правило погашения,
`code_redemptions`, `uses_count`, вызовы `SubscriptionService` (001.22) с `conn` и `emit` (001.51,
зависимость 001.20 → 001.51); бонус трафика → `balance_entries(source=bonus)`. Регистрация по
приглашению вызывает то же погашение в транзакции регистрации (001.14). Блокировку `suspended_admin`
ставит и снимает панель (001.50) через `set_state`; правка `activate` и `renew` этой задачи
сохраняет блокировку и при продлении администратором. Токен подписки при первой активации выпускает
`SubscriptionTokenService.ensure_token` (001.42) в транзакции `activate`, при погашении — через
переданный `conn` в транзакции погашения; отдельного вызова в `redeem` нет; проверка «после
погашения у пользователя есть действующий токен» — в этой задаче (TC-E2E-10). Режим регистрации
форма узнаёт из `GET /auth/aup` (поле `registration_mode`, маршрут — 001.69); поле Redeem-кода в
форме регистрации — 001.63 (В-31). Запись журнала создания кодов — `audit.record` и `AuditContext`
(001.46, зависимость 001.20 → 001.46); строки `audit_log` создания проверяет эта задача (001.48).

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Код активируется однократно
   - Входные данные: активация дважды одним пользователем при `max_uses_per_user = 1`
   - Ожидаемый результат: первая — 200 (`SubscriptionOut`), вторая — 409 `code_used`; в `events` одна строка `subscription_activated`
2. **TC-E2E-02:** Экспорт партии
   - Входные данные: партия из 100 кодов
   - Ожидаемый результат: CSV со 100 строками
3. **TC-E2E-03:** Погашение атомарно
   - Входные данные: сбой после `renew` в транзакции погашения
   - Ожидаемый результат: `code_redemptions` и `uses_count` не изменены; период не продлён
4. **TC-E2E-04:** Создание кодов в журнале аудита
   - Входные данные: `POST /admin/codes` и `POST /admin/codes/batch` сессией администратора
   - Ожидаемый результат: по одной строке `audit_log` на вызов с `actor_type = admin` и `actor_id` администратора; значений кодов в `new_value` нет
5. **TC-E2E-05:** Redeem-код по состоянию подписки
   - Входные данные: Redeem-код тарифа A с `traffic_bonus_bytes` = B; пользователи: без подписки; `active` тарифа A с израсходованным объёмом; `active` тарифа B; `expired` тарифа B; `suspended_admin` тарифа A
   - Ожидаемый результат: активация тарифа A с бонусом B в журнале нового периода; новый период тарифа A, израсходованное нового периода — 0; 409 `code_plan_mismatch`; 409 `code_plan_mismatch`; 409 `subscription_blocked`; при каждом отказе `uses_count` и `code_redemptions` не изменены
6. **TC-E2E-06:** Бонус дней
   - Входные данные: Promo-код с `duration_bonus_days` = 5 у подписок `active` (окончание через 10 дней) и `suspended_quota`; тот же код при `expired` и без подписки; Redeem-код тарифа на 30 дней с `duration_bonus_days` = 5 без подписки
   - Ожидаемый результат: `period_end` + 5 дней, `period_id`, лимит и `used_billable_bytes` прежние, `suspended_quota` сохранено; 409 `no_active_subscription` дважды; новый период длиной 35 дней
7. **TC-E2E-07:** Продление сохраняет блокировку администратора
   - Входные данные: подписка `suspended_admin`; `renew` с `source = admin`
   - Ожидаемый результат: новый период открыт; состояние `suspended_admin`; строки `node_user_state` пользователя остаются `removed`
8. **TC-E2E-08:** Регистрация по приглашению
   - Входные данные: `registration_mode = invite`; `POST /auth/register` без `code`; с действующим Redeem-кодом; с исчерпанным кодом; с Promo-кодом
   - Ожидаемый результат: 403 `invite_required`; 201 и подписка `active` тарифа кода, строка `code_redemptions`; 409 `code_exhausted` и строки `users` с этим адресом нет; 403 `invite_required`
9. **TC-E2E-09:** Redeem-код без тарифа
   - Входные данные: `POST /admin/codes` с `kind = redeem` без `plan_id`
   - Ожидаемый результат: 422 `validation_error`; строки `codes` нет
10. **TC-E2E-10:** Токен после погашения
    - Входные данные: погашение Redeem-кода пользователем без подписки; регистрация по приглашению
      с действующим Redeem-кодом; сбой после `activate` в транзакции погашения
    - Ожидаемый результат: после погашения и после регистрации у пользователя есть действующий
      токен, `GET /s/{token}` отвечает 200; задача `composition.publish_user` стоит в `jobs` в
      транзакции погашения; после сбоя токена и задачи нет

## Критерии приёмки

- [ ] Неверная контрольная сумма отклоняется без запроса к базе
- [ ] Ограничения использования действуют
- [ ] Экспорт содержит все коды партии
- [ ] Код, период и бонус одного погашения фиксируются одной транзакцией (TC-E2E-03)
- [ ] Погашение следует таблице «состояние подписки × вид кода × тариф кода»; Redeem-код без
  тарифа не создаётся (TC-E2E-05, TC-E2E-06, TC-E2E-09)
- [ ] Погашение кода и продление не снимают `suspended_admin` (TC-E2E-05, TC-E2E-07)
- [ ] В режиме `invite` регистрация проходит только с действующим Redeem-кодом и активирует
  подписку (TC-E2E-08)
- [ ] После погашения у пользователя есть действующий токен; публикация состава поставлена в
  транзакции погашения (TC-E2E-10)
