## Цель задачи

Реализовать в транзакции приёма отчёта (001.77) накопление `traffic_hourly` (только увеличение),
`close_hour(conn, node_id, at)` и поздний отчёт — повторную постановку суточной агрегации
`aggregate:{day}`. Пару «группа × коэффициент», долю строки удержанной части и час строки
накопление берёт из шагов 001.77.

### Изменения в существующих файлах

#### Файл: `control-plane/app/accounting/service.py`

- накопление `traffic_hourly` — в транзакции `_Acceptance` под блокировкой строки ноды, после записи строк `traffic_lines` (001.77): ключ строки часа — пара «группа × коэффициент» строки (001.77, шаг 4), час — `hour_of(period_start)` (001.77); операторы — пакетные, по правилу резерва 50 мс 001.77
- `close_hour(conn, node_id, at)` принимает подключение вызывающего (закрытие часа атомарно со сменой коэффициента в 001.19) — метод протокола `HourCloser` (`app/domain/groups.py`), в базу не пишет: закрытие часа держит ключ строки `traffic_hourly` (группа × коэффициент), записи после смены идут в новую строку часа; то же — в докстринге метода
- в `traffic_hourly` удержанная часть вносит только долю `charged` (решение заказчика 2026-10-25, В-2): `raw` часа — доля строки по направлениям после деления доли 001.77 (`split_charged`), `billable` — от этой доли; часть `capped` в `traffic_hourly` не вносит ничего. Полный присланный `raw` остаётся только в `traffic_lines` (14 суток); для часов с удержанными частями Σ `raw` строк `traffic_lines` больше `raw` строки `traffic_hourly`, и это не расхождение

### Сквозные тесты

1. **TC-E2E-01:** Поздний отчёт
   - Входные данные: отчёт за прошлые сутки (UTC `period_start`)

     изменена (AC-07)

   - Входные данные: повтор принятой и удержанной части
   - Ожидаемый результат: `traffic_hourly` не изменилась
4. **TC-E2E-04:** Части без периода
   - Входные данные: часть пользователя с пустым `current_period_id`; часть с `period_start`
     раньше начала первого периода
   - Ожидаемый результат: строки `traffic_hourly` записаны (баланс — 001.77c)
