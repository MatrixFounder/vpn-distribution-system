# Задача 001.29f: Версия раздела `agent` из колонки ноды

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-01 Ввод ноды в эксплуатацию
- UC-11 Обновление парка нод

Требования RTM: R-04.

## Цель задачи

Выдавать версию раздела `agent` ответа состояния (контракт 001.26: поле `agent.version`, курсор
запроса `agent_section_version`) из колонки ноды вместо заглушки `STUB_AGENT_VERSION` и перевести
`max_conn_per_ip` раздела на колонку `nodes.max_conn_per_ip`. Поток конфигурации — 001.29c;
остальные поля раздела переходят на источник у своих владельцев: `new_conn_rate_per_ip` — 001.27
(В-10), `multiplier_milli` — 001.36, `disconnect_strategy` — 001.40.

### Интеграция компонентов

Номер версии раздела растёт у затронутых нод при переводе поля с заглушки на источник (001.27,
001.36, 001.40 — эпохой раскладки, 001.29g) и при смене значения во время работы (колонкой: 001.87
— правка карточки, 001.29g — смена коэффициента); решения заказчика 2026-11-22, см. «Уточнения до
кода».

### Уточнения до кода (2026-11-21, правило 1 «Цикла задачи», без нового выбора поведения)

- Колонка — `nodes.agent_section_version int NOT NULL DEFAULT 2 CHECK (agent_section_version >= 1)`,
  миграция `150_node_agent_section_version.sql` (следующий номер после 140) с откатом. Новая нода
  получает 2: версия 1 закреплена за содержимым заглушки — его под номером 1 выдаёт всем нодам
  предыдущий образ, который штатно работает поверх схемы со 150 (откат кода, deployment.md §10.2).
  С умолчанием 1 нода, созданная после миграции под предыдущим образом, применила бы его версию 1
  с лимитом 32 и после возврата образа 29f осталась бы на 32 при своём лимите (роаст, раунд 1,
  M-1). Агент новой ноды (курсор 0) получает раздел при любом умолчании.
- Начальное значение существующих строк: 1 при `max_conn_per_ip = 32` (значение `STUB_AGENT`),
  иначе 2. Откат удаляет колонку; повторное применение вычисляет значения заново (1 или 2). Агент
  с курсором выше пересчитанного получит 409 `cursor_ahead` и возьмёт снапшот (README `agent_v1`);
  агент, чей курсор совпал с пересчитанным, а содержимое старше (поздняя задача повысила версию
  после того, как агент применил прежнюю), раздела не получит до следующего повышения версии его
  ноды (роаст, раунд 1, L-2).
- Версия и `max_conn_per_ip` читаются в том же снимке `repeatable read`, что курсоры и строки
  состава (`_read`): смена лимита вместе с версией, закоммиченная между чтениями, не попадёт в ответ
  наполовину. Остальные поля раздела — из `STUB_AGENT` до своих владельцев.
- Сценарий с числами: нода A (`max_conn_per_ip` 32, применила версию 1) после миграции — версия 1,
  курсор 1, раздела нет (значения те же); нода B (лимит 8, применила 1) — версия 2, курсор 1 →
  раздел с лимитом 8; нода C (курсор 3 после восстановления из копии) — 409, снапшот отдаёт раздел
  версии 2; нода, созданная после миграции, — версия 2, её агент (курсор 0) получает раздел. Удержание long-poll не меняется:
  раздел — повод ответить только при отставании курсора.
- Передачи: повышать версию при смене значения — механизм 001.27 и правка карточки 001.87 (уже в
  их файлах); формулировка 001.27 о переводе `max_conn_per_ip` на колонку уточняется — перевод
  делает эта задача, за 001.27 остаётся `new_conn_rate_per_ip` и механизм повышения версии.
  Строки «Зависимости:» файлов 001.27, 001.36, 001.40, 001.55, 001.75 и 001.75c дополнены 001.29f
  по `PLAN.md` (роаст, раунд 1, M-2).
- Перевод поля раздела с заглушки на источник (001.27, 001.36, 001.40) не переживает откат кода при
  номере версии, равном колонке: после отката образ этой задачи выдаёт значение колонки со
  значениями заглушки, агент их применяет и после возврата нового образа получает 204 (роаст, раунд
  2, M-1). Решение заказчика 2026-11-22: отдельная задача 001.29g — выдаваемый номер составляется из
  эпохи раскладки раздела образа и колонки; 001.27, 001.36, 001.40 зависят от неё и переводят поле
  повышением эпохи. Собственный откат этой задачи (на образ до неё) закрывает умолчание 2.
- `PUBLISH node:{id}` после коммита — для повышения колонки во время работы (001.87, смена
  коэффициента — 001.29g); повышение эпохи при выпуске будить не нужно: выпуск перезапускает
  процессы `api` (роаст, раунды 1–2, L-4 и L-1). Записано в файлах 001.27, 001.36, 001.40, 001.87 и
  001.75c.
- Смена коэффициента (`set_group_multiplier`, `set_billing_group`, 001.19) повышает колонку версии
  затронутых нод уже в 001.29g, а не в 001.36: иначе смена под образом отката 001.36 после
  возврата образа ответила бы 204 (роаст, раунд 3, M-1; решение заказчика 2026-11-22). 001.75 и
  001.75c, сравнивающие версию раздела, зависят от 001.29g; вопрос о колонке `new_conn_rate_per_ip`
  без умолчания (В-10) при откате кода передан в «решить здесь» 001.27 (роаст, раунд 3, L-5).
- Раздел собирается проверкой модели `StateAgent` (`model_validate`), а не `model_copy`: значения
  колонок проходят те же границы, что поля заглушки (роаст, раунд 1, L-3).

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Версия раздела `agent` из колонки
   - Входные данные: колонка версии раздела ноды увеличена
   - Ожидаемый результат: `agent.version` ответа — значение колонки; курсор
     `agent_section_version` ниже — раздел выдаётся, выше — 409 `cursor_ahead`
2. **TC-E2E-02:** `max_conn_per_ip` из колонки
   - Входные данные: `nodes.max_conn_per_ip` ноды отличается от значения заглушки
   - Ожидаемый результат: раздел `agent` ответа несёт значение колонки
3. **TC-E2E-03:** Версия и лимит одним снимком (роаст, раунды 1–3)
   - Входные данные: смена лимита вместе с версией коммитится в один из двух моментов —
     `first_read` (после первого чтения выдачи) и `begin` (в транзакции `_read` непосредственно
     перед её первым оператором); карточка ноды запроса прочитана до смены
   - Ожидаемый результат: зонд сработал; раздел — точная пара момента: `first_read` — прежняя
     (версия, лимит), `begin` — новая; затем с карточкой до смены — новая пара из строки ноды, а
     не лимит карточки

### Тесты миграции

1. **TC-MIG-01:** Начальная версия раздела
   - Входные данные: ноды с `max_conn_per_ip`, равным значению заглушки и отличным от него
   - Ожидаемый результат: версия 1 у первых, больше 1 у вторых (лимиты 8 и 64 — по обе стороны
     от 32); нода, вставленная после миграции, — 2
