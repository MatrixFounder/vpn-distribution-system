# Задача 001.89: Учётные записи администраторов: раздел панели

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-09 Управление тарифами, группами и кодами

Требования RTM: R-34, R-35, R-36, R-51.

<!-- contract:goal -->

## Цель задачи

Реализовать раздел панели `/admin/admins` для Super Admin: создание учётной записи с обязательным
вторым фактором, назначение роли, блокировку с отзывом сессий не позднее 60 с (Н-27), сброс пароля и
сброс второго фактора другим Super Admin. Реализовать свой профиль каждого администратора: смену
пароля, перевыпуск TOTP и выход на всех устройствах (решения заказчика 2026-10-25, В-33 в, В-35 в;
idea §4.15 «Administrators», §5.11) и выбор языка панели в своём профиле (idea §17.8). Первый Super
Admin (`admin create`) и сброс второго фактора командой хоста `admin reset-2fa`, когда другого
активного Super Admin нет, — 001.47.

### Изменения в существующих файлах

#### Файл: `control-plane/app/domain/admins.py` (создаёт 001.47)

- `create(email, role, ctx)` — строка `admin_users` со `status = active` и пустым
  `totp_enabled_at`; первый вход проходит путь включения второго фактора 001.47, как после
  `admin create`: до включения TOTP полной сессии нет. Занятый адрес — 409 `admin_email_taken`.
  Начальный пароль — по ответу на вопрос 1 «решить здесь»
- `set_role(admin_id, role, ctx)` — роль из `super_admin | admin | operator | support` (§5.11);
  срок действия новой роли для открытых сессий — по ответу на вопрос 2 г (изменение `deps.py`
  ниже или отзыв сессий)
- блокировка — `AdminService.block` (001.47): `status = 'blocked'`, после коммита
  `SessionStore.revoke_all(admin_id)`; маршрут блокировки — эта задача
- `reset_password(admin_id, ctx)` — новый пароль по ответу на вопрос 1;
  `SessionStore.revoke_all(admin_id)` — все сессии учётной записи
- сброс второго фактора другим Super Admin — `AdminService.reset_second_factor` (001.47) с
  контекстом сессии (`actor_type = admin`); задачи `send_email` вида `admin_2fa_reset` каждому
  активному администратору ставит сам метод (001.47), как при команде хоста. Сброс своего второго
  фактора разделом — 409 `self_second_factor_reset`: сброс подтверждает другой Super Admin (idea
  §5.11, В-35 в); свой TOTP администратор перевыпускает в своём профиле
- свой профиль: `change_own_password(admin_id, current, new, sid, ctx)` — неверный текущий пароль —
  401; после смены `SessionStore.revoke_all(admin_id, except_sid=sid)`: смена пароля инвалидирует
  все сессии, кроме текущей (§5.11). `reissue_totp(admin_id, current_password, sid)` и
  `confirm_totp(admin_id, code, sid, ctx)` — новый секрет через `Totp.provision` и подтверждение
  кодом нового секрета, механизм включения второго фактора при первом входе (001.47). До
  подтверждения действует прежний секрет: новый хранится в Redis под ключом
  `admin:totp_pending:{admin_id}` шифротекстом FieldCipher (как `totp_secret_enc`) с TTL 12 ч — TTL
  бездействия сессии администратора (Н-27); `admin_users.totp_secret_enc` до подтверждения не
  меняется; повторный `reissue_totp` перезаписывает ключ; ключа нет (срок истёк или перевыпуск не
  начат) — 409 `totp_not_pending`. После подтверждения — секрет из ключа записывается в
  `totp_secret_enc`, ключ удаляется, 10 новых резервных кодов взамен прежних,
  `revoke_all(admin_id, except_sid=sid)`. Неверные коды подтверждения
  считаются порогом неверных кодов TOTP учётной записи (001.47). `logout_all(admin_id)` —
  `revoke_all(admin_id)`, включая текущую сессию (`docs/architectures/security.md` §7.1)
- язык панели в своём профиле: `set_own_language(admin_id, language, ctx)` — значение из набора
  языков `app/i18n.py::SUPPORTED_LANGUAGES` (из файлов `locales/` после 001.65), иначе 422
  `validation_error`; пишется в `admin_users.language` (колонка миграции 040, по умолчанию `en`);
  язык панели выбирается независимо от языка пользователей (idea §17.8, R-51); ответ
  `GET /admin/auth/session` отдаёт его в поле `language` (001.46), по нему панель выбирает строки
  (001.64)
- каждое действие раздела и своего профиля вызывает `audit.record` на подключении своей транзакции
  (`actor_type = admin`): `admins.create`, `admins.set_role` (прежняя и новая роль), `admins.block`,
  `admins.reset_password`, `admins.reset_second_factor`, `admins.self.password`, `admins.self.totp`,
  `admins.self.logout_all`, `admins.self.language`, `admins.unblock` (по ответу на вопрос 2);
  пароли, секреты и резервные коды в `old_value` и `new_value` не попадают. `block` и
  `reset_second_factor` пишут журнал сами (001.47)

#### Файл: `control-plane/app/api/admin/admins.py` (заглушки 001.49)

- реализация маршрутов через `AdminService`, включая `PATCH /admin/admins/me` (`{language}`);
  разрешения — `admins.manage` (раздел) и `admins.self` (свой профиль), как в заглушке; ответы с

#### Файл: `control-plane/app/security/deps.py` — по ответу на вопрос 2 г

- без выхода (рекомендация): `require_permission` (001.46) берёт роль из `admin_users` по
  `admin_id` сессии на каждой проверке разрешения; роль в сессии не хранится и не кэшируется, новая
  роль действует со следующего запроса — в пределах 60 с (Н-27). Если 001.46 или 001.47 сохранят

  блокировка; `deps.py` не меняется

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Создание с обязательным вторым фактором
   - Входные данные: Super Admin создаёт учётную запись с ролью `support`; вход новой учётной
     записью; включение TOTP; повторное создание с тем же адресом
   - Ожидаемый результат: учётная запись создана; до включения TOTP `GET /admin/auth/session` —
     401; после включения — сессия с ролью `support`; строка `audit_log` `admins.create`; повтор —
     409 `admin_email_taken`
2. **TC-E2E-02:** Раздел только для Super Admin
   - Входные данные: сессии `admin`, `operator`, `support`; `GET /admin/admins`,
     `POST /admin/admins`
   - Ожидаемый результат: 403; строки `audit_log` с `result = denied`
3. **TC-E2E-03:** Блокировка из раздела
   - Входные данные: Super Admin блокирует учётную запись B с активной сессией
   - Ожидаемый результат: запрос B через 1 с — 401; повторный вход B — 401; строка `audit_log`
     `admins.block` (AC-16)
4. **TC-E2E-04:** Смена роли
   - Входные данные: учётная запись B с ролью `admin` и активной сессией; Super Admin меняет роль на
     `support`; B вызывает `DELETE /admin/plans/{id}`
   - Ожидаемый результат: отказ 403 не позднее чем через 60 с после смены; строка `audit_log`
     `admins.set_role` с прежней и новой ролью
5. **TC-E2E-05:** Сброс пароля
   - Входные данные: учётная запись B с двумя сессиями; Super Admin сбрасывает пароль B; вход B
     прежним паролем
   - Ожидаемый результат: обе сессии B — 401; вход прежним паролем — 401; вход по правилу вопроса
     1 проходит
6. **TC-E2E-06:** Сброс второго фактора другим Super Admin
   - Входные данные: Super Admin A и C, Support B — активны; A сбрасывает второй фактор C; A
     сбрасывает свой второй фактор
   - Ожидаемый результат: сессии C — 401, `totp_enabled_at` C пуст, неиспользованных резервных
     кодов C нет, вход C требует включить второй фактор; задачи `send_email` вида
     `admin_2fa_reset` — по одной на A, B и C; строка `audit_log` с `actor_type = admin` и актором
     A. Свой сброс — 409 `self_second_factor_reset`, второй фактор A не изменился
7. **TC-E2E-07:** Свой профиль
   - Входные данные: администратор с сессиями S1 и S2. В S1: смена пароля с неверным текущим, затем
     с верным; перевыпуск TOTP и подтверждение кодом нового секрета; выход на всех устройствах
   - Ожидаемый результат: неверный текущий пароль — 401, пароль не изменился; после смены — S2 401,
     S1 работает; после подтверждения TOTP прежний код и прежние резервные коды при входе
     отклоняются, выдано 10 новых кодов; после выхода везде S1 — 401; строки `audit_log` по
     каждому действию
8. **TC-E2E-08:** Язык панели
   - Входные данные: администраторы A и B с языком `en`; A вызывает `PATCH /admin/admins/me` с
     `language = ru`, затем с языком, которого нет в `SUPPORTED_LANGUAGES`
   - Ожидаемый результат: `GET /admin/auth/session` A отдаёт `language = ru`, у B — `en`; второй
     запрос — 422, язык A не изменился; строка `audit_log` `admins.self.language`
9. **TC-E2E-09:** Перевыпуск TOTP без начатого перевыпуска
   - Входные данные: `confirm_totp` без предшествующего `reissue_totp`; `reissue_totp`, затем
     `confirm_totp` после удаления ключа `admin:totp_pending:{admin_id}` фикстурой (истечение TTL)
   - Ожидаемый результат: оба раза 409 `totp_not_pending`; `totp_secret_enc` и резервные коды не
     изменились; вход прежним кодом TOTP проходит

## Критерии приёмки

- [ ] Раздел `/admin/admins` доступен только Super Admin; отказ остальным ролям — 403 с записью в
  журнале
- [ ] Учётная запись, созданная в разделе, не получает полной сессии до включения второго фактора
- [ ] Блокировка из раздела отзывает сессии не позднее 60 с (AC-16); сброс пароля отзывает все
  сессии учётной записи
- [ ] Второй фактор сбрасывает другой Super Admin; свой сброс разделом — 409; письма всем активным
  администраторам; запись в журнале (В-35 в)
- [ ] Смена пароля и перевыпуск TOTP в своём профиле отзывают все сессии, кроме текущей; выход на
  всех устройствах — все (§5.11)
- [ ] Смена роли действует для открытых сессий не позднее 60 с — без выхода или отзывом сессий, по
  ответу на вопрос 2 г (TC-E2E-04)
- [ ] До подтверждения перевыпуска действует прежний секрет TOTP; новый хранится в
  `admin:totp_pending:{admin_id}` (TC-E2E-07, TC-E2E-09)
- [ ] Язык панели выбирается в своём профиле, хранится в `admin_users.language` и отдаётся в
  ответе сессии (idea §17.8, R-51; TC-E2E-08)
- [ ] Каждое действие раздела и своего профиля пишет строку `audit_log` без паролей и секретов

## Примечания

`tdd-strict`: задача меняет аутентификацию администраторов (TOTP, сессии — 001.47).

Найдено при создании задачи (В-33, В-35), решить здесь:

1. **Начальный пароль и сброс пароля.** idea §4.15 и решение В-33 называют операции, но не способ
   передачи пароля. Варианты: а) временный пароль генерирует сервер (`secrets.token_urlsafe`, не
   меньше 128 бит), ответ показывает его один раз; передача владельцу — вне системы; вход с
   временным паролем требует сменить пароль, затем включить второй фактор (изменение пути входа
   001.47 и колонка признака временного пароля в `admin_users` — миграция этой задачи); сброс
   пароля — так же; б) письмо со ссылкой установки пароля: новый вид `send_email` и значение
   `email_delivery_kind` (например, `admin_password_set`), срок ссылки —
   `settings.email_token_ttl_minutes`, доставка — 001.78; при отказе почты администратор без
   доступа до повторной выдачи; в) пароль задаёт Super Admin в запросе, смены при первом входе нет.
   Рекомендация: а — не зависит от доставки почты (тематика сервиса — частая причина отказа
   почтового провайдера, idea §17.7); пароль, известный Super Admin, действует только до первого
   входа.
2. **Защитные правила раздела.** а) Super Admin не блокирует себя и не меняет свою роль разделом —
   409 `self_operation`; б) блокировка или понижение роли, после которых не остаётся ни одного
   активного Super Admin, — 409 `last_super_admin`: иначе управлять учётными записями и сбрасывать
   второй фактор в панели некому, а `admin create` создаёт только первого Super Admin (001.47);
   в) разблокировка `POST /admin/admins/{id}/unblock` возвращает `status = active`, сессии не
   восстанавливаются, пароль и второй фактор прежние (idea §4.15 разблокировку не называет, без
   неё заблокированный адрес нельзя использовать снова: `admin_users.email` уникален); г) смена роли
   действует для следующих запросов учётной записи без выхода (роль читается из `admin_users` при
   проверке разрешения) либо отзывом сессий, как блокировка. Рекомендация: принять а, б и в; для г
   — без выхода, срок — 60 с, как у блокировки (Н-27); иначе понижение роли действовало бы до конца
   сессии (12 ч бездействия). Ответы на оба вопроса — заказчику до начала задачи; от ответа на
   вопрос 1 зависят схемы ответов заглушки 001.49.

Зависимости: 001.47, 001.48, 001.49. Приоритет: High. Оценка: 4 ч. Этап: 7 — администрирование,
RBAC, аудит, поддержка.
