## Примечания

Требует VPS стенда (по словам заказчика — после создания удалённой VPS).

Найдено при 001.33 (заглушки), решить здесь:

- потолки памяти, процессора и числа процессов в Compose — вывод, не измерение под нагрузкой:
  `api` 1 ГиБ (замер контейнера на стенде — 108 МиБ в покое, 132 МиБ после смешанной нагрузки
  раундов 5–6, 104 после проб раунда 7; один процесс `--reload`, в проде два worker'а), `nginx`
  256 МиБ (19…28 МиБ в покое, 38 после проб раунда 5, 9 после проб раунда 7; буферы равны
  пределам — 1 МиБ на отчёт, 64 КиБ на прочее соединение, тел без известной длины нет — 411;
  tmpfs 64 МиБ на весь `/var/cache/nginx` — только тела публичного server больше 16k), `cpus`
  (nginx 1.0, api 2.0) и `pids_limit` (nginx 256, api 512); измерить всё под нагрузкой парка (§5.7: 50 нод × 8
  соединений, две части отчёта одновременно, худшая запись тел, публичный server под
  анонимным потоком) и уточнить, включая размер tmpfs;
- бюджет Н-4 (по решению заказчика — по времени апстрима `urt`, заливка вне норматива): гейт
  `test_the_fleet_ceiling_keeps_the_parse_budget_of_h4` закреплён на константе стоимости
  элемента 16,7 мкс (p95 `urt` стенда, 200 замеров на теле потолка из 3 000 элементов при двух
  потоках отчётов: p95 50 мс; один поток — p95 46, медиана 23, максимум 105; на теле из 6 000 —
  p95 88, 14,7 мкс), на замере пар одновременных частей (p95 второй из пары 69 мс ≤ 2 × 50 —
  проверка модели «слоты × p95»), на стоимости остальных операций (самый дорогой путь отказа
  64-КиБ тела из минимально коротких лишних ключей после проверки формы по байтам: heartbeat 2 мс, enrollment 2 мс по p95 `urt` — enrollment измерен на заглушке без подписи, перемер после 001.25; худшее тело отчёта в пределах формы — 37 мс, дешевле приёма; в бюджет части входят все операции обеих зон, прибывающие за окно разбора двух частей: при 15 и 2 в секунду — три и две) и
  резерве 50 мс на транзакцию приёма
  001.34/001.77 без замера — измерить на целевой VPS: константа — это сквозной `urt` (установка
  соединения с апстримом, разбор, ответ), а не «разбор»; транзакцию (вставка 500 строк и 2 500
  адресов, `on_report`, `evaluate`, `enqueue`) вместе с пулом (`max_size=10` на процесс против
  двух частей на парк и восьми соединений на ноду) и keepalive к апстриму (`proxy_pass` через
  переменную исключает `upstream … keepalive` — новое соединение на каждый запрос внутри
  `urt`); замер с **занятыми обоими слотами** одновременно — под пределами прокси (2 r/s на
  сертификат) для этого нужно больше 20 сертификатов, на стенде их шесть; заменить константы
  гейта;
- heartbeat под парами частей одновременно на стенде: p95 5 мс, максимум 126 (ждут разбора в
  том же цикле; под одним потоком частей — p95 16, максимум 39; при телах из 6 000 элементов —
  p95 36, максимум 60) — измерить p95 всех операций раздела под парком, а не только отчётов;
- пропускная способность парка по отчётам — `agent_report_total` / (заливка + разбор) частей в
  секунду: слот `limit_conn` занят с начала заливки до конца ответа, заливка части потолка на
  50 Мбит/с — 0,07 с, разбор — 0,05 с, итого 16,2 части в секунду самой широкой частью,
  20,3 — компактной, 23…27 — при 100 Мбит/с Н-17 (один цикл событий
  разбирает не больше ~20 таких частей в секунду) — с запасом против 50 в минуту при §5.7;
  вопрос числа слотов — только если p95 на целевой VPS окажется выше стендового;
- частота парка по остальным операциям (`agent_fleet_rate` 15 r/s, очередь 200) — замкнутый цикл шести сертификатов на стенде держится на пределе задержкой (14,8 r/s, p50 0,4 с), а не 429 (очередь 200 шестью клиентами не заполнить); 429 парку крупнее ~25 нод под залпом — проверить здесь
  парком §5.7;
- решить о `--limit-concurrency` uvicorn для `api` (сегодня не задан: предел одновременности
  живёт только на прокси).
