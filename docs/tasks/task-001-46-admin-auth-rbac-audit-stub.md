## Цель задачи

### Интеграция компонентов

Все маршруты `/admin/*` из 001.18 и 001.24 проверяются зависимостью роутера панели
`declared_permission` по разрешению, которое маршрут объявил в `x-permission`; маршруты 001.49
попадают под неё, подключаясь к тому же роутеру. `require_permission(name)` — для маршрутов вне
роутера панели.

Механизм записи журнала: доменный метод, меняющий данные, принимает `ctx: AuditContext` и
вызывает `audit.record` на подключении своей транзакции — изменение и его след в журнале атомарны.
Транзакцию открывает сам метод (`async with transaction(self._pool)`), поэтому маршрут после
коммита записать журнал в той же транзакции не может. Отказ по разрешению (`result = denied`)
пишет общая проверка (`declared_permission`, `require_permission`) отдельной короткой
транзакцией. Перечень доменных методов, получающих
`AuditContext`, — 001.48.

## Примечания

Ограничения и допущения — `docs/idea.md` §9; архитектура — `docs/ARCHITECTURE.md`.

Решения до кода (правило 1 «Цикла задачи»):

- роль для проверки разрешения берётся из `admin_users` на каждом запросе панели вместе со
  статусом: понижение роли и блокировка действуют со следующего запроса, без перевыпуска сессий;
  администратор, которого нет в `admin_users` или чей статус не `active`, — 401
  `unauthenticated` (решение заказчика 2026-11-04);
- отказ по разрешению — 403 `permission_denied` с `details.permission` (имя разрешения):
  панель различает отказ по правам и прочие 403 (`csrf_failed`);
- маршруты `/admin/auth/*` разрешения не объявляют: вход, второй фактор и резервный код идут до
  сессии; `GET /admin/auth/session` и `POST /admin/auth/logout` — под сессией любой роли (по
  TC-E2E-03 роль `support` читает свою сессию, а при заглушечной матрице у неё нет ни одного
  разрешения); правило «каждый маршрут `/admin/*` — одно разрешение» относится к операциям
  панели вне `/admin/auth`;
- проверка подключена к роутеру панели целиком (`declared_permission`): маршрут объявляет имя
  `permission(...)` в `openapi_extra`, роутер проверяет именно его — объявленное и проверяемое не
  расходятся, маршрут без объявления закрыт; `require_permission(name)` — та же проверка для
  маршрутов вне роутера панели; у изменяющих запросов CSRF проверяется до разрешения (роаст,
  раунд 1).

Решения по роасту, раунд 1 (технические, без вопроса заказчику):

- в журнал идёт несекретная метка сессии (`Session.handle`, SHA-256 идентификатора), а не
  значение cookie `sid`: журнал читает `audit.read`, и идентификатор дал бы вход чужой сессией;
- адрес — клиента запроса (как у входа пользователя), не адрес входа из сессии; `User-Agent` — до
  512 символов; сущность отказа — метод и шаблон маршрута, фактический путь — в `new`, до 256
  символов;
- `AuditContext` несёт `actor_type` (`admin | user | system`), остальные поля необязательны — так
  его смогут собрать 001.16, 001.17, 001.42 (пользователь) и 001.47, 001.30c (система);
- администратор без строки или со статусом не `active` — сессия отзывается вместе с ответом 401
  (раунд 2: все его сессии):
  иначе запрос продлевал бы её, и после разблокировки она снова открыла бы панель;
- действия журнала — «раздел.действие», как имена разрешений (`billing_groups.multiplier`,
  `nodes.billing_group`, `codes.export`; отказ — имя разрешения), коэффициенты — десятичной
  строкой.

Решения по роасту, раунд 2 (технические, без вопроса заказчику):

- администратор без строки или со статусом не `active` — отзываются все его сессии
  (`revoke_all`), а не только предъявленная;
- CSRF проверяется в общей проверке разрешения по токену уже прочитанной сессии: его получают и
  роутер панели, и `require_permission`;
- назначение группы ноды пишет в журнал действующий коэффициент: смена группы без
  переопределения меняет списание;
- вопрос 2 г задачи 001.89 (смена роли для открытых сессий) закрыт решением заказчика
  2026-11-04: без выхода, со следующего запроса.
