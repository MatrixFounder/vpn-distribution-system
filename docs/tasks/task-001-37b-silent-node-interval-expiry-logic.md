## Описание изменений

### Новые файлы

- `control-plane/tests/e2e/test_interval_expiry.py` — закрытие по сроку и по возрасту,
  блокировка строки ноды (TC-E2E-01…TC-E2E-04)

### Изменения в существующих файлах

#### Файл: `control-plane/app/accounting/service.py`

- функция закрытия `close_expired_intervals(conn, at)`: по каждой ноде с истёкшим открытым интервалом — строка ноды `for no key update`, затем закрытие через `closing()`; повторный вызов закрытые интервалы не трогает. Её вызывают обработчик `report_intervals.close_expired` и первым шагом — обработчик сверки непрерывности 001.37d

#### Файл: `control-plane/app/jobs/handlers/__init__.py`

- тип `report_intervals.close_expired` — вызов `close_expired_intervals` (закрытие открытых интервалов молчащих нод по сроку `REPORT_PARTS_DEADLINE` и возрасту `REPORT_MAX_INTERVAL_AGE` 48 ч от первой части, `close_reason` `deadline` и `age`, 001.34: ленивая проверка на приёме следующей части для молчащей ноды не наступит)

#### Файл: `control-plane/app/metrics.py`

- ряд `control_plane_report_intervals_expired{node_id,reason}` — число интервалов ноды, закрытых
  задачей по сроку (`deadline`) или возрасту (`age`) за последние 24 ч; считается из
  `report_intervals` при снятии, как другие ряды модуля; источник алерта о принудительном
  закрытии — 001.68

#### Файл: `control-plane/app/jobs/scheduler.py`

- расписание: закрытие истёкших интервалов молчащих нод — каждые 15 минут (ревью WI-35, группа ACC-F-20); сверка непрерывности 001.37d в своём проходе сама сначала вызывает `close_expired_intervals`, порядок «закрытие, затем сверка» от расписания не зависит

### Интеграция компонентов

Момент и причину закрытия даёт `closing()` принятой 001.34 (`app/accounting/service.py`): срок
`REPORT_PARTS_DEADLINE` (25 ч) от последней принятой части или возраст `REPORT_MAX_INTERVAL_AGE`
(48 ч) от первой — что раньше. Часть к закрытому интервалу получает `interval_closed` (001.34).
Разрыв на недостающие части закрытого интервала записывает сверка непрерывности 001.37d; алерт
на принудительное закрытие по сроку и по возрасту — правило 001.68 по ряду
`control_plane_report_intervals_expired`.

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Закрытие по сроку
   - Входные данные: у ноды открыт интервал из трёх частей, принята часть 1 (`first_received_at` = `last_received_at` = T); нода молчит; проход задачи в T + 25 ч 10 мин; у второй ноды последняя часть открытого интервала принята за 24 ч 50 мин до прохода
   - Ожидаемый результат: интервал первой ноды закрыт: `closed_at` = T + 25 ч (момент истечения, а не прохода), `close_reason = deadline`; часть 2 этого интервала после закрытия — `interval_closed`, в учёт не входит; интервал второй ноды открыт
2. **TC-E2E-02:** Закрытие по возрасту
   - Входные данные: часть 1 интервала принята в T, часть 2 — в T + 24 ч (срок от последней части — T + 49 ч, возраст — T + 48 ч); нода молчит; проход задачи в T + 48 ч 10 мин
   - Ожидаемый результат: `closed_at` = T + 48 ч, `close_reason = age`
3. **TC-E2E-03:** Блокировка строки ноды
   - Входные данные: транзакция приёма держит строку ноды (`for no key update`) и продлевает открытый интервал следующей частью; в это время идёт проход задачи с моментом, для которого интервал по прежней последней части истёк
   - Ожидаемый результат: задача ждёт фиксации приёма и интервал не закрывает (срок считается от новой последней части); приём завершился без ошибки
4. **TC-E2E-04:** Ряд принудительных закрытий
   - Входные данные: после TC-E2E-01 и TC-E2E-02 запрос `/metrics`
   - Ожидаемый результат: `control_plane_report_intervals_expired{node_id=<первая нода>,reason="deadline"} 1` и `{…,reason="age"} 1`; интервал, закрытый завершением, в ряд не входит

## Примечания

Ограничения и допущения — `docs/idea.md` §9; архитектура — `docs/ARCHITECTURE.md`.

`tdd-strict`: денежная логика — закрытие интервала решает, что следующая часть получает
`interval_closed` и не списывается.

Найдено при 001.34 (приём), решить здесь:

- закрытие интервалов молчащих нод по сроку и возрасту — тот же `closing()`
  (`app/accounting/service.py`): момент закрытия — момент истечения, а не прохода задачи; приём
  закрывает истёкшие интервалы своей ноды сам. Задача закрытия обязана сначала брать строку ноды
  (`select … from nodes where id = $1 for no key update`), как приём: обновление продолжения
  (`_CONTINUE_INTERVAL`) пишет только открытую строку и падает, если её закрыли встречной
  записью без этой блокировки.
