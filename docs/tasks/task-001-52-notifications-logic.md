# Задача 001.52: Уведомления: каналы доставки событий, язык получателя, проверка буфера отчётов ноды

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-05 Исчерпание лимита и отзыв доступа
- UC-07 Отказ и возврат ноды
- UC-15 Восстановление пароля
- UC-12 Компрометация ноды

Требования RTM: R-39, R-40.

<!-- contract:goal -->

## Цель задачи

Реализовать постановку задач доставки по таблице §4.17 на языке профиля получателя: семь
пользовательских событий — почта и webhook; пять операторских событий записываются в `events`, а
доставляет их Alertmanager (001.68), кроме «Нода приостановлена провайдером» — webhook приложения
(001.79); проверку заполнения буфера отчётов ноды с событием «Буфер отчётов на ноде заполнен».

## Описание изменений

### Новые файлы

- `control-plane/migrations/NNN_settings_report_buffer_threshold.sql` и откат (NNN — следующий свободный номер): сид ключа `settings.report_buffer_threshold_hours` со значением по умолчанию 20
- `control-plane/tests/e2e/test_notifications.py` — семь пользовательских → две задачи; операторские → строка `events` без задач доставки, «приостановлена провайдером» → задача webhook; повтор не доставляется; буфер отчётов

### Изменения в существующих файлах

#### Файл: `control-plane/app/notifications/events.py`

- `emit` ставит задачи доставки по `channels_for` (заглушка 001.51 ставила обе задачи на каждое событие); язык получателя из профиля; ключ подавления `dedup_key` — 001.51

#### Файл: `control-plane/app/jobs/handlers/notifications.py`

- `channels_for(type)` — каналы постановки `notify.email` и `notify.webhook` по таблице §4.17 с ключами 001.51 (`notify:email:{event_id}`, `notify:webhook:{event_id}:{получатель}`): пользовательские события — почта и webhook; `node_suspended_by_provider` — webhook приложения с идентификатором события: это однократное событие перехода в ручной статус, а правила Alertmanager ноды в ручных статусах исключают (§17.4); остальные операторские события — только строка `events`, доставку, группировку по ноде и типу и окно обслуживания (`silence`) выполняет Alertmanager (001.68)
- проверка по расписанию: нода, у которой возраст `period_end` последнего принятого интервала больше порога из `settings` (ключ `report_buffer_threshold_hours` и миграция-сид со значением по умолчанию 20 ч — эта задача; тот же порог использует правило 001.68), → `emit(node_report_buffer_full, node_id)`; ноды в ручных статусах исключены; источник — данные Control Plane, а не метрики агента: буфер растёт, когда отчёты ноды до Control Plane не доходят, и метрика агента пришла бы только после восстановления связи

### Интеграция компонентов

Тест SMTP — локальный приёмник (`aiosmtpd`); webhook — локальный HTTP-сервер, один
получатель (фикстура теста; сид `settings.webhooks` — 001.79).

Операторские события и алерты §17.4 (решение заказчика 2026-10-25, В-42; правила и метки
приоритета — 001.68; окно обслуживания гасит только алерты приоритета «Отложенный»):

| Событие §4.17 | Доставка | Приоритет алерта |
| :--- | :--- | :--- |
| `node_offline` | Alertmanager, алерт «Нода Offline» | Отложенный |
| `node_recovered` | Alertmanager, разрешение алерта «Нода Offline» | — |
| `reconciliation_mismatch` | Alertmanager, алерт «Расхождение сверки трафика свыше Н-18» | Немедленный |
| `node_report_buffer_full` | Alertmanager, алерт «Заполнение буфера отчётов на ноде» | Немедленный |
| `node_suspended_by_provider` | webhook приложения (001.79) | не алерт: нода в ручном статусе |

Перевод ноды в `Suspended` по повторным удержаниям (001.30c) — алерт приоритета «Немедленный»
(001.68) и запись Audit Log; события `node_suspended_by_provider` он не порождает (решение
заказчика 2026-10-25, В-5).
