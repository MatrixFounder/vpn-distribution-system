## Цель задачи

Реализовать `LimitsService`: сравнение расхода периода с лимитом, однократные уведомления порогов,
перевод в `suspended_quota` с публикацией отзыва в поток состава в сроки Н-14, восстановление при
продлении или бонусе.

## Примечания

`tdd-strict`.

Найдено при 001.33 (заглушки), решить здесь:

- `LimitsService.check(conn, user_ids)` — один вызов на отчёт на подключении обработчика
  (отклонение от `check(user_id)`): задача `limits.check` ставится одна на отчёт с полезной
  нагрузкой `{"node_id", "user_ids"}` и ключом `limits:{node_id}:{counter_epoch}:{report_seq}`;
  по задаче на пользователя критичная очередь получала бы тысячи задач в минуту (бюджет
  ожидания — половина Н-13);
- до этой задачи обработчик `limits.check` (`jobs/handlers/limits.py`) — заглушка, которая
  отказывает без повторов (`NonRetryableError` → задача `failed` с типом в причине): между
  001.77 (ставит) и 001.35 (реализует) отзыв по лимиту не происходит, и это видно в очереди
  как `failed`, а не как зелёный «done»; тест
  `tests/unit/jobs/test_handlers.py::test_the_stubs_refuse_without_retries_and_without_touching_the_connection`
  снимается здесь вместе с заглушкой;
- повторные удержания отчётов ноды (`held_anomaly` по порогу §5.9, потолкам смен эпохи и
  открытых интервалов — README `contracts/agent_v1/`, 001.34) за скользящие сутки переводят
  ноду в `suspended` до разбора оператором: порог числа удержаний и сам переход — здесь вместе
  с 001.30 (ручные и автоматические статусы §4.6); удержание не освобождает от списания в
  пределах потолка канала — списание делает 001.77;
- `LimitsService(pool)` объявлен постановкой с пулом, а единственный вызывающий — обработчик
  очереди — получает от исполнителя только `conn`: либо служба строится над пулом процесса
  (`get_pool()`) один раз при старте исполнителя, либо конструктор принимает `pool=None` —
  решить здесь, сигнатуру `check(conn, user_ids)` не менять.
