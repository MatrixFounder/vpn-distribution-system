## Примечания

Ограничения и допущения — `docs/idea.md` §9; архитектура — `docs/ARCHITECTURE.md`.

Найдено при 001.33 (заглушки), решить здесь:

- `partitions.ensure`, `partitions.drop_expired`, `retention.purge` зарегистрированы заглушками
  (`jobs/handlers/maintenance.py`), которые отказывают без повторов (`NonRetryableError` →
  `failed`): до этой задачи их типы в очередь не ставить; стражем удержаны вне `SCHEDULE`
  (`tests/unit/jobs/test_handlers.py::test_the_stub_types_stay_off_the_schedule_until_they_are_real`);
  партиции до этой задачи обслуживает `ensure_partitions` (001.14). Перевести расписание на
  новые типы и снять `ensure_partitions` вместе со стражем;
- сверка непрерывности обязана видеть буфер, остановленный отказом `node_mismatch` или
  `rejected_time` (номера `report_seq` перестают расти), и фиксировать разрыв, а не тишину;
- три новых источника разрывов (контракт 001.33, README `contracts/agent_v1/`): интервал,
  закрытый без всех объявленных частей — по сроку `REPORT_PARTS_DEADLINE` (25 часов: буфер
  Н-8 плюс час) или частью следующего интервала ноды (001.34 открывает разрыв на недостающие
  части, поздняя часть получает `interval_closed` и в учёт не входит — двойного учёта нет), и
  смена `counter_epoch` (для Control Plane перезапуск Xray и перерыв агента неразличимы —
  правило одно): оценка объёма разрыва — полоса ноды × длительность паузы между `period_end`
  последней принятой части прежней эпохи и `period_start` первой части новой, а не
  «неизвестная эпоха — оценка не ограничена»; смен эпохи у ноды — не больше
  `REPORT_MAX_EPOCHS_PER_DAY` (48) в сутки (001.34 удерживает сверх);
- `traffic_gaps` (data-model §4.2.5, миграция здесь): PK `(gap_start, node_id, reason)` — ключ
  партиционирования обязан входить в первичный ключ (раунд 8 поймал `id uuid PK` при партициях
  по `gap_start`, PostgreSQL такую таблицу не создаёт), тот же ключ — идемпотентность записи
  (повторный проход сверки не удваивает разрыв); 080 создаёт таблицу без партиций и с `id` —
  пересоздание с переносом здесь; партиционирование по дню и срок хранения 90 суток (§4.5) —
  рост таблицы задаёт нода (закрытия и смены эпохи), без срока он не ограничен; то же у
  `reconciliation_runs` — PK `(created_at, id)`, партиции по `created_at`; `node_id` у
  `traffic_gaps` — без FK на `nodes` (§4.3: внешних ключей на партициях нет; 080 создаёт с FK,
  снять при пересоздании);
- закрытие открытых интервалов `report_intervals` по возрасту (`REPORT_MAX_INTERVAL_AGE` 48 ч
  от первой части, `close_reason = age`, 001.34) и по сроку для замолчавших нод — периодическая задача здесь (ленивая проверка на
  приёме следующей части для молчащей ноды не наступит), в `SCHEDULE` вместе с ретенцией;
- `reconcile.*`, `aggregate_day` принимают подключение первым аргументом — обработчик отдаёт
  своё; `ReconciliationRun.scope` — неизменяемое отображение.
- срок хранения строк `jobs` в терминальных статусах (`done`, `failed`, `dead`): в
  `partition_policies` миграции 080 таблицы `jobs` нет, а `failed`-задачи `limits.check` в
  окне между 001.77 и 001.35 копятся по одной на принятый отчёт — ввести удаление по сроку
  (§4.5) здесь или в 001.14/001.74, чтобы `depth()` не считал их вечно.
