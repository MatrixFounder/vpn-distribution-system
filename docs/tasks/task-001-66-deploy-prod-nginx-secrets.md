## Примечания

Конфигурационная задача.

Найдено при 001.33 (заглушки), решить здесь:

- у `api` (1g) и `nginx` (256m) в Compose стоят `mem_limit` = `memswap_limit` (001.33):
  превышение — OOM-kill контейнера, а политики перезапуска в файлах Compose нет (`restart:`
  не задан) — до этой задачи контейнер после OOM остаётся остановленным; ввести
  `restart: unless-stopped` (или эквивалент оркестратора) для всех ролей и алерт на
  перезапуски (001.68);
- публичный `server` nginx (80/443) не имеет ни `limit_conn`, ни `limit_req` и делит
  `worker_connections` с агентским: анонимный клиент может выбрать соединения, на которых
  держатся пределы Node API — задать пределы по адресу источника здесь или в 001.72;
- промышленный профиль Compose обязан сохранить tmpfs временных файлов nginx (весь
  `/var/cache/nginx` — `client_body_temp_path` и `proxy_temp_path` — tmpfs 64 МиБ под потолком
  памяти с правами 0711 на точке монтирования: мастер nginx создаёт подкаталоги рабочему
  процессу, которому нужен проход, с 0700 он получал Permission denied — стенд раунда 8; тела
  Node API туда не попадают — 411 на тела без длины, буферы равны пределам; ответы апстрима
  сверх буферов — до `proxy_max_temp_file_size` 8 МиБ на ответ, 64 МиБ = восемь таких; тела
  пишет только публичный server), `worker_processes` nginx равным квоте `cpus`, потолки
  процессора и числа процессов (`cpus`, `pids_limit`) и предел журналов (`json-file`, 10 МиБ ×
  3) базового файла; страж `test_proxy_contract.py` читает список файлов Compose из команды
  запуска в шапке базового файла, сверяет её с `deploy/README.md` и отвергает любой другой
  `*.y*ml` в каталоге, `include:` и `extends:` — промышленный оверлей добавляется в ту же
  команду (и в README) и не переопределяет пределы памяти, `cpus`/`pids_limit`, `logging` и
  тома nginx; deployment.md §10.4 описывает это;
- публичный `server`: таймауты клиента и апстрима, набор шифров, порт 80 (редирект на 443 или
  закрытие), пределы соединений и тела по адресу источника (сегодня 1 МиБ с буфером 16k — тела
  больше буфера идут в tmpfs; медленное чтение ответа держит соединение с прокси и место в tmpfs
  до 8 МиБ — при заполнении nginx отвечает 500 тому запросу, которому не хватило места; отчёты и
  enrollment не затронуты) — здесь.

Найдено при 001.25 (enrollment и identity), решить здесь:

- **отказ отозванному сертификату на прокси (`ssl_crl`) отложен сюда.** 001.25 держит отзыв в
  C-01: identity сверяется с базой на каждом запросе, и отозванной следующий же запрос — 401
  (Н-31 выполняется синхронно). Прокси при этом отозванный лист принимает и до ответа отдаёт
  его держателю свои пределы (слот отчётов парка, частоту по сертификату) — остаточный риск
  §7.3. Ограничения конструкции, выясненные в 001.25: (1) nginx читает `ssl_crl` при загрузке
  конфигурации — файл CRL обязан существовать и быть подписан тем же CA ещё до старта, иначе
  OpenSSL отвергает **всех** клиентов (`unable to get certificate CRL`), а истёкший `nextUpdate`
  отвергает всех так же — нужен дальний `nextUpdate` либо пересподписание по расписанию; (2)
  смена файла требует перечитывания nginx, а одиночный файл в bind mount rsync подменяет
  переименованием (inode, `skills/vm-deploy`) — монтировать каталог; (3) перечитывание не
  разрывает уже установленные соединения отозванного сертификата — нужен
  `worker_shutdown_timeout`; (4) CRL перечисляет серийные номера — `node_identities.cert_serial`
  хранит их с 001.25 (миграция 130, форма `$ssl_client_serial`; колонку не добавлять) — или карта отказа по `$ssl_client_serial` из
  файла — те же перечитывания без бомбы `nextUpdate`). Карта — только по серийному номеру, не по
  `$ssl_client_fingerprint`: у отозванного листа есть близнец с подписью `(r, n − s)` — другой
  отпечаток при том же номере (податливость ECDSA, `tests/_pki.py::signature_twin`, роаст
  001.25), и карта по отпечатку его пропустила бы; пределы прокси по той же причине ключуются
  номером с 001.25. Без отказа на прокси окно отозванного листа — до конца его срока (90 дней).
  И главное: `ssl_crl` закрывает риск только для **отозванных** сертификатов; медленная заливка
  держателем действующего остаётся, её лечение — предел всей заливки (001.72);
- **профиль сертификата CA.** Рецепт `openssl req -x509 -new -key ca_key …` (`dev-secrets.sh`,
  `secrets/README.md`) даёт CA без `keyUsage`: RFC 5280 требует `keyCertSign` (и `cRLSign` для
  CRL выше) у сертификата, которым проверяют подписи листов, и строгие клиенты его отвергают —
  найдено живой пробой 001.25: Python 3.13+ по умолчанию (`VERIFY_X509_STRICT`) не принимает
  цепочку серверного сертификата агентского порта («CA cert does not include key usage
  extension»). nginx при проверке клиента и Go-агент этого не требуют, поэтому стенд работает;
  промышленный CA выпускать с `-addext "basicConstraints=critical,CA:TRUE,pathlen:0" -addext
  "keyUsage=critical,keyCertSign,cRLSign"` (`pathlen:0` — промежуточных нет, как и
  `ssl_verify_depth 0`: в OpenSSL глубина считает промежуточных CA), тестовый
  `tests/_pki.py::make_ca` — привести к тому же профилю; рецепт `deploy/compose/secrets/README.md`
  исправлен в 001.25 (раунд 2), `dev-secrets.sh` — ещё нет;
- пара `ca_key`/`tls/ca.crt` читается `api` один раз на процесс (`security.ca.get_ca`): смена CA
  — перезапуск `api` и перечитывание nginx вместе, иначе листы новым ключом прокси не примет.

Найдено при 001.25, раунд 4 (решить здесь):

- отказы, которые nginx выносит при разборе заголовков, раньше всех фаз, пределов
  `limit_req`/`limit_conn` не знают: 400 (разбор, негодный `Host`, `Content-Length` вместе с
  `Transfer-Encoding`, HTTP/1.0 с `Transfer-Encoding`, сбой или отсутствие клиентского
  сертификата на 8443, HTTP без TLS на порт TLS), 405 (`TRACE`, `CONNECT`), 408 (заголовки не дошли за
  `client_header_timeout`), 414, 494, 501 (неизвестный `Transfer-Encoding`). Стенд 001.25: залпы по 30 параллельных запросов — 30 × 400 (негодный
  `Host`; без сертификата на 8443), 30 × 405, 30 × 501 без единого 429; по HTTP/1.1 каждый такой
  отказ закрывает соединение. Отказы, которые решает сама конфигурация (404, 411, 413), с 001.25
  идут после пределов (`try_files`; 413 — картой длины до FIND_CONFIG, раунд 5 роаста), но журнал
  от анонимного залпа пределы nginx не защищают: решить здесь — объём и ротация журнала прокси
  отдельно от штатной 3 × 10 МиБ, предел соединений и запросов на соединение с адреса до HTTP
  (`keepalive_requests` на server Node API, предел соединений на уровне хоста); 413 на 8443/8444
  — страница nginx, не единый формат (контракт README это оговаривает);
- возобновление TLS-сессии (`ssl_session_timeout 1d`, общий `ssl_session_cache`): OpenSSL не
  проверяет клиентский сертификат при возобновлении — истёкший лист проходит 8443 до суток после
  срока (C-01 отвечает 401, но пределы прокси он держит), а после `ssl_crl` отозванный лист,
  возобновивший сессию до отзыва, обходит CRL до суток (карта отказа по серийному номеру на
  каждый запрос от этого не зависит). Решить здесь: на агентском server — короткий срок сессии
  или отказ от возобновления (`ssl_session_cache off`; билеты уже выключены —
  `ssl_session_tickets off` на уровне http) вместе с `ssl_crl`, либо карта отказа по номеру
  (роаст 001.25, раунд 4).

Найдено при 001.25, раунд 5 (решить здесь):

- **ключ онлайн-CA в `api` — принятый риск** (решение заказчика 2026-09-25, security.md §7.3):
  сертификат того же CA — единственный якорь агента для серверных сертификатов Control Plane, и
  чтение файлов или выполнение кода в любом публичном маршруте `api` дало бы ключ и подмену
  Control Plane перед нодами. Снижение — здесь: отдельный офлайн-CA серверных сертификатов
  агентских портов (он подписывает `agent.crt`, его сертификат — якорь bootstrap-команды, 001.61

- **сторона C-01 при разделении CA** (роаст 001.25, раунд 6): панель отдаёт якорь в ответе
