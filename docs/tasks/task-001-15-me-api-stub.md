### Интеграция компонентов

Схема `TrafficStats` содержит `raw_uplink`, `raw_downlink`, `billable`, `remaining`, `by_node[]` с
`multiplier`, `by_country[]`, `active_ips`, `device_limit` (§4.12).

Уточнения при реализации:

- восемь операций раздела — три на пути `/me` (`GET`, `PATCH`, `DELETE`) и пять на подпутях;
  ответы — pydantic-схемы с `Literal` для перечислений (состояние подписки — значения
  `subscription_state` базы; платформа — `ios | android | macos | windows | linux | unknown`);
  тела запросов наследуют `StrictModel` (`extra="forbid"`, обрезка краевых пробелов, как в
  `/auth`): `ProfileUpdateIn(language en|ru?, timezone?, announce_consent?)` — часовой пояс
  проверяется по `zoneinfo.available_timezones()` (R-52: имя IANA), `RedeemIn(code 8…64)`;
- все операции — под сессией пользователя: `security/deps.py::current_user` реализован в этой
  задаче (перенос из 001.14, где он не понадобился): cookie `sid` → `SessionStore.get` (TTL
  бездействия продлевается) → сессия вида `user` с `subject_id`-UUID, иначе 401
  `unauthenticated` (сессия администратора кабинет не открывает); результат — `CurrentUser(id,
  session)`; существование и статус пользователя в базе не перепроверяются — блокировка и
  удаление отзывают сессии (Н-27), проверка статуса на каждом запросе — по решению 001.16/001.47;
- раздел включён с `redis_required`: без Redis сессию проверить нельзя — 503 с `Retry-After`
  до поиска сессии для всех восьми операций (fail-closed §9.1; тест 001.12 скорректирован и
  проходит по всем операциям: прежде `/api/v1/me` был заглушкой 501 без зависимости от Redis;
  заглушка `me.profile` из 001.10 снята); вторая линия — обработчик ошибок переводит отказы
  подключения и таймауты Redis (`redis.exceptions.ConnectionError`, `TimeoutError`) в 503 с
  `Retry-After`: отказ Redis посреди запроса с cookie сессии (или на маршруте, где
  `redis_required` забыли) — 503, а не 500; прочие `RedisError` (WRONGTYPE, ошибка Lua) —
  дефекты кода и остаются 500 с трассировкой (ревью раунда 1 C-2, раунда 2 C-1/N-1; страж —
  тест с подменой `SessionStore.get` под живой сессией);
- зависимость пула в маршрутах — `db_pool()` (`db/pool.py`), не `Depends(get_pool)`: у
  `get_pool` есть параметр `settings: Settings | None`, который FastAPI счёл телом запроса и
  вынес схему настроек приложения в OpenAPI (ревью раунда 2, S-1); тест контракта утверждает,
  что у операций без тела нет `requestBody`, а схемы `Settings` нет в компонентах;
- мутации (`PATCH /me`, `DELETE /me`, `redeem`, `reissue`) — под `require_csrf` (§7.3): 403
  `csrf_failed` без заголовка `X-CSRF-Token`;
- действия с необратимыми последствиями требуют `?confirm=true`: перевыпуск токена (UC-16 шаг 4
  — предупреждение о разрыве всех устройств) и удаление аккаунта (UC-14 шаг 1) — без него 409
  `confirmation_required` с `details.warning` и `details.confirm`; подтверждение — параметр
  запроса, а не поле тела, чтобы клиент не мог «подтвердить» случайно вместе с данными;
- заглушки: `ProfileService.get`/`update` возвращают `STUB_PROFILE` (`user@example.com`, `en`,
  `UTC`) под идентификатором сессии с подстановкой переданных полей, `delete_account` ничего не
  делает (логика UC-14 — 001.17) — на стенде кабинет показывает фиксированный профиль, а не
  данные учётной записи; `user_traffic` — `STUB_STATS` (пример §4.12: нода NL с коэффициентом
  2.0, передано 2 + 8 ГБ, списано 20 ГБ, лимит 100 ГБ, остаток 80 ГБ, 1 адрес из 3);
  подписка — `stub_subscription()` (активна, тариф «Standard 100 GB», числа из `STUB_STATS`),
  перевыпуск возвращает другой фиксированный токен; `redeem` отвечает той же подпиской (логика
  и лимиты §5.12 активации — 001.20); онбординг — платформа `unknown` (определение по
  `User-Agent` — 001.16), пять клиентов §4.2 со ссылками установки, `import_url` вида
  `sing-box://import-remote-profile?url=…`, `qr_payload` = первая ссылка, проверка соединения
  `unknown`;
- ссылки подписки строятся из `SUBSCRIPTION_DOMAINS` (`Settings.read()` — чтение окружения на
  запрос без обращения к файлам секретов, которые проверяет только `load()` на старте; в тестах
  окружение задаёт `sub1.example.com,sub2.example.com`): `https://{домен}/s/{token}` на каждом
  домене — единственное место, где заглушка читает настоящую настройку; пустой список — ошибка
  конфигурации: роль `api` не стартует без доменов (валидатор `Settings`), а на запросе это
  500 единого формата в журнал, не 200 с пустыми ссылками (§4.2 требует две); кэш настроек в
  состоянии приложения — 001.16 (ревью раунда 1 S-2/L-1, раунда 2 N-2);
- имена IANA для проверки часового пояса читаются один раз при импорте модуля
  (`IANA_TIMEZONES`): `zoneinfo.available_timezones()` обходит tzdata на диске (~10 мс) и на
  запросе блокировал бы цикл событий (ревью раунда 1, S-1);
- `user_traffic` получает подключение из пула (`pool.acquire()` в маршруте) — обвязка та же, что
  понадобится агрегации 001.16; `import_url` кодирует ссылку подписки в параметре запроса
  (`quote`), тест сверяет раскодированное значение;
- `TrafficStats` сверх контракта: `raw_total`, `limit` (`None` — безлимит), `period`
  (`PeriodRef`: id, начало, конец); байты — целые, коэффициент — десятичная строка (`"2.0"`);
  схемы статистики живут в `accounting/stats.py` и переиспользуются `api/me.py`;
- `GET /me/traffic?period=` принимает UUID периода (иначе 422); без него — текущий период.
