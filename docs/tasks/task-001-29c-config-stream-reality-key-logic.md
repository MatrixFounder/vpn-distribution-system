# Задача 001.29c: Поток конфигурации: версия, закрытый ключ REALITY при выдаче

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-01 Ввод ноды в эксплуатацию
- UC-11 Обновление парка нод
- UC-12 Компрометация ноды

Требования RTM: R-03, R-04.

## Цель задачи

Реализовать поток конфигурации по `docs/architectures/interfaces.md` §5.2 и `data-model.md`
§4.2.3: публикацию версии конфигурации ноды в `node_config_versions` (`publish_config(conn,
node_id)`, первая версия — при подтверждении ноды), выдачу документа из этой строки вместо каркаса
заглушки 001.28 и вставку закрытого ключа REALITY при выдаче ноде из identity запроса. Поток
состава — 001.29; версия раздела `agent` из колонки ноды — 001.29f; генератор по строкам
`inbounds` и ключи из `inbound_secrets` — 001.27.

## Описание изменений

### Изменения в существующих файлах

#### Файл: `control-plane/app/domain/composition.py`

- `publish_config(conn, node_id)`: в транзакции вызывающего — документ `XrayConfigBuilder.build`
  без закрытых ключей REALITY, строка `node_config_versions` (`config_version` =
  `desired_config_version + 1`, `config_json` — документ без ключей, `checksum` — по документу с
  ключами, `config_checksum`), `desired_config_version` ноды; `PUBLISH node:{id}` после коммита
- выдача конфигурации в `state_for`: документ строки `node_config_versions` с версией
  `desired_config_version` ноды; в каждый `realitySettings` вставляется закрытый ключ своего
  inbound для ноды из identity запроса (`node.id`); перед выдачей `config_checksum` документа с
  ключами сверяется с `checksum` строки — расхождение означает, что ключевой материал сменился
  без новой версии, и документ не выдаётся (нода отвергла бы его по контрольной сумме, §5.2):
  раздел `config` в ответе отсутствует, состав и команды выдаются, в журнал приложения — ошибка с
  `node_id` и версией (решение заказчика 2026-11-04, примечания)
- ключ REALITY не получен — контейнер `inbound_secrets.private_key_enc` не открывается привязкой
  своей строки (001.27) или ключ процесса не тот (`CipherMismatch` сверки `checked_cipher`,
  WI-38): раздел `config` не выдаётся, в журнал — ошибка с `node_id` и версией; состав и команды
  — по своим правилам (решение заказчика 2026-11-05, примечания). Источник ключа сообщает отказ
  исключением (`InvalidTag` или `ValueError` — контейнер, `CipherMismatch` — ключ процесса),
  вставка ключей его не перехватывает — решение принимает выдача
- каркас `STUB_CONFIG_DOCUMENT`, `STUB_CONFIG_CHECKSUM`, `stub_config` снимаются; `config`
  фикстур состояния (`contracts/agent_v1/state-*.json`) переписывается по выдаче генератора
  (имена v26.10.31)
- Изменение принятого кода (отступление от сигнатуры заглушки 001.28): `publish_config`
  принимает `conn` вызывающего и работает в его транзакции

#### Файл: `control-plane/app/domain/xray_config.py`

- Изменение принятого кода (отступление от 001.26): `build` не вставляет `realitySettings.privateKey`;
  вставку выполняет отдельная функция по отображению «тег inbound → закрытый ключ»
- источник ключей — функция ноды и тега inbound; до 001.27 — ключ заглушки, выводимый из
  `node_id` и профиля (SHA-256 от `node_id` и кода профиля как закрытый ключ x25519): ключ,
  одинаковый у всех нод, не позволил бы проверить, что нода получает только свой ключ; 001.27
  заменяет источник расшифровкой `inbound_secrets.private_key_enc` (§7.2; контейнер привязан к
  строке inbound, WI-38)
- докстринг модуля («закрытый ключ REALITY — да … в бою документ с ним не хранится открытым»)
  привести к решению ниже; эталон `tests/unit/domain/golden/xray-config.json` — без `privateKey`

#### Файл: `control-plane/app/domain/nodes.py`

- Изменение принятого кода (отступление от 001.25): `approve` вызывает `publish_config(conn,
  node_id)` — первая версия конфигурации (иначе `desired_config_version` остаётся 0 и нода в
  `provisioning` конфигурацию не получает)

#### Файлы: `docs/architectures/data-model.md`, `docs/architectures/interfaces.md`

- `node_config_versions.config_json` — «полная конфигурация Xray без credentials и без закрытых
  ключей REALITY; ключи вставляет C-01 при выдаче, `checksum` — по документу с ключами»
- §5.2 «Поток конфигурации»: закрытый ключ REALITY вставляется при выдаче ноде, определённой по
  identity, как credentials потока состава

#### Ссылки на 001.29 о записи документа конфигурации

- переадресовать на 001.29c: докстринги `CompositionService.publish_config` и модуля

### Интеграция компонентов

`NodeService.approve` → `publish_config` (первая версия). 001.27 вызывает `publish_config(conn,
node_id)` в транзакции изменения inbound и ротации ключевой пары, сборку — по строкам `inbounds`,
источник ключа — `inbound_secrets`. Агент (001.55, 001.80) сверяет `config.checksum` с полученным документом.

## Примечания

`tdd-strict`: контракт `/agent/v1` — ядро системы.

Выделена из 001.29 2026-11-04 по правилу 4 «Цикла задачи» (решение заказчика В-47 а). Версия
раздела `agent` из колонки ноды выделена в 001.29f 2026-11-05 по тому же правилу (решение
заказчика): четвёртое независимое правило 001.29c.

Решение заказчика 2026-11-04 (вопрос «Найдено при 001.26» задачи 001.29): строка
`node_config_versions` хранит документ без закрытого ключа REALITY; C-01 вставляет
расшифрованный ключ при выдаче ноде, определённой по identity, как credentials потока состава
(`interfaces.md` §5.2); `config.checksum` считается при публикации по документу с ключом.
Ключ хранится только в `inbound_secrets.private_key_enc` (§7.2), ротация `APP_ENCRYPTION_KEY`
затрагивает только эту таблицу. Следствие для 001.27: смена ключевой пары выпускает новую версию
конфигурации в той же транзакции (так и записано в `rotate_keypair`). Отклонены: шифрование
`config_json` целиком (копия ключа в каждой версии, перешифровка всей истории при ротации ключа
приложения, документ не читается в базе и панели) и ключ открытым в строке (§7.2).

Решение заказчика 2026-11-04 (правило 1 «Цикла задачи»): при расхождении контрольной суммы
документа с ключами и строки раздел `config` не выдаётся, состав и команды выдаются, ошибка
пишется в журнал приложения; нода остаётся на применённой версии, расхождение Desired/Applied
видно в панели (001.75). Отклонено: 500 на весь ответ состояния — нода перестала бы получать и
отзывы доступа.

Решение заказчика 2026-11-05 (вопрос «Найдено при WI-38»): закрытый ключ REALITY не получен —
контейнер `inbound_secrets.private_key_enc` не открывается привязкой своей строки (подменён или
повреждён) или ключ процесса не тот (`CipherMismatch`) — раздел `config` не выдаётся, ошибка с
`node_id` и версией в журнал, как при расхождении контрольной суммы; нода остаётся на
применённой конфигурации; состав и команды — по своим правилам (WI-38: ответ со строками
`active` при чужом ключе — ошибкой). Отклонено: 500 на весь ответ при чужом ключе процесса —
отзывы не доходили бы до нод с отстающей конфигурацией.

Найдено при 001.26 (заглушки): каркас конфигурации заглушки 001.28
(`composition.STUB_CONFIG_DOCUMENT`) — не выдача генератора и пишет прежние имена-псевдонимы
(`clients`, `network`); поток конфигурации отдаёт документ из строки `node_config_versions`,
которую пишет `publish_config` по `XrayConfigBuilder.build` (имена v26.10.31).

Решения заказчика 2026-11-20 (роаст 001.29c, раунд 1):

- L2 — курсор `config_version` ноды впереди версии сервера (восстановление из копии), а выдача
  конфигурации отказывает: поведение не меняется — дельта 409 `cursor_ahead`, снапшот 200 с
  `config: null`; нода держит свой курсор конфигурации и повторяет, пока отказ ключа не
  устранён. README контракта описывает этот исход. Отклонено: не отклонять дельту по опережающему
  курсору конфигурации при отказе выдачи — меняет принятый контракт курсора 001.26.
- L4 — нода в `disabled` и `suspended` получает конфигурацию с закрытым ключом REALITY по
  вентилю §4.6 (собственный ключ ноды, без него Xray не стартует); «живых ключей не получает»
  README относится к credentials пользователей. Отклонено: не выдавать раздел `config` нодам в
  `disabled`/`suspended`.

Решение заказчика 2026-11-20 после раунда 3 (предел исчерпан, обе линзы REJECTED, дефектов кода
нет): правки пяти находок раунда 3 (H1, H2, R3-L1…L3) без четвёртого роаста — посадки на новые
стражи, `make check`, отчёт, приёмка и коммит.

Технические заметки реализации (2026-11-20, поведение не меняют):

- `publish_config(conn, node_id) -> int` возвращает версию; `PUBLISH node:{id}` после коммита
  делает вызывающий — `wake_config(node_id, version)` (сообщение `config:{версия}`): публикация
  идёт в транзакции вызывающего и момента коммита не знает. `approve` будит ноду после своей
  транзакции; 001.27 — так же (записано в её файле).
- Источник ключа — `RealityKeySource` `(conn, node_id, tag) → bytes` на подключении вызывающего:
  публикация в транзакции ротации ключевой пары видит новый ключ своей транзакции, выдача читает
  ключ в том же снимке `repeatable read`, что и версию ноды и её строку, — ротация, закоммиченная
  между чтениями, не выглядит сменой ключа без новой версии.
- Отказ выдачи (`config` не выдан) сам по себе не повод ответить: при текущих курсорах состава и
  раздела `agent` ответ — 204 (удержание), иначе нода спрашивала бы снова сразу после пустого 200.
- Строки версии `desired_config_version` нет или строка повреждена по форме (нет списка
  `inbounds`, inbound не объект, у inbound REALITY нет тега — `xray_config.MalformedConfig`;
  публикация пишет обе в одной транзакции, так что это повреждение данных) — тот же исход, что у
  расхождения суммы: `config` не выдан, ошибка в журнал (роаст раунд 1, L1). Исключение источника
  ключа вне набора отказов (`InvalidTag`, `ValueError`, `CipherMismatch`) не перехватывается.
- Конфигурацию из снапшота нода применяет и тогда, когда её `version` меньше применённой
  (курсор `config_version` ставит сервер, как у раздела `agent` и `users.seq`); снапшот с
  `config: null` курсор не меняет — правило контракта по образцу раздела `agent`, записано в
  README и передано 001.55 (роаст раунд 2, N2).
- Версию пишет транзакция той операции, что меняет конфигурацию: C-01 — подтверждение ноды и
  операции панели над inbound, в том числе ротация ключевой пары `rotate-keypair`; C-02 — ротация
  ключевой пары всех inbound ноды по отзыву identity (`composition.rotate_node_credentials`) и
  снятие прежнего `short_id` (роаст раунды 1–3, L3/N1/R3-L1; `interfaces.md`,
  `system-architecture.md`).
- Подтверждение после повторного ввода ноды (`pending` после обмена) выпускает следующую версию:
  документ собирается заново по нынешней карточке.
- До 001.27 документ собирается по `inbounds.stub_inbounds(node_id)`; `XrayConfigBuilder.build`
  получает карточку ноды из транзакции публикации (`nodes.read_node`).
- `composition` импортирует `xray_config` и `inbounds` на месте: они импортируют `plans`, а
  `plans` — `composition`.
