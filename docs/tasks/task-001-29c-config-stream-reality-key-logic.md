## Цель задачи

Реализовать поток конфигурации по `docs/architectures/interfaces.md` §5.2 и `data-model.md`
§4.2.3: публикацию версии конфигурации ноды в `node_config_versions` (`publish_config(conn,
node_id)`, первая версия — при подтверждении ноды), выдачу документа из этой строки вместо каркаса
заглушки 001.28, вставку закрытого ключа REALITY при выдаче ноде из identity запроса и версию
раздела `agent` из колонки ноды. Поток состава — 001.29; генератор по строкам `inbounds` и ключи
из `inbound_secrets` — 001.27.

## Описание изменений

### Изменения в существующих файлах

#### Файл: `control-plane/app/domain/composition.py`

- `publish_config(conn, node_id)`: в транзакции вызывающего — документ `XrayConfigBuilder.build`
  без закрытых ключей REALITY, строка `node_config_versions` (`config_version` =
  `desired_config_version + 1`, `config_json` — документ без ключей, `checksum` — по документу с
  ключами, `config_checksum`), `desired_config_version` ноды; `PUBLISH node:{id}` после коммита
- выдача конфигурации в `state_for`: документ строки `node_config_versions` с версией
  `desired_config_version` ноды; в каждый `realitySettings` вставляется закрытый ключ своего
  inbound для ноды из identity запроса (`node.id`); перед выдачей `config_checksum` документа с
  ключами сверяется с `checksum` строки — расхождение означает, что ключевой материал сменился
  без новой версии, и документ не выдаётся (нода отвергла бы его по контрольной сумме, §5.2):
  раздел `config` в ответе отсутствует, состав и команды выдаются, в журнал приложения — ошибка с
  `node_id` и версией (решение заказчика 2026-11-04, примечания)
- каркас `STUB_CONFIG_DOCUMENT`, `STUB_CONFIG_CHECKSUM`, `stub_config` снимаются; `config`
  фикстур состояния (`contracts/agent_v1/state-*.json`) переписывается по выдаче генератора
  (имена v26.10.31)
- раздел `agent`: `version` — колонка ноды (см. миграцию), `max_conn_per_ip` — колонка
  `nodes.max_conn_per_ip`; `new_conn_rate_per_ip` (001.27), `multiplier_milli` (001.36),
  `disconnect_strategy` (001.40) остаются на заглушке `STUB_AGENT` до своих владельцев
- Изменение принятого кода (отступление от сигнатуры заглушки 001.28): `publish_config`
  принимает `conn` вызывающего и работает в его транзакции

#### Файл: `control-plane/app/domain/xray_config.py`

- Изменение принятого кода (отступление от 001.26): `build` не вставляет `realitySettings.privateKey`;
  вставку выполняет отдельная функция по отображению «тег inbound → закрытый ключ»
- источник ключей — функция ноды и тега inbound; до 001.27 — ключ заглушки, выводимый из
  `node_id` и профиля (SHA-256 от `node_id` и кода профиля как закрытый ключ x25519): ключ,
  одинаковый у всех нод, не позволил бы проверить, что нода получает только свой ключ; 001.27
  заменяет источник расшифровкой `inbound_secrets.private_key_enc` (§7.2)
- докстринг модуля («закрытый ключ REALITY — да … в бою документ с ним не хранится открытым»)
  привести к решению ниже; эталон `tests/unit/domain/golden/xray-config.json` — без `privateKey`

#### Файл: `control-plane/app/domain/nodes.py`

- Изменение принятого кода (отступление от 001.25): `approve` вызывает `publish_config(conn,
  node_id)` — первая версия конфигурации (иначе `desired_config_version` остаётся 0 и нода в
  `provisioning` конфигурацию не получает)

#### Миграция `control-plane/migrations/NNN_*.sql`

- колонка версии раздела `agent` у `nodes` (`agent_section_version int NOT NULL`): в
  `data-model.md` §4.2.3 её нет — вносится этой задачей. Начальное значение существующих строк
  больше `STUB_AGENT_VERSION` (1), если `max_conn_per_ip` ноды отличается от значения заглушки:
  нода, применившая версию 1, иначе осталась бы на значениях заглушки

#### Файлы: `docs/architectures/data-model.md`, `docs/architectures/interfaces.md`

- `node_config_versions.config_json` — «полная конфигурация Xray без credentials и без закрытых
  ключей REALITY; ключи вставляет C-01 при выдаче, `checksum` — по документу с ключами»;
  колонка версии раздела `agent` у `nodes`
- §5.2 «Поток конфигурации»: закрытый ключ REALITY вставляется при выдаче ноде, определённой по

#### Ссылки на 001.29 о записи документа конфигурации

### Интеграция компонентов

`NodeService.approve` → `publish_config` (первая версия). 001.27 вызывает `publish_config(conn,
node_id)` в транзакции изменения inbound и ротации ключевой пары, сборку — по строкам `inbounds`,
источник ключа — `inbound_secrets`. Задача, переводящая поле раздела `agent` на источник или
меняющая его значение (001.27, 001.36, 001.40), увеличивает версию раздела у затронутых нод.
Агент (001.55, 001.80) сверяет `config.checksum` с полученным документом.

## Примечания

`tdd-strict`: контракт `/agent/v1` — ядро системы.

Выделена из 001.29 2026-11-04 по правилу 4 «Цикла задачи» (решение заказчика В-47 а).

Решение заказчика 2026-11-04 (вопрос «Найдено при 001.26» задачи 001.29): строка
`node_config_versions` хранит документ без закрытого ключа REALITY; C-01 вставляет
расшифрованный ключ при выдаче ноде, определённой по identity, как credentials потока состава
(`interfaces.md` §5.2); `config.checksum` считается при публикации по документу с ключом.
Ключ хранится только в `inbound_secrets.private_key_enc` (§7.2), ротация `APP_ENCRYPTION_KEY`
затрагивает только эту таблицу. Следствие для 001.27: смена ключевой пары выпускает новую версию
конфигурации в той же транзакции (так и записано в `rotate_keypair`). Отклонены: шифрование
`config_json` целиком (копия ключа в каждой версии, перешифровка всей истории при ротации ключа
приложения, документ не читается в базе и панели) и ключ открытым в строке (§7.2).

Решение заказчика 2026-11-04 (правило 1 «Цикла задачи»): при расхождении контрольной суммы
документа с ключами и строки раздел `config` не выдаётся, состав и команды выдаются, ошибка
пишется в журнал приложения; нода остаётся на применённой версии, расхождение Desired/Applied
видно в панели (001.75). Отклонено: 500 на весь ответ состояния — нода перестала бы получать и
отзывы доступа.

Найдено при 001.26 (заглушки): каркас конфигурации заглушки 001.28
(`composition.STUB_CONFIG_DOCUMENT`) — не выдача генератора и пишет прежние имена-псевдонимы
(`clients`, `network`); поток конфигурации отдаёт документ из строки `node_config_versions`,
которую пишет `publish_config` по `XrayConfigBuilder.build` (имена v26.10.31).

Версия раздела `agent` (контракт 001.26: поле `agent.version`, курсор запроса
`agent_section_version`) — своя колонка ноды; поля раздела переходят с заглушки `STUB_AGENT` на
источник у своих владельцев: `max_conn_per_ip` — здесь (колонка `nodes` есть),
`new_conn_rate_per_ip` — 001.27 (В-10), `multiplier_milli` — 001.36, `disconnect_strategy` —
001.40.
