## Цель задачи

Перевести публикацию состава на задачу очереди, поставленную в транзакции бизнес-операции
(`interfaces.md` §5.4, Н-14), реализовать публикацию состава ноды целиком (`publish_node`) и
снятие доступа удалённого пользователя (`remove_user`). Исполнитель `publish_user`, выделение
`updated_seq` и дельта — 001.29; уплотнение строк `removed` — 001.29e; ротация credentials —
001.29d.

## Описание изменений

### Изменения в существующих файлах

#### Файл: `control-plane/app/domain/composition.py`

- постановка публикации: бизнес-операция ставит задачу `composition.publish_user` в своей транзакции (`enqueue(conn, …)`, очередь `critical`, ключ `publish_user:{user_id}:{xid}`); прямой вызов публикации после коммита и из транзакции, держащей строку ноды (приём отчёта), не допускается — только постановка задачи
- `remove_user(conn, user_id)`: в транзакции вызывающего постановка `composition.publish_user`; исполнитель для `users.status = 'deleted'` пишет только строки `removed` с `updated_seq` через `UPDATE nodes … RETURNING` (001.29)
- `publish_node(node_id)` — исполнитель задачи `composition.publish_node` (очередь `critical`, ключ `publish_node:{node_id}:{xid}` по образцу `publish_user`; задачу ставит вызывающий в своей транзакции): состав ноды целиком — при первом переходе в `active` (001.30), при смене групп тарифа и групп доступа ноды (изменение записи ноды — 001.87)
- Изменение принятого кода (отступление от сигнатуры заглушки 001.28): `remove_user` принимает `conn` вызывающего и работает в его транзакции
- сериализация с `publish_user` (001.29, роаст раунд 3, R3-1): публикации одного пользователя идут под сессионной advisory-блокировкой (`PUBLISH_LOCK_CLASS`, ключ `hashtext(user_id)`), а `publish_node` пишет строки многих пользователей. Писатель строк пользователя обязан либо брать блокировки затронутых пользователей **до** блокировки строки ноды (ключи — по возрастанию), либо ставить `composition.publish_user` на каждого пользователя ноды. Иначе запуск публикации пользователя после смены тарифа выберет кандидатов без незакоммиченной строки `publish_node` и не снимет доступ; блокировка пользователя, взятая после блокировки ноды, даёт взаимную блокировку с `publish_user`. Решение исполнителя (2026-11-05, первый путь по одному пользователю): `publish_node` обходит пользователей ноды (кандидаты — пересечение групп тарифа с группами ноды и пользователи с строкой не `removed` на ноде) по возрастанию `user_id`; на каждого — блокировка пользователя, своя транзакция с блокировкой строки ноды и записью пары (`_publish_pair`), снятие блокировки. Отклонены: блокировки всех пользователей ноды сразу (до 1 000 advisory-блокировок в одной сессии — общая таблица блокировок `max_locks_per_transaction × max_connections`) и задача `publish_user` на каждого (до 1 000 задач, каждая публикует все ноды пользователя). Пробуждение ноды — одно, после последнего коммита

#### Файл: `control-plane/app/jobs/handlers/composition.py`

- обработчик `composition.publish_node` в очереди `critical`

#### Файл: `control-plane/app/domain/subscriptions.py`

- Изменение принятого кода (отступление от 001.22): шесть вызовов `CompositionService.publish_user` после коммита заменяются постановкой задачи `composition.publish_user` в транзакции перехода (`interfaces.md` §5.4: `INSERT INTO jobs` в транзакции бизнес-операции; при крахе между коммитом и прямым вызовом отзыв терялся бы — Н-14). Довод докстринга модуля — ключ `publish:{node_id}:{users_seq}` при постановке неизвестен — снимается ключом `publish_user:{user_id}:{xid}`; докстринги модуля и обработчика привести к этому

#### Файл: `control-plane/app/domain/plans.py`

- Изменение принятого кода (отступление от 001.19): `PlanService._set_composition` ставит задачу `composition.publish_node` нод групп, вошедших в состав тарифа или вышедших из него

### Интеграция компонентов

Задачу `composition.publish_user` ставят `SubscriptionService` (001.22), `LimitsService` (001.35),
`DeviceLimitService` (001.38) и перевыпуск токена (001.42); `remove_user` (`delete_account`
001.17) вызывается с `conn` вызывающего. `StatusService` (001.30) при первом `active`,
`PlanService` (001.19) при смене групп тарифа и изменение записи ноды (001.87) при смене её групп
доступа ставят задачу `composition.publish_node`.

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Публикация — задача в транзакции перехода
   - Входные данные: перевод пользователя в `suspended_quota`; откат транзакции перехода
   - Ожидаемый результат: задача `composition.publish_user` стоит в `jobs` в транзакции перехода; после отката задачи нет; после исполнения дельта содержит строку пользователя
2. **TC-E2E-02:** Смена состава тарифа публикует ноды
   - Входные данные: группа нод вошла в состав тарифа (`PlanService._set_composition`)
   - Ожидаемый результат: задача `composition.publish_node` для каждой ноды группы в транзакции изменения; после исполнения у ноды строки всех пользователей тарифа
3. **TC-E2E-03:** Удалённый пользователь не получает доступ
   - Входные данные: `users.status = 'deleted'`; `publish_user`
   - Ожидаемый результат: на всех нодах только строки `removed`
