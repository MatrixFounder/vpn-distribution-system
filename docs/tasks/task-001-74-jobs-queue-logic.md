# Задача 001.74: Очередь задач: повторы, экспоненциальная задержка, DLQ с алертом, бюджет ожидания

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-05 Исчерпание лимита и отзыв доступа
- UC-04 Учёт трафика и списание с коэффициентом

Требования RTM: R-46.

## Цель задачи

Реализовать логику очереди `jobs` по `docs/architectures/interfaces.md` §5.4: `LISTEN/NOTIFY`,
страховочный опрос, повтор с экспоненциальной задержкой до `max_attempts`, статус `dead` с алертом,
измерение времени ожидания задачи критичного пути (≤ половины бюджета Н-13).

## Описание изменений

### Изменения в существующих файлах

- `LISTEN jobs_critical` / `jobs_background`; опрос 1 с / 10 с; при ошибке `attempts += 1`, `run_at = now() + backoff(attempts)`; `attempts >= max_attempts` → `dead` + событие для алерта

#### Файл: `control-plane/app/jobs/queue.py`

#### Файл: `control-plane/app/main.py`

- метрики `jobs_wait_seconds{queue}`, `jobs_dead_total`

### Интеграция компонентов

Алерт по `dead` — правило Prometheus (001.68).

Уточнения при реализации:

- `LISTEN`/`NOTIFY` и страховочный опрос 1 с / 10 с сделаны в 001.11 и не менялись; «`NOTIFY`
  после коммита через обёртку `transaction()`» не потребовалось: `pg_notify` внутри транзакции
  постановки PostgreSQL доставляет только при её коммите (тест 001.11 `test_notify_only_on_commit`
  это доказывает), отдельная обёртка добавила бы вторую точку отказа между коммитом и
  уведомлением;
- `enqueue` возвращает `Enqueued(id, created)` — именованный кортеж: при активном ключе
  возвращается существующая задача (`created = False`, без `NOTIFY`), `DuplicateJobError` удалён;
  гонка «активная задача завершилась между вставкой и чтением» — вторая вставка, затем
  `RuntimeError`; планировщик считает только созданные; задача в ожидании повтора активна и
  держит ключ — повторная доменная операция получает её (старая полезная нагрузка; для
  outbox-задач она детерминирована ключом);
- аренда выборки (ревью раунда 1, C-01): исполнитель, умерший посреди задачи, оставляет строку
  `running`; `claim` забирает и такие строки, если `locked_at` старше `LEASE` (5 минут) —
  попытка засчитывается, так что бесконечно умирающая задача доходит до `dead`; обработчик
  длиннее аренды может быть выполнен дважды (at-least-once §5.8; обработчики идемпотентны по
  ключу, длинные обработчики — отдельная задача с продлением аренды); свежая `running` не
  отбирается; завершение фехтуется владельцем (ревью раунда 2, C-01): `complete`/`fail`/
  `bury`/`retry` принимают `owner` и меняют строку только при `locked_by = owner` — медленный
  «зомби», у которого задачу перехватили, получает `LookupError` (исполнитель журналирует и
  живёт), не закрывает чужую задачу и не сжигает её попытки; гарантия §5.4 «один исполнитель
  на задачу» сохраняется для записи состояния, а выполнение — at-least-once;
- повторы: попытка засчитывается при выборке (001.11); исключение обработчика →
  `worker.decide`: `NonRetryableError` из обработчика → `jobs.fail` (терминальный `failed`,
  без повторов — для ошибок, которые время не лечит); `attempts >= max_attempts` → `jobs.bury`
  (`dead`, текст последней ошибки, `finished_at`) с записью ERROR в журнале исполнителя —
  это и есть «событие для алерта» вместе с рядом `control_plane_jobs{status="dead"}` (правило
  Prometheus — 001.68; таблица `events` со своим перечислением типов §4.17 для этого не
  предназначена);
  иначе → `jobs.retry` (`pending`, `run_at = now() + backoff(attempts)`, `last_error`);
  задача в ожидании повтора держит ключ идемпотентности (она активна);
- `backoff(attempt, base, cap, rng)` = `min(cap, base · 2^(attempt−1)) · (1 + 0,25·rng())`:
  1, 2, 4 … с, потолок 300 с, джиттер до четверти интервала (константы `BACKOFF_BASE`,
  `BACKOFF_CAP`, `BACKOFF_JITTER`; тесты уменьшают базу до 0,2 с); задержка считается от
  момента выборки часами базы (`run_at − claimed_at`), тесты не сравнивают часы стенда и тестов;
- миграция `110_jobs_retry`: колонки `jobs.claimed_at` (последняя выборка, остаётся после
  завершения — `locked_at` снимается), `jobs.finished_at` и частичный индекс по `claimed_at`
  (окно метрики; откат идемпотентен — `DROP INDEX IF EXISTS`); нумерация `110` — по порядку
  применения (правило карты `control-plane/.AGENTS.md` уточнено: номер задачи — в заголовке
  файла, а не в имени, ревью D-01);
- ожидание задачи: `queue.wait_seconds(window)` — наибольшее по очередям из двух источников —
  выбранные за окно (`claimed_at − run_at`, только строки с `claimed_at ≥ run_at`: у строки в
  ожидании повтора `run_at` перенесён позже прошлой выборки, и она не учитывается до следующей
  выборки) и **ещё не выбранные готовые** (`pending`, `run_at ≤ now()` → `now() − run_at`):
  стоящая очередь без исполнителя видна как растущее ожидание, а не как 0 (ревью раунда 1,
  L-01/L-02/T-01); `/metrics` отдаёт `control_plane_jobs_wait_seconds{queue}` и
  `control_plane_jobs_wait_budget_seconds{queue="critical"} 5` — крыша (половина p95 Н-13),
  строка раскладки §5.4 на пробуждение исполнителя — 1 с, правило 001.68 может быть строже
  (ревью D-02); ветка «не выбранные готовые» считает и задачи типов, которых текущий выпуск
  исполнителей не знает (§17.2 — они ждут намеренно): при поэтапной выкатке ряд растёт на
  здоровой системе, правилу 001.68 нужна оговорка или фильтр по известным типам (ревью
  раунда 2, N-01); `jobs_dead_total` из контракта **не заводится**: DLQ уже виден рядом
  `control_plane_jobs{queue,status="dead"}` (001.11), правило алерта —
  `sum(control_plane_jobs{status="dead"}) > 0` (ревью S-01); метрики — в `app/metrics.py`, а не
  в `main.py` (там только маршрут `/metrics`); гистограмма и ряды исполнителей — 001.68;
- `failed` (терминальный отказ по решению обработчика) отличается от `dead` (исчерпанные
  повторы): оба освобождают ключ; возврат задачи из DLQ — оператор/админ-API позже;
- тесты 001.11 скорректированы под новую семантику (дубль ключа — существующая задача; `boom`
  → повтор, а не `failed`; новый тип `test-fatal` для `NonRetryableError`); `rollback_through`
  считает шаги по числу миграций; страж каталога 001.09 дополнен колонками и индексом `110`.
