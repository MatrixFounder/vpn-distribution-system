# Задача 001.47: Аутентификация администраторов: TOTP, резервные коды, сессии

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-09 Управление тарифами, группами и кодами

Требования RTM: R-36.

<!-- contract:goal -->

## Цель задачи

Реализовать обязательный второй фактор, резервные коды, сессии с TTL бездействия 12 часов (Н-27),
инвалидацию сессий при блокировке ≤ 60 с, первого Super Admin командой на хосте `admin create` и
сброс второго фактора командой на хосте `admin reset-2fa`, когда другого активного Super Admin нет
(решения заказчика 2026-10-25, В-33 и В-35).

## Описание изменений

### Новые файлы

- `control-plane/tests/e2e/test_admin_auth.py` — реальные утверждения; блокировка → сессии недействительны за 60 с (AC-16); `admin reset-2fa`
- `control-plane/app/domain/admins.py` — `class AdminService`: `create_first(email)` (команда
  `admin create`); `block(admin_id, ctx)` — `admin_users.status = 'blocked'`, после коммита
  `SessionStore.revoke_all(admin_id)`, вызов `audit.record`; `reset_second_factor(admin_id, ctx)` —
  снятие `totp_secret_enc` и `totp_enabled_at`, удаление резервных кодов учётной записи,
  `SessionStore.revoke_all(admin_id)`, вызов `audit.record`, задачи `send_email` вида
  `admin_2fa_reset` каждому активному администратору в транзакции сброса — набор писем один у
  команды хоста и у сброса из раздела (001.89); маршруты раздела `/admin/admins` над этими
  методами — задача 001.89

### Изменения в существующих файлах

#### Файл: `control-plane/app/security/totp.py`

- pyotp; секрет в `totp_secret_enc`; 10 резервных кодов, хеши в `admin_recovery_codes`; использование — в Audit Log

#### Файл: `control-plane/app/api/admin/auth.py`

- двухшаговый вход; сессия `kind = admin` с TTL 12 ч бездействия; вход учётной записи со статусом, отличным от `active`, отклоняется так же, как неверный пароль
- `POST /admin/auth/recovery` — вход по резервному коду вместо кода TOTP; второй фактор этот маршрут не сбрасывает
- администратор, потерявший TOTP и все резервные коды, восстанавливает доступ сбросом второго
  фактора: другим Super Admin в разделе `/admin/admins` (001.89), если второй активный Super Admin
  есть, иначе командой на хосте `admin reset-2fa` (эта задача); держатель доступа к хосту — второй
  держатель доступов §17.12 (решение заказчика 2026-10-25, В-35)
- вход, неудачная попытка входа и выход администратора вызывают `audit.record` (`actor_type = admin`, §4.16); строки `audit_log` проверяет 001.48
- пороги частоты §5.12 для `/admin/auth/login`, `/totp`, `/recovery`: по адресу источника и по учётной записи (как `LOGIN_IP` и `LOGIN_ACCOUNT` в 001.84) и отдельный порог неверных кодов TOTP и резервных кодов на учётную запись; реакция — по §5.12 и `docs/architectures/security.md` §7.3

#### Файл: `control-plane/app/cli.py`

- `admin create --email` (первый Super Admin) с обязательным включением второго фактора при первом входе
- `admin reset-2fa --email` — `AdminService.reset_second_factor`; следующий вход требует включить
  второй фактор заново, как первый вход после `admin create`. Запись журнала — `audit.record` с
  `actor_type = system`; задачи `send_email` вида `admin_2fa_reset` каждому активному
  администратору ставит `reset_second_factor` (письмо — 001.78). Если кроме владельца учётной
  записи есть активный Super Admin, команда завершается с кодом 1 и ничего не меняет: сброс
  выполняет он в разделе `/admin/admins` (001.89)

### Интеграция компонентов

Сессии — `SessionStore` (001.14).

Раздел панели `/admin/admins` — создание учётной записи с обязательным TOTP, роль, блокировка,
сброс пароля, сброс второго фактора другим Super Admin — задача 001.89 (решение заказчика
2026-10-25, В-33); она вызывает методы `AdminService` этой задачи. Первый Super Admin создаётся
только командой `admin create`. Задачи `send_email` вида `admin_2fa_reset` обрабатывает 001.78;
до неё они остаются в очереди.

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Вход с TOTP
   - Входные данные: пароль + код
   - Ожидаемый результат: cookie сессии `admin`
2. **TC-E2E-02:** Блокировка инвалидирует
   - Входные данные: `AdminService.block` учётной записи с активной сессией (маршрут блокировки —
     001.89)
   - Ожидаемый результат: запрос через 1 с → 401; повторный вход той же учётной записью → 401
     (AC-16)
3. **TC-E2E-03:** Резервный код однократен
   - Входные данные: один код дважды
   - Ожидаемый результат: второй — 401; оба использования вызвали `audit.record` (строки
     `audit_log` проверяет 001.48)
4. **TC-E2E-04:** Перебор второго фактора
   - Входные данные: неверные коды TOTP сверх порога для одной учётной записи
   - Ожидаемый результат: следующая попытка отклонена по порогу (§5.12)
5. **TC-E2E-05:** Сброс второго фактора на хосте
   - Входные данные: учётные записи: Super Admin A с активной сессией и Support B; `admin reset-2fa
     --email A`; затем `admin reset-2fa --email B` (A — активный Super Admin)
   - Ожидаемый результат: для A — сессия A недействительна, `totp_enabled_at` пуст, неиспользованных
     резервных кодов нет, вход A требует включить второй фактор; `audit.record` вызван с
     `actor_type = system`; задачи `send_email` вида `admin_2fa_reset` — по одной на A и B. Для B —
     код выхода 1, учётная запись B не изменилась
