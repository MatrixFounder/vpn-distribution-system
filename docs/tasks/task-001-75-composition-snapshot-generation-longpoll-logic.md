# Задача 001.75: Подтверждение курсоров и расхождение Desired/Applied

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-01 Ввод ноды в эксплуатацию

Требования RTM: R-04.

<!-- contract:goal -->

## Цель задачи

Реализовать `ack` с проверкой курсоров, снятие `resync_required` и ряд расхождения Desired/Applied
для алерта AC-29. Полный снапшот, `state_generation` и контрольная сумма состава — 001.75b;
удержание long-poll — 001.75c.

<!-- contract:changes -->

## Описание изменений

### Изменения в существующих файлах

#### Файл: `control-plane/tests/e2e/test_agent_api.py`

- дополнить: `ack`; ряд расхождения Desired/Applied (TC-E2E-03)

#### Файл: `control-plane/app/domain/composition.py`

- `ack`: запись `applied_*` через функцию проверки курсоров `validate_applied` — подтверждение выше выданного курсора отклоняется (§11.3: нода недоверенная; иначе компрометированная нода объявляет `applied_users_seq` = 2^63 и выпадает из доставки отзывов, оставаясь «синхронизированной» в панели). Ту же функцию вызывает heartbeat (001.30); запрос состояния с курсором впереди серверного уже отклоняется 409 `cursor_ahead` (001.28)
- `resync_required` читается из колонки `nodes.resync_required` (взводит 001.29); в ответе с `users.full = true` он `false` (README, «Когда пересинхронизироваться и когда остановиться»); при выдаче ответа с `users.full = true` при взведённом признаке его `users.seq` запоминается в новой колонке `nodes.resync_seq` (NULL по умолчанию; каждый взвод признака сбрасывает её в NULL); признак снимается, когда `resync_seq` не NULL и `applied_users_seq ≥ resync_seq`; подтверждение урезанного ответа признак не снимает. `users.full` — признак того, что по ответу можно удалять

#### Файл: `control-plane/app/metrics.py`

- ряд расхождения Desired/Applied по ноде `control_plane_node_applied_lag_seconds{node_id}`: время, в течение которого `applied_*` отстают от `desired_*`; ноды в ручных статусах в ряд не входят (§17.4); правило алерта «дольше 120 с» (AC-29), приоритет «Отложенный» (решение заказчика 2026-10-25, В-42) — 001.68: алерт — правило Prometheus по ряду, а не задача планировщика (ревью WI-35, группа OPS-02)

#### Файлы: `control-plane/app/domain/statuses.py`, миграция `control-plane/migrations/NNN_*.sql` и её откат

- Изменение принятого кода (отступление от 001.28): докстринг `StreamGate.filters_composition` в `statuses.py` («запись и снятие — 001.29») — «запись — 001.29, снятие — 001.75»; колонка `nodes.resync_seq` — миграцией этой задачи

### Интеграция компонентов

Функцию проверки курсоров вызывает и приём heartbeat (001.30). Ответ с `users.full = true` на
настоящих строках выдаёт снапшот 001.75b — от неё задача зависит (TC-E2E-02).

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Подтверждение выше выданного курсора
   - Входные данные: `ack` и heartbeat с `applied_users_seq` больше выданного
   - Ожидаемый результат: отказ; `applied_*` не изменены
2. **TC-E2E-02:** Снятие `resync_required`
   - Входные данные: нода со снапшотом (`users.full = true`) до перевода в `suspended`; вышла из `suspended`; подтверждение урезанного ответа, затем ответа с `users.full = true`
   - Ожидаемый результат: после первого признак остаётся; после второго снят
3. **TC-E2E-03:** Ряд расхождения Desired/Applied (AC-29)
   - Входные данные: нода `active` после публикации, поднявшей `desired_users_seq` выше `applied_users_seq`; два чтения `/metrics` с промежутком; `ack` до `desired_*`; нода `maintenance` с тем же отставанием
   - Ожидаемый результат: значение ряда ноды `active` во втором чтении больше, чем в первом; после `ack` — 0; ноды `maintenance` в ряду нет (§17.4)

### Модульные тесты

- Не требуются: проверка курсоров, снятие признака и ряд расхождения проверяются сквозными
  TC-E2E-01…TC-E2E-03 на базе.

### Регрессионные тесты

- Команда: `cd control-plane && pytest tests/e2e/test_agent_api.py -k 'ack or resync or desired'`
- Полный набор: `make test` — существующие тесты проходят.
