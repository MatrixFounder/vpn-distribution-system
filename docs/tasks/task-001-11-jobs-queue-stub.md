# Задача 001.11: Очередь задач в PostgreSQL: интерфейс и каркас исполнителей

Тип задачи: `[STUB CREATION]`.

- UC-04 Учёт трафика и списание с коэффициентом

## Цель задачи

Определить интерфейс очереди `jobs` и процессы `worker` и `scheduler` с заглушками обработчиков,
чтобы сквозной тест ставил и забирал задачу.

## Описание изменений

### Новые файлы

- `control-plane/app/jobs/queue.py` — `async def enqueue(conn, queue: str, type: str, payload: dict, idempotency_key: str, run_at=None) -> int`; `async def claim(conn, queue: str, worker_id: str) -> Job | None` (`FOR UPDATE SKIP LOCKED`); `async def complete(conn, job_id) -> None`; `async def fail(conn, job_id, error: str) -> None`
- `control-plane/app/jobs/worker.py` — `async def run(queue: str) -> None`: `LISTEN jobs_<queue>`, страховочный опрос 1 с / 10 с, диспетчер `HANDLERS: dict[str, Handler]`
- `control-plane/app/jobs/scheduler.py` — `async def run() -> None`: `pg_advisory_lock`, расписание из `SCHEDULE: list[Periodic]` (заглушка без задач)
- `control-plane/app/jobs/handlers/__init__.py` — реестр обработчиков; заглушка `noop`
- `control-plane/tests/e2e/test_jobs.py` — постановка и выборка задачи

### Интеграция компонентов

`enqueue` вызывается внутри транзакций доменных операций (outbox). `NOTIFY` выполняется после
коммита обёрткой `transaction()`.

Уточнения при реализации:

- `NOTIFY` не требует обёртки: `enqueue` вызывает `pg_notify('jobs_<queue>', id)` в той же
  транзакции, а PostgreSQL доставляет уведомления только при её коммите (откат — без
  уведомления; страж — `test_notify_only_on_commit`); `transaction()` из 001.10 не меняется;
- дубль ключа среди `pending`/`running` — `INSERT … ON CONFLICT (idempotency_key) WHERE status
  IN ('pending', 'running') DO NOTHING RETURNING id` → `DuplicateJobError`, без ошибки PostgreSQL:
  транзакция доменной операции остаётся живой и её можно продолжить (первый вариант с
  перехватом `UniqueViolationError` молча откатывал всю транзакцию — найдено пробой на стенде);
- `claim(conn, queue, worker_id, *, types=None)` — один `UPDATE … WHERE id = (SELECT … FOR
  UPDATE SKIP LOCKED LIMIT 1) RETURNING`: задача становится `running` за `locked_by` атомарно,
  `attempts` увеличивается при выборке (упавший исполнитель не теряет попытку — база для
  001.74), выбираются только `run_at <= now()` в порядке `run_at, id`; `types` (сверх контракта)
  ограничивает выборку типами, известными исполнителю (`HANDLERS`): `None` — любые, пустой набор —
  ничего (ревью раунда 2: раньше пустой набор означал «любые»); задачи новых типов ждут
  исполнителя нового выпуска, а не падают у старого — наше решение в духе expand/contract (§4.6
  модели данных, §17.2 постановки о порядке выпуска; про типы задач там прямо не сказано);
  `complete`/`fail`
  переводят только из `running` (иначе `LookupError`), снимают `locked_at`/`locked_by`; `fail`
  терминален (`failed`), `max_attempts` хранится (умолчание 3), повторы и `dead` — 001.74;
- `Job` — frozen dataclass строки; `payload` — `jsonb` (str ↔ dict);
- исполнитель: `run_once(pool, queue, worker_id)` — забирать и выполнять задачи известных типов
  до пустой очереди (для тестов «одной итерации»), `run(queue, stop=, pool=)` — главный цикл:
  отдельное подключение `LISTEN jobs_<queue>` (`application_name = worker:<очередь>:listener`),
  ожидание NOTIFY или страховочного опроса (1 с critical, 10 с background — §5.4), остановка по
  событию или SIGTERM/SIGINT; `worker_id` = `хост:pid:очередь`; исключение обработчика →
  `failed` с текстом (до 2000 символов); обработчик и запись статуса идут на разных
  подключениях из пула (подключение, испорченное обработчиком, не используется для
  завершения); переданный `pool` принадлежит вызывающему, общий пул процесса закрывается при
  выходе;
- живучесть исполнителя (ревью раунда 1: процесс умирал от `LookupError` при исчезнувшей
  строке и от `cache lookup failed for type` после пересоздания перечислений тестами схемы):
  ошибки базы и сети (`asyncpg.PostgresError`, `InterfaceError`, `OSError`, таймауты) в выборке
  журналируются, подключения пула обновляются `pool.expire_connections()` (устаревшие кэши
  типов и разорванные сессии уходят при возврате в пул), цикл продолжается после паузы 1 с;
  `LookupError` при завершении (строку удалили или перевели вручную) — предупреждение, не
  остановка; обрыв подключения LISTEN обнаруживается (`add_termination_listener` будит цикл,
  `is_closed()`), подключение восстанавливается с паузой 1 с (флаг пробуждения сбрасывается в
  начале витка, иначе взведённый обрывом флаг превращал паузу в холостую прокрутку — ревью
  раунда 2, 48 тысяч попыток за 2 с); транзиентные и постоянные ошибки базы (разрыв против
  отозванного права или опечатки в SQL) не различаются — журналируются каждую паузу, пока не
  исправят среду или код, счётчик подряд идущих отказов и метрика — 001.68; ошибки программы
  (KeyError и подобные) не глотаются — это дефект кода;
- герметичность тестов на живом стенде (там работают исполнители и планировщик): тесты
  регистрируют собственные типы `test-noop`/`test-boom`/`test-vanish` в `HANDLERS` своего
  процесса и ставят только их — живые исполнители такие задачи не выбирают; планировщик тестов
  берёт свой ключ лидерства; ключи `test-jobs:*` удаляются до и после;
- планировщик: `Periodic(name, interval, queue, type, payload)` (интервал > 0 и известная
  очередь проверяются при создании), слот = номер интервала от эпохи, ключ `<имя>:<слот>` —
  один экземпляр на слот при любом числе планировщиков (R-46); `tick(pool, now, schedule)`
  ставит все элементы слота, дубли пропускает; `run(stop=, schedule=, pool=, lock_key=)` ждёт
  лидерства `pg_try_advisory_lock(lock_key)` на отдельной сессии (`application_name =
  scheduler:leader`, повтор раз в 5 с), затем `tick` раз в секунду; ошибки базы в цикле
  журналируются с обновлением пула, цикл продолжается; блокировка снимается закрытием сессии;
  живость сессии-держателя не проверяется — при разрыве её сессии лидерство получит другой
  экземпляр, и короткое время могут работать два лидера: «один активный планировщик» §5.4
  обеспечивается ключом слота (один enqueue на слот), а не исключительностью процесса;
  `SCHEDULE` пуст;
- метрики: `app/metrics.py` — `/metrics` отдаёт `control_plane_up`, `control_plane_db_up` и
  `control_plane_jobs{queue,status}` по всем 10 парам (нули включены, ряды стабильны);
  недоступная база → `control_plane_db_up 0` без ошибки ответа и с обновлением подключений
  пула; пул создаётся лениво при первом запросе метрик (сборка приложения к базе по-прежнему не
  обращается); `count(*) … group by` по всей таблице `jobs` на каждый опрос Prometheus —
  таблицу ограничивает срок хранения `done` 7 суток (§4.5, задача 001.37); сводный индекс при
  необходимости — 001.68;
- `docker-entrypoint.sh`: перед `setpriv` задаётся `HOME=/app USER=app` — `setpriv` наследовал
  `HOME=/root`, и asyncpg, ища клиентский сертификат в `~/.postgresql/`, падал с
  `PermissionError` на закрытом `/root` (найдено при первом запуске ролей worker/scheduler на
  стенде; роль api до 001.11 к базе через asyncpg не обращалась);
- тесты очереди помечают свои задачи ключами `test-jobs:` и удаляют их до и после; тесты
  «одной итерации» и планировщика передают пул стенда явно.

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Задача проходит цикл
   - Входные данные: `enqueue(...)` с ключом `k1`; `worker` одной итерации
   - Ожидаемый результат: статус `done`; повторный `enqueue` с `k1` в статусе `pending` отклонён
   - Примечание: заглушка обработчика `noop` возвращает успех
2. **TC-E2E-02:** Две очереди независимы
   - Входные данные: задача в `background` и задача в `critical`
   - Ожидаемый результат: исполнитель `critical` не забирает задачу `background`

### Модульные тесты

1. **TC-UNIT-01:** Частичная уникальность ключа
   - Проверяемая функция: `app/jobs/queue.py::enqueue`
   - Входные данные: ключ существующей задачи в статусе `done`
   - Ожидаемый результат: новая задача создана
