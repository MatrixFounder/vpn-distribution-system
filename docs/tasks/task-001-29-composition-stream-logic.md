## Цель задачи

Реализовать дельту потока состава по `docs/architectures/interfaces.md` §5.2 и `data-model.md`
§4.2.3: выделение `updated_seq` через `UPDATE nodes … RETURNING`, исполнитель публикации
пользователя на строках `node_user_state`, вентиль по статусу на этих строках, продвижение
курсора и `resync_required`, расшифровку credentials только для ноды из identity. Постановка
публикации в транзакции бизнес-операции, состав ноды целиком, снятие доступа удалённого
пользователя и уплотнение — 001.29b; поток конфигурации и закрытый ключ REALITY — 001.29c;
ротация credentials и сброс курсоров при пересоздании — 001.29d. Полный снапшот и поколение —
001.75b; удержание long-poll — 001.75c; подтверждение курсоров и снятие `resync_required` —
001.75; команды — 001.76.

## Описание изменений

### Изменения в существующих файлах

#### Файл: `control-plane/tests/e2e/test_agent_api.py`

- дополнить: дельта; вентиль для каждого из восьми статусов на строках `node_user_state`

#### Файл: `control-plane/app/domain/composition.py`

- `next_users_seq(conn, node_id)`: `UPDATE nodes SET desired_users_seq = desired_users_seq + 1 … RETURNING` — единственный способ выделить `updated_seq`
- `publish_user(user_id)` (исполнитель задачи `composition.publish_user`): для каждой ноды из пересечения групп доступа — upsert `node_user_state` (состояние, `quota_grant_bytes`, `blocked_ips`) с `updated_seq` из `next_users_seq`; создание `node_user_credentials` при отсутствии; `NOTIFY` + `PUBLISH node:{id}` после коммита. До 001.29b принятые прямые вызовы `SubscriptionService` (001.22) после коммита исполняют ту же публикацию
- нода, где у пользователя есть строка не в `removed`, но тариф больше не разделяет с ней группу доступа: строка переводится в `removed`, запись `node_user_credentials` пары удаляется (`data-model.md` §4.2.3 «Состав строк»)
- одна транзакция на ноду, ноды — в порядке `node_id`: выделение номера, чтение состояния пользователя и запись строки — в ней (§4.2.3 «Выделение `updated_seq`»); состояние пользователя (подписка, группы тарифа, `users.status`) читается **после** `UPDATE nodes … RETURNING` — под блокировкой строки ноды, — иначе запуск, прочитавший состояние до чужого коммита, записал бы устаревшее состояние с большим номером (сценарий в примечаниях); задача завершается успехом, когда обработаны все ноды, сбой посередине повторяет её целиком
- `state_for` (дельта): вентиль по таблице §5.2 (`pending` 403; `provisioning` только конфигурация; `disabled`/`suspended` только отзывы) на строках `node_user_state` — правила вентиля берутся из `app/domain/statuses.py::STREAM_GATE`, сверенного с матрицей §4.6 построчно в `tests/unit/domain/test_statuses.py` (001.28); курсор продвигается до max `updated_seq` выборки **до** фильтра по статусу — иначе нода застревает всякий раз, когда самое свежее изменение вентиль скрыл (свойство заглушки 001.28, `state_for`); ответ дельты идёт с `users.full = false` — `true` только у снапшота, вентиль которого отдаёт состав целиком (001.75b): это разрешение ноде удалять отсутствующих (§4.2.3); расшифровка credentials только для `node_id` из identity
- `resync_required`: при выдаче отфильтрованного ответа взводится колонка `nodes.resync_required`, в ответ идёт значение колонки, а не признак, выведенный из статуса (§5.2 требует показать его **при выходе** из фильтрующего статуса; заглушка 001.28 отдаёт `node.resync_required or gate.filters_composition`); снятие — 001.75

#### Файл: `control-plane/app/jobs/handlers/composition.py`

- обработчик `composition.publish_user` (вместо заглушки, завершающей задачу успехом) в очереди `critical`

Добавлена зависимость от 001.25 (найдено при 001.28): критерий приёмки «credentials
расшифровываются только для ноды из identity» невыполним, пока `current_node` — заглушка,
отдающая фиксированную карточку. Без этого ребра настоящие credentials поехали бы поверх
аутентификации, принимающей любой токен нужной формы, а отзыв identity (Н-31) не применялся бы
нигде.

Пункты «Найдено при 001.28 (заглушки)» разобраны 2026-11-04 по правилу 1 «Цикла задачи»:
вентиль (`STREAM_GATE`, сверен с §4.6 в 001.28), курсор по выборке до фильтра и `users.full =
false` у урезанного ответа решены принятым кодом 001.28 и `data-model.md` §4.2.3 и внесены в
«Описание изменений» и тесты TC-E2E-03; выбора поведения среди них нет.

Общий сценарий публикации (правило 1): пользователь U, тариф с группами G1 и G2; нода N1 в G1
(`desired_users_seq` 41), N2 в G2 (7), N3 в G3 — у U строка `active` от прежнего тарифа
(`updated_seq` 15, `desired_users_seq` 20).

- Прогон: N1 → номер 42, строка `active`, credentials версии 1; N2 → 8; N3 → 21, строка
  `removed`, запись credentials пары удалена; после коммита каждой ноды — `PUBLISH node:{id}`.
- Отказ: сбой после коммита N1, до N2. Повтор задачи: N1 → 43 (та же строка; нода с курсором 42
  получит её ещё раз — применение идемпотентно), N2 → 8, N3 → 21. Потерь нет: задача завершена,
  только когда обработаны все ноды.
- Повтор: вторая задача по U из другой бизнес-операции, пока идёт первая. Номера одной ноды
  выдаются под блокировкой её строки, коммиты по ноде упорядочены; последней коммитится запись
  запуска, прочитавшего состояние под блокировкой, то есть самое свежее. Если бы состояние
  читалось до `UPDATE nodes … RETURNING`, запуск A мог бы прочитать состояние до коммита
  перехода T2, ждать блокировку, пока запуск B (поставленный T2) пишет новое состояние с
  номером 42, и затем записать старое с номером 43 — у ноды остался бы доступ, который T2 снял.
- Деление: транзакция на ноду, ноды — по `node_id`: две публикации с пересекающимися наборами
  нод не блокируют друг друга взаимно, и приём отчёта ноды ждёт не дольше записи одной ноды.
- Поздняя часть: задача, повторённая через часы, читает состояние на момент своего запуска и
  публикует его — устаревшее состояние она не переносит.
