Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Цель задачи

Реализовать дельту потока состава по `docs/architectures/interfaces.md` §5.2 и `data-model.md`
§4.2.3: выделение `updated_seq` через `UPDATE nodes … RETURNING`, исполнитель публикации
пользователя на строках `node_user_state`, вентиль по статусу на этих строках, продвижение
курсора и `resync_required`, расшифровку credentials только для ноды из identity. Постановка
публикации в транзакции бизнес-операции, состав ноды целиком, снятие доступа удалённого
пользователя и уплотнение — 001.29b; поток конфигурации и закрытый ключ REALITY — 001.29c;
ротация credentials и сброс курсоров при пересоздании — 001.29d. Полный снапшот и поколение —
001.75b; удержание long-poll — 001.75c; подтверждение курсоров и снятие `resync_required` —
001.75; команды — 001.76.

- публикации одного пользователя идут по очереди — сессионная advisory-блокировка по `user_id` до выбора нод-кандидатов (раунд 1 роаста, H-1); пробуждения — после коммита всех нод

- `resync_required`: при выдаче отфильтрованного ответа взводится колонка `nodes.resync_required`, в ответ идёт значение колонки, а не признак, выведенный из статуса (§5.2 требует показать его **при выходе** из фильтрующего статуса; заглушка 001.28 отдаёт `node.resync_required or gate.filters_composition`); снятие — 001.75

## Примечания

`tdd-strict`: контракт `/agent/v1` — ядро системы.

Задача разделена 2026-11-04 по правилу 4 «Цикла задачи» (решение заказчика В-47 а): постановка
публикации в транзакции, `publish_node`, `remove_user` и уплотнение — 001.29b; поток
конфигурации, закрытый ключ REALITY и версия раздела `agent` — 001.29c (решение заказчика о
ключе 2026-11-04 — там же); ротация credentials и сброс курсоров при пересоздании — 001.29d.

Добавлена зависимость от 001.25 (найдено при 001.28): критерий приёмки «credentials
расшифровываются только для ноды из identity» невыполним, пока `current_node` — заглушка,
отдающая фиксированную карточку. Без этого ребра настоящие credentials поехали бы поверх
аутентификации, принимающей любой токен нужной формы, а отзыв identity (Н-31) не применялся бы
нигде.

Решения сборщика 2026-11-04 (технические, поведения не меняют):

- снапшот (`full=1`) читает те же строки базы — все, кроме `removed`; урезанный вентилем — дельтой
  от нуля с `removed` (правило заглушки 001.28; «от нуля» — раунд 1 роаста): иначе полный ответ нёс бы фиксированных
  пользователей заглушки поверх настоящей дельты. Поколение, контрольная сумма состава и 409
  остаются 001.75b;
- курсор ноды (`desired_users_seq`), её `resync_required` и строки читаются в одном снимке базы
  (`repeatable read`): строка, закоммиченная между чтениями, не попадёт в ответ без курсора,
  который её покрывает;
- `NOTIFY` не вводится: удержание long-poll ждёт канал Redis `node:{id}` (§5.2 «Long-poll»),
  подписчика на `NOTIFY` нет; потеря сообщения стоит до 30 с таймаута удержания (раскладка Н-13,
  `interfaces.md` §5.4), поэтому сбой `PUBLISH` пишется в журнал и публикацию не валит;
- размер гранта `quota_grant_bytes` публикация не трогает — его пишет служба грантов (001.36);
  новая строка получает значение столбца по умолчанию;
- номер изменения выделяется, только когда строка пишется: сначала блокировка строки ноды
  (`SELECT … FOR NO KEY UPDATE`), затем `UPDATE nodes … RETURNING` — пустой номер оставил бы дыру в
  курсоре ноды;
- полезная нагрузка задачи `composition.publish_user` — `{"user_id": …}`;
- фиксированные строки заглушки (`stub_rows`, `stub_credentials`, `STUB_USERS_SEQ`) ушли из боевого
  модуля в тесты — раскладка фикстур контракта (`tests/_agent.py`); герметичные прогоны подставляют
  её службе состава, а живая служба на той же раскладке строками базы отвечает записанными
  фикстурами (`tests/e2e/test_composition.py`).

Решения по роасту, раунд 1 (2026-11-04, технические):

- публикации одного пользователя сериализованы advisory-блокировкой сессии (пространство
  `PUBLISH_LOCK_CLASS`, ключ — хеш `user_id`): иначе запуск после смены тарифа выбирал кандидатов,
  не видя незакоммиченной строки предыдущего запуска на ноде прежнего тарифа, и доступ там
  оставался; режим блокировки строки ноды — `FOR NO KEY UPDATE`, как у `UPDATE nodes` и приёма
  отчёта (страж — TC-E2E-06 с держателем-публикатором и тест двух публикаций на одной ноде);
- пробуждения отправляются после коммита всех нод; первый отказ Redis прекращает остальные
  пробуждения (в журнал): недоступный Redis задерживает пробуждения, а не запись строк;
- взведённый `resync_required` — повод ответить только вне фильтрующего статуса: в самом статусе
  снять его нечем, и нода без 204 не дожидалась бы удержания;
- урезанный вентилем «снапшот» читает строки от нуля: снапшот присланный курсор игнорирует
  (README контракта), нода просит его, когда курсору нельзя верить;
- строка `removed` — без заблокированных адресов; негодная полезная нагрузка задачи —
  `NonRetryableError` (задача сразу `failed`);
- статус ноды для вентиля берётся из `current_node` того же запроса; перечитать его после
  удержания long-poll — 001.75c (записано там).

Решения по роасту, раунд 2 (2026-11-04, технические):

- взведённый `resync_required` — повод ответить только там, где вентиль отдаёт состав целиком
  (`composition == "all"`): в `provisioning` состав закрыт, и признак, оставшийся с прежней
  жизни ноды (повторная регистрация, снятие ручного статуса до первой активации, 001.30b), там
  тоже нечем снять — нода не получала бы 204;
- исполнитель отказывает (`RuntimeError`) подключению, уже открывшему транзакцию: внутри неё
  транзакции нод стали бы точками сохранения, а блокировка пользователя снялась бы до внешнего
  коммита (вызовы с `conn` вызывающего вводит 001.29b — поставить задачу, а не исполнять);
- полезная нагрузка задачи не объект (массив, строка, число) — тот же `NonRetryableError`.

Пункты «Найдено при 001.28 (заглушки)» разобраны 2026-11-04 по правилу 1 «Цикла задачи»:
вентиль (`STREAM_GATE`, сверен с §4.6 в 001.28), курсор по выборке до фильтра и `users.full =
false` у урезанного ответа решены принятым кодом 001.28 и `data-model.md` §4.2.3 и внесены в
«Описание изменений» и тесты TC-E2E-03; выбора поведения среди них нет.

Общий сценарий публикации (правило 1): пользователь U, тариф с группами G1 и G2; нода N1 в G1
(`desired_users_seq` 41), N2 в G2 (7), N3 в G3 — у U строка `active` от прежнего тарифа
(`updated_seq` 15, `desired_users_seq` 20).

- Прогон: N1 → номер 42, строка `active`, credentials версии 1; N2 → 8; N3 → 21, строка
  `removed`, запись credentials пары удалена; после коммита всех нод — `PUBLISH node:{id}`.
- Отказ: сбой после коммита N1, до N2. Повтор задачи: N1 → 43 (та же строка; нода с курсором 42
  получит её ещё раз — применение идемпотентно), N2 → 8, N3 → 21. Потерь нет: задача завершена,
  только когда обработаны все ноды.
- Повтор: вторая задача по U из другой бизнес-операции, пока идёт первая. Публикации одного
  пользователя идут по очереди (advisory-блокировка по `user_id`, раунд 1 роаста): запуск B
  ждёт конца запуска A и выбирает кандидатов уже по закоммиченным строкам A — иначе B, выбрав
  кандидатов до коммита A на ноде прежнего тарифа, не снял бы там доступ. Для двух публикаций
  одного пользователя этого достаточно. Чтение состояния под блокировкой строки ноды нужно
  против писателей строк пользователя, которые блокировку пользователя не берут (состав ноды
  целиком — 001.29b, ротация credentials — 001.29d): если бы состояние читалось до блокировки
  ноды, запуск мог бы прочитать его до коммита перехода T2, ждать блокировку, пока такой
  писатель пишет новое состояние, и записать старое с большим номером — у ноды остался бы
  доступ, который T2 снял.
- Деление: транзакция на ноду, ноды — по `node_id`: две публикации с пересекающимися наборами
  нод не блокируют друг друга взаимно, и приём отчёта ноды ждёт не дольше записи одной ноды.
- Поздняя часть: задача, повторённая через часы, читает состояние на момент своего запуска и
  публикует его — устаревшее состояние она не переносит.
