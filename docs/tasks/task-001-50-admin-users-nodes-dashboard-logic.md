# Задача 001.50: API панели: пользователи, карточка с данными поддержки, действия

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-13 Поддержка пользователя
- UC-09 Управление тарифами, группами и кодами
- UC-02 Регистрация и активация подписки Redeem-кодом

Требования RTM: R-09, R-34, R-38.

<!-- contract:goal -->

## Цель задачи

Реализовать поиск и действия над пользователями, карточку пользователя с данными поддержки,
корректировку баланса в обе стороны, включая уменьшение с причиной (ей же выполняется разбор
удержанных отчётов, В-4), блокировку одним действием (В-40), ручное подтверждение адреса (В-32) и
данные расширенной карточки режима от лица пользователя (В-36); решения заказчика 2026-10-25.

### Изменения в существующих файлах

- реальные утверждения вместо заглушек 001.49; UC-13 A2 корректировка с причиной

#### Файл: `control-plane/app/api/admin/users.py`

- поиск по адресу и идентификатору; действия через `SubscriptionService`, `CompositionService.rotate_user_credentials`; карточка из `subscription_access_log`, последнего подключения, `traffic_hourly` и причины отзыва; корректировка баланса с причиной
- последнее подключение к ноде — `max(user_online_ips.last_seen)` по ноде, при отсутствии строки — последний `hour_start` в `traffic_hourly` с ненулевым raw; `node_user_state.updated_at` — время изменения строки состава, а не подключения
- причина отзыва — `subscriptions.state_reason`
- пометка недоставляемого адреса — `users.email_undeliverable_at` (колонка — 001.51, ставит и
  снимает 001.78; решение заказчика 2026-10-25, В-37)
- `POST …/traffic` с отрицательным значением вызывает `SubscriptionService.deduct_traffic`
- разбор удержанного отчёта ноды (`held_anomaly`, части `capped`) отдельного действия не имеет:
  оператор снимает с ноды `Suspended` (ручной статус: перевод по повторным удержаниям — 001.30c,
  снятие — 001.30b) и корректирует баланс пользователей
  ноды в обе стороны — начислением и уменьшением этой задачи. Часть сверх потолка канала и части
  `capped` не списываются; изменить списание по итогам разбора можно только корректировкой (решение
  заказчика 2026-10-25, В-4)
- назначение тарифа и продление администратором вызывают `emit(subscription_activated, user_id)` (001.51) с ключом `subscription_activated:{user_id}:{period_id}`; для подписки в `suspended_admin` событие не порождается
- продление администратором подписки в `suspended_admin` продлевает период, состояние не меняет:
  блокировку снимает только разблокировка (решение заказчика 2026-10-25, В-24); правку `renew`
  (отступление от 001.22) вносит 001.20 — зависимость от 001.20
- `POST …/traffic` с положительным значением и `POST …/renew` вызывают `ApprovalService.submit`
  (001.48): сверх включённого порога `approval.traffic_bytes` или `approval.renew_days` ответ —
  202 `approval_required` с идентификатором запроса, операция выполняется при подтверждении
  другой учётной записью; при выключенном пороге (по умолчанию) — сразу (решение заказчика
  2026-10-25, В-34)
- блокировка `POST …/block` — одно действие с обязательной причиной (`reason`; без неё — 422
  `reason_required`; решение заказчика 2026-10-25, В-40): в одной транзакции
  `users.status = 'blocked'` и состояние подписки `suspended_admin` с причиной в `state_reason`; в
  той же транзакции — задача `composition.publish_user` (outbox §5.4, обработчик 001.29: доступ
  снимается на нодах в срок Н-14); после коммита — `SessionStore.revoke_all(user_id)`. Вход и
  кабинет закрыты; причину пользователь видит в заголовке `announce` и на странице подписки
  (эндпоинт отвечает `blocked`, §5.6). Без подписки меняется только статус учётной записи
- разблокировка `POST …/unblock`: `users.status = 'active'`; состояние подписки — по фактам на
  момент разблокировки: период истёк — `expired`, остаток исчерпан — `suspended_quota`, иначе
  `active`; публикация состава
- ручное подтверждение адреса `POST …/verify-email` (Support и выше; решение заказчика
  2026-10-25, В-32): ставит `users.email_verified_at = now()` и вызывает `audit.record` с прежним и
  новым значением; адрес уже подтверждён — 409 `email_already_verified`. Повторную отправку
  письма подтверждения пользователем реализует 001.16
- `GET …/impersonate` — данные расширенной карточки режима от лица пользователя (начало и
  завершение режима — 001.48; решение заказчика 2026-10-25, В-36): то, что пользователь видит в
  кабинете (`/me`: профиль, состояние подписки с причиной, лимит и остаток, статистика по
  периодам, нодам и странам, данные мастера подключения), собранное службами 001.16. Ссылок
  подписки ответ не содержит: их просмотр — отдельное разрешение `users.view_subscription_url` с
  записью в журнал (001.48). Режим для этого пользователя не начат — 409 `impersonation_not_active`
- действия над пользователем с `users.status = 'deleted'`
  (`POST …/block|unblock|plan|renew|traffic|reset-credentials|verify-email`) отвечают 409
  `user_deleted` до вызова сервисов и ничего не меняют (правило передано из 001.17):
  `SubscriptionService` статус пользователя не проверяет, а `block` и `unblock` иначе
  перезаписали бы `deleted`; поиск и
  карточка — чтение, правило их не касается; `GET …/subscription-url` для удалённого отвечает
  тем же 409 `user_deleted` по 001.48

#### Файл: `control-plane/app/domain/subscriptions.py` — изменение принятого кода (отступление от 001.22)

- `set_state` сохраняет `reason` в `subscriptions.state_reason`; принимает необязательное
  подключение вызывающего, чтобы блокировка меняла `users.status` и состояние подписки в одной
  транзакции; с подключением вызывающего задача `composition.publish_user` ставится на этом
  подключении в той же транзакции (001.29), а не после коммита
- `deduct_traffic(user_id, bytes, actor, reason)` — уменьшение баланса: положительная дельта `adjustment` в `balance_entries` с обязательной причиной (`reason_required`); исчерпание остатка переводит подписку в `suspended_quota` и публикует состав (`publish_user`); подписка в `suspended_admin` состояние сохраняет

### Интеграция компонентов

Все действия проходят `require_permission` и `audit.record`. Событие `subscription_activated`
ставится через `emit` 001.51 — зависимость от 001.51. Данные расширенной карточки собирают службы
`/me` задачи 001.16 — зависимость от 001.16. Сохранение `suspended_admin` при продлении — правка
`renew` в 001.20 — зависимость от 001.20.

Передано из 001.84/001.14 (Н-27, пользовательская половина): блокировка учётной записи
(`users.status = 'blocked'` вместе с `suspended_admin`, В-40) в той же операции вызывает
`SessionStore.revoke_all(user_id)` — сессии кабинета недействительны немедленно (постановка
допускает ≤ 60 с); проверка статуса в `current_user` (001.16, В-40) закрывает запросы между
фиксацией блокировки и отзывом, а отзыв удаляет сами сессии, иначе они жили бы до истечения TTL
бездействия. Вход заблокированного уже закрыт (`authenticate` требует `status = 'active'`). Тест:
заблокировать пользователя с двумя живыми сессиями → `GET /api/v1/me` обеими → 401.

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Карточка содержит данные поддержки
   - Входные данные: три пользователя — без обращений к подписке; с обращениями без
     подключений; с подключением к ноде
   - Ожидаемый результат: поля §17.5 заполнены; по карточке различаются три состояния §14
     «Рабочее место поддержки» (AC-27)
2. **TC-E2E-02:** Уменьшение баланса без причины
   - Входные данные: `POST …/traffic` с отрицательным значением без `reason`
   - Ожидаемый результат: 422 с кодом `reason_required`
3. **TC-E2E-03:** Уменьшение баланса с причиной
   - Входные данные: `POST …/traffic` с отрицательным значением и `reason`, больше остатка
   - Ожидаемый результат: строка `balance_entries` (`adjustment`, положительная дельта,
     причина) и запись журнала; подписка в `suspended_quota`
4. **TC-E2E-04:** Причина отзыва
   - Входные данные: подписка переведена в `suspended_admin` с причиной
   - Ожидаемый результат: карточка показывает состояние и причину из `state_reason`
5. **TC-E2E-05:** Второе подтверждение
   - Входные данные: начисление трафика и продление подписки при выключенных порогах; те же
     операции сверх включённых порогов `approval.traffic_bytes` и `approval.renew_days`
   - Ожидаемый результат: при выключенных — выполнены сразу; при включённых — 202
     `approval_required`, баланс и период не изменены до подтверждения другой учётной записью
     (R-35, idea §5.11)
6. **TC-E2E-06:** Событие активации
   - Входные данные: назначение тарифа администратором
   - Ожидаемый результат: строка `events` типа `subscription_activated`
7. **TC-E2E-07:** Действия над удалённым пользователем
   - Входные данные: пользователь с подпиской, строками `node_user_state` и
     `users.status = 'deleted'` (фикстура записывает статус в базу; `delete_account` 001.17 в
     зависимостях задачи нет); `POST …/block`, `…/unblock`, `…/plan`, `…/renew`, `…/traffic`,
     `…/reset-credentials`
   - Ожидаемый результат: каждый запрос — 409 `user_deleted`; `users.status` остаётся `deleted`;
     строк `subscription_periods` и `balance_entries` не прибавилось; строки `node_user_state`
     пользователя не изменились
8. **TC-E2E-08:** Блокировка и разблокировка
   - Входные данные: пользователь с активной подпиской и двумя живыми сессиями; `POST …/block` без
     `reason`; с `reason`; продление администратором; `POST …/unblock`
   - Ожидаемый результат: без причины — 422 `reason_required`; с причиной — `users.status =
     'blocked'`, подписка `suspended_admin`, `state_reason` — причина, задача
     `composition.publish_user` стоит в `jobs` в транзакции блокировки,
     `GET /api/v1/me` обеими сессиями — 401; продление — период продлён, состояние
     `suspended_admin`; разблокировка — `users.status = 'active'`, подписка `active`
9. **TC-E2E-09:** Ручное подтверждение адреса
   - Входные данные: пользователь с неподтверждённым адресом; `POST …/verify-email` дважды; вход
     пользователя паролем
   - Ожидаемый результат: первый — `email_verified_at` заполнен, строка журнала; второй — 409
     `email_already_verified`; вход успешен
10. **TC-E2E-10:** Расширенная карточка
    - Входные данные: `GET …/impersonate` до начала режима; после `POST …/impersonate`
    - Ожидаемый результат: до начала — 409 `impersonation_not_active`; после — данные `/me`
      пользователя без ссылок подписки
