# Задача 001.66c: Отказ отозванному сертификату на прокси

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-12 Компрометация ноды
- UC-01 Ввод ноды в эксплуатацию

Требования RTM: R-44, R-02.

<!-- contract:goal -->

## Цель задачи

Отказывать на прокси листу отозванной identity (Н-31) до пределов прокси. Сегодня отзыв действует
только в C-01 (001.25): держатель отозванного листа получает 401, но до ответа занимает пределы
своего сертификата (слот отчётов парка, частоту по сертификату) до конца срока листа — 90 дней
(остаточный риск security.md §7.3). Способ — техническое решение OPS-07
(`docs/reviews/wi-35-spec-review.md`): карта отказа по `$ssl_client_serial` из
`node_identities.cert_serial`, без CRL (у CRL — «бомба» `nextUpdate` и отказ всем при негодном
файле, примечания); на агентском `server` возобновление TLS-сессий выключено.

## Примечания

`tdd-strict`: отзыв identity — граница безопасности (enrollment и identity).

Stub-First: заглушки модуля `control-plane/app/jobs/handlers/identity.py` нет ни в одной задаче
плана. Первый шаг этой задачи — заглушка (сигнатуры `render_revoked_map` и обработчика
`export_revoked_serials` с `NotImplementedError`, тип в `HANDLERS`) и красные TC-UNIT-01,
TC-UNIT-02; реализация — следующим шагом.

Найдено при 001.25 (enrollment и identity), решить здесь:

- **отказ отозванному сертификату на прокси (`ssl_crl`) отложен сюда.** 001.25 держит отзыв в
  C-01: identity сверяется с базой на каждом запросе, и отозванной следующий же запрос — 401
  (Н-31 выполняется синхронно). Прокси при этом отозванный лист принимает и до ответа отдаёт
  его держателю свои пределы (слот отчётов парка, частоту по сертификату) — остаточный риск
  §7.3. Ограничения конструкции, выясненные в 001.25: (1) nginx читает `ssl_crl` при загрузке
  конфигурации — файл CRL обязан существовать и быть подписан тем же CA ещё до старта, иначе
  OpenSSL отвергает **всех** клиентов (`unable to get certificate CRL`), а истёкший `nextUpdate`
  отвергает всех так же — нужен дальний `nextUpdate` либо пересподписание по расписанию; (2)
  смена файла требует перечитывания nginx, а одиночный файл в bind mount rsync подменяет
  переименованием (inode, `skills/vm-deploy`) — монтировать каталог; (3) перечитывание не
  разрывает уже установленные соединения отозванного сертификата — нужен
  `worker_shutdown_timeout`; (4) CRL перечисляет серийные номера — `node_identities.cert_serial`
  хранит их с 001.25 (миграция 130, форма `$ssl_client_serial`; колонку не добавлять) — или карта отказа по `$ssl_client_serial` из
  файла — те же перечитывания без бомбы `nextUpdate`). Карта — только по серийному номеру, не по
  `$ssl_client_fingerprint`: у отозванного листа есть близнец с подписью `(r, n − s)` — другой
  отпечаток при том же номере (податливость ECDSA, `tests/_pki.py::signature_twin`, роаст
  001.25), и карта по отпечатку его пропустила бы; пределы прокси по той же причине ключуются
  номером с 001.25. Без отказа на прокси окно отозванного листа — до конца его срока (90 дней).
  И главное: `ssl_crl` закрывает риск только для **отозванных** сертификатов; медленная заливка
  держателем действующего остаётся, её лечение — предел всей заливки (001.72).

Найдено при 001.25, раунд 4 (решить здесь):

- возобновление TLS-сессии (`ssl_session_timeout 1d`, общий `ssl_session_cache`): OpenSSL не
  проверяет клиентский сертификат при возобновлении — истёкший лист проходит 8443 до суток после
  срока (C-01 отвечает 401, но пределы прокси он держит), а после `ssl_crl` отозванный лист,
  возобновивший сессию до отзыва, обходит CRL до суток (карта отказа по серийному номеру на
  каждый запрос от этого не зависит). Решить здесь: на агентском server — короткий срок сессии
  или отказ от возобновления (`ssl_session_cache off`; билеты уже выключены —
  `ssl_session_tickets off` на уровне http) вместе с `ssl_crl`, либо карта отказа по номеру
  (роаст 001.25, раунд 4). Решение OPS-07 — карта и `ssl_session_cache off` (в «Описании
  изменений»).

Найдено при 001.25, раунд 5 (решить здесь):

- **исключение из «номер каждого листа хранится»:** `dev/dev-node.crt` стенда
  (`deploy/scripts/dev-secrets.sh`) выпущен тем же CA мимо обмена — строки identity у него нет,
  и карта отказа по `cert_serial` его не найдёт; в промышленном контуре CA ничего мимо обмена не
  подписывает (клиентский тестовый сертификат — только стенду).
