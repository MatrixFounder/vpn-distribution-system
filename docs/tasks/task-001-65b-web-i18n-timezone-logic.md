# Задача 001.65b: Web-локализация и часовой пояс в интерфейсах

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-16 Работа в личном кабинете
- UC-13 Поддержка пользователя

Требования RTM: R-51, R-52.

<!-- contract:goal -->

## Цель задачи

Реализовать в web-приложениях отображение времени в поясе профиля и добавление третьего языка
интерфейса только файлом пакета `i18n`; проверить полноту ключей web-файлов и совпадение наборов
языков сервера и web. Серверная локализация — 001.65 (дробление по В-47, решение заказчика
2026-10-25).

<!-- contract:changes -->

## Описание изменений

### Новые файлы

- `web/packages/i18n/completeness.test.ts` — тест web-локализации: набор языков `locales/` сервера
  (001.65) и `web/packages/i18n/` совпадает; в каждом web-файле — те же ключи, что в web-файле
  `en.json`. Полноту ключей серверных файлов этот тест не проверяет: это тест 001.65
  (TC-UNIT-02 001.65)

### Изменения в существующих файлах

#### Файл: `web/packages/i18n/` (создаёт 001.62)

- набор языков интерфейса — из списка файлов пакета, а не константа: `de.json` добавляется без
  изменения кода (следует из TC-E2E-01 и AC-22); выбор языка `pickLanguage` — правило 001.62 и
  001.65
- `formatDateTime(utc, timeZone, lang)` — значение времени из ответа API (ISO 8601 UTC, 001.65) в
  поясе профиля и формате языка; кабинет берёт пояс из ответа `/me` (поле пояса профиля, 001.65)

#### Файлы: `web/apps/cabinet/src/`, `web/apps/admin/src/` (каркасы 001.62)

- язык и пояс передаются экранам через пакет `i18n`; экраны кабинета (001.63) и панели (001.64)
  выводят время только через `formatDateTime`; пояс панели — по ответу на вопрос «решить здесь»
  ниже

### Интеграция компонентов

Полнота ключей серверных файлов `locales/` — тест 001.65; полнота ключей web-пакета `i18n`
(001.62) и совпадение наборов языков сервера и web — тест этой задачи; ключи серверных файлов
он не сравнивает. Правило выбора языка без профиля — одно на обеих сторонах
(001.65).

Экраны 001.63 и 001.64 выводят время через `formatDateTime` этой задачи. Поэтому 001.63 и 001.64
зависят от 001.65b.

## Тестовые случаи

### Сквозные тесты

1. **TC-E2E-01:** Третий язык в интерфейсе
   - Входные данные: в `web/packages/i18n/` добавлен `de.json` без изменения кода (фикстура
     теста); профиль `de`
   - Ожидаемый результат: `pickLanguage` → `de`; маршруты кабинета 001.62 отрисованы строками
     `de.json`; интерфейс на немецком при профиле `de`

### Модульные тесты

1. **TC-UNIT-01:** Время в поясе профиля
   - Проверяемая функция: `packages/i18n::formatDateTime`
   - Входные данные: `2026-10-25T21:30:00Z`; пояс `Asia/Tokyo`, язык `ru`; пояс `UTC`, язык `en`
   - Ожидаемый результат: 26 октября 2026, 06:30 (Токио, UTC+9) в формате `ru`; 25 октября 2026,
     21:30 (UTC) в формате `en`
2. **TC-UNIT-02:** Полнота web-ключей и совпадение наборов языков
   - Проверяемая функция: `packages/i18n/completeness.test.ts`
   - Входные данные: файлы репозитория; фикстура с `de.json` только в `locales/` сервера; фикстура
     с web-файлом без ключа
   - Ожидаемый результат: на файлах репозитория тест проходит; на фикстурах — падает с именем
     языка или ключа

### Регрессионные тесты

- Команда: `cd web && npm run test -- packages/i18n`
- Полный набор: `make test` — существующие тесты проходят.

## Примечания

Ограничения и допущения — `docs/idea.md` §9; архитектура — `docs/ARCHITECTURE.md`.

Найдено при дроблении 001.65 (В-47), решить здесь:

- **Пояс отображения в панели.** Пояс хранится в профиле пользователя (`users.timezone`, R-52); у
  `admin_users` поля пояса нет (data-model §4.2.1), а язык панели выбирается независимо (idea
  §17.8). Варианты: а) панель показывает время в UTC с пометкой «UTC» — как сутки агрегатов и
  журнал; б) пояс браузера администратора с указанием смещения; в) поле пояса в профиле
  администратора (`admin_users.timezone`, своя миграция; свой профиль — 001.89). Рекомендация: а —
  без изменения схемы; время в панели совпадает с журналом и алертами. Ответ — вопрос заказчику до
  начала задачи.
