# Задача 001.38: Лимит уникальных адресов: подсчёт, `blocked_ips`, вытеснение

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-08 Ограничение числа адресов и перепродажа доступа

Требования RTM: R-27.

<!-- contract:goal -->

## Цель задачи

Реализовать `DeviceLimitService` по `docs/idea.md` §4.13: подсчёт уникальных адресов за окно
`settings.device_window` (по умолчанию 1 ч; ОВ-23 закрыт решением заказчика 2026-10-25, В-8),
сохранение свежих в пределах `device_limit`, список `blocked_ips` в потоке состава,
автоматическое снятие при вытеснении.

### Изменения в существующих файлах

#### Файл: `control-plane/app/accounting/device_limit.py`

- `class DeviceLimitService`: `evaluate(conn, node_id, user_ids) -> Blocked` (отклонение от `evaluate(user_id)`, 001.33) — один вызов на отчёт в транзакции приёма (001.77c): окно `settings.device_window` читается вместе со строками `user_online_ips`, которые этот же отчёт записал и ещё не закоммитил
- `evaluate` пишет `user_blocked_ips` и возвращает `Blocked` только по пользователям, у которых изменился набор блокируемых адресов (уточнение докстринга заглушки 001.33, сигнатура прежняя); по каждому из них приём в той же транзакции ставит задачу `composition.publish_user` (очередь `critical`, outbox §5.4, бюджет Н-13 как у отзыва). Прямой вызов `CompositionService.publish_user` из транзакции приёма запрещён: публикация обновляет строку ноды, которую приём держит до фиксации, — взаимоблокировка на уровне приложения
- окно читает только `user_online_ips`: адреса удержанных и `capped` частей 001.77 пишет в `held_online_ips`, в окно они не входят и позже не вводятся: действия разбора удержанного отчёта нет (решение заказчика 2026-10-25, В-4); `held_online_ips` хранится 90 суток (В-49, удаление — 001.37)
- вход — адреса и `last_seen` недоверенной ноды (§11.3; security.md §7.3, угроза «Ложные адреса в отчёте»): потолок различных адресов на пару «пользователь × нода» за окно; при отборе — предпочтение адресам, подтверждённым строкой трафика того же интервала; алерт на кардинальность адресов ноды — ряд `/metrics` этой задачи `control_plane_node_address_cardinality{node_id}` (раздел `app/metrics.py` ниже), правило Prometheus по нему — 001.68
- `last_seen` не позже `period_end` интервала (у частей интервала границы общие, README контракта; допуск часов 5 с) и не позже времени приёма, иначе приводится к `period_end`: адрес с меткой в будущем не остаётся «самым свежим» навсегда
- функция подсчёта активных адресов пользователя — различные адреса по всем нодам за окно `device_window`, без удержанных; её вызывает кабинет (001.16), чтобы число в кабинете совпадало с решением о блокировке

#### Файл: `control-plane/app/accounting/service.py`

- изменение кода задачи-зависимости 001.77c: в транзакции приёма после вызова `evaluate` — задача `composition.publish_user` по каждому пользователю из `Blocked` (`jobs.enqueue(conn, 'critical', …)`, ключ `publish_user:{user_id}:{xid}`, обработчик — 001.29); 001.77c только вызывает `evaluate`

#### Файл: `control-plane/app/metrics.py`

- ряд `control_plane_node_address_cardinality{node_id}` для правила алерта «кардинальность адресов ноды» (001.68; имя ряда правило берёт отсюда): наибольшее число различных адресов на пару «пользователь × нода» за окно `device_window` по `user_online_ips`, запросом к базе при опросе, по образцу `control_plane_report_intervals` (001.34); строки `user_online_ips` пишет приём (001.77) для всех адресов принятых частей, потолок отсекает адреса при отборе в `evaluate`, поэтому ряд видит адреса сверх потолка

#### Файл: `control-plane/app/domain/composition.py`

- `blocked_ips[]` из `user_blocked_ips` в строке состояния для всех нод пользователя

## Примечания

Ограничения и допущения — `docs/idea.md` §9; архитектура — `docs/ARCHITECTURE.md`.

Найдено при 001.33 (заглушки), решить здесь:

- отчёт несёт все наблюдаемые адреса пользователя (превышение лимита обнаруживается только по
  адресам сверх него); предел адресов одной части — 2 500, при большем числе нода делит адреса
  по частям интервала, и адреса одного пользователя могут лежать в разных частях (README
  контракта) — окно обязано собираться из нескольких частей; пара сравнивается вместе с
  семейством адреса (`192.0.2.1` и `::192.0.2.1` — разные, как у `inet`);
- `Device limit` тарифа не ограничен сверху ни в схеме, ни в `PlanIn` — верхнюю границу
  задать здесь, если правило подсчёта от неё зависит;
- вход лимита устройств (адреса и `last_seen` недоверенной ноды) защищён правилами «Описания
  изменений»; здесь решить значение потолка различных адресов на пару «пользователь × нода» за
  окно (константа или настройка);
- `DeviceLimitService(pool)` объявлен постановкой с пулом, а единственный вызывающий —
  транзакция приёма — передаёт `conn`: у `LimitsService` в 001.35 выбран пул процесса
  (`get_pool()`) при старте; здесь — пул процесса при старте или `pool=None`; сигнатуру
  `evaluate(conn, node_id, user_ids)` не менять.
