# Задача 001.87: Изменение и вывод ноды

Тип задачи: `[LOGIC IMPLEMENTATION]`.

## Связь со сценариями
- UC-07 Отказ и возврат ноды
- UC-09 Управление тарифами, группами и кодами
- UC-12 Компрометация ноды

Требования RTM: R-02, R-18, R-23, R-28, R-34, R-39.

<!-- contract:goal -->

## Цель задачи

Реализовать изменение записи ноды (`PATCH /admin/nodes/{id}`) и вывод ноды из эксплуатации
(`DELETE /admin/nodes/{id}`, idea §4.6 строка «Удаление», UC-12 A2) на стороне Control Plane:
поля записи, адрес с историей и событием «Адрес или параметры ноды изменены», группы доступа,
тарифицируемая группа и переопределение коэффициента, лимиты раздела `agent`; вывод — отметка,
отзыв identity без ротации, аудит. Сейчас обе операции отвечают 501, владельца у них не было
(отчёт 001.25; группы PLAN-V-01, NODE-26, DEC-07, ADM-09; решение заказчика 2026-10-25, В-21 а).

## Описание изменений

### Изменения в существующих файлах

#### Файл: `control-plane/app/domain/nodes.py` — изменение принятого кода (отступление от 001.25)

- `update(node_id, patch, ctx)` — одна транзакция; первым шагом — блокировка строки ноды
  `FOR NO KEY UPDATE` (порядок блокировок модуля). Исключение — PATCH с тарифицируемой группой
  или переопределением: первым шагом идёт назначение (ниже), строку ноды оно блокирует своим
  `UPDATE nodes`. Нет ноды — 404; нода выведена из эксплуатации — 409 «нода выведена из
  эксплуатации» (как `approve` и `issue_bootstrap_token`). Занятый `code` — 409, как при создании.
  Поле, значение которого не изменилось, изменением не считается. PATCH без изменений ничего не
  пишет: ни аудита, ни событий
- поля записи без побочных действий: `code`, `name`, `country`, `city`, `provider`,
  `public_ipv6`, `fqdn`, `legal_profile`, поля экономики (§5.10), `bandwidth_mbps`.
  `bandwidth_mbps` — вход порога аномалии §5.9 (DEC-07): приём отчёта читает его под той же
  блокировкой строки ноды (`app/accounting/service.py`, `_LOCK_NODE`), новое значение действует
  для частей, принятых после фиксации PATCH
- адрес: смена `public_ipv4` закрывает действующую строку `node_ip_history` (`valid_to` — момент
  операции) и открывает новую от того же момента (idea §4.4, §4.7 «Смена адреса ноды»); в той же
  транзакции — `emit(conn, node_address_changed, user_id, node_id, payload={"kind": "address"})`
  строкой на каждого пользователя ноды. Пользователь ноды — строка `node_user_state` ноды в
  состоянии, отличном от `removed` (001.29), тот же набор, что у замены ключевой пары (001.27).
  Ключ `dedup_key` — формула 001.51, версия — `id` новой строки `node_ip_history`. Смена
  `public_ipv6` и `fqdn` истории и события не порождает: история адреса задана для `public_ipv4`
  (idea §4.4), а ссылки профилей MVP — REALITY по `public_ipv4` (001.43); ключевой материал REALITY
  смена адреса не меняет (idea §4.7)
- группы доступа: `access_group_ids` заменяет строки `node_access_groups` (повторы схлопываются,
  как при создании; неизвестная группа — 422 `unknown_access_group`, транзакция откатывается
  целиком); в той же транзакции — задача `composition.publish_node` (очередь `critical`, ключ по
  образцу `publish_user` 001.29: `publish_node:{node_id}:{xid}`). Состав ноды публикует 001.29
- тарифицируемая группа и переопределение коэффициента — только через
  `GroupService.set_billing_group` (001.19). Прямой записи `nodes.billing_group_id` и
  `nodes.multiplier_milli` нет: она потеряла бы интервал истории и не закрыла бы час учёта (001.24,
  «Найдено при 001.19»). PATCH только с `multiplier_milli` — назначение с действующей группой;
  `null` снимает переопределение. Отказы `set_billing_group` (409 на вторую группу UC-09 A1, 409 на назначение,
  начатое не раньше момента операции, 422 на коэффициент вне 0…10000 или не кратный 100 UC-09 A2)
  откатывают весь PATCH
- лимиты раздела `agent`: смена `max_conn_per_ip` или `new_conn_rate_per_ip` выпускает новую
  версию раздела `agent` ответа состояния механизмом 001.27, без новой версии конфигурации Xray
  (001.26, 001.27: «Значения меняет изменение записи ноды (001.87)»)
- аудит: `audit.record(conn, ctx, "nodes.update", "node", old, new, "success")` — прежние и новые
  значения только изменённых полей; смену группы и коэффициента журналирует `set_billing_group`
  (001.46), PATCH её не повторяет. Событие таблицы 001.48 «Создание и изменение ноды … изменение
  записи и вывод — 001.87»
- `decommission(node_id, ctx)` — одна транзакция: блокировка строки ноды; нет ноды — 404; повторный
  вывод — 409 «нода выведена из эксплуатации»; момент — `statement_timestamp()` после блокировки
  (правило модуля). Действия: `nodes.decommissioned_at` — момент вывода; общий шаг отзыва (ниже) —
  `revoked_at` у всех неотозванных identity, аннулирование неиспользованного bootstrap-токена,
  статус `disabled` (`ON_REVOCATION`); `audit.record(…, "nodes.decommission", …)`. Вывод без
  компрометации (UC-12 A2) не ставит `composition.rotate_node_credentials`, не меняет ключевую
  пару REALITY и не порождает события «Адрес или параметры ноды изменены». Запись периода недоучёта
  в `traffic_gaps` — по ответу на вопрос «решить здесь» ниже
- общий шаг отзыва: тело `revoke_identity` выносится в `_revoke(conn, node_id, at, *, compromise)`.
  При `compromise=True` шаг ставит `composition.rotate_node_credentials` (постановку в
  `revoke_identity` вводит 001.29; задача вызывает `rotate_keypair(reason=compromise)` 001.27).
  `revoke_identity` вызывает шаг с `compromise=True`, вывод — с `compromise=False`. Постановку
  строки внешнего журнала отзывов, которую 001.67 вводит в `revoke_identity`, задача переносит в
  общий шаг: вывод ноды пишет строку на каждую identity и каждый аннулированный токен тем же путём
  (тест — вывод ноды с действующей identity и неиспользованным токеном ставит задачу журнала на
  каждую из них)
- докстринги модуля, `update`, `decommission`: «не реализовано — 501», «владельца в плане нет
  (отчёт 001.25)» → описание операций и ссылка на 001.87

### Интеграция компонентов

Вывод ноды на VPS выполняет подкоманда `node-agent decommission` по SSH: слив буфера отчётов,
финальное чтение счётчиков, затирание identity (001.81; решение заказчика 2026-10-25, В-21 а). Канал
команд §5.2 для вывода не используется. Порядок «подкоманда на VPS → вывод в панели → уничтожение
VPS» — инструкция оператора 001.71. После вывода приём отчёта отклоняет ноду (`gone`, принятый код
001.34), раздел `/agent/v1` отвечает 401 (`usable` учитывает `decommissioned_at`, 001.25), выдача
bootstrap-токена и подтверждение — 409, установка и снятие ручного статуса — 409 (001.30b). Из
выдачи подписки нода уходит по статусу `disabled`
(001.44).

Событие «Адрес или параметры ноды изменены» (`node_address_changed`, решение заказчика 2026-10-25,
В-41): тип и `dedup_key` — 001.51, смена ключевой пары — 001.27, доставка — 001.52, текст письма по
`payload.kind` — 001.78.

Включение и отключение ноды — ручные статусы (001.30b), включение и отключение inbound — 001.27; в
эту задачу они не входят. Экраны изменения и вывода ноды — 001.64.

## Примечания

`tdd-strict`: задача меняет отзыв identity (enrollment, 001.25) и назначение коэффициента
(закрытие часа учёта, 001.19, 001.77b).

Найдено при создании задачи (В-21) и при сверке 2026-10-25, решить здесь:

- **Период недоучёта при выводе.** idea §5.9: нода, уничтоженная без вывода, получает запись
  периода недоучёта «интервал, нода, причина», такие интервалы исключаются из расчёта Н-18.
  Control Plane не знает, выполнена ли подкоманда `node-agent decommission`: в обоих случаях
  heartbeat прекращается. Варианты: а) запрос вывода несёт признак «подкоманда завершилась с кодом
  0» (`DELETE …?flushed=true`); без признака — строка `traffic_gaps` от конца последнего принятого
  интервала ноды (нет интервала — от `nodes.created_at`) до момента вывода, причина
  `decommissioned`; б) строка пишется при каждом выводе на тот же отрезок: после слива буфера
  отрезок без трафика (Xray остановлен подкомандой), запись только помечает его; в) строку при
  выводе не писать, разрывы — только сверки 001.37d. Рекомендация: б — запись не зависит от
  утверждения оператора, маршрут не меняется; при в хвост буфера уничтоженной ноды не
  фиксируется ничем: следующего отчёта, по которому сверка нашла бы пропуск, нет. Ответ — вопрос
  заказчику до начала задачи. Строку пишет эта задача (001.81: «запись интервала недоучёта —
  001.87»); повтора вывода нет (409), поэтому ключ `traffic_gaps` идемпотентности не требует.
  Исключение записанного периода из расчёта Н-18 — сверки 001.37d. При ответе а или б строка
  пишется в `traffic_gaps`, пересозданную 001.37 (партиции по суткам `gap_start`, срок хранения
  90 суток, `data-model.md` §4.5): к зависимостям задачи добавляется 001.37 (правка PLAN), а начало
  отрезка ограничивается снизу началом самой старой существующей партиции `traffic_gaps` — иначе
  вставка в отсутствующую партицию откатила бы вывод ноды.
- **PATCH только с `billing_group_id` при действующем переопределении коэффициента.** Варианты:
  а) переопределение сохраняется — назначение новой группы с действующим `nodes.multiplier_milli`
  (поле, которого нет в PATCH, не меняется; симметрично PATCH только с `multiplier_milli`, который
  сохраняет группу); б) переопределение снимается — назначение без `override_milli`, как вызов
  `set_billing_group` без коэффициента. Рекомендация: а — смена группы не меняет поле, которого
