## 1. Описание задачи

Задача: `docs/TASK.md`, Task 001 `vpn-control-plane-mvp`.

Система состоит из центрального Control Plane и парка VPN-нод. Control Plane хранит пользователей,
подписки, тарифы, ноды и учёт трафика; выдаёт подписки клиентским приложениям; управляет нодами
через собственный Node Agent. Нода несёт Xray-core и Node Agent; агент устанавливает исходящее
соединение к Control Plane (§3.3).

Границы MVP: до 1 000 активных пользователей и 10 нод (О-3), один хост Docker Compose (О-4), один
оператор (О-6), без приёма платежей (О-2). Три профиля подключения на ноду: `vless-raw-vision`,
`vless-xhttp`, `trojan-reality` (§4.4). Форматы подписки `base64` и `singbox` (§5.6).

Решение §0.3 — вариант Build (заказчик, 2026-10-25, В-11 б); настоящий документ описывает его.
PoC-1а выполняется отдельной ранней задачей 001.88 до логики разрыва соединений (001.40, 001.60):
замер на VPS заказчика выбирает механизм ОВ-22 и подтверждает Н-17. `restart_inbound` только
замеряется и выбран быть не может (В-9 а); реализуется одна выбранная стратегия.

## 8. Масштабируемость и производительность

### 8.1 Стратегия

MVP развёртывается на одном хосте (О-4). Архитектура не запрещает горизонтальный рост C-01 и C-02:
процессы не хранят состояние (сессии, счётчики и пробуждения — в Redis; очередь — в PostgreSQL).

| Шаг роста | Что меняется | Что не меняется |
| :--- | :--- | :--- |
| Второй экземпляр `api` | `nginx upstream` из двух адресов; потолки прокси для Node API (два одновременных отчёта, частота парка — §5.2, гейт бюджета Н-4) выведены из одного цикла событий и пересчитываются на число экземпляров | код, схема, Redis |
| Второй `worker-background` | ещё один процесс той же очереди | `SKIP LOCKED` распределяет задачи |
| Standby PostgreSQL | потоковая репликация, `pgbackrest` уже архивирует WAL | схема, приложение |

Нагрузка при О-3 (Н-1…Н-4): единицы запросов в секунду. Узкое место Node API — разбор тела
отчёта о трафике в цикле событий C-01: часть потолка (500 строк, 2 500 адресов) стоит около
50 мс по p95 стенда, прокси допускает две части одновременно на весь парк, остальным операциям
отведена четверть цикла, а путь отказа не дороже пути приёма (проверка формы по байтам до
разбора) — бюджет Н-4 закреплён гейтом (§5.2, `control-plane/tests/unit/test_proxy_contract.py`);
пропускная способность парка по отчётам — 16…27 частей в секунду по ширине части и полосе
ноды, на насыщении цикла 20, при потребности §5.7 в 50 частей в минуту. Снапшот потока состава (расшифровка credentials для ноды с 1 000 пользователей)
запрашивается редко (§5.2), ответ отдаётся из буферов прокси и tmpfs, не удерживая C-01; дельты
содержат единицы строк.

### 8.2 Кеширование

| Объект | Стратегия | Инвалидация |
| :--- | :--- | :--- |
| Ответ подписки | не кешируется: формируется за один запрос к базе | — |
| Соответствие `User-Agent → формат`, режим регистрации | не кешируется: `settings` читаются из базы на каждом запросе, в ответе подписки — тем же запросом, что и данные (кеш в памяти процесса запрещает §4.20) | — |
| Домены подписки | не в `settings`: окружение развёртывания `SUBSCRIPTION_DOMAINS`, задаётся при запуске процесса; панель показывает домены только для чтения (В-27 а) | переразвёртывание (deployment.md §10.3) |
| Разрешения ролей | в коде | выпуск |
| Сессии | Redis | TTL, явная инвалидация |

### 8.3 Оптимизация базы

- Партиционирование по суткам для `traffic_lines`, `traffic_hourly`, `subscription_access_log`,
  `auth_events`, `node_metrics`, `traffic_gaps`, `reconciliation_runs` (§4.5); удаление устаревших партиций вместо `DELETE`.
- Суточная агрегация `traffic_daily` выполняется инкрементально по закрытым суткам: ночной прогон
  пересчитывает сутки D−1…D−3 (окно приёма 72 ч), а поздний отчёт — у которого сутки
  `period_start` (UTC) раньше суток приёма — ставит пересчёт своих суток задачей
  `traffic.aggregate_day` с ключом `aggregate:{day}` (постановка — 001.77b, агрегация — 001.37c).
- Индексы §4.4; `EXPLAIN` для запросов выдачи подписки и дельты потока 2 — обязательная часть
  приёмки Н-2.
- `autovacuum` с пониженным порогом для `jobs` и `node_user_state`: таблицы с высокой частотой
  обновления.
