# Приложение: полный реестр находок по `docs/idea.md`

Источник: 7 независимых разборов + адверсариальная верификация каждой находки. Подтверждено 91, опровергнуто при верификации 6.

Формат записи: идентификатор, серьёзность, формулировка, основание в документе, последствие, что дописать.

## Учёт трафика и биллинг (10)

### TB-01 · BLOCKER · gap

**Формулировка.** Не зафиксирована семантика снятия счётчиков Xray и поведение учёта при перезапуске процесса Xray (обновление §6.5, ребут, крэш): счётчики StatsService живут в памяти и обнуляются вместе с процессом, поэтому без явного контракта (кумулятив + признак «поколения» счётчиков, либо reset=true с durable-подтверждением) на каждом рестарте система получает либо потерю трафика, либо повторное списание. Требуется требование уровня постановки: учёт трафика обязан быть устойчив к перезапуску Xray и к повторной доставке отчётов.

**Основание в документе.** §5.9: «VPN Node ↓ Node Agent ↓ Aggregation ↓ Control Plane ↓ Hourly / Daily records», «Необходимо хранить: Raw bytes / Billable bytes / Traffic multiplier / Node / Server group / Period». §3.4: «Node Agent получает актуальное состояние и приводит локальную инфраструктуру к нему». В документе отсутствует описание того, как именно Node Agent снимает счётчики с Xray и что происходит со счётчиками при перезапуске/reload Xray.

**Последствие.** Xray StatsService отдаёт per-user счётчики uplink/downlink, и у вызова есть два режима: reset=true (вернуть и обнулить, т.е. дельта) и reset=false (кумулятив с момента старта процесса). Оба ломаются на границе рестарта, а рестарты по §3.4/§5.4 будут постоянными: любое изменение состава пользователей на ноде — это новая версия конфигурации, которую Node Agent применяет. Вариант reset=false: после рестарта счётчик пользователя падает с 40 GB до 0; Control Plane, вычисляя дельту как current-previous, получает -40 GB (уйдёт в минус или будет отброшено), а затем каждый следующий опрос снова считает уже учтённые байты — при наивном clamp'е к нулю (delta = max(0, current)) весь трафик после рестарта учитывается повторно, т.е. двойное списание. Вариант reset=true: между GetStats(reset=true) и успешной записью в Control Plane нет ни одного места, где эти байты существуют — любой сбой (см. dim-02, dim-03) означает безвозвратную потерю. Без выбранной семантики нельзя спроектировать ни таблицу traffic-событий, ни протокол §5.2, ни тесты — это переписывание всего слоя учёта позже.

**Что дописать.** Зафиксировать в §5.9/§5.2 контракт: (1) Node Agent читает счётчики в режиме кумулятива (reset=false) и сам вычисляет дельты; (2) вводится counter_epoch — UUID, генерируемый Node Agent при каждом старте/reload процесса Xray и передаваемый в каждом отчёте; (3) дельта вычисляется только внутри одного epoch, смена epoch = базовая точка 0, значение до рестарта фиксируется финальным чтением перед применением конфигурации; (4) явно описать, что применение новой конфигурации обязано выполняться через API добавления/удаления пользователей без рестарта процесса там, где это возможно, а если рестарт неизбежен — обязателен pre-restart flush счётчиков; (5) на стороне Control Plane отдельно логировать и алертить события 'counter regression' (current < previous при том же epoch).

### TB-02 · BLOCKER · gap

**Формулировка.** Нет требования к идемпотентности отправки статистики: ретрай после сетевого таймаута приводит к двойному списанию квоты

**Основание в документе.** §5.2: «API должен поддерживать: … * metrics; * traffic statistics; * commands.» — перечень возможностей без описания семантики доставки. В документе отсутствуют слова idempotency key, sequence number, at-least-once, дедупликация.

**Последствие.** Отправка статистики нодой по HTTPS (§3.3) — это at-least-once по определению: если Control Plane принял и записал отчёт, а ответ 200 потерялся (таймаут, разрыв, перезапуск reverse proxy), Node Agent обязан повторить, иначе трафик потеряется. Без ключа идемпотентности повтор будет принят как новая дельта, и у пользователя дважды спишется один и тот же объём. При multiplier 3.0 (§4.9, Singapore) один задвоенный отчёт за час на скорости 200 Мбит/с — это 270 GB ложного списания, т.е. мгновенное исчерпание Premium-лимита 500 GB (§4.10) и отключение платящего пользователя. Обратная стратегия (не повторять) даёт систематическую недобилловку. Оба исхода — инцидент с деньгами, а не с логами.

**Что дописать.** В §5.2 задать контракт эндпоинта статистики: тело содержит (node_id, counter_epoch, report_seq — монотонный номер отчёта в рамках epoch, period_start, period_end) и массив per-user дельт; Control Plane хранит unique-констрейнт (node_id, counter_epoch, report_seq) и на повторный приём возвращает 200 с пометкой duplicate, не изменяя балансы; ответ содержит last_accepted_seq, чтобы агент понимал, с какого места продолжать. Альтернатива, которую надо явно выбрать или отвергнуть: передавать не дельты, а кумулятивные счётчики (node_id, epoch, user_id, uplink_total, downlink_total) — тогда повтор идемпотентен по построению, а дельту считает Control Plane.

### TB-03 · BLOCKER · gap

**Формулировка.** Не описано поведение системы при исчерпании лимита, блокировке пользователя и окончании подписки: §3.4 (desired state со списком Users) и §5.2 («commands») дают каркас, но нигде не сказано, что пользователь исключается из desired state ноды, разрываются ли активные сессии, за какое время изменение должно примениться и что делать с нодами в статусе Offline. Отдельно не решено, есть ли soft/hard-лимит и grace-объём (§6.8 упоминает grace period только для платежей).

**Основание в документе.** §4.17 перечисляет только событие уведомления: «Traffic limit reached». §4.3: «он автоматически исключается из выдаваемых пользователю конфигураций» — это про содержимое subscription-ответа. §7 MVP → Traffic: «traffic limits» — одна строка. В документе отсутствует описание enforcement: удаление пользователя из Xray, разрыв соединений, degradation скорости.

**Последствие.** Есть три принципиально разных варианта, и они дают разный продукт, разную схему API и разные сроки: (а) удалить пользователя из конфигурации Xray на всех нодах — это N=200 (§5.7) синхронизаций конфигурации, задержка = интервал pull (§3.4 интервал не задан), и на нодах, которые сейчас Offline, пользователь продолжит качать; (б) послать команду разрыва активных соединений — требует отдельного типа команды в §5.2 и поддержки на стороне Xray, чего нет ни в §5.2, ни в §5.5; (в) просто перестать отдавать конфиг в subscription URL — не работает вообще, потому что клиенты (Shadowrocket, v2rayNG, Hiddify, sing-box, §4.2) кэшируют полученный конфиг локально и обновляют подписку по своему расписанию (часто вручную или раз в сутки): пользователь с исчерпанным лимитом продолжит пользоваться VPN неограниченно долго. Тот же дефект делает нерабочими блокировку пользователя (§4.15 «блокировка») и окончание подписки — документ нигде не описывает отзыв доступа у уже выданного конфига. Пока вариант не выбран, нельзя спроектировать ни таблицу состояния пользователя на ноде, ни API §5.2.

**Что дописать.** Явно описать в §4.11 модель принуждения и её состояния: user_node_state ∈ {active, suspended_quota, suspended_admin, expired} как часть desired state ноды; обязательное требование — при переходе в suspended пользователь удаляется из inbound Xray И его активные соединения разрываются (для VLESS/Trojan — удаление UUID/пароля через Xray API + kill существующих сессий), максимальное время применения (SLA, например ≤60 с) с указанием интервала pull/push в §3.4; поведение для нод в статусе Offline (пользователь остаётся заблокированным до восстановления связи, при регистрации ноды состояние применяется до приёма трафика); отдельно решить и записать, что делать с 'мягким' исчерпанием — soft-limit с уведомлением и hard-limit с отключением, grace-объём.

### TB-04 · BLOCKER · gap

**Формулировка.** Не задан максимально допустимый лаг между потреблением и учётом/принуждением и не задана периодичность отправки traffic-отчётов (30 с в §4.7 — только heartbeat). При единственной названной гранулярности «Hourly» перерасход после обнуления баланса измеряется десятками-сотнями GB billable на дорогих нодах (multiplier 3x), что напрямую бьёт по экономике §5.10. Требуется зафиксировать целевой максимальный перерасход и механизм его соблюдения (например, предоплаченный грант квоты на ноду).

**Основание в документе.** §5.9: «Hourly / Daily records». §4.7 задаёт интервал только для heartbeat: «every 30 seconds». В документе отсутствует требование к периодичности отправки traffic-статистики и к максимально допустимому перерасходу квоты.

**Последствие.** Единственная временная гранулярность, названная в документе для трафика, — часовая. Расчёт на реалистичной скорости: VLESS Reality на нормальном европейском VPS уверенно даёт 100–200 Мбит/с на клиента. 200 Мбит/с = 25 МБ/с = 1,5 GB/мин = 90 GB/час raw. Тариф Premium (§4.10) разрешает 5 устройств: 450 GB raw за час. На ноде Japan с multiplier 3.0 (§8, шаг 6) это 1350 GB billable — в 2,7 раза больше всего месячного лимита 500 GB, украденных ПОСЛЕ того, как баланс уже стал нулевым, и это до того, как Control Plane вообще узнает о первом байте. Даже при 5-минутной агрегации: 7,5 GB raw × 3.0 × 5 устройств = 112 GB перерасхода. Добавьте время применения блокировки (§3.4 интервал pull не задан) — цифра удваивается. Для сервиса, где себестоимость привязана к трафику (§5.10 «Cost per GB»), это прямой денежный убыток и открытая дыра для абьюза: злоумышленнику достаточно купить один Basic за 100 GB и качать через дорогую ноду.

**Что дописать.** Ввести в §4.11/§5.9 явные требования: (1) отчётность о трафике — не реже чем раз в N секунд (предложение: 30 с, совмещённо с heartbeat), отдельно от часовой агрегации в хранилище (агрегация — это про хранение, не про принуждение); (2) модель предоплаченной квоты по образцу RADIUS interim-update / Diameter Gy: Control Plane выдаёт ноде вместе с конфигурацией пользователя грант (quota_grant_bytes, рассчитанный уже с учётом multiplier), нода локально ведёт счётчик и при исчерпании гранта блокирует пользователя, не дожидаясь Control Plane, и запрашивает следующий грант; (3) зафиксировать целевой максимальный перерасход (например ≤1 GB billable на пользователя) и вывести из него размер гранта; (4) описать, как грант делится между 200 нодами при одновременном использовании (например грант = min(остаток/число активных нод, cap), с пересчётом при возврате неиспользованного).

### TB-05 · BLOCKER · underspecified

**Формулировка.** «Monthly limit» не имеет определения: нет якорной даты, часового пояса, правил сброса, поведения при смене тарифа и продлении

**Основание в документе.** §4.11: «Unlimited / Fixed subscription limit / Monthly limit / Custom limit», пример «100 GB per month» и «500 GB for subscription lifetime». §4.12: «Current period». §4.15 (Users): «изменение тарифа; продление подписки; добавление трафика». В документе отсутствуют слова timezone, UTC, дата сброса, проration.

**Последствие.** «100 GB per month» допускает минимум четыре несовместимых реализации: календарный месяц в UTC; календарный месяц в таймзоне пользователя; 30-дневное окно от даты активации подписки; скользящее окно 30 дней. Они дают разный «Remaining traffic» (§4.12) и разный момент отключения — и поменять реализацию после запуска нельзя без пересчёта истории и скандала с пользователями. Дополнительно не определено: (а) при смене тарифа Basic 100 GB → Premium 500 GB в середине периода — счётчик обнуляется, переносится, пропорционируется? Если не обнулять, пользователь, потративший 100 GB, получит только 400 GB за полную цену Premium; если обнулять — тривиальный абьюз (потратил 100 GB, переключился туда-сюда); (б) при продлении подписки на тот же тариф — сбрасывается ли счётчик и в какой момент; (в) переносится ли неиспользованный остаток; (г) куда попадает «Traffic bonus» промокода (§4.14) и «добавление трафика» админом (§4.15) — увеличивают лимит текущего периода или создают отдельный неистекающий bucket (и что из них тратится первым); (д) что делает Fixed subscription limit при продлении. Без этих правил нельзя написать ни джоб сброса, ни таблицу балансов.

**Что дописать.** Ввести отдельную сущность quota_period (subscription_id, period_start, period_end, limit_bytes, consumed_billable_bytes, source) с явными правилами: якорь периода = дата активации подписки, все границы в UTC, длительность = duration тарифа (§4.10), сброс — идемпотентный джоб, создающий новую запись периода (а не UPDATE балансов); правила смены тарифа — закрыть текущий период фактическим потреблением и открыть новый с пропорционально пересчитанным лимитом (формула привести явно); правило продления — новый период, остаток не переносится (или переносится с cap — выбрать); бонусный трафик — отдельная запись типа bonus_bucket с собственным сроком годности и явным порядком списания (сначала период, потом бонус, или наоборот); отдельно указать таймзону отображения в ЛК и то, что расчёты всегда в UTC.

### TB-06 · BLOCKER · wrong-assumption

**Формулировка.** Не определено, действует ли изменение Traffic Multiplier только вперёд: §5.9 требует хранить применённый множитель в записи статистики, но одновременно обещает «корректно пересчитывать статистику», и нигде не сказано, что уже списанное (charged_bytes) неизменяемо. Нужно зафиксировать датированность множителя (действует с момента изменения) и запрет ретроактивного пересчёта пользовательских списаний, оставив what-if пересчёт только аналитическому слою §5.10/§6.13.

**Основание в документе.** §5.9: «Это позволит в будущем корректно пересчитывать статистику и анализировать экономику серверов.» §4.9: «Для каждого Server Group и отдельного Node можно настроить коэффициент расхода трафика». В документе отсутствуют требования к версионированию/датированию множителя (effective_from) и к неизменяемости истории списаний.

**Последствие.** Множитель — это не аналитический атрибут, а операнд биллинга. Если администратор в середине месяца поднимает Japan с 2.0 до 3.0 (ровно тот сценарий, который описан в §8, шаги 4 и 6), возникает развилка, которую документ не разрешает: либо новый множитель применяется только к трафику после изменения, либо (как предлагает «пересчитывать статистику») пересчитывается весь период — и тогда у пользователя, потратившего 200 GB на Japan, списанное вырастает со 400 до 600 GB, он мгновенно уходит за лимит 500 GB и отключается за трафик, который на момент потребления стоил дешевле. Это гарантированные возвраты денег и репутационный инцидент. Обратная ситуация (снижение множителя) требует возврата квоты, что без описанной модели тоже негде отразить. Плюс §6.14 добавляет измерения «по тарифу» и «по времени» — при них множитель вообще не является свойством ноды и не может быть 'просто пересчитан'.

**Что дописать.** Записать в §4.9 и §5.9 два жёстких правила: (1) множитель хранится как effective-dated запись (scope=node|group|plan|default, scope_id, multiplier NUMERIC, valid_from, valid_to, actor) — редактирование существующей записи запрещено, изменение = закрытие старой и создание новой; (2) charged_bytes вычисляется в момент приёма дельты по множителю, действовавшему на период этой дельты, и записывается в таблицу как immutable факт; последующее изменение множителя НИКОГДА не меняет уже списанное. Для аналитики (§5.10) разрешить what-if пересчёт только в отдельном отчётном слое, не затрагивающем баланс пользователя. В UI редактирования множителя (§4.15 Server Groups) показывать предупреждение и дату вступления в силу.

### TB-07 · MAJOR · gap

**Формулировка.** Не «противоречие §3.1 vs §3.2», а незакрытый гэп: §3.1 объявляет статистику критическими данными и запрещает ноде быть единственным местом их хранения, но §3.2 (уничтожение ноды) и §6.4 (draining, Phase 2) не задают ни требования к локальному durable-буферу неподтверждённых отчётов, ни процедуры decommission со сбросом статистики перед удалением VPS, ни правила фиксации периода недоучёта.

**Основание в документе.** §3.2: «Любой VPN-сервер должен иметь возможность быть: выключен; удалён; полностью уничтожен…». Там же: «При этом не должны теряться: пользователи; подписки; тарифы; права доступа.» — статистика/трафик в этом списке отсутствуют, хотя §3.1 включает «статистика» в перечень критических централизованно хранимых данных.

**Последствие.** Между двумя явными списками §3.1 и §3.2 — прямое противоречие: статистика объявлена критическими данными, но её сохранность при уничтожении ноды не требуется. Практический сценарий: нода теряет связь с Control Plane (сеть провайдера, блокировка IP), продолжая обслуживать уже подключённых клиентов, накапливает 6 часов статистики локально; администратор видит Offline (§4.7) и по сценарию §3.2 уничтожает VPS и создаёт новый. Весь трафик за 6 часов — на скорости 100 Мбит/с это до 270 GB на пользователя — не будет списан ни с кого. Это не крайний случай, а штатный операционный сценарий, описанный самим документом как «желаемый». Дополнительно: §6.4 Server Draining («ждёт завершения существующих соединений») отнесён в Phase 2 и всё равно не упоминает финальный сброс статистики.

**Что дописать.** Добавить в §3.2 статистику в список несохраняемых потерь и описать механизм: (1) Node Agent обязан вести локальный durable-спул неподтверждённых отчётов (SQLite/файл с fsync) с ограничением по объёму и времени и повторять отправку до подтверждения; (2) ввести обязательную процедуру decommission ноды в Control Plane (отдельная команда через §5.2 commands): flush статистики → подтверждение → перевод ноды в Decommissioned → только после этого разрешено удаление VPS; (3) описать поведение при уничтожении ноды без decommission — Control Plane помечает период как traffic_gap с оценкой недоучёта (по last_seen счётчикам) и выводит его в отчётах; (4) задать максимальный горизонт локального спула (например 72 часа) и правило приёма «поздних» отчётов задним числом (см. dim-06 — попадают ли они в уже закрытый период).

### TB-08 · MAJOR · contradiction

**Формулировка.** Не определено, что именно списывается с лимита: §4.12 требует показывать Upload/Download/Total, а иллюстрации §4.9 и §8 говорят только о скачанном («downloaded», «Использует 10 GB»). Нужно явно записать базу списания (uplink+downlink или только downlink) и то, что показывается пользователю как raw и как charged; отдельным пунктом — исключается ли служебный трафик Node Agent и учитывается ли оверхед транспорта при расчёте Cost per GB (§5.10). Категория — underspecified, а не contradiction.

**Основание в документе.** §4.12: «Upload / Download / Total / Remaining traffic». §4.9: «User downloaded: 10 GB / Server multiplier: 2.0 / Raw traffic: 10 GB / Billable traffic: 20 GB»; таблица §4.9 оперирует колонкой «Реальный трафик» без разбиения на направления. §8 шаг 11: «Использует 10 GB».

**Последствие.** Xray отдаёт per-user два независимых счётчика (uplink и downlink), и выбор между 'billable = downlink' и 'billable = uplink + downlink' меняет списание у разных пользователей на 5–100%: у обычного потребителя контента uplink ~5–10% от downlink, у пользователя торрентов/бэкапов/видеозвонков uplink сопоставим с downlink. Отсюда: разная реальная ёмкость тарифа, разная себестоимость (провайдер VPS считает исходящий трафик ноды, а это как раз downlink пользователя + uplink), разные цифры в ЛК и в жалобах саппорту. Решение принимается один раз и зашивается в формулу billable_bytes при ingest (см. dim-10), переиграть его задним числом невозможно без пересчёта всей истории. Смежно: не определено, учитывается ли служебный трафик — heartbeat/метрики/config-sync Node Agent, latency-пробы клиентов (Hiddify/sing-box с urltest опрашивают ВСЕ серверы подписки, а по §4.3 их будет до 200), DNS-запросы через прокси; и учитывается ли оверхед REALITY/TLS/TCP-ретрансмиссий — Xray считает байты полезной нагрузки, а провайдер выставляет счёт за байты на проводе (обычно на 3–8% больше), из-за чего «Cost per GB» из §5.10 будет систематически занижен.

**Что дописать.** В §4.11 записать формулу явно: billable_bytes = round(( uplink + downlink ) × multiplier) (либо только downlink — выбрать и обосновать), в §4.12 показывать пользователю uplink/downlink раздельно как raw и одно число как charged. Отдельным пунктом: служебный трафик Node Agent идёт мимо пользовательских inbound и не учитывается никогда; latency-пробы клиентов учитываются (иначе появится вектор абьюза) — но тогда нужен порог/фильтр на счётчики <X байт за период, чтобы не плодить строки (см. dim-11). Для §5.10 ввести отдельный коэффициент overhead_factor ноды или брать реальный трафик интерфейса из §4.7 «network traffic» для сверки с суммой пользовательских счётчиков.

### TB-09 · MAJOR · gap

**Формулировка.** Иерархия §4.9 не определяет правило разрешения, когда ноде применимы несколько групповых множителей (группы §4.8 пересекаются, §4.4 разрешает менять «группы» ноды), и не задаёт момент фиксации применённого множителя при переносе ноды между группами внутри периода агрегации (§5.9). Тезис о том, что множитель якобы становится свойством ноды и требует раскатки конфигурации на 200 нод, из документа не следует и снимается: §4.15/§5.9/§5.10 однозначно помещают множитель в Control Plane.

**Основание в документе.** §4.9: «Node Traffic Multiplier → highest priority → Server Group Traffic Multiplier → Default Multiplier». §4.4: «изменять группы» (множественное число). §4.8 приводит пересекающиеся группы: «Europe / Premium Europe / … / High Cost / Streaming». §6.14 добавляет уровень «По тарифу»: «Basic user: Japan: 3x / Premium user: Japan: 1.5x».

**Последствие.** Группы в §4.8 заведомо пересекаются по смыслу (нода одновременно в Europe, High Cost и Streaming), а §4.4 разрешает менять группы ноды во множественном числе. При этом §4.9 описывает строго линейную цепочку из трёх уровней и не говорит, что делать, когда для ноды применимы ДВА групповых множителя 1.0 и 3.0: max, min, произведение, приоритет по порядку групп? Разница в 3 раза в списании у реальных пользователей. Второй незакрытый вопрос — момент разрешения: если ноду перевели из Asia Premium (2.0) в Europe (1.0) в 14:30, а запись агрегации покрывает 14:00–15:00 (§5.9), какой множитель применён ко всему часу? Ответ сейчас зависит от того, когда джоб агрегации прочитает справочник, то есть недетерминирован. Третий: §4.9 называет уровень «Node Traffic Multiplier», что читается как свойство ноды — но нода не должна знать бизнес-правила списания, иначе изменение множителя требует push конфигурации на 200 нод и создаёт рассинхрон с §5.4 (Applied v143 при Desired v145 = списание по устаревшему коэффициенту).

**Что дописать.** Дописать в §4.9: (1) правило разрешения при нескольких группах — детерминированное и одно (предложение: применяется максимальный множитель среди групп ноды, обоснование — защита себестоимости; либо ввести на группе поле priority и брать группу с наибольшим приоритетом) с примером на пересекающихся группах из §4.8; (2) множитель разрешается и фиксируется в момент приёма конкретной дельты Control Plane'ом и записывается в строку traffic-факта (поле traffic_multiplier из §5.9 — именно применённое значение, а не ссылка на справочник); (3) явно указать, что billable вычисляет Control Plane, а нода передаёт только raw — тогда рассинхрон конфигурации (§5.4) не влияет на биллинг; (4) заранее зарезервировать порядок разрешения для будущих уровней из §6.14 (plan-override поверх node, time-based как модификатор).

### TB-10 · MAJOR · gap

**Формулировка.** Нет требования к проверяемости учёта: документ собирает два независимых источника (пользовательские счётчики Xray и «network traffic» ноды из §4.7), но нигде не требует их сверки, обнаружения пропусков в потоке отчётов и алертов о расхождении (§5.14 содержит только инфраструктурные алерты), а Audit Log (§4.16) покрывает только административные действия и не даёт трассировки конкретного списания до конкретного отчёта конкретной ноды.

**Основание в документе.** §3.1: «Control Plane является единственным источником истины … статистика». §4.7 требует собирать с ноды «network traffic». §5.10: «Cost per GB». В документе отсутствуют требования к сверке, к обнаружению пропусков в последовательности отчётов и к алертам о расхождении.

**Последствие.** Все дефекты dim-01…dim-03 (регрессия счётчика после рестарта, задвоенный ретрай, потерянный спул уничтоженной ноды) — тихие: они не роняют сервис и не пишут ошибок, они просто искажают числа. Без сверки расхождение обнаружится либо через жалобу пользователя («у меня списалось вдвое»), либо через убыток при сведении экономики (§5.10), то есть спустя недели и уже на всей базе. При этом у системы есть два независимых источника для сверки, которые документ уже собирает и не использует: сумма пользовательских счётчиков Xray на ноде против «network traffic» интерфейса ноды (§4.7), и сумма charged_bytes по фактам против consumed_bytes в балансе пользователя. Отсутствие сверки также делает невозможным ответ на вопрос саппорта «почему у пользователя списано 520 GB» — нет способа доказать корректность.

**Что дописать.** Добавить в §5.9 пункт Reconciliation: (1) ежечасный джоб сверки Σ(charged_bytes фактов за период) с приращением consumed_billable_bytes в quota_period; расхождение != 0 — критический алерт (§5.14 Alerts); (2) ежесуточная сверка Σ(raw_bytes по пользователям ноды) с сетевым трафиком интерфейса ноды (§4.7) с допуском на оверхед; выход за коридор (например ±15%) — алерт о вероятной утечке/недоучёте; (3) контроль непрерывности: пропуск report_seq (dim-02) или неизвестный counter_epoch (dim-01) фиксируется как traffic_gap с оценкой объёма и попадает в отчёт; (4) хранить на балансе пользователя ссылку на последний применённый факт, чтобы любое списание можно было раскрутить до конкретного отчёта конкретной ноды (аудируемость §4.16 сейчас покрывает только административные действия, но не биллинговые списания).

## Домен Xray/VPN (14)

### XR-01 · BLOCKER · gap

**Формулировка.** §4.4 задаёт исчерпывающий перечень полей ноды, в котором нет ни одного параметра подключения (порт, dest, serverNames/SNI, private/public key, shortIds, fingerprint, flow, spiderX), при том что 'автоматическая генерация конфигураций' и subscription URL объявлены обязательными в §7. Постановка должна зафиксировать хотя бы категорию 'параметры inbound на ноду × протокол' и указать, что REALITY-ключевой материал хранится в Control Plane. Severity: major (не blocker) — §5.5 уже требует протокольной абстракции, поэтому речь о недостающем разделе, а не о переделке всей схемы.

**Основание в документе.** §4.4: «Для каждого сервера необходимо хранить: Name / Country / City / Provider / Public IP / IPv6 availability / Status / Created at / Last heartbeat». В документе отсутствуют слова port, serverNames, SNI, dest, publicKey, privateKey, shortIds, fingerprint, spiderX, flow, xtls-rprx-vision (проверено grep: 0 вхождений).

**Последствие.** Рабочая ссылка выглядит как vless://{uuid}@{host}:{port}?type=tcp&security=reality&sni={serverName}&fp=chrome&pbk={publicKey}&sid={shortId}&spx=%2F&flow=xtls-rprx-vision. Из перечисленных в §4.4 полей доступен только host (Public IP). Порт, pbk (публичная часть X25519-пары, генерируемой `xray x25519`), sid (hex-строка из списка shortIds inbound'а), sni (обязан входить в serverNames inbound'а и совпадать с реальным сертификатом узла dest), fp (uTLS-отпечаток) и flow брать неоткуда. При несовпадении sid/sni REALITY не отдаёт ошибку, а прозрачно проксирует соединение на dest — пользователь получает страницу реального сайта вместо VPN, а поддержка получает нерепродуцируемый инцидент «подписка есть, интернета нет». Генератор подписок — ядро продукта — на такой модели данных физически не реализуется, всю схему БД придётся переделывать.

**Что дописать.** Ввести в §4.4 сущность Inbound (нода × протокол) с обязательными полями: protocol, listen_port, для REALITY — dest (target host:port), server_names[], private_key, public_key, short_ids[], fingerprint (по умолчанию chrome), spider_x, flow (xtls-rprx-vision или пусто), transport/type (tcp), а для Trojan — domain, port, sni, alpn, путь к сертификату. Явно указать, что private_key/short_ids генерируются в Control Plane и пушатся на ноду, а public_key отдаётся клиенту.

### XR-02 · BLOCKER · wrong-assumption

**Формулировка.** §3.4/§5.4 сводят и протокольную конфигурацию, и список пользователей к одному номеру версии, из-за чего в постановке отсутствует требование применять изменения пользователей горячо (gRPC HandlerService) без рестарта Xray и без смены версии конфигурации. §2 уже различает 'синхронизацию конфигурации' и 'синхронизацию пользователей' — нужно довести это различие до модели версионирования и API §5.2 (отдельный курсор для user-level изменений). Severity: major, не blocker; тезис 'каждая продажа будет рвать соединения всем' — риск неверной реализации, а не утверждение документа.

**Основание в документе.** §2: Node Agent отвечает за «синхронизацию конфигурации; синхронизацию пользователей». §3.4: «Node Agent получает актуальное состояние и приводит локальную инфраструктуру к нему», «Desired configuration version / Applied configuration version». §5.2: API поддерживает «configuration sync; configuration versioning». Слова gRPC, HandlerService, AddUser, restart/рестарт/reload в документе отсутствуют.

**Последствие.** Модель «одна конфигурация — одна версия — применить целиком» подразумевает перезапись config.json и рестарт Xray. Xray-core не умеет частичный reload: `systemctl restart xray` обрывает все TCP/UDP-сессии всех пользователей ноды. При 10 000 пользователей и добавлении пользователя на ноду хотя бы раз в минуту нода будет находиться в состоянии постоянного разрыва. На самом деле добавление/удаление пользователя делается горячо, без рестарта: gRPC HandlerService.AlterInbound с AddUserOperation{tag, user{email, level, account: VLESSAccount/TrojanAccount}} / RemoveUserOperation{tag, email} через api-inbound (dokodemo-door на 127.0.0.1 + api.services=["HandlerService","StatsService","LoggerService"] + routing-правило inboundTag:api → outboundTag:api). Версионирование обязано различать два класса изменений, чего в §3.4/§5.4 нет.

**Что дописать.** Разделить desired state на два уровня: (1) inbound/protocol level — редкие изменения, требуют рестарта Xray, применяются только через drain/окно обслуживания; (2) user level — применяется горячо через gRPC HandlerService, без рестарта и без смены версии конфигурации. В §5.2 добавить в API отдельные операции user_add / user_remove / user_sync (полная сверка списка) с их собственным курсором версии, отдельным от config_version. Прописать требование, что api-inbound Xray обязателен и слушает только localhost.

### XR-03 · BLOCKER · gap

**Формулировка.** Постановка требует пер-пользовательский учёт трафика и лимиты в MVP, но не фиксирует источник данных и его семантику: стабильный идентификатор пользователя в статистике (email-тег), требование включить policy statsUser*, выбор между накопительным и reset-режимом опроса, поведение при рестарте Xray (обнуление счётчиков) и при недоступности Control Plane (буферизация дельт, идемпотентность приёма). Конкретный интервал опроса и формат batch_id — уже уровень архитектуры, а не постановки. Severity: major.

**Основание в документе.** §5.9: «VPN Node → Node Agent → Aggregation → Control Plane → Hourly / Daily records», «Необходимо хранить: Raw bytes / Billable bytes / Traffic multiplier / Node / Server group / Period». §4.12 требует Upload/Download/Total по пользователю и «Usage by server». Слова StatsService, QueryStats, email tag, policy, statsUserUplink в документе отсутствуют.

**Последствие.** В Xray персональные счётчики существуют, только если (а) у каждой client-записи задан уникальный email и (б) в policy.levels.{level} включены statsUserUplink/statsUserDownlink. Счётчики называются user>>>{email}>>>traffic>>>uplink|downlink, живут в памяти процесса и обнуляются при любом рестарте Xray. Читаются через StatsService.QueryStats; при reset=true возвращается дельта и счётчик обнуляется, при reset=false — накопительное значение. Из документа нельзя выбрать ни одну из двух несовместимых схем: с reset=true потерянный ответ агента = безвозвратно потерянный трафик пользователя (недосписание), с reset=false рестарт Xray даёт отрицательную дельту, а наивная реализация «взять значение как есть» даст двойное списание. Кроме того, email должен быть стабильным идентификатором подписки, иначе «Usage by server» и лимиты не сойдутся; трафик по протоколам вообще не разделяется, если один и тот же email используется в двух inbound'ах.

**Что дописать.** Зафиксировать: формат email = стабильный идентификатор (например sub_{subscription_id} или {user_id}.{protocol}); обязательный policy для statsUser*; периодичность опроса StatsService (например 30–60 с) с reset=true; идемпотентность приёма дельт в Control Plane (batch_id / node_id + monotonic seq, дедупликация); поведение при рестарте Xray (агент обязан сообщить факт рестарта, чтобы CP не трактовал обнуление как отрицательную дельту); политику при недоступности Control Plane (локальный буфер дельт на ноде и его максимальный объём/TTL).

### XR-04 · BLOCKER · wrong-assumption

**Формулировка.** Постановка описывает только исключение ноды из будущих ответов подписки и не задаёт ни SLA обновления профиля на клиенте, ни механизм автоматического переключения активного соединения. Это гэп (gap), а не ложное утверждение документа: §8 п.15 корректно говорит про 'новые subscription responses', а п.16 верен при ручном переключении пользователя. Требуется добавить: заголовок Profile-Update-Interval, форматы с автоселектором (sing-box urltest / Clash url-test) для клиентов, которые их поддерживают, и измеримое целевое время восстановления. Severity: major.

**Основание в документе.** §4.3: «Если сервер становится недоступным: Node → Offline — он автоматически исключается из выдаваемых пользователю конфигураций». §8, шаги 13–16: «Japan node выходит из строя. / Node автоматически получает Offline. / Japan исчезает из новых subscription responses. / Пользователь продолжает пользоваться другими серверами».

**Последствие.** Исключение сервера из ответа subscription URL не влияет ни на один уже установленный профиль клиента. v2rayNG, Shadowrocket, Streisand, Hiddify и sing-box обновляют remote-профиль по собственному расписанию (интервал в минутах-часах, у части клиентов автообновление выключено по умолчанию, у Clash/Mihomo типичный profile update interval — 24 часа). То есть после падения ноды пользователь до суток будет вручную тыкать в мёртвый сервер. Реальный быстрый фейловер обеспечивается не выдачей списка, а конструкциями на стороне клиента: urltest/url-test/fallback-группами outbound'ов, которые существуют только в форматах sing-box JSON и Clash/Mihomo YAML и принципиально невозможны в плоском base64 uri-list. Строка §8 п.16 «Пользователь продолжает пользоваться другими серверами» — ложное обещание, на котором построена вся ценность продукта, и оно закладывает неверные требования к MVP.

**Что дописать.** Переписать §4.3: разделить «исключение из будущих ответов подписки» (SLA = интервал обновления клиента) и «фейловер активного соединения». Для последнего в MVP задать: отдача форматов с автоселектором (sing-box urltest / Clash url-test-group) для клиентов, которые их поддерживают; заголовки Profile-Update-Interval в ответе подписки; явное указание пользователю в UI, что после падения ноды нужно обновить подписку; целевое время «нода упала → пользователь работает» как измеримое требование.

### XR-05 · BLOCKER · wrong-assumption

**Формулировка.** §5.6 противоречит §4.2/§7: base64 uri-list и sing-box JSON отнесены в 'будущее', хотя без них перечисленные в §4.2 клиенты не обслуживаются уже в MVP; сам термин 'Universal subscription URL' не определён (один URL с контент-негоциацией по User-Agent или один формат — из текста неясно). В MVP требуется минимум два генератора (base64 uri-list + sing-box JSON) и правило выбора формата; Clash/Mihomo YAML в §4.2 не заявлены и в MVP не обязательны. Аргумент про заголовок Subscription-Userinfo нужно переформулировать как рекомендацию (в §4.2 речь про личный кабинет, а не про UI клиента). Severity: major.

**Основание в документе.** §5.6: «Первоначально: Universal subscription URL», а «Clash / Mihomo / sing-box / Base64 / Client-specific formats» отнесены к «В будущем». При этом §4.2 требует совместимости с «Shadowrocket; v2rayNG; Streisand; Hiddify; sing-box» уже на первом этапе.

**Последствие.** Универсального формата не существует. v2rayNG/Shadowrocket/Streisand потребляют base64 от списка URI (vless://, trojan://, по строке на сервер). sing-box в качестве remote profile ожидает свой JSON-конфиг (outbounds + urltest + route). Clash/Mihomo — YAML с proxies/proxy-groups. Hiddify конвертирует сам, но остальные — нет. Значит уже в MVP нужны минимум три генератора и роутинг по User-Agent запроса, то есть §5.6 неверно отправляет обязательную работу в «будущее» и приведёт к переделке эндпоинта подписки. Отдельно: §4.2 требует показывать «доступный трафик / использованный трафик», но внутри клиента эти цифры берутся исключительно из HTTP-заголовка ответа подписки Subscription-Userinfo: upload=…; download=…; total=…; expire=… — в документе он не упомянут ни разу, из-за чего квота и дата окончания не появятся ни в одном из перечисленных клиентов.

**Что дописать.** В §5.6 перенести в MVP: (1) base64 uri-list, (2) sing-box JSON, (3) Clash/Mihomo YAML; описать выбор формата по User-Agent + явному суффиксу URL (?format=singbox). Добавить обязательные заголовки ответа: Subscription-Userinfo (upload/download/total/expire в байтах и unix-времени, с указанием, отдаётся ли billable или raw), Profile-Update-Interval, Profile-Title/content-disposition. Определить поведение при истёкшей подписке (пустой ответ клиенты часто игнорируют, сохраняя старый профиль — нужен явный контракт).

### XR-06 · BLOCKER · gap

**Формулировка.** Постановка не выбирает схему транспортной безопасности для Trojan: либо TLS с валидным сертификатом (тогда нужны поле FQDN у ноды, DNS-запись, ACME-выпуск/продление, мониторинг срока и шаги в онбординге §4.5, а также сценарий смены IP по §3.2), либо Trojan поверх REALITY (тогда сертификат и домен не нужны, но параметры REALITY обязаны появиться в модели ноды — см. dim-01). Дополнительно не зафиксировано распределение портов между inbound'ами REALITY и Trojan на одном IP. Severity: major, не blocker.

**Основание в документе.** Trojan заявлен в §1 («Trojan»), в §4.10 (Protocols: VLESS Reality, Trojan) и в §7 MVP. При этом в §4.4 нет поля domain, а слова «сертификат», TLS (кроме «HTTPS / mTLS» в §3.3 про канал агента), ACME, Let's Encrypt в документе отсутствуют. Онбординг §4.5 из 10 шагов заканчивается «Node becomes Active» и не содержит ни DNS-записи, ни выпуска сертификата.

**Последствие.** Trojan — это TLS-туннель: клиент устанавливает обычный TLS к домену и проверяет сертификат. Без валидного сертификата (или с allowInsecure=1) соединение либо не поднимется, либо станет тривиально детектируемым активным пробингом, а часть клиентов откажется подключаться. Отсюда следуют требования, которых нет: A/AAAA-запись на каждую ноду, автоматический выпуск и продление сертификата (ACME HTTP-01 требует открытый 80/tcp, DNS-01 — API DNS-провайдера и токен в secrets), мониторинг срока действия. Дополнительно: REALITY и Trojan обычно оба претендуют на 443/tcp одного IP — нужен явный выбор (разные порты, второй IP, либо REALITY dest → локальный TLS-сервер с Trojan), иначе конфигурация ноды просто не соберётся. Наконец, это ломает §3.2: пересозданный VPS получает новый IP, а значит требует обновления DNS и, возможно, повторного выпуска сертификата — в схеме «Bootstrap → Node Active» этого шага нет.

**Что дописать.** Добавить в модель ноды поля domain/fqdn, cert_provider, cert_expires_at, acme_challenge_type; в §4.5 — шаги «создать/обновить DNS-запись» и «выпустить сертификат», в §4.6 — статус/алерт по истекающему сертификату. Явно зафиксировать распределение портов между REALITY и Trojan на одной ноде и требование к DNS-провайдеру с API.

### XR-07 · BLOCKER · contradiction

**Формулировка.** Противоречие есть, но локальное: §4.13 требует базовый Device limit в MVP, а §6.2 ('Max devices') относит его же к необязательным возможностям — нужно устранить именно эту строку. Содержательный гэп: в Xray нет понятия 'устройство', поэтому постановка обязана определить, что именно измеряется (уникальные source IP на email), источник данных (GetStatsOnline с минимальной версией Xray или парсинг access.log), окно и место агрегации (глобально в Control Plane, а не на ноде) и действие при превышении. Утверждение о том, что RemoveUser разрывает активные сессии, неверно: Xray не даёт операции принудительного разрыва вовсе, уже установленные соединения живут до закрытия — это и есть дополнительная проблема. Severity: major.

**Основание в документе.** §4.10 (тариф): «Device limit / Concurrent connection limit». §4.13: «В MVP необходимо предусмотреть хотя бы базовое ограничение: Device limit». §6.2 «Ограничение одновременных подключений» находится в разделе «6. Будущие возможности... не являются обязательными для MVP», и Phase 2 в §7 содержит «concurrent connection limits».

**Последствие.** Во-первых, прямое противоречие: одно и то же ограничение одновременно обязательно в MVP и отложено в Phase 2 — команда не сможет оценить объём работ. Во-вторых, в Xray нет сущности «устройство»: один VLESS UUID / Trojan-пароль используется всеми устройствами пользователя одновременно, и ядро это не различает. Практически измеримо только число уникальных исходящих IP на один email, и получить его можно двумя способами: (а) через StatsService (GetStatsOnline / список онлайн-IP по email — только в свежих версиях Xray-core), либо (б) парсингом access.log (log.access + loglevel: info, строки содержат email и source IP), как это делают 3x-ui-подобные панели, что требует включённого лога, дискового I/O и обработки на агенте. В-третьих, лимит по замыслу глобальный (устройства пользователя размазаны по нодам), а измерение — локальное на каждой ноде, значит нужен агрегатор в Control Plane и решение о задержке принятия решения. В-четвёртых, у Xray нет операции «разорвать сессию»: единственный способ выкинуть лишнее устройство — RemoveUser + AddUser (рвёт все сессии этого пользователя) или блокировка IP файрволом. Ничего из этого нет в §5.2 (API Node Agent) и §4.7.

**Что дописать.** Устранить противоречие: либо убрать Device limit из MVP и оставить его декоративным полем тарифа, либо описать механику целиком — источник данных (GetStatsOnline с минимальной версией Xray или парсинг access.log), период агрегации, глобальное окно подсчёта уникальных IP, действие при превышении (уведомление / RemoveUser+AddUser / firewall drop) и его побочный эффект в виде разрыва всех сессий пользователя. Добавить соответствующий метод в API Node Agent §5.2.

### XR-08 · BLOCKER · gap

**Формулировка.** Формулировку стоит сузить до трёх конкретных пробелов: (1) один домен подписки без резервных зеркал, (2) отсутствие статуса/сигнала 'нода недоступна из страны X' и внешних проб достижимости — heartbeat 'нода → Control Plane' измеряет не то, (3) отсутствие процедуры смены IP ноды (поле Public IP без истории и без регламента перевыдачи конфигураций). Severity: major — это гэп по объёму MVP, а не внутреннее противоречие.

**Основание в документе.** §4.2: «https://sub.domain.com/s/{secure-random-token}» — единственный домен подписки. §4.6 перечисляет статусы «Pending / Provisioning / Active / Degraded / Maintenance / Offline / Disabled». §4.7: «Node должен регулярно отправлять heartbeat... При отсутствии heartbeat сервер автоматически считается Offline». Слова «заблокирован», DPI, «ротация IP», «резервный домен» в документе отсутствуют (grep: 0; «ротаци» встречается один раз — про секреты в §5.13).

**Последствие.** Основной режим отказа этого класса сервисов — не падение VPS, а блокировка. (1) Домен подписки sub.domain.com блокируется/отравляется DNS в стране пользователя — тогда клиент вообще не может получить обновлённый список серверов, то есть механизм из §4.3 (единственный заявленный механизм фейловера) отключается ровно в момент, когда он нужен. (2) IP ноды блокируется в стране X: нода при этом жива, heartbeat идёт исправно, CPU в норме, статус остаётся Active, и §4.3 никогда не исключит её из подписки — пользователи из страны X получают «рабочий» сервер, который у них не работает. Heartbeat строится «нода → Control Plane» и по определению не измеряет достижимость «пользователь из страны X → нода». (3) Смена IP ноды не предусмотрена моделью данных (одно поле Public IP, без истории и без процедуры пере-выдачи конфигураций). Проектирование без этих сценариев приведёт к переделке модели статусов, health-check и эндпоинта подписки.

**Что дописать.** Добавить: (а) множественные домены/зеркала подписки (набор доменов + правило выдачи резервных ссылок в UI и в теле подписки), требование не хардкодить один домен в клиентские конфиги; (б) сущность reachability по парам (node × country/ISP) с внешними пробами из целевых стран и/или телеметрией клиентов, отдельный статус ноды вида BlockedIn(countries), влияющий на выдачу подписки конкретному пользователю; (в) процедуру смены IP ноды: поле current_ip + история, использование FQDN в ссылках, регламент пере-выдачи конфигураций после ротации.

### XR-09 · MAJOR · gap

**Формулировка.** Отсутствует модель VPN-credentials пользователя (UUID для VLESS, пароль для Trojan) и решение «общий credential vs per-node»

**Основание в документе.** §4.15 (Users) содержит действие «сброс VPN credentials», §5.3 «Private credential» относится к identity ноды (mTLS), §5.13 перечисляет «private keys» в контексте хранения секретов. Слов UUID/uuid, «пароль Trojan», «per-node credential» в документе нет (grep: 0).

**Последствие.** Идентификатор пользователя в Xray — это UUID (VLESS) и пароль (Trojan); он же попадает в каждую ссылку подписки и он же служит ключом сопоставления статистики (email). Не выбран базовый вариант: один UUID на все ноды (простая генерация, но утечка конфига с одной ноды компрометирует доступ ко всем, а отзыв требует fan-out RemoveUser по всем 200 нодам) либо отдельный credential на пару (пользователь × нода/протокол) (больше строк в БД и сложнее выдача, зато точечный отзыв и точная атрибуция). Это структурное решение: оно определяет схему БД, содержимое подписки, семантику «сброса credentials» и объём операции при блокировке пользователя. Принять его после начала разработки = миграция всей таблицы пользователей и всех конфигураций нод.

**Что дописать.** Добавить раздел «VPN Identity»: сущность user_credential(user_id, protocol, node_id|null, uuid|password, created_at, revoked_at), выбранная стратегия (глобальный или per-node), правило генерации email-тега для статистики, семантика операции «сброс credentials» (какие ноды затрагиваются, сколько времени занимает fan-out, что видит пользователь) и требование к отзыву при блокировке/окончании подписки.

### XR-10 · MAJOR · wrong-assumption

**Формулировка.** Сценарий пересоздания ноды (§3.2, §8 п.17–21) не описывает судьбу уже скачанных пользователями конфигураций: у нового VPS другой IP, а при генерации REALITY-пары на ноде — ещё и другие pbk/shortIds, поэтому 'Новый сервер снова появляется в subscription URL' не означает восстановления связи до следующего обновления профиля клиентом. Требуется явно записать, что ключевой материал и порты — состояние Control Plane (это согласуется с §3.1, но не выражено в §4.4), и описать процедуру смены адреса ноды (FQDN вместо голого IP либо принудительная инвалидация подписок). Формулировку 'постановка толкает к генерации ключей на ноде' снять — §3.1 требует обратного. Severity: major.

**Основание в документе.** §3.2: «Server destroyed → New VPS created → Bootstrap script executed → Node Agent installed → Node registered → Configuration synchronized → Node Active». §8, шаги 17–21: «Администратор создаёт новый Japan VPS. / Устанавливает Node Agent. / Node автоматически получает конфигурацию. / Node становится Active. / Новый сервер снова появляется в subscription URL». В документе отсутствует указание, где генерируется X25519-пара REALITY.

**Последствие.** Если privateKey REALITY и shortIds генерируются на ноде при bootstrap (типовой путь: `xray x25519` в скрипте установки), у пересозданной ноды будет другая пара ключей и другой IP. Все клиенты, у которых профиль уже скачан, продолжат ходить со старыми pbk/sid на старый IP — соединение не поднимется, и восстановится оно только после следующего автообновления подписки (см. dim-04, до суток). При этом §3.1 объявляет Control Plane единственным источником истины, но в §4.4 нет полей для хранения ключевого материала ноды, то есть текущая постановка прямо толкает разработчика к генерации ключей на ноде.

**Что дописать.** Явно записать: REALITY private_key/public_key/short_ids и назначенные порты — состояние Control Plane, генерируется централизованно и пушится агенту при первом sync; пересозданная нода с тем же node_id получает те же ключи. Для смены IP описать отдельный сценарий (обновление адреса ноды + принудительная инвалидация подписки, либо использование доменного имени вместо голого IP в ссылках, чтобы смена IP решалась DNS).

### XR-11 · MAJOR · structure

**Формулировка.** Переформулировать как дополнение к dim-01, а не отдельный блокер: §5.5 уже декларирует нужное требование (расширяемость по протоколам), недостаёт лишь указания, что параметры протокола принадлежат паре нода×протокол, а не самой ноде. Самостоятельная часть находки — WireGuard: он не укладывается ни в модель 'один credential — много нод', ни в subscription URL перечисленных в §4.2 клиентов и требует собственного адресного плана; §6.6 перечисляет его наравне с прокси-протоколами без оговорки. Severity: minor/major, конкретная схема хранения (JSONB) — вне объёма постановки.

**Основание в документе.** §4.4: «изменять доступные протоколы» и плоский список полей ноды. §5.5: «Protocol Provider / VLESS Provider / Trojan Provider / Hysteria Provider / WireGuard Provider», «Архитектура должна позволять добавлять новые VPN-протоколы без полного переписывания системы».

**Последствие.** Наборы параметров у протоколов не пересекаются: VLESS-REALITY требует dest/serverNames/shortIds/privateKey/flow/fingerprint; Trojan — домен, сертификат, alpn; Hysteria2 — UDP-порт, пароль, obfs (salamander) и параметры bandwidth up/down; WireGuard — вообще не прокси: пара ключей на пир, выделение IP-адреса из подсети на каждое устройство, отсутствие понятия «подписка» в привычном виде (перечисленные в §4.2 клиенты, кроме sing-box/Hiddify, не потребляют WG из subscription URL). Если «доступные протоколы» — это чекбоксы на ноде, то любое добавление протокола потребует новых колонок в таблице нод и переписывания генератора подписок, то есть ровно того, чего §5.5 запрещает.

**Что дописать.** Заменить «список протоколов на ноде» на сущность node_inbound(node_id, protocol, enabled, listen_port, params JSONB) с версионируемой JSON-схемой параметров на каждый протокол и с валидацией на стороне Control Plane; генератор подписки описать как набор рендереров (протокол × формат клиента). Отдельно зафиксировать, что WireGuard не вписывается в модель «один credential — много нод» и требует собственного адресного плана, либо исключить его из §5.5/§6.6.

### XR-12 · MAJOR · gap

**Формулировка.** Уточнение к формулировке: единственная неточность — 'единственный способ' отключения. Помимо RemoveUser доступны и другие рычаги (исключение из выдачи подписки, блокировка на уровне ноды), а RemoveUser не разрывает уже установленные сессии, поэтому требование к постановке — задать не только команду, но и целевую задержку, допустимый перерасход, локальный предохранитель на ноде при потере связи с Control Plane и обратный сценарий восстановления доступа.

**Основание в документе.** §4.11 требует лимиты «Unlimited / Fixed subscription limit / Monthly limit / Custom limit», §4.17 содержит событие «Traffic limit reached». В документе отсутствует описание того, что происходит на ноде при исчерпании лимита.

**Последствие.** Xray-core не умеет отключать пользователя по достижении объёма трафика — это чисто внешняя логика. Реально нужно: Control Plane по агрегированным дельтам обнаруживает превышение и рассылает RemoveUser (gRPC HandlerService) по всем нодам, где пользователь присутствует. Отсюда два неописанных следствия. Первое — задержка: при опросе StatsService раз в 30–60 секунд и последующем fan-out на N нод пользователь на гигабитном канале успевает перерасходовать лимит на единицы гигабайт, а при отвале связи агента с CP — на порядки больше; должно быть явно решено, допустим ли перерасход и есть ли локальный предохранитель на ноде. Второе — отсутствие описания обратной операции (продление/докупка трафика → AddUser на все ноды) и её времени. Без этого биллинг и лимиты будут реализованы как «уведомление без отключения».

**Что дописать.** Описать пайплайн enforcement: порог обнаружения → команда quota_exceeded в API Node Agent §5.2 → RemoveUser на всех нодах пользователя → отражение в подписке; задать целевую задержку и допустимый перерасход; предусмотреть локальный предохранитель на ноде (лимит, переданный агенту заранее, чтобы отключение работало при потере связи с Control Plane); описать обратный сценарий восстановления доступа.

### XR-13 · MAJOR · wrong-assumption

**Формулировка.** Категория — underspecified, а не wrong-assumption: §5.10 не указывает, какой трафик служит знаменателем для Cost per GB, а §4.7 не определяет источник метрик 'network traffic' и 'количество активных соединений'. Требуется зафиксировать два независимых источника — пользовательский трафик из StatsService (в биллинг) и интерфейсный трафик ноды (в экономику и сверку с инвойсом провайдера), — поскольку первый систематически меньше второго и на ноде под активным пробингом расходится существенно. Severity: minor/major.

**Основание в документе.** §5.10: «Для сервера желательно хранить: Monthly server cost / Traffic cost / Provider / Currency», «В будущем можно рассчитывать: Revenue per node / Cost per GB / Profitability». §4.7 требует отслеживать «network traffic» и «количество активных соединений».

**Последствие.** uplink/downlink в StatsService считаются на уровне прокси-конвейера и не включают накладные расходы TCP/IP и TLS-фрейминга, ретрансмиссии, а также весь трафик, не привязанный к пользователю: handshake-пробы сканеров, которые REALITY проксирует на dest (при активном сканировании это могут быть заметные объёмы), трафик Node Agent, обновления системы. Хостер тарифицирует трафик интерфейса. Расхождение обычно составляет единицы-десятки процентов, а на ноде под пробингом — существенно больше. Считать «Cost per GB», деля стоимость сервера на сумму пользовательских счётчиков, значит систематически завышать себестоимость гигабайта и принимать неверные решения о тарифах и Traffic Multiplier. Отдельно: «количество активных соединений» из §4.7 у Xray не экспонируется как метрика по умолчанию — источник данных не определён (онлайн-пользователи через StatsService, либо счёт established-соединений через ss/conntrack, либо inbound-счётчики при включённых policy.system.statsInbound*).

**Что дописать.** Ввести два независимых источника: пользовательский трафик (StatsService, идёт в биллинг) и интерфейсный трафик ноды (/proc/net/dev или vnstat, идёт в экономику и в сверку с инвойсом хостера); в §5.9/§5.10 явно указать, какой из них используется для Cost per GB, и требовать хранения коэффициента расхождения. Для §4.7 указать источник каждой метрики, включая «активные соединения», и включение policy.system.statsInboundUplink/Downlink.

### XR-14 · MINOR · underspecified

**Формулировка.** Основная часть находки — не коды ответа, а неопределённая семантика перевыпуска: §4.2 обещает 'отключить старую ссылку', но пока не зафиксировано, ротируются ли при этом VPN-credentials, старый скачанный конфиг остаётся полностью рабочим — обещание в UI не соответствует поведению системы (связано с dim-08). Дополнительно требуется контракт ответа эндпоинта для состояний active / expired / traffic_exceeded / blocked / revoked_token. Severity: major, а не minor.

**Основание в документе.** §4.2: «Пользователь получает персональную subscription URL... скопировать ссылку; открыть QR-код; перевыпустить ссылку; отключить старую ссылку». §4.3 описывает только формирование списка серверов с учётом «активности подписки».

**Последствие.** Ответ подписки — единственный канал коммуникации с клиентом. Если при истёкшей подписке вернуть пустое тело или 404, v2rayNG/Shadowrocket/Clash обычно сохраняют предыдущий профиль и показывают невнятную ошибку обновления, то есть пользователь не узнает причину и пойдёт в поддержку; распространённая практика — возвращать один фиктивный сервер с именем-сообщением («Подписка истекла») плюс корректный заголовок Subscription-Userinfo с expire в прошлом. Также не определено: сам токен подписки является полноценным носителем доступа (кто получил URL — получил рабочие credentials), поэтому «перевыпустить ссылку» обязано либо ротировать UUID/пароль (разрывая сессии на всех устройствах), либо не ротировать (и тогда старые скачанные конфиги продолжают работать после «отключения старой ссылки» — прямое противоречие ожиданию пользователя).

**Что дописать.** Описать контракт эндпоинта: коды ответа и тело для состояний active / expired / traffic_exceeded / blocked / revoked_token; обязательные заголовки; и явно зафиксировать, ротируются ли VPN-credentials при перевыпуске ссылки, с описанием последствий (обрыв активных сессий, необходимость fan-out RemoveUser/AddUser по всем нодам).

## Архитектура (12)

### AR-01 · BLOCKER · wrong-assumption

**Формулировка.** Модель распространения состояния на ноды не специфицирована, а единственная иллюстрация (§3.4) подразумевает полный снапшот с поимённым списком пользователей; при заявленных 100k пользователей / 200 нод (§5.7) это даёт конфиг в десятки МБ на ноду и не имеет механизма инкрементального обновления. В постановке нужно явно зафиксировать: (1) разделение потоков «состав пользователей» и «структурная конфигурация ноды»; (2) инкрементальную доставку состава (add/remove/update с монотонным per-node seq, периодический снапшот и сверка контрольной суммы); (3) горячее применение состава через Xray HandlerService без рестарта, рестарт — только для структурной части; (4) решение «все пользователи на всех нодах vs подмножества»; (5) числовые потолки ёмкости (размер конфига, пользователей на ноду, время применения). Количественные оценки трафика/RSS в находке — оценки наихудшего сценария, а не следствие текста документа.

**Основание в документе.** §3.4: «Users:
- User A
- User B
- User C

Config version:
145» и «Node Agent получает актуальное состояние и приводит локальную инфраструктуру к нему»; §5.7: «100 000 users», «200 nodes», «без изменения базовой архитектуры».

**Последствие.** Арифметика при 100k/200: запись клиента VLESS в inbound Xray ({id, flow, email, level}) — ~110–130 байт JSON, Trojan ({password, email, level}) — ~80–90 байт. Два inbound-а (§1: VLESS Reality + Trojan) на 100k пользователей = 20–40 МБ конфига на КАЖДУЮ ноду. Разбор такого JSON в Go + построение индекса валидаторов + по два счётчика статистики на пользователя (они обязательны, иначе §4.11/§4.12 не реализуемы) — это 0.5–1 ГБ RSS и единицы–десятки секунд на применение на типовом VPN-VPS 1–2 vCPU / 2 ГБ; нода уходит в OOM или в многосекундный простой. Частота изменений: 100k подписок по 30 дней (§4.10 «Duration: 30 days») дают ~3 300 истечений в сутки + сопоставимое число активаций/продлений + блокировки (§4.15 «блокировка»), исчерпание лимита трафика (§4.17 «Traffic limit reached»), перевыпуск ссылки и сброс credentials (§4.2 «перевыпустить ссылку», §4.15 «сброс VPN credentials») ≈ 8–10 тыс. изменений состава пользователей в сутки, т.е. одно изменение каждые ~10 секунд, с пиками при ночном sweep истечений. По модели §3.4 каждое такое изменение инвалидирует desired-конфиг всех нод, где пользователь доступен (для группы Europe это практически весь парк). При heartbeat/poll раз в 30 с (§4.7) версия будет новой почти на каждом опросе: 200 нод × 2 880 опросов/сутки × 25 МБ ≈ 14 ТБ/сутки исходящего трафика Control Plane (~1.3 Гбит/с постоянно), CP при этом обязан рендерить 200 конфигов по 100k строк каждые 30 с (~700 тыс. строк/с из PostgreSQL), а каждая нода — перезагружать Xray каждые 30 с, разрывая все живые VPN-соединения. Команда, начав кодировать по §3.4, реализует полный конфиг-снапшот и упрётся в стену уже на 5–10 тыс. пользователей — с переписыванием и Node Agent, и Node API, и модели данных.

**Что дописать.** Зафиксировать в постановке: (1) поток «состав пользователей» отделён от потока «конфигурация ноды» — это два независимых ресурса Node API с разными версиями и разной частотой; (2) пользователи доставляются инкрементальными дельтами (add/remove/update) с монотонным per-node sequence и семантикой since=<seq>, плюс периодический снапшот и сверка контрольной суммы (хеш/Merkle множества пользователей) для устранения дрейфа; (3) применение изменений состава — через Xray HandlerService gRPC (AddUser/RemoveUser) без рестарта процесса; рестарт Xray допустим только при изменении структурной части (inbounds, порты, Reality-ключи, routing); (4) явно принять и записать решение «все пользователи на всех нодах» vs «подмножества по Server Group», с правилом пересчёта состава при изменении тарифа/группы/статуса; (5) внести числовые потолки: макс. размер конфига ноды, макс. RSS Xray, макс. время применения одного изменения (propagation SLA), макс. число пользователей на ноду.

### AR-02 · BLOCKER · gap

**Формулировка.** Не описано ни требование HA для Control Plane, ни поведение сервиса при недоступности Control Plane

**Основание в документе.** §3.5 описывает только одно направление: «Выход из строя отдельной VPN-ноды не должен приводить к потере Control Plane». Требований к доступности самого Control Plane, к его резервированию и к деградации сервиса при его падении в документе отсутствует; §5.14 упоминает алерт «Control Plane failure», но без требований к последствиям.

**Последствие.** Сценарий «CP недоступен 2 часа» не имеет определённого поведения ни по одному из четырёх критичных вопросов. (1) Работает ли VPN: Node Agent не смог синхронизироваться — он оставляет последний конфиг или очищает его? Спецификация не отвечает, и это ровно тот выбор, который разработчик агента сделает молча и произвольно; выбор «очистить» кладёт весь сервис вместе с CP. (2) Работает ли выдача подписки: subscription URL обслуживается Control Plane (§4.2, §4.3 «список серверов ... должен формироваться динамически»), значит при падении CP новые устройства и перевыпущенные ссылки не работают вовсе. (3) Что с учётом трафика: требований к локальной буферизации статистики на ноде, к её объёму, TTL и поведению при переполнении в документе отсутствует — за 2 часа простоя CP теряется или задваивается трафик всех 100k пользователей, то есть деньги. (4) Что с истёкшими подписками: в desired state (§3.4) у пользователя нет ни expires_at, ни лимита — нода физически не может применить срок действия локально, поэтому при долгом простое CP все истёкшие пользователи продолжают получать сервис бесплатно. Без явного решения fail-open/fail-closed по каждому пункту нельзя проектировать ни Node Agent, ни модель desired state.

**Что дописать.** Добавить раздел «Отказ Control Plane» с явными требованиями: режим работы нод при недоступности CP (fail-open с ограничением по времени: работать по последнему конфигу не дольше N часов/суток), обязательные поля валидности в desired state пользователя (expires_at, traffic_limit) для локального enforcement, требования к локальному персистентному буферу статистики (объём, TTL, поведение при переполнении, дедупликация при досылке), деградированный режим выдачи подписки (статический кеш последнего ответа, отдельный failure domain), требуемая доступность CP (целевой % и допустимое окно простоя), а также состав HA: минимум два инстанса API за балансировщиком и standby базы.

### AR-03 · BLOCKER · underspecified

**Формулировка.** §5.2 перечисляет «commands» как возможность Node API без описания контракта: не заданы модель доставки (поллинг/long-poll), очередь и порядок применения, идемпотентность по command_id, TTL и отмена просроченных команд, статусы жизненного цикла и отчёт об ошибке, запрет команд для нод в Offline/Disabled. Не зафиксировано и соотношение императивного канала с decl-моделью §3.4 (правило: всё декларативно выразимое идёт через desired state, команды — исключение). Ссылка на §3.3 как на признак персистентного соединения некорректна — там задано только направление инициации соединения.

**Основание в документе.** §5.2: список возможностей Node API заканчивается пунктом «commands» без каких-либо деталей; §3.4 называется «Pull / Desired State модель»; §3.3: «Node Agent самостоятельно устанавливает исходящее защищённое соединение с центральной системой». Слов long-poll, websocket, gRPC, очередь команд, идемпотентность в документе отсутствует.

**Последствие.** Императивные команды («перезапусти Xray», «обнови агент», «ротируй credentials») по своей природе не описываются desired-state-моделью, поэтому §5.2 вводит второй, императивный канал, никак не согласованный с §3.4. Не определено главное — как команда доезжает: если через тот же поллинг раз в 30 с, то задержка операций админа до 30 секунд и любой «restart» может быть прочитан дважды при ретрае; если это persistent-соединение (что подразумевает формулировка §3.3 «устанавливает исходящее защищённое соединение»), то это другая архитектура CP — 200 висящих соединений, sticky-состояние на инстансах API, невозможность держать их в наивном Compose-бэкенде за reverse proxy с таймаутами. Конкретные отказы, которые это породит: (а) агент получил команду restart, выполнил, но ответ потерялся — CP повторяет, нода уходит в цикл рестартов с разрывом соединений пользователей; (б) команды «rotate credentials» и «apply config» доставлены в обратном порядке — нода остаётся с ключами, которых нет в CP, и требует ручного вмешательства по SSH, что прямо нарушает §3.3; (в) команда, выданная ноде, которая была Offline трое суток, применяется при возврате — без TTL это «команда из прошлого», отменить её нечем.

**Что дописать.** Описать Node API командный канал явно: модель доставки (рекомендую long-poll поверх того же исходящего HTTPS, чтобы не вводить второй транспорт), очередь команд на ноду с монотонным command_id и строгим порядком применения, обязательную идемпотентность по command_id (повтор не выполняет действие второй раз), TTL команды и автоматическую отмену просроченных, статусы жизненного цикла (queued/delivered/running/succeeded/failed/expired/cancelled) с отчётом ноды и текстом ошибки, ограничение параллелизма, ручную отмену из админки и запрет команд для нод в Offline/Disabled. Явно записать, что императивные команды — исключение, а всё, что выразимо декларативно (протоколы, пользователи, версия Xray), идёт через desired state.

### AR-04 · BLOCKER · gap

**Формулировка.** Регистрация ноды: не описано, чем аутентифицируется нода при первичной регистрации и что именно проверяет админ при approve

**Основание в документе.** §4.5: «3. System generates bootstrap command», «6. Node Agent registers in Control Plane», «8. Admin approves node»; §5.3 требует «Каждая нода должна иметь собственную identity» и «Нельзя использовать единый credential для всех серверов», но что предъявляет нода в момент, когда identity ещё нет, в документе не описано.

**Последствие.** Классическая проблема первичного доверия (bootstrap trust) не решена, а §5.3 её только маскирует: правило «у каждой ноды своя identity» относится к состоянию после регистрации. Bootstrap command по §4.5 — это строка, которую админ копирует в консоль VPS; она неизбежно содержит какой-то секрет и оседает в истории shell, в скриншотах, в тикетах, в §4.16 Audit Log. Не задано: одноразовый ли этот токен, есть ли у него срок жизни, привязан ли он к конкретной записи ноды и к её ожидаемому IP, чем нода подтверждает владение ключом (CSR/attestation) и что именно админ верифицирует на шаге 8 — в документе нет ни одного проверяемого признака (отпечатка ключа, кода подтверждения, сверки IP). Атака прямолинейна: получивший bootstrap-строку регистрирует СВОЮ машину, админ видит в панели ожидаемое имя ноды и нажимает Approve, после чего злоумышленник по §3.4 получает desired state — то есть учётные данные всех пользователей — и весь трафик тех, кто на этот сервер подключится. То же самое произойдёт при повторном использовании одной bootstrap-строки на нескольких серверах, что §3.2 («заново создан») делает штатным сценарием.

Нужно зафиксировать: разделение минимум на две очереди с раздельными пулами воркеров и приоритетами, гарантию доставки (at-least-once) с обязательной идемпотентностью обработчиков, влияющих на биллинг, ретраи с backoff и dead-letter-очередь с алертом, требование переживания перезапуска брокером (технологически нейтрально — в §4.20 Redis назван лишь как компонент, не как брокер), и максимальное время нахождения задачи критичного пути в очереди как измеримый NFR.

**Основание в документе.** §5.8: «Долгие операции не должны блокировать API», «Для background jobs необходимо предусмотреть очередь», список задач: «отправка email; обработка статистики; генерация конфигураций; синхронизация; уведомления; backup jobs». §4.20 включает «Redis» и «Worker» без требований к persistence. Слова «идемпотент», «DLQ», «приоритет», «at-least-once» в документе отсутствуют.

**Последствие.** В один список сведены задачи с несовместимыми требованиями: «генерация конфигураций» и «синхронизация» — это критичный путь с бюджетом в секунды (см. dim-11), а «отправка email» и «backup jobs» — массовые и медленные. При единой очереди и общем пуле воркеров рассылка «Subscription expiring» (§4.17) по десяткам тысяч адресов или ночной backup займут воркеров, и блокировка пользователя, исчерпавшего лимит трафика, будет распространяться часами — то есть перестанет работать биллинговое ограничение §4.11. Второе: Redis в §4.20 без требования persistence — при перезапуске контейнера теряются задачи, в том числе задачи агрегации трафика (§5.9), то есть деньги. Третье: нет требования идемпотентности джоб при at-least-once доставке — повтор задачи «добавить трафик» или «начислить бонус промокода» (§4.14) выполнится дважды.

**Что дописать.** В §5.8 задать: разделение на минимум две очереди с раздельными пулами воркеров (критичный путь: генерация конфигураций, синхронизация, блокировки; фоновый: email, агрегация, бэкапы) и приоритеты; гарантию доставки (at-least-once) и обязательное требование идемпотентности обработчиков с ключом идемпотентности; политику ретраев с backoff и dead-letter-очередь с алертом; требование persistence брокера; максимальное время нахождения задачи критичного пути в очереди как измеримый NFR.

### AR-12 · MAJOR · gap

**Формулировка.** Отчёты о трафике от ноды к Control Plane не имеют требований к идемпотентности, дедупликации и порядку — при потере или повторе отчёта теряются или задваиваются деньги

**Основание в документе.** §5.2 перечисляет «traffic statistics» без деталей протокола; §5.9: «VPN Node → Node Agent → Aggregation → Control Plane → Hourly / Daily records», «Raw traffic events не должны бесконечно записываться в основную базу». Требований к идемпотентности отчёта, дедупликации, монотонной нумерации периодов, поведению при рассинхронизации часов ноды и повторной досылке в документе отсутствует.

**Последствие.** Статистика Xray читается как счётчики, и типовая реализация агрегации читает их со сбросом — то есть дельта существует ровно в одном экземпляре и в одном месте. Без описанного протокола любой из трёх штатных сбоев ведёт к денежной ошибке: (1) агент отправил отчёт, ответ CP не дошёл, агент повторяет — CP начисляет трафик дважды, пользователь досрочно упирается в лимит §4.11 и получает «Traffic limit reached» (§4.17); (2) агент упал между чтением со сбросом и отправкой — трафик потерян безвозвратно, дорогие ноды с multiplier 3x (§4.9) недосчитываются выручки; (3) часы ноды сдвинуты — трафик попадает в чужой hourly-бакет, а при связке с Traffic Multiplier (§5.9 требует хранить multiplier в записи) неверный период даст неверный коэффициент. Поскольку весь биллинг §4.9–§4.12 стоит на этих числах, протокол отчётности — часть контракта Node API, а не деталь реализации.

**Что дописать.** Описать в §5.2/§5.9 контракт отчёта о трафике: монотонный report_seq на ноду и явные границы периода (from/to с UTC), идемпотентный приём на стороне CP по (node_id, report_seq) с игнорированием дубликатов, персистентный локальный журнал непринятых отчётов на ноде с ограничением объёма и правилом досылки после восстановления связи, порядок применения отчётов, требование к синхронизации времени на нодах (NTP) и допустимому смещению, поведение CP при получении отчёта за уже закрытый период, а также требование фиксировать в записи применённый multiplier и его версию.

### SE-05 · BLOCKER · wrong-assumption

**Формулировка.** Отсутствует допущение о доверии: документ нигде не фиксирует, что нода находится вне периметра оператора и может быть скомпрометирована, изъята или снята снапшотом. Из-за этого §3.1 читается как разрешение хранить на VPS полный набор данных при наличии копии в центре, а §5.14 прямо предполагает Xray-логи на ноде. Отдельное следствие для §5.9: списание с лимита пользователя опирается на самоотчёт агента без идемпотентного идентификатора отчёта, монотонного счётчика и верхнего порога прироста за интервал — повтор после ретрая даёт двойное списание, сбойный или подменённый агент обнуляет лимиты пользователям ноды, и умножается это на коэффициент до 3x (§4.9).

**Основание в документе.** §2: «Отдельные VPN-серверы, расположенные у различных VPS-провайдеров и в разных странах». §3.1: «VPN-нода не должна быть единственным местом хранения критической информации» — сформулировано как требование к отказоустойчивости, а не к доверию. §5.9: «VPN Node → Node Agent → Aggregation → Control Plane». В документе отсутствует утверждение, что нода может быть скомпрометирована или изъята.

**Последствие.** Формулировка §3.1 «не должна быть единственным местом хранения» разрешает хранить на ноде вообще всё, лишь бы копия была в центре. При таком прочтении на VPS стороннего провайдера окажутся: полный список пользователей с credential, статистика потребления по пользователям и Xray-логи (§5.14 прямо перечисляет «Xray logs»). Изъятие или снапшот одного VPS = утечка клиентской базы и журналов соединений всего сервиса. Вторая, денежная проблема: биллинг по §4.9 (Billable traffic) строится на цифрах, которые сообщает сама нода, а множитель до 3x усиливает любую ошибку втрое. В постановке нет ни идемпотентности отчётов (повторная отправка после ретрая = двойное списание у пользователя), ни верхнего предела прироста за интервал, ни сверки с независимым счётчиком — сломанный или скомпрометированный агент обнулит лимиты всем пользователям ноды, и это будет выглядеть как штатная работа.

**Основание в документе.** В документе отсутствуют разделы об AUP/оферте, abuse-жалобах, DMCA и реакции на обращения VPS-провайдера. §4.6 перечисляет статусы ноды: «Pending / Provisioning / Active / Degraded / Maintenance / Offline / Disabled». §3.4: «Node Agent получает актуальное состояние и приводит локальную инфраструктуру к нему». §4.7: heartbeat «every 30 seconds».

**Последствие.** Исходящий трафик пользователей идёт с IP VPS-провайдера, и первым же операционным инцидентом станет abuse-письмо: спам с порта 25, сканирование чужих сетей, торренты/DMCA, брутфорс. Типичный провайдер даёт 24 часа на ответ, иначе выключает сервер — и по §4.7 он молча станет Offline, а по §4.3 просто исчезнет из подписок, то есть система воспримет коммерческую блокировку как техническую аварию. В постановке нет: (1) исходящих ограничений на ноде (блокировка 25/587, лимит новых соединений в секунду, блокировка RFC1918 и адресов метаданных облака — иначе нода становится SSRF-плацдармом в сеть Control Plane); (2) статуса ноды «Suspended by provider» и сценария реакции; (3) процедуры «найти пользователя по времени и порту» для ответа на жалобу — а она напрямую конфликтует с минимизацией логов (dim-07) и должна быть решена осознанно, а не по факту; (4) механизма мгновенного отключения конкретного пользователя на всех нодах — при pull-модели §3.4 заблокированный продолжает работать, пока нода не заберёт новую конфигурацию, и время этой задержки не задано; (5) AUP, на который можно сослаться при блокировке абонента, — без него блокировка юридически произвольна.

**Что дописать.** Добавить AUP/оферту в перечень артефактов MVP (§7 Operations). Задать обязательный egress-фильтр на ноде: блок 25/587, RFC1918 и 169.254.169.254, лимит concurrent connections и новых соединений в секунду на пользователя. Добавить статус ноды «Suspended by provider» в §4.6 и сценарий реакции. Задать SLA распространения команды revoke/ban отдельно от config sync (push-канал или опрос ≤ 30 секунд для команд) и внести «commands» из §5.2 в требование с числом. Принять и записать решение о минимальном наборе данных, достаточном для ответа на abuse-жалобу, и сроке их хранения, согласовав с политикой приватности.

### SE-13 · MAJOR · gap

**Формулировка.** Формулировку сохранить, сняв два преувеличения: (1) redeem-эндпоинт формально попадает под обобщённый пункт «API» в §5.12 — требуется не внесение в список, а отдельный порог попыток на аккаунт и на IP с блокировкой после N неудач; (2) «VPN-ABCD-EFGH» — пример, а не заданный формат; требование — зафиксировать минимальную энтропию кода и отбрасывание неверных кодов без обращения к БД, а не констатировать перебираемость. Остальное подтверждается: не определено, что считается уникальным пользователем для «Maximum uses per user» при открытой регистрации, и Device limit из §4.10/§4.13 не имеет механизма исполнения в MVP при том, что §6.2 переносит ограничение подключений в будущее.

**Основание в документе.** §4.14: свойства кода «Expiration date / Maximum uses / Maximum uses per user / Plan restriction / Traffic bonus / Duration bonus», формат «VPN-ABCD-EFGH». §4.1: «Open registration» с защитой «CAPTCHA; rate limiting; email verification». §4.10: тариф содержит «Device limit» и «Concurrent connection limit», §4.13: «В MVP необходимо предусмотреть хотя бы базовое ограничение: Device limit», при этом §6.2 «Ограничение одновременных подключений» отнесено к будущим возможностям.

**Последствие.** «Maximum uses per user» считает пользователя по аккаунту, а при открытой регистрации аккаунт стоит одного одноразового email: N регистраций = N бесплатных redeem-кодов, и убыток считается по billable-трафику, то есть на ноде с multiplier 3x утраивается (§4.9). Формат «VPN-ABCD-EFGH» — 8 значащих символов; при массовой генерации кодов (§4.14 «массово генерировать коды») пространство становится перебираемым, а endpoint активации кода в списке защищаемых §5.12 отсутствует («login; registration; password reset; subscription endpoints; API; Node API»).

**Что дописать.** Определить, что считается уникальным пользователем для лимитов промокодов: нормализация email (снятие плюс-адресации и точек), блок-лист disposable-доменов, опционально привязка телефона или платёжного инструмента; зафиксировать это как требование, а не как настройку. Внести endpoint активации промо/redeem-кода в §5.12 с лимитом попыток на аккаунт и на IP и блокировкой после N неудач. Задать энтропию кода ≥ 60 бит либо встроенную HMAC-контрольную сумму, чтобы неверный код отбрасывался без обращения к БД. Перенести минимальное исполнение Device/Concurrent limit в MVP хотя бы в виде счётчика уникальных источников на пользователя с алертом и мягким ограничением.

### SE-14 · MINOR · underspecified

Для Node API — лимит на идентичность ноды, а не на IP, плюс требование джиттера heartbeat и экспоненциального backoff на стороне агента (§5.2). Для subscription endpoint — лимит на токен, а не на IP, плюс отдельный порог enumeration по несуществующим токенам. Дополнить список: активация promo/redeem-кода, перевыпуск subscription URL, повторная отправка email verification.

### RQ-03 · BLOCKER · contradiction

**Формулировка.** Иерархия Traffic Multiplier не определяет правило разрешения, когда нода входит в несколько тарифицируемых групп (а §4.8 задаёт заведомо пересекающиеся группы Europe / Premium Europe / High Cost / Streaming, §4.4 разрешает менять «группы» во множественном числе). Дополнительно не заданы: поведение при отсутствии коэффициента, допустимый диапазон/шаг и правило округления billable_bytes, политика изменения множителя задним числом. ### RQ-04 · BLOCKER · wrong-assumption

**Формулировка.** Device limit сформулирован как решение без определения «устройства» и потому нереализуем однозначно. Уточнение: вариантов не три, а четыре — отдельный credential на устройство, подсчёт уникальных IP в окне, подсчёт одновременных соединений (вынесен в §6.2/Phase 2) и HWID-заголовок от клиента; последний отпадает, так как ни один из пяти клиентов, перечисленных в §4.2, его штатно не отправляет. В постановке нужно зафиксировать выбранную единицу учёта, окно измерения, действие при превышении и явно признать погрешность на CGNAT.

**Основание в документе.** §4.13: «В MVP необходимо предусмотреть хотя бы базовое ограничение: Device limit». §4.10: «Devices: 2» / «Devices: 5». §6.1 «Полноценное Device Management» (список устройств, last seen, отключение устройства) отнесено в «Будущие возможности». В документе отсутствует определение того, что считается «устройством» и как оно идентифицируется.

**Последствие.** В VLESS/Trojan пользователь — это один UUID/пароль; протокол не передаёт идентификатор устройства, поэтому «базовое ограничение» реализуемо только одним из трёх взаимоисключающих способов: (а) отдельный credential на каждое устройство — это меняет генерацию подписки, синхронизацию пользователей на ноды и механику §4.2 «перевыпустить ссылку / отключить старую ссылку»; (б) подсчёт уникальных IP в окне — даёт ложные срабатывания на мобильных сетях и CGNAT (один пользователь, десятки IP за час) и, наоборот, не ловит 5 устройств за одним домашним NAT; (в) подсчёт одновременных соединений — но это §6.2, вынесенный в Phase 2. Выбор (а) задним числом означает миграцию всех пользовательских credential и полную пересинхронизацию всех нод.

**Последствие.** Честная оценка по блокам: Node Agent + bootstrap-установщик + версионирование конфигурации + сбор статистики ≈ 2,5 чел.-мес.; конвейер трафика (multiplier, raw/billable, лимиты, агрегация) ≈ 2; подписка + генерация конфигураций VLESS Reality и Trojan + совместимость с пятью клиентами ≈ 1,5; auth, email-верификация, CAPTCHA, RBAC из 4 ролей, audit log ≈ 1,5; тарифы, подписки, промокоды и redeem-коды с массовой генерацией и экспортом ≈ 1,5; админка из 7 разделов + личный кабинет ≈ 2,5; ops (Compose, backup + DR, secrets, observability, rate limiting) ≈ 1,5. Требует проверки на конкретных версиях: по документации Marzban нода слушает порт 62050 и панель сама инициирует к ней соединение с клиентским сертификатом; по документации Remnawave нода слушает NODE_PORT=2222 и рекомендуется «Close NODE_PORT in the node firewall only for the IP panel», то есть соединение также идёт панель → нода.

**Последствие.** Это, вероятно, самая ценная и самая уникальная часть постановки: outbound-only агент снимает требование открывать порт на каждой ноде и белого списка IP панели, и позволяет ноды за NAT. Но поскольку документ не отмечает это как отличие, при первом же техническом упрощении («давайте панель будет ходить на ноду, это проще») требование будет отброшено — и вместе с ним исчезнет одно из немногих обоснований собственной разработки. Обратный риск того же порядка: pull-модель требует иного дизайна доставки команд (long-poll / очередь команд на стороне Control Plane), чего §5.2 не описывает — там просто перечислено «commands».

**Что дописать.** В разделе прайор-арта явно записать: «направление соединения нода → Control Plane — отличие от Marzban/Remnawave, где панель инициирует соединение к ноде», с проверенной ссылкой. В §5.2 дописать транспорт для команд в pull-модели (long-poll, интервал, backoff, семантика at-least-once, идемпотентность команды), иначе «commands» невозможно реализовать без повторного проектирования.

**Последствие.** Для измерения «прайор-арт» это не косметика: документ, обосновывающий отказ от готовых решений, обязан быть проверяемым — с версиями, датами и ссылками. Сейчас ключевое утверждение о ценности Traffic Multiplier (строка 1962) держится на личной оценке «я считаю», а не на факте проверки конкурентов. При этом строки 1–11 и 1960–2004 — это переписка, а не требования, и при разбиении документа на TASK/ARCHITECTURE они попадут в артефакты как якобы требования. Дополнительно: §4.9 и §5.10 частично дублируют друг друга (коэффициент и стоимость сервера объясняются дважды), а §6.14 повторяет §4.9 в третий раз.

**Что дописать.** Удалить строки 1–13 и раздел «Мой комментарий…» (строки 1958–2004), перенеся содержательную часть последнего (модель Traffic Charging Policy, raw_bytes/charged_bytes) в §4.9 как требование. Оценочные обороты «важное», «критически важно», «очень хорошая основа» заменить на проверяемые формулировки. Ввести сквозной формат ссылки на прайор-арт: «решение, версия, дата проверки, URL» — и использовать его во всех утверждениях о том, чего в существующих системах нет.

## Опровергнуто при верификации

- **Не заданы типы хранения и правило округления для raw/billable — при дробных множителях (1.5x, 2.5x) цифры в ЛК и в биллинге разойдутся** — Цитаты формально верны, но находка не является дефектом постановки. §5.9 уже фиксирует ровно то, что нужно на этом уровне: хранить Raw bytes, Billable bytes и применённый Traffic multiplier раздельно, а §8 и §5.10 повторяют требование хранить raw_bytes и charged_bytes с первого дня. Выбор типов (BIGINT vs float, NUMERIC(6,3)) и правила округления — это решения этапа проектирования схемы, то есть ровно тот класс требований, который от постановки задачи требовать некорректно; никакой развилки продукта здесь нет, единицы измерения по умолчанию — байты (документ нигде не предписывает хранить GB как float, это домысел). Количественная часть аргумента опирается на два изобретённых допущения: интервал отчётов 30 секунд (в документе его нет, он взят из рекомендации dim-05) и округление на уровне MB при агрегации (документ такого не предлагает), из-за чего оценка «2,8 GB/сутки потерь» ничем не обоснована. Расхождение между «Actual × коэффициент» и «Charged» в ЛК устраняется общим требованием хранить оба значения, которое в документе уже есть.
- **Объём статистики при 100k пользователей × 200 нод не оценён; нет требований к гранулярности, партиционированию, retention и downsampling** — Ключевой тезис «фраза не даёт требования» неверен: §5.9 формулирует именно требование — сырые события не хранятся бесконечно в основной базе, а модель хранения — Aggregation → Hourly / Daily records; §5.7 отдельно требует масштабируемости до 100 000 пользователей и 200 нод без смены базовой архитектуры. То есть уровни агрегации и цель по нагрузке в постановке уже заданы. Остальное — партиционирование PostgreSQL, TTL партиций, размеры строк, индексы — типовые решения этапа проектирования схемы, требовать которых от постановки некорректно. Количественная часть держится на выдуманных допущениях: верхняя граница 480 млн строк/сутки предполагает, что каждый из 100k пользователей ежечасно имеет ненулевой счётчик на всех 200 нодах, а «реалистичные» 10 нод на пользователя ничем не обоснованы; поведение urltest у клиентов сильно зависит от настроек и режима выбора и не даёт заявленной равномерной нагрузки. Ссылка на §4.19 «Configurable retention» как «единственное упоминание retention» корректна, но эта строка про бэкапы и к статистике отношения не имеет — она не опровергает наличие требования в §5.9.
- **Не определено, где вычисляется billable и что нода вообще знает о лимитах — это развилка архитектуры §5.2, а не деталь реализации** — Заявленная развилка «обе архитектуры поддерживаются текстом» документом не подтверждается. Множитель однозначно живёт в Control Plane: §4.15 помещает управление Traffic Multiplier в раздел админки Server Groups, §5.9 требует хранить применённый Traffic multiplier в записях статистики Control Plane, §5.10 прямо называет Traffic Multiplier бизнес-правилом списания и отделяет его от реальной стоимости сервера, а §3.1 объявляет CP единственным источником истины по статистике. Нигде в документе нода не получает ни множитель, ни лимит, ни остаток квоты — вариант (А) текстом не поддерживается, значит противоречия между разделами нет. Оставшаяся содержательная часть находки — «передаёт ли CP ноде остаток квоты для быстрого принуждения» — это ровно предмет dim-04 (механизм принуждения) и dim-05 (лаг принуждения) и отдельной находкой не является. Слово «Aggregation» в конвейере §5.9 действительно не уточняет сторону, но это про агрегирование объёма записей, а не про то, кто умножает на коэффициент.
- **Модель данных тарифа (§4.10) не выражает четыре типа лимитов из §4.11 и не предусматривает per-user override** — Квалификация «противоречие» не подтверждается: §4.10 — это пример состава тарифа («Тариф должен содержать: ... Traffic limit») с иллюстрацией Basic/Premium, а нормативное требование поддержать четыре режима лимита прямо стоит рядом, в §4.11 («Unlimited / Fixed subscription limit / Monthly limit / Custom limit» с примерами «100 GB per month» и «500 GB for subscription lifetime»). То есть требование в документе есть, и разработчик, читающий постановку, а не один §4.10, его увидит; претензия сводится к тому, что в перечне полей тарифа не расписана структура поля — это требование готовой схемы данных от постановки задачи. Содержательный остаток — неопределённость «Custom limit», носителя индивидуального лимита и бонусного трафика промокода/админа — уже полностью покрыт находкой dim-06 (пункты «г» и «д») и дублируется. Самостоятельно новым остаётся только мелкий вопрос, считается ли billable для unlimited-тарифов ради аналитики §5.10/§6.13, что тянет максимум на minor-уточнение и не оправдывает формулировку находки.
- **Одна скалярная «config version» на ноду не работает: смешивает горячие и рестартующие изменения, не даёт базы для дельты и статуса ошибки применения** — Цитаты §3.4 и §5.4 верны, но два центральных технических утверждения находки ложны. (1) «У скаляра нет семантики base/since, поэтому протокол физически не может быть инкрементальным» — неверно: монотонный скалярный счётчик и есть каноническая база для since-семантики (агент сообщает applied=v143, CP отдаёт diff v143→v145); отсутствие дельт в документе — это пробел в описании протокола (уже зафиксирован в dim-01), а не следствие скалярности версии. (2) «При одной версии агент не может применить состав пользователей без риска задеть структурную часть, и любой апдейт вырождается в полную перезапись+рестарт» — неверно: агент, получив желаемое состояние, сам локально сравнивает его с применённым и определяет класс изменений, применяя пользователей горячо, а структурную часть — через reload; гранулярность версии этого не диктует. Разделение на config_revision/user_seq — одна из допустимых реализаций, а не обязательное требование. Остаётся живым только хвост находки — в §5.4 действительно нет ни кода/причины ошибки применения, ни ретраев, ни last-known-good, ни порога «рассинхронизации» по времени; но это узкий пробел в отчётности агента, он не тянет на blocker и по существу дублирует контракт Node API из dim-01/dim-07, а сформулирован в находке через ложную техническую посылку.
- **Нет требований к окружениям, CI/CD, миграциям схемы БД и тестированию — включая проверку заявлений §5.7 и §4.19** — Фактическая часть подтверждается (grep: «тест», «staging», «prod», «CI/CD» — 0; «миграц» — единственное вхождение в заключительном комментарии автора), но по критерию №4 находка не проходит. Во-первых, окружения, CI/CD, набор видов тестов и учения по восстановлению — это процесс поставки и организация работы команды, а не постановка задачи на систему; отсутствие раздела «Окружения и поставка» в документе, который явно позиционирован как «удобная стартовая постановка для дальнейшей проработки» (преамбула), не является дефектом самой постановки — эти решения принимаются на этапе плана разработки. Во-вторых, ключевое требование находки — канареечная выкатка Node Agent — в документе не пропущено, а сознательно проскоуплено: §6.5 Rolling Updates описан именно как поэтапное обновление с health check, «чтобы массовое обновление не отключило всю инфраструктуру», и отнесён в Phase 2 (раздел 7). Спор с приоритизацией автора — это возражение против принятого решения, а не пробел. В-третьих, требование нагрузочного теста как критерия приёмки §5.7 уже покрывается dim-11 и там сформулировано точнее. Единственный несводимый остаток — стратегия версионированных миграций схемы БД, актуальная в свете предупреждения автора о болезненности изменения модели статистики; но это один пункт минорной значимости, а не major-находка о «нет требований к окружениям, CI/CD, миграциям и тестированию».
