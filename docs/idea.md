## 0. Прайор-арт и решение build / adopt / fork

### 0.1 Существующие решения

Данные проверены 2026-09-04 по GitHub API, исходному коду репозиториев и официальной документации.
Строки таблицы перепроверяются при каждом пересмотре решения §0.3.

| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Remnawave | AGPL-3.0 | Отдельный агент | Панель → нода | Да, на ноду, 0.0–100.0 шаг 0.1 | Да | Нет | Нет | Активен |

Уточнения к таблице:

1. В Remnawave коэффициент реализован полем `consumptionMultiplier` таблицы `nodes`; значение хранится
   в наноединицах, `1000000000` соответствует 1.0. Есть второй коэффициент
   `nodeConsumptionMultiplier` для счётчика трафика самой ноды.
2. В Remnawave история (`nodes_usage_history`, `nodes_user_usage_history`) пишется без коэффициента,
   а счётчики лимитов (`users.used_traffic_bytes`) — с коэффициентом. Это и есть раздельное хранение
   raw и billable.
3. В Marzban и PasarGuard коэффициент `usage_coefficient` применяется в момент записи
   (`int(value * coefficient)`), поэтому сырой расход по пользователю не сохраняется.
4. Промокодов, купонов и приёма платежей нет ни в одном из шести решений. Проверено поиском по
   полным деревьям репозиториев по ключам `coupon`, `promo`, `tariff`.
5. Направление соединения «нода → панель» не реализовано ни в одном из шести решений.
6. Лицензии Hiddify различаются по репозиториям: `hiddify/hiddifypanel` (ядро панели) —
   CC BY-NC-SA 4.0 с условием NonCommercial; `hiddify/Hiddify-Manager` — GPL-3.0;
   `hiddify/hiddify-app` (клиент) — расширенная GPLv3 с отдельным условием NonCommercial.

| ДЛ-2 | Коэффициент трафика на уровне группы серверов с иерархией «нода → группа → значение по умолчанию» | §4.9 | Коэффициент существует только на уровне ноды |

Префикс ДЛ обозначает строки дельты. Префикс Д в §9.1 обозначает допущения; это разные реестры.

Требования ДЛ-3 и ДЛ-4 не относятся к управлению VPN-инфраструктурой и реализуемы поверх внешнего
API.

Требование «раздельное хранение raw и billable» в §5.9 не входит в дельту: оно реализовано в
Remnawave. Оно остаётся обязательным требованием настоящего документа, но не является основанием
для собственной разработки.

### 0.3 Принятое решение

Решение build / adopt / fork не принято. До его принятия выполняется PoC.

**Состав PoC.**

PoC-1. Развернуть Remnawave на двух нодах в разных странах и измерить:

- совместимость каждого из пяти клиентов §4.2 с выдаваемым форматом подписки;
- погрешность учёта трафика при передаче известного объёма (сверка счётчика панели с эталоном);
- поведение учёта при перезапуске процесса Xray: потеря или повторное списание;
- фактическую задержку применения блокировки пользователя;
- поведение подписки при переводе ноды в недоступное состояние.

PoC-1а. Дополнительно проверить на том же стенде, независимо от выбора build / adopt / fork:

- разрывает ли соединения приём «удалить пользователя из inbound и добавить обратно» — от ответа
  зависит выполнимость Н-14 и Н-17 (§4.11, §4.13);
- проходит ли профиль `vless-xhttp` там, где не проходит `vless-raw-vision`, и на каких портах;
- даёт ли выигрыш профиль с SNI из белого списка оператора по сравнению с обычным SNI. Решение о
  включении такого профиля в продукт принимается по результату, ОВ-12;
- отображает ли каждый из пяти клиентов §4.2 заголовки `subscription-userinfo`, `profile-title` и
  `announce`; результат заносится в реестр клиентов §17.10;
- работает ли профиль `vless-xhttp` в клиенте Hiddify, использующем собственную сборку ядра.

PoC-2. Проверить, реализуем ли слой тарифов, промокодов и подписок поверх публичного API панели без
модификации её кода. Результат — перечень требуемых вызовов и перечень отсутствующих.

PoC-3. По результатам PoC-1 и PoC-2 оценить трудоёмкость трёх вариантов в человеко-днях.

**Критерии выбора.**

| Условие | Решение |
| :--- | :--- |
| Публичного API достаточно для §4.10, §4.14 и §4.2 без модификации панели, погрешность учёта в PoC-1 укладывается в §13, отказ от ДЛ-1 признан приемлемым | Adopt |
| Не выполнено хотя бы одно из первых двух условий, либо требование ДЛ-1 признано обязательным | Build |
| Adopt невозможен, а разница трудоёмкости с Build по PoC-3 превышает 40 % | Fork |

**Timebox.** 10 рабочих дней с момента запуска PoC.

**Владелец решения.** Владелец продукта. Персональное закрепление — открытый вопрос ОВ-1 (§15).

**Условие пересмотра.** Решение пересматривается при прекращении развития выбранного проекта, при
смене его лицензии и при появлении требования, которое выбранный вариант не покрывает.

**Размен при выборе Adopt.** Требование §3.3 не выполняется: панель подключается к ноде, а не
наоборот. Следствия — на каждой ноде открыт входящий порт управления, ноды за NAT не
поддерживаются. При выборе Adopt §3.3 переписывается как «канал управления защищён взаимной
аутентификацией сторон», а направление соединения перестаёт быть требованием.

### 0.4 Ограничение по использованию чужого кода

Фрагменты кода существующих панелей не копируются в кодовую базу проекта. Панель используется
только как отдельно развёрнутый сервис, взаимодействие — по сетевому API.

Обоснование ограничения:

| Способ использования | Обязательство по AGPL-3.0 | Статус собственного кода |
| :--- | :--- | :--- |
| Развёртывание немодифицированной панели, обращение по сетевому API | Не возникает | Остаётся закрытым |
| Модификация панели и её выставление в сеть | Раскрыть исходный код модифицированной панели её сетевым пользователям | Отдельная программа может остаться закрытой |
| Копирование фрагментов кода в собственную кодовую базу | Кодовая база становится производной работой | Раскрывается целиком |

Дополнительно:

- GPL-3.0 (нода PasarGuard, 3x-ui) не считает сетевое использование распространением. Обязательство
  возникает при передаче бинарных сборок и образов третьим лицам.
- Код Hiddify исключён при любом сценарии: ядро панели `hiddify/hiddifypanel` распространяется под
  CC BY-NC-SA 4.0 с условием NonCommercial, а клиент `hiddify/hiddify-app` — под расширенной GPLv3
  с отдельным условием NonCommercial. Лицензия GPL-3.0 у репозитория `hiddify/Hiddify-Manager`
  этого не отменяет.
- Трактовка в этом разделе является инженерной. Подтверждение у юриста до коммерческого запуска —
  риск Р-9 (§12).

## 1. Цель проекта

Необходимо разработать централизованную платформу для управления собственной распределённой VPN-инфраструктурой.

Платформа должна позволять управлять:

* пользователями;
* VPN-подписками;
* тарифами;
* VPN-серверами;
* группами серверов;
* VPN-протоколами;
* трафиком пользователей;
* промокодами;
* доступом пользователей;
* мониторингом инфраструктуры.

Основная цель — создать систему, позволяющую управлять большим количеством VPN-серверов из единой панели и предоставлять пользователям удобный личный кабинет с единой подпиской для подключения к различным VPN-серверам.

На первом этапе система ориентирована на использование Xray-core и трёх профилей подключения
(§4.4):

* VLESS поверх RAW с REALITY и flow `xtls-rprx-vision`;
* VLESS поверх XHTTP с REALITY;
* Trojan поверх RAW с REALITY.

При этом архитектура не должна быть жёстко привязана к конкретному VPN-протоколу или реализации VPN-сервера.

## 2. Общая концепция системы

Система должна состоять из двух основных уровней:

```text
                    CONTROL PLANE
                         │
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
     VPN NODE         VPN NODE         VPN NODE
    Germany         Netherlands       Finland
```

### Control Plane

Центральная система управления.

Отвечает за:

* пользователей;
* аутентификацию;
* подписки;
* тарифы;
* доступ;
* промокоды;
* серверы;
* группы серверов;
* конфигурацию VPN;
* статистику;
* мониторинг;
* управление VPN-нодами.

Control Plane является единственным источником истины для всей инфраструктуры.

---

### VPN Nodes

Отдельные VPN-серверы, расположенные у различных VPS-провайдеров и в разных странах.

Каждая нода содержит:

```text
VPN Node
│
├── Xray-core
│
└── Node Agent
```

#### Xray-core

Непосредственно обслуживает VPN/Proxy-подключения пользователей.

#### Node Agent

Специальный агент управления, отвечающий за:

* регистрацию сервера;
* синхронизацию конфигурации;
* синхронизацию пользователей;
* обновление Xray;
* health checks;
* отправку heartbeat;
* сбор статистики;
* управление сервисами.

## 3. Архитектурные принципы

При проектировании необходимо соблюдать следующие принципы.

### 3.1 Control Plane является единственным источником истины

Все критические данные хранятся централизованно:

* пользователи;
* подписки;
* тарифы;
* права доступа;
* серверы;
* конфигурации;
* статистика.

VPN-нода не должна быть единственным местом хранения критической информации.

---

### 3.2 VPN-ноды являются disposable infrastructure

Любой VPN-сервер должен иметь возможность быть:

* выключен;
* удалён;
* полностью уничтожен;
* заново создан;
* автоматически возвращён в инфраструктуру.

При этом не должны теряться:

* пользователи;
* подписки;
* тарифы;
* права доступа.

Желаемый сценарий:

```text
Server destroyed
       ↓
New VPS created
       ↓
Bootstrap script executed
       ↓
Node Agent installed
       ↓
Node registered
       ↓
Configuration synchronized
       ↓
Node Active
```

---

### 3.3 Управление нодами через Node Agent

Control Plane не должен зависеть от постоянного SSH-доступа к VPN-серверам.

Основной канал взаимодействия:

```text
VPN Node
    │
    │ HTTPS / mTLS
    ▼
Control Plane
```

Node Agent самостоятельно устанавливает исходящее защищённое соединение с центральной системой.

---

### 3.4 Desired State модель

Control Plane хранит желаемое состояние инфраструктуры. Node Agent приводит локальную
инфраструктуру к нему.

Желаемое состояние разделено на два независимых потока с собственными курсорами. Разделение введено
потому, что структурная конфигурация меняется редко и требует перезапуска Xray, а состав
пользователей меняется постоянно и применяется без перезапуска (допущение Д-4). Единый номер версии
на оба потока приводил бы к перезапуску Xray при каждом изменении состава пользователей и разрыву
соединений всех пользователей ноды.

```text
Node DE-01

Поток 1 — структурная конфигурация          config_version: 145
  inbound vless-raw-vision  :443
  inbound vless-xhttp       :2087
  inbound trojan-reality    :8443
  параметры REALITY, маршрутизация, лимиты

Поток 2 — состав пользователей              users_seq: 20431
  user A  active            credentials, quota_grant_bytes, blocked_ips[]
  user B  suspended_quota
  user C  active            credentials, quota_grant_bytes, blocked_ips[]
```

Запись пользователя в потоке 2 содержит состояние (§4.11), credentials для этой ноды (§11.3),
предоплаченный грант квоты `quota_grant_bytes` (§4.11) и список блокируемых адресов (§4.13).

Отслеживаются четыре значения:

```text
Desired config_version   / Applied config_version
Desired users_seq        / Applied users_seq
```

Расхождение любой пары отображается администратору (§5.4).

Контракт передачи описан в §5.2.

---

### 3.5 Разделение Control Plane и Data Plane

Центральная система управления и VPN-трафик должны быть логически разделены.

Control Plane:

```text
Users
Billing
Configuration
Management
Monitoring
```

Data Plane:

```text
Xray
VPN Traffic
Connections
```

Выход из строя отдельной VPN-ноды не должен приводить к потере Control Plane.

## 4. MVP

### 4.1 Пользовательская система

Необходимо реализовать:

* регистрацию;
* вход;
* выход;
* восстановление пароля;
* подтверждение email;
* управление профилем.

Настройки регистрации:

```text
Registration mode:

- Open registration
- Invite only
- Closed registration
```

При открытой регистрации должна поддерживаться защита от ботов:

* CAPTCHA;
* rate limiting;
* email verification.

---

### 4.2 Личный кабинет пользователя

Пользователь должен видеть:

#### Основная информация

* текущий тариф;
* статус подписки;
* дату окончания;
* доступный трафик;
* использованный трафик.

---

#### VPN Subscription

Пользователь получает персональную subscription URL на двух доменах в разных зонах регистрации
(§5.6):

```text
https://{домен-1}/s/{token}
https://{домен-2}/s/{token}
```

В личном кабинете пользователь может:

* скопировать любую из двух ссылок;
* открыть QR-код;
* перевыпустить токен.

Перевыпуск делает прежний токен недействительным немедленно и ротирует VPN-credentials пользователя
на всех нодах. Отдельного действия «отключить старую ссылку» нет: перевыпуск и есть отключение.

Subscription URL предоставляет актуальный список доступных серверов. Контракт эндпоинта, форматы,
заголовки и состояния описаны в §5.6.

---

#### Поддерживаемые клиенты

На первом этапе необходимо обеспечить совместимость с популярными клиентами:

* Shadowrocket;
* v2rayNG;
* Streisand;
* Hiddify;
* sing-box.

В будущем список может расширяться.

---

### 4.3 Автоматическое обновление серверов в подписке

Список серверов в subscription URL должен формироваться динамически.

При формировании учитываются:

* активность подписки;
* тариф пользователя;
* доступные Server Groups;
* доступные VPN-протоколы;
* статус сервера;
* ограничения доступа;
* подтверждённый нодой курсор состава пользователей `users_seq` (§5.2).

Если сервер становится недоступным:

```text
Node → Offline
```

он автоматически исключается из выдаваемых пользователю конфигураций. Условие перевода в Offline
задано требованием Н-15: три пропущенных подряд интервала heartbeat.

Если сервер возвращается, он снова становится доступным пользователям после двух успешных heartbeat
подряд (Н-15).

Автоматический возврат применяется только к нодам, переведённым в Offline автоматикой. Статусы
Maintenance и Disabled устанавливаются администратором и имеют приоритет над автоматическими:
нода в этих статусах продолжает слать heartbeat, но в выдачу подписок не возвращается до снятия
статуса администратором.

Ограничение механизма: клиент обновляет подписку по собственному расписанию (допущение Д-6).
Исключение ноды из ответа эндпоинта не означает мгновенного переключения уже подключённого
пользователя.

Целевое время восстановления работы пользователя после перевода ноды в Offline задаётся раздельно
для двух групп клиентов:

| Группа | Механизм | Требование |
| :--- | :--- | :--- |
| Клиенты формата `singbox` | Автоселектор `urltest` в профиле (§5.6) | Н-34: не более 60 с, без действий пользователя |
| Клиенты формата `base64` | Автоселектор невозможен: это плоский список ссылок | Н-35: восстановление выполняется вручную — переключением сервера в клиенте либо обновлением подписки |

Для второй группы это ограничение продукта, а не дефект реализации. Оно отражается в мастере
первого подключения (§17.6) и в тексте личного кабинета. Целевое значение для неё определяется
решением ОВ-18.

### 4.4 Модель VPN-сервера

#### Действия администратора

* добавить сервер;
* удалить сервер;
* включить и отключить сервер;
* перевести сервер в Maintenance;
* изменить название и географию;
* изменить группы доступа;
* изменить тарифицируемую группу;
* задать и снять переопределение коэффициента трафика;
* включить и отключить отдельный inbound.

#### Сущность Node

```text
id
name
country
city
provider
public_ipv4

fqdn                     — необязательно, для профилей поверх TLS
```

Поле `public_ipv4` имеет историю изменений: пересоздание ноды по §3.2 является штатным сценарием, и
смена адреса должна быть прослеживаема.

#### Сущность Inbound

Параметры подключения принадлежат не ноде, а паре «нода × профиль». Одна нода несёт несколько
inbound одновременно, на разных портах.

```text
id
node_id
profile                  — код профиля, см. ниже
port
tag                      — тег inbound в конфигурации Xray
enabled
```

Параметры REALITY, общие для всех трёх профилей MVP:

```text
reality_private_key      — генерирует и хранит Control Plane
reality_public_key       — выдаётся клиенту как pbk
reality_short_ids[]      — выдаётся клиенту как sid; hex, чётное число символов, не более 16
reality_target           — dest, домен-цель
reality_server_names[]   — допустимые SNI
reality_min_client_ver   — минимальная версия клиента
reality_max_client_ver   — максимальная версия клиента, необязательно
reality_xver             — версия PROXY protocol, рандомизируется на ноду
reality_limit_fallback_upload   — рандомизируется на ноду
reality_limit_fallback_download — рандомизируется на ноду
client_fingerprint       — uTLS-профиль, выдаётся клиенту как fp
client_spider_x          — выдаётся клиенту как spx; индивидуально на профиль
```

Поля `reality_min_client_ver` и `reality_max_client_ver` обязательны в модели, поскольку ядро
выставляет минимальную версию клиента по умолчанию и отклоняет более старые клиенты. Обновление
Xray на ноде без явного значения способно отключить часть клиентов §4.2. Значение задаётся явно, а
не наследуется от версии ядра.

Поля `reality_xver` и `reality_limit_fallback_*` рандомизируются для каждой ноды: одинаковые
значения на всём парке образуют признак, по которому парк опознаётся как единая инфраструктура.

Параметры сокета inbound, общие для профилей:

```text
trusted_x_forwarded_for[]  — соответствует streamSettings.sockopt.trustedXForwardedFor;
                             задаётся при размещении inbound за CDN или обратным прокси
```

Ключевую пару x25519 генерирует Control Plane и хранит как секрет (§5.13). Обоснование: §3.1
объявляет Control Plane единственным источником истины, а §3.2 делает пересоздание ноды штатным
сценарием. При генерации ключей на ноде пересоздание меняет `pbk` и делает недействительными все
ранее скачанные конфигурации клиентов до следующего обновления подписки.

#### Профили MVP

| Код | Протокол | Транспорт | Безопасность | Порт | Назначение |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `vless-raw-vision` | VLESS | RAW (TCP) | REALITY | 443 | Основной. Максимальная пропускная способность, минимальный расход процессора, снят признак TLS-in-TLS |
| `vless-xhttp` | VLESS | XHTTP | REALITY | Из набора 2053, 2083, 2087, 2096, 8443 | Проходит там, где основной профиль не проходит |
| `trojan-reality` | Trojan | RAW (TCP) | REALITY | Отдельный порт | Совместимостный запас для клиентов и сетей |

Дополнительные поля профиля `vless-raw-vision`:

```text
flow                     — xtls-rprx-vision
decryption               — none, обязательное поле VLESS
```

Дополнительные поля профиля `vless-xhttp`:

```text
flow                     — none
decryption               — none
xhttp_path
xhttp_mode               — auto | packet-up | stream-up | stream-one
xhttp_host               — необязательно
x_padding_bytes          — по умолчанию 100-1000
x_padding_obfs_mode      — булев переключатель расширенной обфускации;
                           пока false, четыре следующих поля ядром игнорируются
x_padding_key
x_padding_header
x_padding_placement      — cookie | header | query | queryInHeader
x_padding_method         — repeat-x | tokenish
uplink_http_method       — POST; GET допустим только в режиме packet-up
session_placement        — path | cookie | header | query; в конфигурации ядра sessionPlacement
session_key              — в конфигурации ядра sessionKey
```

Имена полей приведены к закреплённой версии Xray-core v26.3.27 (§17.3). В предварительных выпусках
ветки 26.x, начиная с промежутка между v26.5.9 и v26.6.27, эти поля переименованы в
`sessionIDPlacement` и `sessionIDKey` без обратной совместимости. При переходе на следующий
стабильный релиз имена перепроверяются по исходному коду ядра до обновления парка.

Профиль `trojan-reality` использует REALITY и не требует собственного домена и TLS-сертификата
(допущение Д-7). Поля `flow` у Trojan нет.

#### Обоснование набора профилей

Профили закрывают разные механизмы блокировки, поэтому один профиль не заменяет другой.

| Слой маскировки | Что снимает | Чем задаётся | Доступен в профиле |
| :--- | :--- | :--- | :--- |
| REALITY | Серверный TLS-fingerprint, активное зондирование, фильтрацию по SNI | `reality_*` | Все три |
| uTLS | Клиентский TLS-fingerprint | `client_fingerprint` | Все три |
| Vision | Признак TLS-in-TLS | `flow=xtls-rprx-vision` | Только `vless-raw-vision` |
| Обфускация XHTTP | Форму трафика, размеры и тайминги пакетов | `x_padding_*` | Только `vless-xhttp` |

Vision работает только с транспортом RAW и TLS либо REALITY. С XHTTP он недоступен; вместо него
действует собственная обфускация XHTTP.

REALITY не защищает от блокировки по адресу, по объёму переданного и по поведению соединения.
Наблюдения сообщества, положенные в основу набора профилей и требующие проверки в PoC:

* соединение к зарубежному дата-центру прекращает передачу после примерно 15–20 КБ, полученных
  клиентом, без разрыва — состояние, в котором профиль `vless-raw-vision` не работает, а
  `vless-xhttp` работает;
* ограничение числа одновременных TLS-соединений на порту 443 у части операторов — состояние, в
  котором помогает смена порта.

#### Ротация ключевого материала REALITY

| Основание | Действие |
| :--- | :--- |
| Плановая ротация | Смена `short_ids` с окном перекрытия (Н-33) |
| Компрометация или изъятие ноды | Обязательная смена ключевой пары и `short_ids`; переиспользование прежнего ключа запрещено |
| Недоступность `reality_target` | Смена цели и `server_names`, ключевая пара сохраняется |
| Пересоздание ноды по иным причинам | Ключевая пара сохраняется (§4.5) |

Смена ключевой пары делает недействительными все ранее выданные клиентам конфигурации этого inbound:
у клиента изменяется `pbk`. Новое значение доводится обновлением подписки; пользователи затронутой
ноды получают уведомление (§4.17).

Окно перекрытия по `short_ids` позволяет плановую ротацию без разрыва: прежнее и новое значения
действуют одновременно.

#### Требования к параметру `reality_target`

Цель обязана поддерживать TLS 1.3 и HTTP/2, не использоваться для перенаправлений и находиться вне
зоны блокировки. Значения `reality_server_names` должны входить в сертификат цели. Адрес цели
географически близок к адресу ноды.

Доступность цели проверяется при вводе ноды в эксплуатацию и периодически. Недоступная или
заблокированная цель переводит inbound в состояние ошибки.

### 4.5 Ввод нового сервера в эксплуатацию

#### Сценарий

```text
1.  Администратор создаёт VPS.
2.  Администратор создаёт запись Node в Control Plane: имя, география, провайдер,
    группы доступа, тарифицируемая группа, юридический профиль.
3.  Control Plane генерирует ключевой материал REALITY для каждого inbound (§4.4)
    и одноразовый bootstrap-токен.
4.  Система выдаёт bootstrap-команду с токеном.
5.  Команда выполняется на VPS: устанавливаются Xray, Node Agent и зависимости.
6.  Node Agent обменивает bootstrap-токен на постоянную identity: клиентский
    сертификат и токен (§5.3).
7.  Нода переходит в статус Pending.
8.  Администратор подтверждает ноду, сверив предъявленные ею признаки.
9.  Нода переходит в Provisioning, получает поток структурной конфигурации (§3.4)
    и применяет его; поток состава пользователей в этом статусе пуст (§4.6, §11.3).
10. Нода переходит в Active; Control Plane публикует ей состав пользователей.
```

#### Свойства bootstrap-токена

| Свойство | Значение |
| :--- | :--- |
| Использование | Одноразовое |
| Срок жизни | Не более 60 минут (Н-24) |
| Привязка | К конкретной записи Node |
| Обмен | На постоянную identity; после обмена токен недействителен |
| Повторная выдача | Создаёт новый токен и аннулирует прежний |

Требование введено потому, что bootstrap-команда содержит секрет и попадает в историю оболочки на
VPS и в буфер обмена администратора.

#### Подтверждение ноды

На шаге 8 администратор сверяет предъявленные нодой признаки с ожидаемыми: адрес источника
запроса, отпечаток выданного сертификата, версия агента и версия Xray.

До подтверждения нода не получает ни одного VPN-credential (§11.3). Требование ограничивает
последствия компрометации bootstrap-токена: обладатель токена получает identity ноды, но не
получает доступов пользователей.

#### Пересоздание ноды

Пересоздание ноды по §3.2 использует ту же запись Node и тот же ключевой материал REALITY. Выдаётся
новый bootstrap-токен; прежняя identity отзывается.

Исключение: при пересоздании по причине компрометации или изъятия VPS ключевой материал REALITY
обязательно заменяется (§4.4). Переиспользование прежнего ключа в этом случае запрещено: приватный
ключ считается утёкшим.

### 4.6 Статусы VPN-ноды

#### Набор статусов

| Статус | Значение | Устанавливает |
| :--- | :--- | :--- |
| `Pending` | Нода зарегистрирована, не подтверждена администратором | Автоматика при регистрации |
| `Provisioning` | Идёт первичная настройка и применение конфигурации | Автоматика после подтверждения |
| `Active` | Обслуживает пользователей | Автоматика |
| `Degraded` | Обслуживает пользователей, но нарушен один из порогов §4.7 | Автоматика |
| `Offline` | Нет heartbeat | Автоматика |
| `Maintenance` | Временно выведена администратором | Администратор |
| `Disabled` | Отключена администратором | Администратор |
| `Suspended` | Приостановлена хостинг-провайдером | Администратор |

Статус `Suspended` введён отдельно от `Offline`, поскольку отключение сервера провайдером по жалобе
(риск Р-3) требует иной реакции, чем техническая авария: восстановление зависит от ответа провайдеру,
а не от перезапуска.

Статус `Draining` отнесён к §10.

#### Приоритет статусов

Статусы делятся на автоматические (`Provisioning`, `Active`, `Degraded`, `Offline`) и ручные
(`Maintenance`, `Disabled`, `Suspended`).

Ручной статус имеет приоритет. Нода в ручном статусе продолжает слать heartbeat, но автоматика не
переводит её в `Active`. Снятие ручного статуса выполняет только администратор.

#### Матрица переходов

| Из | В | Условие | Инициатор |
| :--- | :--- | :--- | :--- |
| — | `Pending` | Регистрация ноды | Агент |
| `Pending` | `Provisioning` | Подтверждение администратором | Администратор |
| `Provisioning` | `Active` | Применён поток структурной конфигурации, Xray запущен, получен heartbeat | Автоматика |
| `Provisioning` | `Offline` | Нет heartbeat дольше порога Н-15 | Автоматика |
| `Active` | `Degraded` | Нарушен порог §4.7 | Автоматика |
| `Degraded` | `Active` | Пороги в норме два интервала подряд | Автоматика |
| `Active`, `Degraded` | `Offline` | Три пропущенных heartbeat подряд (Н-15) | Автоматика |
| `Offline` | `Active` | Два успешных heartbeat подряд (Н-15) | Автоматика |
| Любой автоматический | `Maintenance`, `Disabled`, `Suspended` | Действие администратора | Администратор |
| `Maintenance`, `Disabled`, `Suspended` | `Active` или `Offline` | Снятие ручного статуса; далее применяются автоматические правила | Администратор |
| Любой | Удаление | Вывод из эксплуатации по §5.9 | Администратор |

Переход из `Maintenance`, `Disabled` и `Suspended` в автоматические статусы без действия
администратора запрещён.

#### Матрица влияния

| Статус | Выдаётся в подписке | Принимает новых пользователей | Учитывается трафик | Поток состава пользователей | Канал команд |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `Pending` | Нет | Нет | Нет | Нет | Нет |
| `Provisioning` | Нет | Нет | Нет | Нет | Да |
| `Active` | Да | Да | Да | Да | Да |
| `Degraded` | Да | Да | Да | Да | Да |
| `Offline` | Нет | Нет | Да, из буфера после возврата | Да, при первом обмене | Да, при первом обмене |
| `Maintenance` | Нет | Нет | Да | Да | Да |
| `Disabled` | Нет | Нет | Да, из буфера | Только отзывы | Нет |
| `Suspended` | Нет | Нет | Да, из буфера | Только отзывы | Нет |

Настоящая таблица является единственным источником правил приёма потоков и команд по статусам.
Перечни в §4.11 и §5.2 ссылаются на неё и не повторяют её содержания.

«Только отзывы» означает: нода получает изменения, снимающие доступ, и не получает изменений,
выдающих доступ новым пользователям. Отзыв доставляется потоком состава, а не командой, поэтому
применяется во всех статусах, кроме `Pending`, при первом успешном обмене и до передачи трафика
этого пользователя (§4.11).

Существующие соединения при переводе ноды в `Maintenance` не разрываются. Нода исключается только из
новых ответов subscription-эндпоинта.

### 4.7 Health Monitoring

#### Собираемые показатели

| Показатель | Источник | Периодичность |
| :--- | :--- | :--- |
| Heartbeat агента | Агент | 30 с |
| Состояние процесса Xray | Агент | 30 с |
| Загрузка процессора, память, диск | Агент | 60 с |
| Сетевой трафик интерфейса | Агент | 60 с |
| Число уникальных адресов онлайн | Агент, через локальный API Xray | 60 с |
| Время работы ноды и агента | Агент | 60 с |
| Версии агента и Xray | Агент | При изменении |
| Доступность `reality_target` каждого inbound | Агент | 1 ч (Н-30) |

Число одновременных соединений через API Xray недоступно (допущение Д-13). Оно снимается агентом на
ноде средствами операционной системы и передаётся в отчёте метрик (§5.2).

#### Пороги и гистерезис

| Условие | Результат |
| :--- | :--- |
| Три пропущенных heartbeat подряд (90 с) | `Offline` |
| Два успешных heartbeat подряд | Возврат из `Offline` |
| Процесс Xray не запущен | `Degraded` |
| Загрузка процессора выше 90 % пять интервалов подряд | `Degraded` |
| Свободное место на диске ниже 10 % | `Degraded` |
| `reality_target` недоступна | inbound в состоянии ошибки, нода `Degraded` |
| Пороги в норме два интервала подряд | Возврат из `Degraded` |

Пороги заданы с гистерезисом. Требование исключает дребезг статуса и связанное с ним изменение
выдачи подписок (§4.3).

#### Внешняя проверка доступности

Heartbeat измеряет достижимость «нода → Control Plane» и не измеряет достижимость «пользователь из
страны X → нода». Заблокированная в отдельной стране нода остаётся в статусе `Active`.

Для каждой ноды ведётся признак доступности по странам присутствия пользователей. Источник —
внешние пробы. Недоступность из страны исключает ноду из выдачи подписок пользователям этой страны,
не изменяя её статус.

Способ получения проб и перечень стран определяются на этапе проектирования.

#### Смена адреса ноды

Изменение `public_ipv4` фиксируется с историей (§4.4). Изменение адреса не изменяет ключевой материал
REALITY: он хранится в Control Plane и переносится на пересозданную ноду (§4.4).

После изменения адреса ранее выданные конфигурации клиентов перестают работать до следующего
обновления подписки. Событие порождает уведомление пользователям затронутой ноды.

#### Уведомления и подавление

Переводы в `Offline` и возвраты порождают уведомления (§4.17). Повторные уведомления по одному
событию подавляются.

Ноды в статусах `Maintenance`, `Disabled` и `Suspended` алертов не порождают.

### 4.8 Server Groups

Необходимо реализовать группы серверов. Различаются два вида групп с разным назначением.

#### Группа доступа

Управляет видимостью нод в тарифах. Тариф предоставляет доступ к группам доступа, а не к конкретным
серверам. Нода входит в произвольное число групп доступа.

Примеры:

```text
Europe
Premium Europe
North America
Asia
Streaming
```

Модель:

```text
Plan
 │
 ▼ many-to-many
Access Group
 │
 ▼ many-to-many
VPN Node
```

Группы доступа позволяют:

* добавлять серверы без изменения тарифов;
* заменять серверы;
* создавать премиальные регионы;
* управлять доступом пользователей;
* добавлять специальные группы.

#### Тарифицируемая группа

Задаёт коэффициент расхода трафика (§4.9). Нода принадлежит ровно одной тарифицируемой группе.
Ограничение обеспечивается на уровне схемы данных.

Примеры:

```text
Standard
High Cost
Premium Asia
```

Модель:

```text
Billing Group ──1:N──> VPN Node
```

Разделение введено потому, что группы доступа пересекаются по назначению: одна и та же нода может
одновременно относиться к Europe, Premium Europe и Streaming. Коэффициент, привязанный к
пересекающимся группам, не имеет однозначного значения. Тарифицируемая группа не пересекается, и
коэффициент определяется однозначно.

---

### 4.9 Traffic Multiplier

#### Назначение

Разные VPN-серверы имеют разную стоимость эксплуатации. Коэффициент расхода трафика позволяет
управлять потреблением дорогих регионов, не вводя отдельных тарифов на каждый регион.

Коэффициент является бизнес-правилом списания пользовательского трафика. Он не равен фактической
стоимости сервера и не выводится из неё. Фактическая экономика ноды описана в §5.10 и является
независимой сущностью.

#### Терминология

Настоящий документ использует единственный набор имён:

| Понятие | Имя | Поле |
| :--- | :--- | :--- |
| Коэффициент расхода трафика | Traffic Multiplier | `traffic_multiplier` |
| Фактически переданный объём | Raw Traffic | `raw_bytes` |
| Объём, списанный с лимита | Billable Traffic | `billable_bytes` |

#### Модель и разрешение

Коэффициент задаётся на трёх уровнях:

```text
Node Traffic Multiplier          — переопределение для отдельной ноды
        │ приоритет выше
Billing Group Traffic Multiplier — коэффициент тарифицируемой группы
        │
Default Multiplier               — системное значение по умолчанию, 1.0
```

Правило разрешения: если у ноды задано собственное значение, применяется оно; иначе применяется
значение тарифицируемой группы ноды; иначе применяется значение по умолчанию.

Правило однозначно, поскольку нода принадлежит ровно одной тарифицируемой группе (§4.8). Группы
доступа на коэффициент не влияют.

Пример:

```text
Default:                 1.0
Billing Group Premium Asia: 2.0
Node JP-Tokyo-01:        3.0
```

Для JP-Tokyo-01 применяется 3.0. Для остальных нод группы Premium Asia — 2.0.

#### Диапазон и представление

| Свойство | Значение |
| :--- | :--- |
| Диапазон | 0.0–10.0 |
| Шаг | 0.1 |
| Значение по умолчанию | 1.0 |
| Хранение | Целое число тысячных: `1000` соответствует 1.0 |
| Значение 0.0 | Трафик на такой ноде не списывается с лимита; `raw_bytes` продолжает записываться |

Списываемый объём вычисляется как `billable_bytes = floor(raw_bytes * traffic_multiplier)` в байтах.
Вычисление выполняется в целочисленной арифметике. Значения с плавающей точкой в расчёте списаний
не используются.

Пример:

| Уровень применения | Коэффициент | Реальный трафик | Списание с лимита |
| :--- | ---: | ---: | ---: |
| Тарифицируемая группа Standard | 1.0 | 1 ГБ | 1 ГБ |
| Тарифицируемая группа Premium Asia | 2.0 | 1 ГБ | 2 ГБ |
| Нода JP-Tokyo-01, переопределение | 3.0 | 1 ГБ | 3 ГБ |

#### Датированность

Коэффициент фиксируется в записи статистики в момент её создания и хранится вместе с ней (§5.9).

Изменение коэффициента действует только на записи, создаваемые после изменения. Ранее записанные
значения `billable_bytes` не пересчитываются. Ретроактивный пересчёт списаний запрещён.

При переносе ноды в другую тарифицируемую группу или при изменении переопределения ноды текущий
период агрегации закрывается принудительно, и открывается новый период с новым коэффициентом.
Момент фиксации коэффициента таким образом детерминирован и не зависит от расписания фонового
задания.

Изменение коэффициента фиксируется в Audit Log (§4.16) с прежним и новым значением.

#### Раздельное хранение

Значения `raw_bytes` и `billable_bytes` хранятся раздельно и постоянно. Требование обязательно с
первой версии: добавление раздельного учёта задним числом требует миграции всей истории статистики,
а восстановить `raw_bytes` из `billable_bytes` невозможно.

Раздельное хранение обеспечивает:

* корректное отображение пользователю фактического и списанного объёма (§4.12);
* анализ экономики нод по фактическому потреблению (§5.10);
* проверку гипотез о коэффициентах без изменения истории списаний.

#### Прозрачность для пользователя

Коэффициент, отличный от 1.0, отображается пользователю до подключения: он включается в
отображаемое имя сервера в выдаваемой подписке. Выбор сервера выполняется в стороннем клиенте, где
доступно только это имя.

После подключения фактический и списанный объём отображаются в личном кабинете (§4.12).

### 4.10 Тарифы

Необходимо реализовать управление тарифами.

Тариф должен содержать:

```text
2

```


### 4.11 Лимиты трафика и принуждение

#### Типы лимитов в MVP

```text
Unlimited

Subscription limit — объём на период действия подписки
```

Лимит задаётся тарифом (§4.10) и расходуется в течение всего периода подписки. Сброс выполняется
только при продлении или при активации нового периода.

Типы `Monthly limit` и `Custom limit` в MVP не реализуются и отнесены к §10. Причина: месячный
лимит вводит сущность расчётного периода с якорной датой, часовым поясом, неполным первым периодом
и правилом прорации при смене тарифа. Для тарифов длительностью 30 дней он совпадает с лимитом на
период подписки.

#### База списания

С лимита списывается сумма `uplink + downlink`, умноженная на коэффициент §4.9. Служебный трафик
Node Agent в списание не входит.

Значения `Upload`, `Download` и `Total` хранятся раздельно и отображаются пользователю (§4.12).

#### Пороговые уведомления

| Порог | Событие | Канал |
| :--- | :--- | :--- |
| 80 % лимита | Предупреждение | Электронная почта, webhook |
| 95 % лимита | Предупреждение | Электронная почта, webhook |
| 100 % лимита | Отзыв доступа | Электронная почта, webhook |

Повторные уведомления по одному порогу в пределах одного периода подписки подавляются.

#### Действие при исчерпании

При достижении 100 % лимита пользователь переводится в состояние `suspended_quota` и удаляется из
inbound на всех нодах, обменивающихся с Control Plane. Максимальное время применения — Н-14.

Удаление пользователя из inbound не разрывает уже установленные соединения (допущение Д-2).
`connIdle` — таймаут бездействия, а не предельное время жизни соединения: активно передающее
соединение им не прерывается вообще. Поэтому одного удаления из inbound недостаточно, и требуется
механизм принудительного разрыва.

Механизм принудительного разрыва выбирается по результату PoC-1а (§0.3) из трёх кандидатов:

| Кандидат | Действие | Побочный эффект |
| :--- | :--- | :--- |
| Удаление и повторное добавление пользователя | Приём, применяемый существующими панелями | Требует проверки: штатно операция сессии не разрывает |
| Правило маршрутизации по источнику | `RoutingService.AddRule` с блокировкой адресов пользователя | Правило живёт в памяти и не переживает перезапуск |
| Перезапуск inbound | Гарантированный разрыв | Разрывает соединения всех пользователей этого inbound |

До получения результата PoC-1а верхняя граница перерасхода не считается достижимой (Н-17).

Отзыв доступа доставляется потоком состава пользователей, а не командой, поэтому применяется на
ноде в любом статусе, в котором она обменивается с Control Plane (§4.6). Нода, не имеющая связи,
применяет отзыв при первом успешном обмене и до передачи трафика этого пользователя.

#### Автономный режим ноды

Требование Н-7 допускает работу ноды без связи с Control Plane до 24 часов. В этом режиме отзыв по
команде невозможен, а перерасход ничем не ограничен: на ноде с коэффициентом 3.0 это десятки
гигабайт списания на пользователя.

Поэтому в состав потока пользователей (§3.4) входит поле `quota_grant_bytes` — предоплаченный объём
в единицах списания, то есть уже с учётом коэффициента ноды.

| Правило |
| :--- |
| Node Agent уменьшает грант по мере потребления и при его исчерпании локально переводит пользователя в `suspended_quota` |
| Агент запрашивает следующий грант, когда израсходовано 50 % текущего |
| Размер гранта задаётся конфигурацией и не превышает Н-17 |
| При отсутствии связи новый грант не выдаётся; пользователь остаётся отключённым до восстановления связи |
| Грант не заменяет учёт: фактическое потребление передаётся отчётами (§5.9) |

Механизм ограничивает перерасход в автономном режиме размером гранта, а не длительностью потери
связи.

#### Состояние пользователя на ноде

```text
active            — пользователь присутствует в inbound
suspended_quota   — исчерпан лимит трафика
suspended_admin   — заблокирован администратором
expired           — истёк срок подписки
```

Состояние является частью желаемой конфигурации ноды (§3.4). Пользователь в любом состоянии, кроме
`active`, в inbound отсутствует.

#### Восстановление доступа

Доступ восстанавливается при продлении подписки, при увеличении лимита администратором и при
активации Redeem-кода с бонусом по трафику. Время восстановления — то же, что и время отзыва
(Н-14).

#### Продление подписки

Продление начинает новый период независимо от того, активна подписка или истекла.

| Состояние на момент продления | Срок | Лимит |
| :--- | :--- | :--- |
| Подписка активна | Новый период начинается от текущей даты окончания | Лимит устанавливается равным лимиту тарифа; израсходованный объём обнуляется; неиспользованный остаток прежнего периода не переносится |
| Подписка истекла | Новый период начинается от момента активации | То же |

Пример: тариф 100 ГБ на 30 дней, израсходовано 60 ГБ, до окончания 5 дней. После продления
доступно 100 ГБ и 35 дней. Оставшиеся 40 ГБ прежнего периода не переносятся.

Правило одинаково для продления администратором и активации Redeem-кода.

#### Смена тарифа в середине периода

При смене тарифа период подписки и лимит трафика заменяются значениями нового тарифа. Израсходованный
объём переносится: смена тарифа не является продлением и лимит не обнуляет. Прорация не выполняется:
в MVP отсутствует приём платежей (ограничение О-2), и денежного основания для пересчёта нет.

Если новый тариф предоставляет меньший набор групп доступа, состав серверов в подписке изменяется в
течение Н-13. Уже установленные соединения к исключённым нодам не разрываются.

#### Бонусный трафик

Бонус, начисленный промокодом или Redeem-кодом (§4.14), увеличивает лимит текущего периода подписки.
Отдельного бонусного бакета с собственным порядком списания в MVP нет.

### 4.12 Статистика трафика пользователя

Пользователь видит за текущий период подписки:

| Показатель | Состав |
| :--- | :--- |
| Raw Traffic | `uplink` и `downlink` раздельно и суммарно |
| Traffic Multiplier | Применённое значение по каждой ноде |
| Billable Traffic | Списанный объём, `billable_bytes` |
| Остаток лимита | Лимит тарифа за вычетом Billable Traffic |
| Разбивка | По ноде и по стране |
| Число активных адресов | Текущее значение и лимит `Device limit` (§4.13) |

Пример отображения для ноды с коэффициентом 2.0:

```text
Фактически передано:   10 ГБ
Коэффициент:           2.0
Списано с лимита:      20 ГБ
```

Состав, проверяемый на приёмке, задан §14.

### 4.13 Ограничение числа устройств и противодействие шерингу

#### Задача

Ограничение решает две разные задачи, и они требуют разных механизмов.

| Задача | Проявление | Механизм |
| :--- | :--- | :--- |
| Передача подписки третьим лицам | Подключения с нескольких независимых адресов | Лимит уникальных адресов |
| Перепродажа доступа через собственный маршрутизатор | Один адрес, множество пользователей за NAT | Лимит одновременных соединений на ноде |

Второй сценарий подсчётом адресов не выявляется: с точки зрения ноды это один источник.

#### Доступные средства

Проверено по исходному коду Xray-core:

| Данные | Доступность |
| :--- | :--- |
| Уникальные адреса пользователя, время последней активности | API статистики Xray, вызывается агентом локально. Метод и минимальная версия ядра закрепляются вместе с версией Xray-core (§17.3) |
| Блокировка отдельного адреса источника | `RoutingService.AddRule` и `RemoveRule`; правило действует в памяти процесса и не переживает его перезапуск |
| Объём трафика пользователя | Счётчики `user>>>email>>>traffic`, снимаются агентом локально |
| Поток событий по соединениям: адрес источника, назначение, пользователь | Правило маршрутизации `webhook`, доставка без подтверждения, блокировать соединение через него нельзя |
| Число одновременных соединений пользователя | Отсутствует. Внутренний счётчик существует, но в API не публикуется |
| Идентификатор устройства, User-Agent клиента | Отсутствует. Из пяти клиентов §4.2 заголовок идентификатора устройства отправляет не каждый |

#### Механизм MVP

Первый контур — лимит уникальных адресов. Node Agent опрашивает API статистики Xray локально
(Control Plane не имеет доступа к API ноды: §3.3, §5.2) и передаёт сводку «пользователь → адреса →
время последней активности» в отчёте (§5.2).

Control Plane сравнивает число уникальных адресов пользователя с `Device limit` тарифа. При
превышении сохраняются адреса с наиболее свежей активностью в пределах лимита; остальные вносятся в
список блокируемых, который доставляется ноде в потоке состава пользователей (§3.4).

Node Agent применяет список правилом маршрутизации по источнику через `RoutingService`. Правило
действует в памяти процесса, поэтому агент переустанавливает его после каждого перезапуска Xray.

Время применения — Н-13. При смене сети пользователем прежний адрес вытесняется по времени
последней активности: блокировка снимается автоматически.

Пользователь видит в личном кабинете число активных адресов и факт достижения лимита.

Второй контур — жёсткий лимит одновременных соединений с одного адреса источника, реализуемый на
ноде средствами межсетевого экрана (Н-29). Значение задаётся конфигурацией ноды и синхронизируется
из Control Plane. Контур направлен на перепродажу доступа через маршрутизатор и не является
ограничением числа подключений на пользователя, которое отнесено к §10.

Третий контур — наблюдение. Собираются признаки, по которым выявляется перепродажа: объём трафика,
частота новых соединений, круглосуточность активности. Адреса назначения не собираются (§16.3).
Признаки отображаются в карточке пользователя. Решение принимает администратор.

#### Ограничения механизма

* При размещении inbound за CDN или обратным прокси все пользователи имеют один адрес источника,
  если не задан `trusted_x_forwarded_for` (§4.4). Без него лимит адресов бессмыслен.
* В мобильных сетях с общим адресом трансляции разные пользователи имеют один адрес, а один
  пользователь при переключении между сетями — разные. Лимит адресов даёт ложные срабатывания в обе
  стороны.
* Разрыв уже установленных соединений штатными средствами не выполняется (допущение Д-2). Приём,
  применяемый существующими панелями, — удаление пользователя из inbound с последующим повторным
  добавлением; его действие проверяется в PoC.
* Ограничение является оценочным: клиентское приложение недоверенное (§11.1).

#### Вне MVP

Список устройств, время последнего обращения каждого устройства, удалённое отключение устройства и
сброс всех устройств отнесены к §10.

Необходимо реализовать два типа кодов.

#### Promo Code

В MVP предоставляет:

### 4.19 Backup

Необходимо реализовать:

* backup PostgreSQL;
* backup конфигурации;
* backup критических secrets.

Требования:

```text

Configurable retention

Remote storage support

Encrypted backups
```

Цели восстановления заданы требованиями Н-9 (RPO не более 15 минут) и Н-10 (RTO не более 4 часов).
RPO 15 минут требует архивации журнала транзакций, а не только периодического дампа.

Ключ шифрования резервных копий хранится вне контура, восстанавливаемого из этих копий (Н-12).
Требование введено потому, что ключ, лежащий внутри восстанавливаемого контура, делает полное
восстановление невозможным.

Восстановление проверяется учебным прогоном на чистом хосте не реже одного раза в квартал (Н-11).
Успешный прогон является единственным подтверждением исправности резервных копий.

Сценарий восстановления описывает и восстановление доверия нод: после отката базы к состоянию до
ротации identity ноды перестают проходить аутентификацию. Процедура не должна требовать ручного
доступа к каждой ноде.

### 5.2 Контракт Control Plane ↔ Node Agent

#### Транспорт и направление

Node Agent устанавливает исходящее соединение к Control Plane по HTTPS (§3.3). Входящие порты
управления на ноде не открываются.

Аутентификация — взаимная: клиентский сертификат ноды и токен, привязанный к её identity (§5.3).

Базовый путь версионирован: `/agent/v1/`.

#### Операции

| Операция | Направление | Периодичность |
| :--- | :--- | :--- |
| Регистрация | Агент → Control Plane | Однократно при вводе ноды |
| Heartbeat | Агент → Control Plane | Раз в 30 с |
| Получение желаемого состояния | Агент → Control Plane, long-poll | Постоянно |
| Подтверждение применения | Агент → Control Plane | После применения |
| Отчёт о трафике и о наблюдаемых адресах | Агент → Control Plane | Раз в 60 с (§5.9) |
| Запрос следующего гранта квоты | Агент → Control Plane | При израсходовании 50 % гранта (§4.11) |
| Отчёт о метриках ноды | Агент → Control Plane | Раз в 60 с |
| Результат выполнения команды | Агент → Control Plane | По факту |

#### Получение изменений

Модель доставки — long-poll. Агент отправляет запрос с текущими курсорами и удерживает соединение;
Control Plane отвечает при изменении любого из потоков либо по истечении таймаута удержания.

```text
GET /agent/v1/state?config_version=145&users_seq=20431
    таймаут удержания: 30 с
```

Ответ содержит инкрементальные изменения относительно переданных курсоров, новые значения курсоров и
контрольную сумму полного состояния.

Полный снапшот запрашивается явно: при первом запуске агента, при расхождении контрольной суммы и
периодически, не реже одного раза в сутки.

Отсутствие изменений в течение таймаута приводит к ответу без изменений. Агент немедленно открывает
следующий запрос. Задержка распространения изменения определяется требованием Н-13.

Агент применяет джиттер к моменту переподключения и экспоненциальную задержку при ошибках. Требование
исключает одновременное переподключение всех нод после перезапуска Control Plane.

#### Применение изменений

| Поток | Способ применения |
| :--- | :--- |
| Состав пользователей | Горячее добавление и удаление через API Xray, без перезапуска процесса (допущение Д-4) |
| Структурная конфигурация | Перезапись конфигурации и перезапуск Xray |

Перед перезапуском Xray выполняется финальное чтение счётчиков и отправка отчёта (§5.9).

Агент подтверждает применение, передавая применённые значения курсоров. До подтверждения Control
Plane считает состояние непримененным.

#### Канал команд

Команды доставляются в том же ответе long-poll, что и изменения состояния. Отдельного канала нет.

```text
command_id      — идентификатор, ключ идемпотентности
type            — restart_xray | rotate_credentials | collect_diagnostics | update_agent
issued_at
expires_at      — по истечении команда не выполняется
payload
```

Требования:

* Повторная доставка команды с тем же `command_id` не приводит к повторному выполнению.
* Команды выполняются в порядке возрастания `issued_at`.
* Просроченная команда не выполняется; агент возвращает результат `expired`.
* Выдача команд по статусам ноды определяется матрицей влияния §4.6.
* Результат выполнения содержит `command_id`, статус и текст ошибки.

Статусы команды: `issued`, `delivered`, `applied`, `failed`, `expired`.

#### Версионирование и совместимость

Rolling updates отнесены к §10, поэтому смешанный парк версий агента является штатным состоянием.

* Версия API входит в путь. Изменение, ломающее совместимость, вводит новую версию пути.
* Control Plane поддерживает предыдущую версию API не менее трёх релизов.
* Агент передаёт свою версию в каждом запросе. Control Plane отклоняет неподдерживаемую версию с
  явной ошибкой, а не тихим игнорированием полей.
* Неизвестное поле в ответе агент игнорирует. Неизвестный обязательный раздел состояния переводит
  ноду в Degraded и порождает алерт: расхождение не должно быть невидимым.

#### Поколение конфигурации

Помимо монотонных курсоров Control Plane хранит `state_generation` — значение, изменяемое при
восстановлении базы из резервной копии.

Требование введено потому, что после восстановления курсоры откатываются назад: агент, применивший
`config_version 145`, не переприменит `config_version 130` при сравнении «больше — меньше». При
несовпадении `state_generation` агент запрашивает полный снапшот и применяет его безусловно.

#### Поведение при недоступности Control Plane

* Агент продолжает обслуживать пользователей по последней применённой конфигурации (Н-7).
* Отчёты о трафике накапливаются в локальном буфере (§5.9).
* Истечение срока подписки локально не применяется: в состоянии ноды нет срока. Отзыв по этому
  основанию выполняется потоком состава после восстановления связи.
* Исчерпание лимита применяется локально по гранту квоты `quota_grant_bytes` (§4.11): при его
  исчерпании агент переводит пользователя в `suspended_quota` без участия Control Plane.
* После восстановления связи агент отправляет буфер и запрашивает состояние.

---

### 5.3 Безопасность Node Communication

Механизм восстановления доверия после отката базы: Control Plane принимает предыдущее поколение
identity ноды в течение окна перекрытия (Н-28) и продлевает это окно автоматически при изменении
`state_generation` (§5.2). Агент, получивший отказ аутентификации, переходит к повторному
подтверждению по сохранённому на ноде секрету, не требуя ручного доступа к серверу.

Каждая нода должна иметь собственную identity.

Например:

```text
Node ID

Certificate / token

Private credential
```

Необходимо поддерживать:

* rotation;
* revoke;
* expiration;
* regeneration.

Нельзя использовать единый credential для всех серверов.

---

### 5.4 Версионирование конфигурации

Для каждой ноды хранятся четыре значения и поколение состояния:

```text
Control Plane                     Node Agent
  desired config_version: 145       applied config_version: 143
  desired users_seq:      20431     applied users_seq:      20431
  state_generation:       7         state_generation:       7
```

Расхождение любой пары отображается администратору в карточке ноды и в списке нод.

Расхождение, сохраняющееся дольше 120 с, порождает алерт. Значение равно удвоенному максимуму Н-13.

Значения курсоров монотонно возрастают в пределах одного `state_generation`. Правила изменения
`state_generation` и поведение агента при его несовпадении описаны в §5.2.

### 5.5 Протокольная абстракция

Добавление нового протокола или транспорта не должно требовать изменения модели пользователей,
подписок, тарифов и учёта трафика.

Единицей абстракции является профиль — сочетание протокола, транспорта и транспортной безопасности,
существующее на ноде в виде отдельного inbound (§4.4).

```text
Profile
 ├── protocol      — VLESS, Trojan, в будущем Hysteria2, TUIC, Shadowsocks, WireGuard
 ├── transport     — RAW, XHTTP, в будущем другие
 ├── security      — REALITY, TLS
 ├── параметры профиля
 └── генератор клиентской конфигурации для каждого формата подписки (§5.6)
```

Реализация MVP — три профиля из §4.4: `vless-raw-vision`, `vless-xhttp`, `trojan-reality`.

Набор выбран так, чтобы абстракция была проверена в MVP по двум осям: два разных протокола и два
разных транспорта. Профиль с единственным протоколом не проверяет расширяемость.

Требование к модели: параметры принадлежат профилю, а не ноде и не пользователю. Добавление профиля
не изменяет схему пользователя.

Ограничение: WireGuard в эту модель не укладывается без дополнительных решений. Он требует адресного
плана и пары ключей на каждое соединение, а не общего credential, и не поддерживается частью
клиентов §4.2. При его добавлении модель профиля расширяется отдельным решением.

---

### 5.6 Контракт subscription-эндпоинта

#### Форматы MVP

«Универсального» формата подписки не существует: клиенты §4.2 потребляют разные представления.

| Формат | Представление | Клиенты §4.2 |
| :--- | :--- | :--- |
| `base64` | Список ссылок `vless://` и `trojan://`, разделённых переводом строки, закодированный в base64 | Shadowrocket, v2rayNG, Streisand |
| `singbox` | JSON конфигурации sing-box | sing-box, Hiddify |

Форматы Mihomo и Clash отнесены к §10.

Формат `singbox` генерируется по схеме конфигурации закреплённой версии sing-box (§17.3). Поля, не
существующие в этой версии, не используются.

#### Матрица «профиль × формат»

Формат не выражает произвольный профиль. sing-box не поддерживает транспорт XHTTP: в его схеме
транспорт ограничен значениями `http`, `ws`, `quic`, `grpc`, `httpupgrade`, неизвестное значение
приводит к ошибке.

| Профиль (§4.4) | `base64` | `singbox` |
| :--- | :--- | :--- |
| `vless-raw-vision` | Да | Да |
| `vless-xhttp` | Да | Нет |
| `trojan-reality` | Да | Да |

Требования:

* Генератор конфигурации возвращает признак «профиль неприменим для формата».
* Эндпоинт исключает неприменимые пары «нода × профиль» из ответа, а не выдаёт неработающую запись.
* Для клиента sing-box резервным профилем служит `trojan-reality` на отдельном порту: он выражается
  в формате `singbox` и закрывает сценарий ограничения соединений на порту основного профиля.
  Сценарий, в котором помогает именно XHTTP, для клиента sing-box в MVP не покрыт; это фиксируется
  в реестре клиентов §17.10.
* Клиент Hiddify использует собственную сборку и допускает переключение ядра; его поведение с
  профилем `vless-xhttp` проверяется в PoC-1а и заносится в реестр §17.10.

#### Выбор формата

Формат определяется по заголовку `User-Agent` запроса. Соответствие «подстрока User-Agent → формат»
задаётся конфигурацией и изменяется без выпуска новой версии.

Явное указание формата в пути переопределяет определение по `User-Agent`:

```text
https://{домен}/s/{token}            — формат по User-Agent
https://{домен}/s/{token}/base64     — принудительно base64
https://{домен}/s/{token}/singbox    — принудительно sing-box
```

Неизвестный `User-Agent` без явного суффикса обслуживается форматом `base64`.

Обращение из браузера возвращает страницу подписки с инструкциями и кнопками импорта, а не файл
конфигурации.

#### Заголовки ответа

| Заголовок | Содержание |
| :--- | :--- |
| `subscription-userinfo` | `upload`, `download`, `total`, `expire`; значения в байтах и в формате времени Unix |
| `profile-update-interval` | Рекомендуемый интервал обновления в часах |
| `profile-title` | Отображаемое имя профиля |
| `announce` | Текст объявления, используется при инцидентах |
| `support-url` | Адрес поддержки |

Заголовки являются отраслевым соглашением, а не спецификацией, и поддерживаются клиентами
неоднородно. В частности, `profile-update-interval` не поддерживается v2rayNG (допущение Д-6), а
поддержка заголовка `announce` ни одним из пяти клиентов §4.2 не подтверждена.

Фактическая поддержка каждого заголовка каждым клиентом проверяется в PoC-1 и заносится отдельной
колонкой в реестр клиентов §17.10.

Поэтому лимит трафика, срок действия и объявления дублируются на странице подписки и в личном
кабинете. Работоспособность требования §4.3 не зависит от поддержки заголовков клиентом.

#### Состояния эндпоинта

| Состояние | Код ответа | Тело |
| :--- | :--- | :--- |
| `active` | 200 | Конфигурация в выбранном формате |
| `expired` | 200 | Пустой список серверов и заголовок `announce` с причиной |
| `traffic_exceeded` | 200 | Пустой список серверов и заголовок `announce` с причиной |
| `blocked` | 200 | Пустой список серверов и заголовок `announce` с причиной |
| `unknown_token` | 404 | Пусто |

Ответ 404 и пустое тело клиенты в общем случае игнорируют, сохраняя предыдущий профиль. Поэтому для
состояний, отличных от `unknown_token`, возвращается код 200 с пустым списком и объявлением. Это
способ показать причину средствами клиента там, где заголовок `announce` поддерживается; там, где он
не поддерживается, причина доступна на странице подписки и в личном кабинете.

Нулевое число доступных серверов при активной подписке обрабатывается как состояние `active` с
пустым списком и объявлением; событие порождает алерт.

#### Токен подписки

| Свойство | Значение |
| :--- | :--- |
| Энтропия | Не менее 128 бит (Н-25) |
| Срок действия | Бессрочный |
| Ротация | Только по явному действию пользователя или администратора |
| Перевыпуск | Создаёт новый токен, немедленно делает прежний недействительным и ротирует VPN-credentials пользователя на всех нодах |
| Логирование | Путь запроса не записывается в логи обратного прокси и приложения |
| Защита от перебора | Отдельный порог ограничения частоты для несуществующих токенов, независимый от порога для существующих |

Перевыпуск ротирует VPN-credentials, поэтому он разрывает работу всех устройств пользователя. Это
поведение отображается в интерфейсе до подтверждения действия.

#### Домены

В MVP используются два домена подписки в разных зонах регистрации. Оба выдаются пользователю в
личном кабинете и в письме об активации.

Домены обслуживают одинаковый контент и не используются для административного API. Требование
введено как техническая реакция на риск Р-1: при блокировке одного домена пользователь переключается
самостоятельно.

#### Содержимое ответа

Для каждой доступной пользователю пары «нода × профиль» (§4.4) формируется отдельная запись.
Отображаемое имя записи содержит код ноды, код профиля и коэффициент трафика, если он отличается от
1.0 (§4.9).

В формате `singbox` дополнительно формируется автоселектор `urltest`, обеспечивающий переключение на
доступный сервер без участия пользователя. В формате `base64` автоселектор невозможен: это плоский
список ссылок.

### 5.7 Масштабируемость

Целевой масштаб MVP задан ограничением О-3 и требованиями §13: до 1 000 активных пользователей и до
10 нод. Нефункциональные требования §13 проверяются на приёмке именно на этих значениях.

Требование к архитектуре: рост до 20 000 пользователей и 50 нод не должен требовать замены модели
данных, контракта Node API (§5.2) и контракта subscription-эндпоинта (§5.6).

Известные границы, за которыми требуется изменение архитектуры, а не конфигурации:

| Граница | Что перестаёт работать | Что требуется |
| :--- | :--- | :--- |
| Полная выгрузка состава пользователей на ноду | Размер состояния и частота его пересылки | Инкрементальные дельты — уже заложены в §5.2 |
| Один экземпляр API | Отказ одного процесса останавливает обслуживание | Несколько экземпляров за балансировщиком, состояние сессий вне процесса |
| Одна база без секционирования таблиц статистики | Время выполнения запросов агрегации | Секционирование — уже заложено в Н-22 |
| Выдача всем нодам credentials всех пользователей | Радиус поражения при компрометации ноды | Подмножества по группам доступа — уже заложено в §11.3 |

Значения 100 000 пользователей и 200 нод в настоящем документе не являются требованием и на приёмке
не проверяются.

### 5.8 Асинхронные задачи

Долгие операции не блокируют API. Фоновая обработка разделена на две очереди с раздельными пулами
исполнителей.

| Очередь | Задачи | Приоритет |
| :--- | :--- | :--- |
| Критичный путь | Генерация конфигураций, изменение состава пользователей, отзыв доступа, выдача гранта квоты, применение списка блокируемых адресов | Высокий |
| Фон | Рассылка почты, вызовы webhook, агрегация статистики, сверки, резервное копирование, отчёты | Обычный |

Разделение обязательно: без него массовая рассылка почты по §4.17 задерживает отзыв доступа и
делает Н-13 и Н-14 недостижимыми.

Требования к обработке:

| Требование |
| :--- |
| Доставка не менее одного раза; обработчики, изменяющие баланс или состав пользователей, идемпотентны по ключу задачи |
| Повторы с экспоненциальной задержкой и ограничением числа попыток |
| Очередь необработанных задач с алертом (§17.4) |
| Задачи переживают перезапуск брокера (§4.20) |
| Время ожидания задачи критичного пути в очереди не превышает половины бюджета Н-13 |

### 5.9 Контракт учёта трафика

#### Конвейер

```text
Xray (Stats API)
    ↓ чтение счётчиков
Node Agent
    ↓ агрегация за интервал + локальный буфер
Control Plane
    ↓ дедупликация и применение коэффициента
Hourly records → Daily records
```

Интервал отчёта — 60 секунд. Значение определяет верхнюю границу перерасхода Н-17 и не изменяется
без пересмотра Н-17.

#### Семантика счётчиков

Счётчики Stats API хранятся в памяти процесса Xray и обнуляются при его перезапуске (допущение Д-3).
Контракт учёта обязан быть устойчив к перезапуску (Н-19).

Node Agent читает счётчики в кумулятивном режиме, без сброса, и вычисляет дельты самостоятельно.

Node Agent генерирует значение `counter_epoch` при каждом запуске или перезапуске процесса Xray и
передаёт его в каждом отчёте. Дельта вычисляется только внутри одного `counter_epoch`. Смена
`counter_epoch` означает базовую точку 0.

Перед плановым перезапуском Xray выполняется финальное чтение счётчиков и их отправка. При
внеплановом перезапуске теряется объём, переданный с момента последнего успешного отчёта; величина
входит в бюджет Н-18.

Убывание счётчика в пределах одного `counter_epoch` является ошибкой. Такое событие записывается в
журнал, порождает алерт и не изменяет баланс пользователя.

#### Идемпотентность доставки

Доставка отчётов является at-least-once: потеря ответа заставляет агента повторить отчёт (Н-20).

Отчёт содержит ключ идемпотентности `(node_id, counter_epoch, report_seq)`, где `report_seq` —
монотонный номер отчёта в пределах `counter_epoch`. Control Plane хранит ограничение уникальности по
этому ключу. Повторный приём отчёта не изменяет балансы и возвращает признак дубликата.

Ответ Control Plane содержит `last_accepted_seq`, по которому агент определяет точку продолжения.

#### Буфер на ноде

Node Agent хранит неотправленные отчёты в локальном персистентном буфере. Буфер переживает
перезапуск агента и недоступность Control Plane (Н-8).

| Свойство | Значение |
| :--- | :--- |
| Ёмкость буфера | Не менее 24 часов отчётов |
| Поведение при переполнении | Наиболее старые отчёты отбрасываются, событие фиксируется в журнале и порождает алерт |
| Порядок отправки | В порядке возрастания `report_seq` |

#### Вывод ноды из эксплуатации

Принцип §3.2 делает уничтожение ноды штатным сценарием. Перед выводом ноды выполняется
принудительная отправка буфера и финальное чтение счётчиков.

Если нода уничтожена без вывода из эксплуатации, период недоучёта фиксируется записью с явным
признаком: интервал, нода, причина. Такие интервалы исключаются из расчёта Н-18.

#### База списания

С лимита списывается `uplink + downlink` (§4.11). Значения `uplink` и `downlink` хранятся раздельно.

Служебный трафик Node Agent не входит в списание. Трафик API-инбаунда Xray не попадает в
пользовательские счётчики, на которых основано списание: счётчик пользователя создаётся только при
непустом идентификаторе, а у служебного инбаунда пользователя нет. В инбаунд-счётчиках по тегу этот
трафик учитывается и в базу списания не входит.

#### Хранимые поля записи

```text
node_id
user_id
period_start
period_end
counter_epoch
raw_uplink_bytes
raw_downlink_bytes
billable_bytes
traffic_multiplier   — значение, применённое к этой записи
billing_group_id     — тарифицируемая группа на момент создания записи
```

Поле `billable_bytes` неизменяемо. Изменение коэффициента не приводит к пересчёту ранее записанных
значений (§4.9). Пересчёт «что если» выполняется только в аналитическом слое (§5.10, §6.13) и не
изменяет ни записи статистики, ни баланс пользователя.

#### Два источника трафика

Учёт ведётся по двум независимым источникам:

| Источник | Назначение | Основание |
| :--- | :--- | :--- |
| Счётчики пользователей Xray | Списание с лимита, статистика пользователя | Stats API, тег `email` на пользователя |
| Сетевые счётчики интерфейса ноды | Экономика инфраструктуры, сверка со счётом хостера | Показания ОС на ноде |

Второй источник не участвует в списании. Расхождение между источниками является ожидаемым:
пользовательские счётчики не включают служебный трафик, накладные расходы протокола и трафик
fallback.

#### Включение счётчиков и идентификатор пользователя

Пользовательские счётчики Xray включаются в конфигурации, генерируемой Control Plane. Без них
списание невозможно.

Значение тега, по которому счётчик связывается с пользователем, формируется из устойчивого
идентификатора пользователя и не содержит credential. Требование введено потому, что credentials
различны на каждой ноде (§11.3) и ротируются, а идентификатор пользователя обязан оставаться
стабильным при ротации и при пересоздании ноды.

#### Синхронизация времени и поздние отчёты

Границы периода в записи формируются по часам ноды.

| Требование |
| :--- |
| Часы ноды синхронизируются по протоколу сетевого времени; допустимое отклонение — 5 с |
| Отчёт с отклонением границ периода больше допустимого отклоняется и порождает алерт |
| Отчёт, поступивший за уже закрытый период агрегации, принимается и относится к своему периоду; суточный агрегат пересчитывается |
| Коэффициент выбирается по интервалу `[period_start, period_end)`, а не по моменту приёма отчёта |

Последнее правило обязательно: буфер допускает досылку отчётов возрастом до 24 часов, и выбор
коэффициента по моменту приёма нарушал бы запрет ретроактивного изменения списаний (§4.9).

#### Защита от аномального отчёта

Нода является недоверенной средой (допущение Д-8), а её отчёт — самоотчётом. Проверяется не только
убывание счётчика, но и верхний предел прироста.

| Требование |
| :--- |
| Прирост трафика пользователя за интервал отчёта, превышающий физически достижимый на канале ноды, не списывается |
| Порог выводится из полосы пропускания канала ноды и задаётся её конфигурацией |
| Отчёт с превышением удерживается до разбора и порождает алерт |
| Тот же порог применяется к суммарному отчёту ноды |

#### Сверка

Выполняются три независимые сверки.

| Сверка | Что сравнивается | Реакция |
| :--- | :--- | :--- |
| Арифметическая, ежесуточно | Сумма принятых отчётов по нодам против изменения баланса пользователей за те же сутки | Расхождение свыше Н-18 порождает алерт |
| Межисточниковая, ежесуточно | Сумма `raw_bytes` пользователей ноды против сетевых счётчиков её интерфейса | Расхождение свыше коридора допуска порождает алерт |
| Непрерывность отчётов, постоянно | Пропуск `report_seq` в пределах `counter_epoch`; неизвестный `counter_epoch` | Фиксируется запись пропуска с оценкой объёма, порождается алерт |

Первая сверка проверяет только арифметику Control Plane: обе величины производны от одних и тех же
отчётов. Дефекты доставки и учёта выявляют вторая и третья.

Коридор допуска межисточниковой сверки задаётся конфигурацией: расхождение ожидаемо, поскольку
пользовательские счётчики не включают служебный трафик и накладные расходы протокола.

Каждое списание прослеживается до конкретного отчёта конкретной ноды по ключу
`(node_id, counter_epoch, report_seq)`.

#### Агрегация и хранение

| Уровень | Гранулярность | Срок хранения |
| :--- | :--- | :--- |
| Почасовые записи | Пользователь × нода × час | 90 дней (Н-21) |
| Суточные агрегаты | Пользователь × нода × сутки | 24 месяца (Н-21) |

Таблица почасовых записей партиционируется по суткам (Н-22). Отдельные события трафика в основную
базу не записываются.

### 5.10 Экономическая аналитика серверов

Поскольку разные серверы имеют различную стоимость содержания, архитектура должна позволять в будущем рассчитывать экономику инфраструктуры.

Для сервера желательно хранить:

```text
Monthly server cost

Traffic cost

Provider

Currency
```

Поля хранятся в модели данных MVP (§4.4, §10) и не обязаны отображаться в интерфейсе.

Состав полей экономики ноды:

```text
monthly_cost
currency
provider_account
cost_valid_from          — период действия стоимости
cost_valid_to
traffic_included_bytes   — включённый в тариф провайдера объём
traffic_overage_cost     — стоимость гигабайта сверх включённого объёма
```

Историчность обязательна: стоимость сервера меняется, а расчёт экономики за прошедший период должен
использовать значение, действовавшее в том периоде.

В будущем можно рассчитывать:

```text
Revenue per node

Cost per GB

Profitability

Cost per active user

Server utilization
```

Traffic Multiplier должен быть отделён от фактической стоимости сервера.

То есть:

```text
Server Cost
```

— это реальная экономика.

А:

```text
Traffic Multiplier
```

— бизнес-правило списания пользовательского трафика.

Это две независимые сущности.

#### Решения по политикам

| Политика | Решение |
| :--- | :--- |
| Просмотр subscription URL пользователя | Доступен ролям Support и выше; равнозначен доступу к VPN пользователя, поэтому каждый просмотр регистрируется в Audit Log |
| Работа от лица пользователя | Разрешена в режиме только для чтения; начало и завершение регистрируются; пользователь уведомляется |
| Начисление трафика и продление подписки | Операции сверх порога, заданного настройкой, требуют второго подтверждения другой учётной записью |
| Уменьшение баланса трафика вручную | Требует указания причины; причина попадает в Audit Log |

#### Аутентификация административных ролей

| Требование |
| :--- |
| Второй фактор обязателен для всех административных ролей |
| Сессия истекает после 12 часов бездействия (Н-27) |
| Блокировка учётной записи инвалидирует её сессии не позднее 60 с (Н-27) |
| Смена пароля и перевыпуск второго фактора инвалидируют все сессии, кроме текущей |
| Действие «выход на всех устройствах» доступно пользователю и администратору |
| При включении второго фактора выдаются резервные коды восстановления; их использование регистрируется в Audit Log |
| Сброс второго фактора по одному лишь доступу к почте запрещён; процедура восстановления требует участия второго держателя доступов (§17.12) и уведомляет остальных администраторов |

Требование к инвалидации введено потому, что схема сессий без серверного состояния делает
неисполнимыми уже заявленные требования: блокировка не подействует до истечения токена, а выход
окажется формальным.

### 5.12 Ограничение частоты запросов

Ограничение задаётся ключом, порогом и реакцией. Ключ определяет, что именно ограничивается.

| Защищаемая операция | Ключ | Реакция при превышении |
| :--- | :--- | :--- |
| Вход | Раздельно по адресу источника и по учётной записи | CAPTCHA; блокировка учётной записи не применяется |
| Регистрация | Адрес источника и домен адреса электронной почты | CAPTCHA |
| Восстановление пароля | Адрес электронной почты | Отказ с задержкой |
| Повторная отправка письма подтверждения | Адрес электронной почты | Отказ с задержкой |
| Subscription-эндпоинт, существующий токен | Токен | Отказ |
| Subscription-эндпоинт, несуществующий токен | Адрес источника, отдельный и более низкий порог | Отказ |
| Активация промокода и Redeem-кода | Учётная запись и адрес источника | Отказ |
| Перевыпуск subscription-токена | Учётная запись | Отказ |
| Публичный API | Учётная запись | Отказ |
| Node API | Identity ноды | Отказ |

Ограничение subscription-эндпоинта по адресу источника не применяется: в мобильных сетях с общим
адресом трансляции это отсекает добросовестных пользователей.

Node Agent применяет случайное смещение момента отправки heartbeat и экспоненциальную задержку при
ошибках (§5.2). Требование исключает ситуацию, в которой одновременное переподключение всех нод
после перезапуска Control Plane выводит его из строя.

### 5.13 Secrets Management

Требования настоящего раздела относятся к Control Plane.

В Control Plane нельзя хранить в открытом виде:

* private keys;
* API keys;
* passwords;
* node credentials;
* database credentials.

Необходимо предусмотреть безопасное хранение и возможность ротации секретов. Ротация identity ноды
выполняется с окном перекрытия и не переводит ноду в Offline (Н-28). Ключ шифрования бэкапов
хранится вне контура, восстанавливаемого из этих бэкапов (Н-12).

На VPN-ноде секреты хранятся в открытом виде: этого требует формат конфигурации Xray (допущение
Д-9). Распространить требование настоящего раздела на ноду невозможно. Вместо него действуют
компенсирующие требования §11.3: уникальный ключевой материал на ноду, ограничение состава
выдаваемых ноде credentials, отзыв identity и ротация credentials при компрометации, затирание
секретов при выводе ноды из эксплуатации.

## 8. Сквозные сценарии

### 8.1 Основной сценарий

```text
1.  Администратор создаёт тарифицируемые группы: Standard (1.0) и Premium Asia (2.0).
2.  Администратор создаёт группы доступа: Europe, USA, Asia Premium.
3.  Администратор создаёт тариф Premium: 30 дней, 500 ГБ,
    группы доступа Europe, USA, Asia Premium.
4.  Администратор создаёт ноду JP-Tokyo-01: тарифицируемая группа Premium Asia,
    переопределение коэффициента 3.0, группа доступа Asia Premium.
5.  Control Plane генерирует ключевой материал REALITY для трёх inbound ноды
    и одноразовый bootstrap-токен.
6.  Администратор выполняет bootstrap-команду на VPS, нода переходит в Pending.
7.  Администратор подтверждает ноду; она получает состояние и переходит в Active.
8.  Пользователь регистрируется, подтверждает адрес, активирует подписку Redeem-кодом.
9.  Пользователь получает subscription URL на двух доменах.
10. Клиент запрашивает подписку; формат выбран по User-Agent.
11. Ответ содержит по три записи на каждую доступную ноду — по одной на профиль.
    Имя записи ноды JP-Tokyo-01 содержит коэффициент 3.0.
12. Пользователь подключается к JP-Tokyo-01 и передаёт 10 ГБ.
13. Node Agent отправляет отчёт с ключом идемпотентности; Control Plane записывает
    raw_bytes = 10 ГБ, billable_bytes = 30 ГБ, traffic_multiplier = 3.0.
14. Пользователь видит фактический объём 10 ГБ и списанный 30 ГБ.
15. Нода перестаёт слать heartbeat; после трёх пропусков она переходит в Offline
    и исключается из новых ответов эндпоинта.
16. Пользователь продолжает работу через другие ноды: у клиента остаётся
    ранее полученный профиль с остальными серверами.
17. Администратор создаёт новый VPS для той же записи Node и выполняет
    новый bootstrap; прежняя identity отозвана.
18. Нода получает тот же ключевой материал REALITY и переходит в Active.
19. При изменившемся адресе пользователи затронутой ноды получают уведомление;
    ранее скачанные конфигурации восстанавливаются после обновления подписки.
```

### 8.2 Исчерпание лимита

```text
1.  Израсходовано 80 % лимита — пользователь получает уведомление.
2.  Израсходовано 95 % — второе уведомление.
3.  Израсходовано 100 % — Control Plane переводит пользователя
    в состояние suspended_quota во всех потоках состава.
4.  Ноды применяют изменение не позднее 60 с (Н-14).
5.  Установленные соединения разрываются не позднее 60 с (Н-17а);
    суммарный перерасход не превышает 3 ГБ raw (Н-17).
6.  Subscription-эндпоинт возвращает пустой список и объявление с причиной.
7.  Пользователь активирует Redeem-код с бонусом трафика;
    доступ восстанавливается за то же время.
```

### 8.3 Истечение и продление подписки

```text
1.  За заданный срок до окончания пользователь получает уведомление.
2.  В момент истечения пользователь переводится в состояние expired.
3.  Ноды применяют изменение; эндпоинт возвращает пустой список и объявление.
4.  Продление Redeem-кодом начинает новый период: от текущей даты окончания,
    если подписка активна, и от момента активации, если она истекла (§4.11).
5.  Лимит устанавливается равным лимиту тарифа; израсходованный объём обнуляется;
    неиспользованный остаток прежнего периода не переносится.
```

### 8.4 Смена тарифа с уменьшением набора групп

```text
1.  Администратор переводит пользователя на тариф без группы Asia Premium.
2.  Лимит и срок заменяются значениями нового тарифа; израсходованный объём переносится.
3.  Состав пользователей нод группы Asia Premium изменяется;
    пользователь удаляется из их inbound.
4.  Установленные соединения к этим нодам не разрываются.
5.  Следующий ответ эндпоинта не содержит серверов группы Asia Premium.
```

### 8.5 Подозрение на перепродажу доступа

```text
1.  У пользователя один адрес источника, но число одновременных соединений
    достигает предела, заданного на ноде (Н-29).
2.  Соединения сверх предела отклоняются на ноде.
3.  Признаки перепродажи — объём, частота новых соединений, круглосуточность —
    отображаются в карточке пользователя.
4.  Администратор принимает решение и при подтверждении блокирует пользователя
    с указанием причины в Audit Log.
```

### 8.6 Массовая недоступность нод одного провайдера

```text
1.  Провайдер приостанавливает несколько нод; администратор переводит их
    в статус Suspended.
2.  Ноды исключаются из выдачи; число доступных пользователю серверов
    может стать нулевым.
3.  Эндпоинт возвращает код 200, пустой список и объявление с причиной;
    событие порождает алерт.
4.  Объявление публикуется на странице состояния и в независимом канале (§17.11).
5.  После ввода замещающих нод выдача восстанавливается автоматически.
```

### 8.7 Блокировка домена подписки

```text
1.  Один из двух доменов перестаёт открываться у части пользователей.
2.  Пользователь переключается на второй домен, выданный ему при активации.
3.  Оператор регистрирует событие и вводит замещающий домен.
4.  Смена домена объявляется через независимый канал со способом
    проверки подлинности нового адреса (§17.11).
```

### 8.8 Восстановление Control Plane

```text
1.  Control Plane недоступен.
2.  Ноды продолжают обслуживать пользователей по последней применённой
    конфигурации (Н-7); отчёты накапливаются в буфере.
3.  Выдача подписок недоступна; уже установленные соединения работают.
4.  Control Plane восстанавливается из резервной копии; state_generation изменяется.
5.  Агенты обнаруживают несовпадение поколения и запрашивают полный снапшот.
6.  Буферы отправляются; повторные отчёты отбрасываются по ключу идемпотентности.
7.  Сверка за период недоступности выявляет расхождение и порождает алерт,
    если оно превышает Н-18.
```

## 9. Допущения и ограничения

### 9.1 Допущения

Допущения проверены по официальной документации и исходному коду на 2026-09-04. Каждое допущение
перепроверяется при смене любой закреплённой версии Xray-core (§17.3), а не только мажорной:
имена полей конфигурации переименовывались внутри одной мажорной версии.

| № | Допущение | Основание |
| :--- | :--- | :--- |
| Д-1 | Xray-core не выполняет ограничение по квоте трафика. Отключение пользователя выполняет Control Plane удалением клиента из inbound | `LevelPolicyObject` содержит тайминги (`handshake`, `connIdle`, `uplinkOnly`, `downlinkOnly`), флаги статистики и `bufferSize`; поля квоты в нём нет |
| Д-2 | Удаление пользователя из inbound не разрывает установленные соединения. `connIdle` (по умолчанию 300 с) — таймаут бездействия: активно передающее соединение им не прерывается вообще | `proxy/vless/validator.go`, метод `Del` очищает map; таймер бездействия сбрасывается при каждой передаче данных |
| Д-3 | Счётчики Stats API хранятся в памяти процесса Xray и обнуляются при его перезапуске; у чтения есть режим `reset` | `app/stats/stats.go`, `app/stats/counter.go`, `command.proto` |
| Д-4 | Добавление и удаление пользователя выполняются без перезапуска процесса, через `HandlerService.AlterInbound`; поддерживаются VMess, VLESS, Trojan, Shadowsocks; удаление выполняется по полю `email` | `app/proxyman/command/command.proto`, документация `config/api` |
| Д-5 | Xray-core не ограничивает число одновременных подключений и число устройств; предоставляется только наблюдение через `GetStatsOnlineIpList` и `GetAllOnlineUsers` | Запросы `#2118` и `#4567`, последний закрыт со статусом not planned |
| Д-6 | Клиент обновляет подписку по собственному расписанию; заголовок `profile-update-interval` поддерживается не всеми клиентами | `2dust/v2rayNG` issue `#3438`: клиент заголовок не поддерживает |
| Д-7 | Trojan работает поверх REALITY; собственный домен и TLS-сертификат не обязательны | Матрица совместимости `transport.md`: `trojan` + `security=reality` поддерживается |
| Д-8 | VPN-нода размещается у стороннего провайдера и является недоверенной средой | §11 |
| Д-9 | Секреты пользователей и приватный ключ REALITY хранятся на ноде в открытом виде; иначе Xray не работает | Требование формата конфигурации Xray |
| Д-10 | Инфраструктура создаётся с нуля: действующих пользователей и нод для миграции нет | Подтверждено, ОВ-2 |
| Д-11 | `flow=xtls-rprx-vision` работает только с транспортом RAW и с TLS либо REALITY; с XHTTP недоступен | Документация VLESS; ядро отвергает сочетание |
| Д-12 | REALITY работает только с транспортами RAW, XHTTP и gRPC | Таблица совместимости `transport.md` |
| Д-13 | Число одновременных соединений пользователя через API Xray получить нельзя: внутренний счётчик не публикуется | `features/stats/stats.go`, интерфейс `OnlineMap` |
| Д-14 | За CDN или обратным прокси адрес источника схлопывается в один, если не задан `sockopt.trustedXForwardedFor` | `transport/internet/splithttp/hub.go` |

## 10. Вне рамок MVP

Перечисленное ниже не разрабатывается в MVP. Раздел является нормативным: работа, не попавшая ни в
§7, ни в этот раздел, считается неопределённой и подлежит уточнению до планирования.

- Приём платежей, рекуррентные платежи, автопродление, возвраты (§6.7, §6.8).
- Скидочные и процентные промокоды. Следствие О-2: без суммы заказа скидка не имеет объекта
  применения. В MVP остаются Redeem-коды и бонусы по трафику и сроку.
- Полноценное управление устройствами: список, last seen, удалённое отключение (§6.1).
- Ограничение числа одновременных подключений на пользователя как свойство тарифа (§6.2). Жёсткий
  лимит соединений с одного адреса источника на ноде (Н-29) в MVP входит.
- Месячный и произвольный лимит трафика (§4.11).
- Форматы подписки Mihomo и Clash (§5.6).
- Автоматизированный оркестратор поэтапного обновления парка (§6.5). Ручное канареечное обновление
  оператором (§17.3) в MVP входит.
- Интеграции через n8n (§4.18).
- Автоматическое создание VPS, интеграция с провайдерами, Terraform, Ansible (§6.3).
- Server Draining (§6.4) и Rolling Updates (§6.5).
- Протоколы, кроме VLESS+REALITY и Trojan (§6.6).
- Telegram-бот (§6.9) и мобильные приложения (§6.10).
- Smart Server Selection (§6.11), Capacity Planning (§6.12), Economics Dashboard (§6.13).
- Политики тарификации трафика сложнее иерархии §4.9: по тарифу, по времени суток, по пользователю
  (§6.14).
- White-label, внешний API для третьих лиц, партнёрская система (Phase 3).
- Языки интерфейса, писем и страницы подписки, кроме русского и английского (§17.8).

**Граница обязательства «архитектура должна позволять».** Для перечисленного выше обязательство
ограничивается тем, что модель данных и контракты не препятствуют добавлению. Абстракции,
интерфейсы расширения и точки подключения под эти возможности в MVP не создаются. Исключение
составляют четыре позиции, для которых поля закладываются в модель данных сразу, поскольку их
добавление задним числом требует миграции исторических данных:

| Позиция | Что закладывается в MVP | Раздел |
| :--- | :--- | :--- |
| Платежи | Сущности `Order` и `Payment`, связь подписки с основанием выдачи | §6.7 |
| Экономика ноды | Стоимость сервера, валюта, провайдер, период действия стоимости | §5.10 |
| Раздельный учёт | `raw_bytes` и `billable_bytes` с зафиксированным коэффициентом в записи | §5.9 |
| Обращения к подписке | Время, домен, формат, `User-Agent`, адрес источника | §16.1, §17.5 |

## 11. Границы доверия и модель угроз

### 11.1 Зоны доверия

| Зона | Статус | Следствие |
| :--- | :--- | :--- |
| Control Plane | Доверенная | Единственный источник истины (§3.1) |
| VPN-нода | Недоверенная | Компрометация ноды раскрывает VPN-credentials выданных ей пользователей и приватный ключ REALITY этой ноды. Отчёты ноды о трафике являются самоотчётом и подлежат сверке |
| Клиентское приложение | Недоверенное | Идентификатор устройства подделываем; ограничение устройств является оценочным, а не гарантией |
| Канал Control Plane ↔ нода | Защищаемый | Взаимная аутентификация, индивидуальная identity ноды (§5.3) |

Требование §5.13 о запрете хранения секретов в открытом виде относится к Control Plane. На ноде
секреты хранятся в открытом виде по требованию Xray (Д-9). Компенсирующие требования — §11.3.

### 11.2 Акторы угроз

| № | Актор | Возможности |
| :--- | :--- | :--- |
| У-1 | Хостинг-провайдер ноды | Физический доступ к диску и памяти, снятие снапшота, изъятие, отключение сервера по жалобе |
| У-2 | Цензор или оператор DPI | Наблюдение трафика пользователя, блокировка IP ноды, блокировка домена подписки |
| У-3 | Внешний злоумышленник | Перебор токенов подписки, попытка регистрации поддельной ноды, атака на публичные эндпоинты |
| У-4 | Инсайдер с административной ролью | Доступ к персональным данным, выдача себе доступа, изменение баланса трафика |
| У-5 | Недобросовестный пользователь | Передача подписки третьим лицам, мультиаккаунт, злоупотребление промокодами, abuse-трафик |

### 11.3 Компенсирующие требования для недоверенной ноды

- VPN-credentials выдаются на пару «пользователь × нода». Каждая нода получает собственный набор
  значений, действительных только на ней. Компрометация ноды не даёт доступа к остальным нодам.
- Нода получает credentials только тех пользователей, которым доступна хотя бы одна её группа
  доступа (§4.8).
- В статусах Pending и Provisioning нода не получает ни одного VPN-credential.
- При компрометации ноды выполняется отзыв её identity (Н-31), исключение из выдачи подписок,
  ротация VPN-credentials затронутых пользователей (Н-32) и обязательная смена ключевого материала
  REALITY этой ноды (§4.4, Н-33).
- При выводе ноды из эксплуатации секреты на диске затираются до уничтожения VPS.
- Приватный ключ REALITY уникален для каждой ноды. Компрометация одной ноды не затрагивает
  остальные.

## 13. Нефункциональные требования

Значения заданы для целевого масштаба О-3: до 1 000 активных пользователей и до 10 нод. Значения
являются нормативными и проверяются на приёмке (§14).

### 13.1 Нагрузка

| № | Требование | Обоснование |
| :--- | :--- | :--- |
| Н-1 | Subscription-эндпоинт обслуживает не менее 5 запросов в секунду | 1 000 подписок при обновлении раз в 6 часов дают 0,05 запроса в секунду; стократный запас на синхронные обновления после инцидента, повторы и обращения к двум доменам |
| Н-2 | API личного кабинета: не менее 10 запросов в секунду, p95 ≤ 300 мс, p99 ≤ 800 мс | — |
| Н-3 | Административный API: не менее 5 запросов в секунду, p95 ≤ 500 мс | — |
| Н-4 | Node API: не менее 2 запросов в секунду, p95 ≤ 200 мс | 10 нод при heartbeat раз в 30 с и отчёте статистики раз в 60 с дают 0,5 запроса в секунду |

### 13.2 Доступность

| № | Требование |
| :--- | :--- |
| Н-5 | Доступность subscription-эндпоинта: 99,5 % за календарный месяц (не более 3 часов 39 минут) |
| Н-6 | Доступность личного кабинета и административного API: 99,0 % за календарный месяц (не более 7 часов 18 минут) |
| Н-7 | Недоступность Control Plane не прерывает VPN-подключения: ноды обслуживают пользователей по последней применённой конфигурации не менее 24 часов |
| Н-8 | При недоступности Control Plane статистика буферизуется на ноде и не теряется в пределах ёмкости буфера §5.9 — не менее 24 часов |

Значения Н-5 и Н-6 согласованы с Н-10 и с ограничениями О-4 и О-6: одно восстановление,
укладывающееся в RTO 4 часа, расходует месячный бюджет Н-5 полностью. Развёртывание на одном хосте
без дежурства не позволяет задать более высокие значения. Плановое обслуживание в объявленном окне
(§17.4) в расчёт не входит.

### 13.3 Восстановление

| № | Требование |
| :--- | :--- |

## 14. Критерии приёмки

Критерий формулируется как проверяемое действие с ожидаемым результатом. Функция считается принятой
при выполнении критерия на стенде с не менее чем двумя реальными нодами в разных странах.

| Функция | Раздел | Критерий приёмки |
| :--- | :--- | :--- |
| Регистрация и вход | §4.1 | Регистрация с подтверждением адреса завершается входом; повторная регистрация того же адреса отклоняется; при закрытой регистрации форма недоступна |
| Восстановление пароля | §4.1 | Письмо доставлено, ссылка одноразовая, повторное использование отклонено |
| Subscription URL | §4.2, §5.6 | Каждый из пяти клиентов §4.2 импортирует подписку и устанавливает соединение; клиенту выдаются только применимые для его формата профили; перевыпуск токена делает прежний недействительным и ротирует credentials |
| Автообновление списка серверов | §4.3 | Перевод ноды в Offline исключает её из ответа эндпоинта в течение Н-15; возврат в Active возвращает её в ответ |
| Онбординг ноды | §4.5 | От выполнения bootstrap-команды до статуса Active проходит не более Н-16; нода в статусе Pending не получает ни одного VPN-credential |
| Статусы ноды | §4.6 | Каждый переход выполняется только разрешённым инициатором; нода в Maintenance не возвращается в Active автоматически |
| Health monitoring | §4.7 | Остановка Node Agent переводит ноду в Offline за 90 с; восстановление возвращает в Active после двух heartbeat |
| Server Groups | §4.8 | Добавление ноды в группу делает её доступной всем тарифам с этой группой без изменения тарифов |
| Traffic Multiplier | §4.9 | Передача 1 ГБ на ноде с коэффициентом 2,0 увеличивает `billable_bytes` на 2 ГБ и `raw_bytes` на 1 ГБ; изменение коэффициента не изменяет ранее записанные значения |
| Тарифы | §4.10 | Тариф ограничивает доступные группы и протоколы; смена тарифа изменяет состав серверов в подписке в течение Н-13 |
| Лимиты трафика | §4.11 | При исчерпании лимита доступ отзывается в течение Н-14, установленные соединения разрываются в течение Н-17а, перерасход не превышает Н-17; при недоступности Control Plane перерасход ограничен грантом Н-17в |
| Продление подписки | §4.11 | Продление активной подписки продлевает срок и обнуляет израсходованный объём; неиспользованный остаток не переносится |
| Статистика пользователя | §4.12 | Отображаются Raw Traffic с разделением на `uplink` и `downlink`, применённый Traffic Multiplier, Billable Traffic и остаток лимита по каждой ноде за период |
| Профили подключения | §4.4 | Каждый из трёх профилей ноды импортируется клиентом и устанавливает соединение; отключение одного профиля не влияет на остальные |
| Device limit | §4.13 | Превышение лимита уникальных адресов приводит к блокировке адресов сверх лимита правилом маршрутизации на ноде; при смене сети прежний адрес вытесняется и блокировка снимается; превышение лимита одновременных соединений с одного адреса отклоняется на ноде; признаки перепродажи отображаются в карточке пользователя |
| Redeem-коды | §4.14 | Код активирует подписку однократно; повторная активация отклоняется; массовая генерация и экспорт выполняются |
| Административная панель | §4.15 | Каждое действие раздела доступно только ролям с соответствующим разрешением и попадает в Audit Log |
| Audit Log | §4.16 | Запись содержит время, актора, роль, действие, сущность, прежнее и новое значение, адрес; изменение записи из приложения невозможно |
| Уведомления | §4.17 | Каждое из семи пользовательских событий порождает письмо и вызов webhook; каждое из пяти операторских — вызов webhook; повторные уведомления по одному событию подавляются |

| Версионирование конфигурации | §5.4 | Расхождение желаемой и применённой версии отображается администратору |
| Нагрузка | Н-1…Н-4 | Нагрузочная проверка на стенде: профиль соответствует О-3, длительность не менее 30 минут, целевые значения и перцентили достигнуты |
| Доступность | Н-5, Н-6 | Проверяется не на приёмке, а по данным эксплуатации за календарный месяц |
| Обновление парка | Н-26, §17.3 | Обновление применено на канареечной ноде, все клиенты §4.2 подключились, откат при неуспехе выполнен |

| :--- | :--- | :--- |
| Учётные данные | Адрес электронной почты, хеш пароля, дата регистрации | Работа личного кабинета |
| Данные обращений | Адрес источника при регистрации, входе и обращении к subscription-эндпоинту, `User-Agent` | Безопасность, поддержка, лимит адресов (§4.13) |
| Учёт потребления | Пользователь, нода, час, `raw_bytes`, `billable_bytes`, коэффициент | Биллинг, §5.9 |
| Онлайн-состояние | Уникальные адреса пользователя, время последней активности | Лимит адресов, §4.13 |
| Административные действия | Audit Log, §4.16 | Разбор инцидентов |

Система хранит связь «кто, когда, на какой ноде и в какой стране потреблял трафик». Почасовая
разбивка (§5.9) позволяет восстановить распорядок активности пользователя. Это осознанное решение,
принятое ради корректности биллинга; ограничением служат сроки хранения §16.2.

Содержимое трафика пользователя не записывается и не анализируется.

### 16.2 Сроки хранения

| Данные | Срок |
| :--- | :--- |
| Почасовые записи потребления | 90 дней (Н-21) |
| Суточные агрегаты потребления | 24 месяца (Н-21) |
| Записи обращений к subscription-эндпоинту | 30 дней |
| Адреса входа и регистрации | 90 дней |
| Audit Log | 12 месяцев (Н-23) |
| Журналы приложения | 30 дней |

Удаление по истечении срока выполняется автоматически.

### 16.3 Логирование на ноде

Журнал обращений Xray (`access.log`) по умолчанию отключён. Он содержит адреса источника и
назначения по каждому соединению и не требуется ни для биллинга, ни для лимита адресов: оба
механизма используют API статистики (§5.9, §4.13).

Включение журнала обращений выполняется администратором на ограниченный срок для диагностики и
регистрируется в Audit Log.

Журнал ошибок Xray ведётся постоянно и не содержит адресов назначения.

### 16.4 Удаление аккаунта

Пользователь может удалить аккаунт из личного кабинета. При удалении:

* учётные данные и данные обращений удаляются;
* VPN-credentials отзываются на всех нодах, subscription-токен аннулируется;
* записи потребления сохраняются с идентификатором пользователя, который после удаления
  персональных данных становится суррогатом и не связан ни с одним лицом; агрегаты сохраняются
  для экономической аналитики;
* записи Audit Log сохраняются; персональных данных они не содержат, ссылки — по идентификатору.

Данные в резервных копиях удаляются по истечении срока хранения копий, а не в момент удаления
аккаунта. Срок указывается в политике конфиденциальности.

### 16.5 Правила допустимого использования

Правила допустимого использования являются артефактом MVP. Пользователь принимает их при
регистрации; факт и версия принятия сохраняются.

Правила запрещают: рассылку нежелательных сообщений, сканирование сетей, атаки на отказ в
обслуживании, распространение вредоносного программного обеспечения, перепродажу доступа третьим
лицам (§4.13).

### 16.6 Ограничения исходящего трафика на ноде

| Ограничение | Назначение |
| :--- | :--- |
| Блокировка исходящих портов 25 и 587 | Рассылка нежелательных сообщений — основная причина жалоб провайдеру |
| Блокировка адресов частных сетей | Пользователь не должен достигать внутренней сети провайдера через ноду |
| Блокировка адреса службы метаданных облачного провайдера | Пользователь не должен достигать метаданных экземпляра VPS |
| Ограничение частоты новых исходящих соединений с одного адреса источника | Сканирование сетей |
| Ограничение числа одновременных соединений с одного адреса источника | Перепродажа доступа, Н-29 |

### 16.7 Реакция на обращения провайдера

Типичный срок ответа хостинг-провайдеру на жалобу — 24 часа. Процесс:

```text
Жалоба провайдера
      ↓
Регистрация обращения, статус ноды при необходимости Suspended (§4.6)
      ↓
Сопоставление времени и адреса назначения из жалобы с записями потребления
      ↓
Ответ провайдеру
      ↓
Блокировка пользователя при подтверждении нарушения
```

Состав данных, раскрываемых провайдеру, ограничен минимально необходимым для ответа. Требование
конфликтует с политикой минимизации §16.2 и разрешено в пользу сохранения инфраструктуры.

### 16.8 Противодействие фроду

| Риск | Мера |
| :--- | :--- |
| Мультиаккаунт при открытой регистрации | Нормализация адреса электронной почты, отклонение одноразовых доменов, подтверждение адреса |
| Перебор Redeem-кодов | Контрольная сумма в коде, отклонение неверных кодов без обращения к базе, ограничение частоты (§5.12) |
| Повторное использование кодов | Ограничения по числу использований и по числу использований на пользователя (§4.14) |
| Перепродажа доступа | §4.13 |

Убыток от злоупотребления считается в `billable_bytes`: на ноде с коэффициентом 3.0 он втрое выше
фактического расхода.

## 17. Эксплуатация и сопровождение

### 17.1 Окружения и тестовый контур

| Окружение | Состав | Назначение |
| :--- | :--- | :--- |
| Разработка | Control Plane локально, нода в контейнере | Разработка и модульные тесты |
| Стенд | Control Plane и не менее двух реальных нод в разных странах | Приёмка (§14) |
| Промышленное | По §4.20 | Обслуживание пользователей |

Ключевые дефекты системы — неработающая ссылка подключения, неверный учёт байтов, разрыв соединений
при синхронизации — не воспроизводятся в модульных тестах и не проверяются на ноде в контейнере без
публичного адреса. Стенд с реальными нодами является обязательным условием приёмки.

Состав проверок:

* Контрактные тесты Node API на зафиксированных запросах и ответах.
* Эталонные ответы subscription-эндпоинта для каждого формата (§5.6), сравниваемые побайтно.
* Генератор синтетического трафика с известным объёмом — проверка Н-18, Н-19, Н-20.
* Ручная приёмка на каждом клиенте §4.2 перед выпуском, включая проверку отображаемых заголовков
  подписки и применимых профилей (§5.6).

Определение работоспособной конфигурации: клиент импортировал подписку, установил соединение,
передал трафик, и переданный объём отражён в статистике в пределах Н-18.

### 17.2 Выпуск и миграции

* Миграции схемы обратно совместимы: изменение выполняется в два шага — расширение, затем сжатие.
  Требование обусловлено тем, что откат Control Plane при уже применённой несовместимой миграции
  невозможен, а сервис обслуживает действующие подписки.
* Node Agent предыдущих версий работает с новым Control Plane не менее трёх релизов (§5.2).
* Порядок обновления: сначала Control Plane, затем агенты.
* Процедура отката определяет критерий принятия решения об откате и проверяется на стенде.
* Набор проверок, блокирующих выпуск, фиксируется отдельно.

### 17.3 Обновление парка нод

| Требование |
| :--- |
| Версии Xray и Node Agent закреплены; обновление выполняется явным действием |
| Закрепляются последние стабильные релизы на момент начала разработки; предварительные выпуски не применяются (О-8). Проверено 2026-09-07: Xray-core v26.3.27 (выпуск 2026-03-27; все последующие теги до v26.7.28 включительно помечены как предварительные), sing-box v1.14.0 (выпуск 2026-08-31) для схемы формата `singbox` |
| Node Agent — собственный компонент; версионируется по семантическим версиям вместе с Node API (§5.2), закрепление внешней версии к нему не относится |
| Пересмотр закреплённой версии выполняется при выходе следующего стабильного релиза и при публикации исправления уязвимости (Н-26); при пересмотре перепроверяются допущения §9.1 и имена полей §4.4 |
| Обновление проверяется на канареечной ноде до применения к остальным; последовательность задаёт оператор вручную. Автоматизированный оркестратор поэтапного обновления отнесён к §10 |
| Перед обновлением Xray на канареечной ноде проверяется подключение каждого клиента §4.2; результат заносится в реестр §17.10 |
| Целевая версия Xray-core и Node Agent закрепляется явно; имена полей конфигурации в §4.4 приводятся к ней |
| Исправление уязвимости применяется не позднее 7 суток с публикации (Н-26) |
| Обновление агента выполняется командой (§5.2) без доступа по SSH |
| Неуспешное обновление откатывается, нода переводится в Degraded |

### 17.4 Дежурство и алерты

| Алерт | Приоритет | Реакция |
| :--- | :--- | :--- |
| Control Plane недоступен | Немедленный | Восстановление |
| Subscription-эндпоинт недоступен | Немедленный | Восстановление, объявление (§17.11) |
| Расхождение сверки трафика свыше Н-18 | Немедленный | Разбор до следующего расчётного периода |
| Нода Offline | Отложенный | Разбор в рабочее время |
| Нода Degraded | Отложенный | Разбор в рабочее время |
| Заполнение буфера отчётов на ноде | Немедленный | Восстановление связи |
| Цель `reality_target` недоступна | Отложенный | Замена цели |

Требования: алерты группируются по ноде и по типу; повторные подавляются; ноды в ручных статусах
алертов не порождают (§4.7); для каждого типа алерта существует инструкция с шагами разбора.

Окно планового обслуживания объявляется заранее и отключает отложенные алерты.

### 17.5 Поддержка пользователей

Роль Support (§5.11) требует данных, которых нет в перечне §4.15. В карточке пользователя
отображаются:

* обращения к subscription-эндпоинту: время, домен, формат, `User-Agent`, страна адреса источника;
* последнее успешное подключение к каждой ноде;
* потребление по периодам и нодам с применённым коэффициентом и его значением;
* текущее состояние подписки и причина отзыва доступа, если он выполнен.

Без этих данных обращение «не работает» неотличимо от ситуации, в которой пользователь не установил
клиент.

Ручная корректировка баланса трафика доступна с обязательным указанием причины (§4.16).

### 17.6 Первое подключение

Онбординг является основной точкой оттока: пользователь получает ссылку и остаётся один на один с
незнакомым приложением.

Требования MVP:

* определение платформы и предложение соответствующего клиента из §4.2;
* ссылки на установку клиента для каждой платформы;
* импорт подписки одним действием: ссылка импорта и QR-код;
* экран проверки соединения с однозначным результатом;
* показатель времени до первого успешного подключения и его целевое значение.

### 17.7 Доставляемость почты

На письмах держатся регистрация, восстановление пароля и все уведомления §4.17.

| Требование |
| :--- |
| Отдельный домен или поддомен для писем, не совпадающий с доменами подписки |
| Настроенные SPF, DKIM и DMARC |
| Обработка отказов доставки и жалоб; адрес с устойчивым отказом помечается |
| Показатель доли доставленных писем подтверждения |
| Запасной путь подтверждения адреса при недоставке |

Тематика сервиса является типичной причиной отказа почтового провайдера в обслуживании. Выбор
провайдера фиксируется до начала работ.

### 17.8 Время и язык

* Все значения времени хранятся и вычисляются в UTC.
* Отображение выполняется в часовом поясе пользователя; пояс хранится в профиле.
* Сутки для агрегатов и отчётов определяются в UTC.
* Интерфейс, письма и страница подписки в MVP поддерживают два языка: русский и английский
  (ОВ-4).
* Язык берётся из профиля пользователя; до его выбора — из заголовка `Accept-Language`; при
  отсутствии совпадения применяется английский.
* Язык административной панели выбирается администратором независимо от языка пользователей.
* Все строки интерфейса и шаблоны писем вынесены из кода в файлы локализации; добавление третьего
  языка выполняется добавлением файла и не требует изменения кода.
* Уведомления (§4.17) отправляются на языке профиля получателя.

### 17.9 Требования к интерфейсу

* Личный кабинет проектируется под мобильное устройство: его открывают с того же телефона, на
  который устанавливают клиент. Критичные операции — копирование ссылки, показ QR-кода, переход в
  приложение.
* Административная панель проектируется под настольный экран.
* Перечень поддерживаемых браузеров и их версий фиксируется.
* QR-код читается с экрана телефона: размер и контраст проверяются на приёмке.

### 17.10 Реестр клиентов

Список §4.2 не является константой: клиенты меняют формат подписки и пропадают из магазинов
приложений.

Ведётся реестр: клиент, платформа, версия, дата последней проверки, поддерживаемый формат. Проверка
выполняется перед каждым выпуском (§17.1). Вывод клиента из списка поддерживаемых сопровождается
уведомлением затронутых пользователей.

### 17.11 Коммуникация во время инцидента

Личный кабинет, почта и домены подписки размещены в той же инфраструктуре, которая отказывает.

| Требование |
| :--- |
| Страница состояния сервиса размещена вне инфраструктуры Control Plane |
| Независимый канал объявлений; согласие на него запрашивается при регистрации |
| Заголовок `announce` subscription-эндпоинта используется для объявлений (§5.6) |
| Процедура объявления смены домена подписки включает способ, которым пользователь проверяет подлинность нового адреса |

### 17.12 Преемственность

Домен, учётные записи хостинг-провайдеров, платёжная учётная запись, ключи и резервные копии по
умолчанию сосредоточены у одного лица (риск Р-7).

| Требование |
| :--- |
| Реестр учётных записей и их владельцев |
| Депонирование доступов: второй держатель или процедура вскрытия |
| Автоматическая оплата у хостинг-провайдеров |
| Определение режима работы сервиса без оператора и допустимого срока такого режима |
