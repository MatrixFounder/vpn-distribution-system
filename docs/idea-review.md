## 1. Вердикт

Документ является функциональным каталогом, а не постановкой задачи.

Он отвечает на вопрос «что система делает» примерно на 80 %. На вопрос «в каких границах, с какими
гарантиями и что происходит при отказе» он не отвечает.

Признаки, по которым это измеряется:

| Признак постановки задачи | Наличие в документе |
| :--- | :--- |
| Функциональные требования | Есть, перечнями |
| Архитектурные принципы | Есть, §3 |
| Нормативные числа (SLA, RPO/RTO, RPS, задержки, погрешность учёта) | Отсутствуют |
| Критерии приёмки | Отсутствуют |
| Определение готовности (DoD) | Отсутствует |
| Допущения | Отсутствуют |
| Ограничения | Отсутствуют |
| Явные границы «вне рамок» | Отсутствуют; §6 — отложенные требования с открытым обязательством |
| Риски | Отсутствуют |
| Модель угроз, граница доверия | Отсутствует |
| Метрики успеха | Отсутствуют |
| Прайор-арт, обоснование собственной разработки | Отсутствует |
| Оценка трудоёмкости, команда, сроки | Отсутствуют |
| Сценарии отказов | Отсутствуют; §8 описывает только успешный путь |

Числа в документе есть, но все они иллюстративные: примеры тарифов, примеры коэффициентов,
«Например: every 30 seconds» (§4.7), «85% load» (§6.12). Ни одно число не является обязывающим.
Формулировка §5.7 «10 000 → 100 000 users без изменения базовой архитектуры» — декларация, у неё
нет ни источника, ни способа проверки.

Начинать проектирование по текущей редакции нельзя. Причина не в объёме, а в том, что десять
развилок, определяющих схему базы данных и контракт Control Plane ↔ Node одновременно, в документе
не разрешены и будут молча выбраны разработчиком (раздел 5).

## 2. Что в постановке сделано верно

Этот раздел не является формальностью. Перечисленное ниже — несущая конструкция, которую правки не
должны разрушить.

1. **Периметр проведён корректно, плоскости разделены.** §2 разводит Control Plane и VPN-ноды,
   §3.1 объявляет Control Plane единственным источником истины, §3.5 фиксирует разделение
   Control Plane и Data Plane.

2. **Принцип disposable infrastructure (§3.2) сформулирован явно.** Из него корректно следует
   большая часть остальной архитектуры. Пробелы, найденные вокруг него (durable-буфер статистики,
   смена IP, инвалидация скачанных конфигов), означают, что принцип содержательный.

3. **Исходящее соединение агента к Control Plane (§3.3) — фактическое архитектурное отличие от всех
   проверенных существующих решений.** Проверено по исходному коду: Remnawave, Marzban, Marzneshin,
   PasarGuard и 3x-ui используют обратное направление — панель подключается к ноде. Раздел 4
   содержит подтверждение.

4. **Модель Desired / Applied configuration version (§3.4, §5.4) выбрана верно.** Претензии
   касаются грануляции, а не концепции.

5. **Raw и Billable трафик разделены, коэффициент требуется хранить в самой записи статистики
   (§5.9).** Это решение действительно тяжело встроить задним числом. Проверка показала, что в
   Marzban и PasarGuard оно не сделано: множитель применяется до записи, и сырой расход по
   пользователю не сохраняется.

6. **Экономика сервера отделена от коэффициента списания (§5.10).** Формулировка «Traffic Multiplier
   должен быть отделён от фактической стоимости сервера» разводит две сущности, которые обычно
   склеивают.

7. **Операционный слой присутствует:** backup и DR (§4.19), secrets management (§5.13),
   observability (§5.14), audit log (§4.16), RBAC (§5.11), rate limiting (§5.12), очередь фоновых
   задач (§5.8). Претензия к ним — отсутствие чисел и механизмов, а не отсутствие раздела.

8. **§8 — сквозной сценарий.** Единственное место, где система описана как работающее целое. Через
   него найдены три противоречия (П-4, П-7 и дефект F4 в приложении).

9. **Список клиентов §4.2 конкретен** (Shadowrocket, v2rayNG, Streisand, Hiddify, sing-box). Это
   проверяемое требование, от которого удалось оттолкнуться при анализе форматов подписки.

## 4. Фактические допущения о технологии

Проверено по исходному коду `XTLS/Xray-core` и официальной документации `xtls.github.io` на
2026-09-04. Каждый пункт меняет объём работ или состав требований.

### 4.1 Счётчики статистики обнуляются при рестарте Xray

Менеджер статистики хранит `counters map[string]*Counter` в памяти процесса; `Counter` — структура с
единственным полем `int64`, персистентности нет. У операций `GetStats` и `QueryStats` есть параметр
`reset`, обнуляющий счётчик при чтении.

Следствие для §5.9: контракт «нода отправляет накопленное значение» недостаточен. Требуется признак
поколения счётчиков (epoch) либо чтение с `reset` и durable-подтверждением приёма. Иначе каждый
рестарт ядра, обновление Xray (§6.5) и перезагрузка VPS дают либо потерю трафика, либо повторное
списание.

### 4.2 Удаление пользователя не разрывает установленные соединения

`proxy/vless/validator.go`, метод `Del(email)` удаляет запись из `sync.Map`. Реестра активных
соединений валидатор не ведёт. Проверка пользователя выполняется на хендшейке; авторизованный
туннель работает до собственного закрытия или до таймаута `connIdle` (по умолчанию 300 секунд).
Штатного средства разрыва по пользователю нет; ближайшее — блокировка по source IP через
`xray api sib`, гарантированное — рестарт ядра.

Следствие для §4.11, §4.15 и §4.17: «блокировка пользователя» и «Traffic limit reached» не
приводят к отключению. Постановка обязана выбрать: разрывать рестартом, ждать таймаута, блокировать
по IP или ограничиться прекращением выдачи конфигурации.

### 4.3 Встроенной квоты трафика в Xray нет

`LevelPolicyObject` содержит только тайминги и флаги статистики. Полей лимита трафика, срока
действия и скорости для пользователя нет. Квота — задача внешней системы: посчитать, сравнить,
удалить пользователя.

Следствие: enforcement всегда асинхронный, лаг «потребление → учёт → отключение» неустраним. Его
допустимая величина и допустимый перерасход — предмет решения постановки, а не реализации.

### 4.4 Встроенного ограничения устройств и одновременных подключений нет

Запрос `#2118` и запрос `#4567` закрыты, `#4567` — со статусом «not planned». Ядро предоставляет
только наблюдение: `statsUserOnline`, `GetStatsOnline`, `GetStatsOnlineIpList`, `GetAllOnlineUsers`.

Следствие для §4.10 и §4.13: `Device limit` и `Concurrent connection limit` требуют собственного
механизма. Существующие подходы: отдельный credential на устройство; подсчёт уникальных source IP в
окне; заголовок идентификатора устройства от клиента. Третий вариант работает только с клиентами,
которые его отправляют, и ни один из пяти клиентов §4.2 не назван в документе как поддерживающий
такой заголовок.

### 4.5 Модель ноды в §4.4 не позволяет сгенерировать ни одной ссылки

Обязательные серверные параметры REALITY: `target` (прежнее имя `dest`), `serverNames`,
`privateKey`, `shortIds`. Для VLESS-инбаунда дополнительно обязательно поле `decryption`. Клиенту
обязательны `sni`, `fp` (fingerprint), `pbk` (публичный ключ, ныне `password`) и `sid`. REALITY
работает только поверх транспортов RAW, XHTTP и gRPC.

Перечень полей ноды в §4.4 — Name, Country, City, Provider, Public IP, IPv6 availability, Status,
Created at, Last heartbeat. Ни одного параметра подключения в нём нет, включая порт.

Следствие: требуется сущность уровня «нода × протокол» (inbound), а не набор чекбоксов протоколов
на ноде. Без неё §5.5 (протокольная абстракция) невыполнимо, а «автоматическая генерация
конфигураций» из §7 не имеет входных данных.

### 4.6 Trojan не требует собственного домена и сертификата

По матрице совместимости связка `trojan` + `security=reality` поддерживается. Trojan требует
транспортной безопасности, но ею может быть REALITY.

Следствие: §4.4 и §5.5 должны зафиксировать выбор. Вариант с TLS требует FQDN у каждой ноды,
DNS-записи, выпуска и продления сертификата, мониторинга срока и дополнительных шагов в §4.5.
Вариант поверх REALITY этого не требует, но требует параметров REALITY в модели ноды (п. 4.5).
Отдельно не зафиксировано распределение портов между инбаундами на одном IP.

### 4.7 Автоматическое обновление подписки не гарантировано для одного из заявленных клиентов

Заголовки `subscription-userinfo` (upload/download/total/expire) и `profile-update-interval` (в
часах) — де-факто отраслевое соглашение, не спецификация. Их отдают 3x-ui, Marzban, Remnawave,
Hiddify. Клиентская поддержка неоднородна: документирована у Happ и v2RayTun, обрабатывается в
семействе Clash Meta и в Karing; в `2dust/v2rayNG` issue `#3438` указано, что клиент
`profile-update-interval` не поддерживает.

Следствие для §4.3: обещание «список серверов обновляется автоматически» для v2rayNG выполняется
только при ручном обновлении подписки пользователем. Требуется либо задать интервал обновления как
требование к каждому клиенту отдельно, либо дублировать лимиты и срок в теле ответа и на
веб-странице подписки.

### 4.8 Пользователя можно добавлять и удалять без рестарта

`HandlerService.AlterInbound` с `AddUserOperation` и `RemoveUserOperation` поддерживается для VMess,
VLESS, Trojan и Shadowsocks. Удаление выполняется по `email`, поэтому поле `email` обязательно как
идентификатор пользователя в конфигурации. Начиная с версии 1.8.12 отдельный api-инбаунд не
обязателен: достаточно `api.listen`.

Следствие для §3.4 и §5.4: единый номер версии конфигурации на ноду смешивает два разных потока
изменений. Изменение состава пользователей должно применяться горячим вызовом с собственным
курсором. Применение его через полную перезапись конфигурации и рестарт Xray разрывает соединения
всех пользователей ноды.

## 5. Решения, которые нужно принять до проектирования

Одиннадцать позиций. Каждая определяет схему базы данных, контракт Control Plane ↔ Node или формат
подписки. Пока решение не принято явно, оно будет принято молча.

| № | Решение | Что определяет | Уровень |
| :--- | :--- | :--- | :--- |
| 1 | Build / fork / adopt относительно существующих решений | Объём работ целиком | Блокер |
| 2 | Монетизация MVP: продажа или только выдача по Redeem Code | П-7, П-8, состав §7 | Блокер |
| 3 | Целевой масштаб MVP и нормативные числа | Все архитектурные развилки | Блокер |
| 4 | Модель квоты и enforcement | Схема подписки, протокол синхронизации | Блокер |
| 5 | Контракт учёта трафика end-to-end | Схема статистики, Node API | Блокер |
| 6 | Модель VPN-идентичности пользователя и устройства | Схема БД, объём операции блокировки | Блокер |
| 7 | Модель синхронизации Control Plane ↔ Node | Node API, поведение при изменениях | Блокер |
| 8 | Модель ноды и ключевого материала REALITY | §4.4, §5.5, генерация конфигураций | Блокер |
| 9 | Контракт subscription-эндпоинта | §4.2, §4.3, §5.6 | Блокер |
| 10 | Разрешение коэффициента и его датированность | §4.9, §5.9 | Блокер |
| 11 | Границы доверия и поведение при недоступности Control Plane | §3.1, §3.3, §5.13 | Блокер |

Зависимости: 7 зависит от 6 и 4; 9 зависит от 6 и 8; 5 зависит от 10; 3 зависит от 1 и 2.
Решение 1 переопределяет остальные, поэтому идёт первым.

### 5.1 Состав каждого решения

**Решение 2 — монетизация.** Записать один из двух вариантов. Вариант «MVP без монетизации»:
подписка выдаётся только Redeem-кодом, скидочные типы промокодов переносятся в Phase 2 вместе с
правилами применения, §8 шаг 7 переписывается, поле `Price` помечается как справочное. Вариант
«минимальный платёжный контур в MVP»: в §7 добавляются заказ, платёж и один провайдер.

**Решение 3 — числа.** Целевые значения на MVP отдельно от §5.7: число пользователей, число нод,
RPS публичного API, RPS subscription-эндпоинта, p95 латентности. Доступность Control Plane. RPO и
RTO для §4.19. Максимальная задержка распространения изменения состава пользователей до всех
Active-нод. Допустимая погрешность учёта трафика. Глубина хранения статистики. На каждую функцию
§7 — одна строка «как проверяем».

**Решение 4 — квота и enforcement.** Действие при исчерпании лимита (разрыв, ограничение скорости,
grace-объём). Действие при истечении подписки и при блокировке. Максимальная задержка отзыва
доступа. Допустимый перерасход. Судьба установленных сессий (п. 4.2). Определение `Monthly limit`:
якорная дата, часовой пояс, судьба остатка, поведение для подписки длиннее месяца. Правило смены
тарифа в середине периода. Место бонусного трафика промокода в модели баланса и порядок списания.

**Решение 5 — учёт трафика.** Семантика снятия счётчиков и признак поколения (п. 4.1). Ключ
идемпотентности отчёта. Локальный персистентный буфер неотправленных отчётов на ноде, его объём и
TTL. Процедура вывода ноды из эксплуатации со сбросом статистики. База списания: `uplink + downlink`
или только `downlink`. Исключение служебного трафика агента. Правило сверки суммы по нодам с
балансом пользователя. Два независимых источника трафика: пользовательский для биллинга и
интерфейсный для экономики и сверки с инвойсом хостера.

**Решение 6 — идентичность.** Ключ учётной записи: `user`, `user × node` или
`user × device × protocol`. Кто генерирует credential. Семантика «сброса VPN credentials» из §4.15.
Единица учёта устройства, окно, место агрегации, действие при превышении, погрешность на CGNAT
(п. 4.4). Семантика «перевыпустить ссылку» и «отключить старую»: ротируются ли при этом
VPN-credentials.

**Решение 7 — синхронизация.** Разделение потока состава пользователей и потока структурной
конфигурации, каждый со своим курсором. Инкрементальные дельты с монотонным per-node seq,
периодический снапшот, сверка контрольной суммы. Горячее применение состава без рестарта (п. 4.8).
Канал команд: модель доставки, очередь и порядок, идемпотентность по `command_id`, TTL и отмена,
статусы, отчёт об ошибке, запрет команд для Offline и Disabled. Версионирование Node API и правило
совместимости версий агента, поскольку rolling updates отложены в §6.5 и смешанный парк версий —
норма. Поведение при откате базы из бэкапа: скалярная монотонная версия после отката не заставит
агента переприменить конфигурацию.

**Решение 8 — модель ноды.** Сущность inbound «нода × протокол» с полями подключения (п. 4.5). Кто
генерирует пару ключей REALITY, попадает ли приватная часть в базу Control Plane и в бэкапы §4.19,
как версионируются `target` и `serverNames`, как выполняется ротация с окном перекрытия. Выбор
транспортной безопасности Trojan (п. 4.6). Распределение портов. История смены IP и регламент
перевыдачи конфигураций при пересоздании ноды.

**Решение 9 — подписка.** Форматы MVP, привязанные к каждому клиенту §4.2, и правило выбора формата.
Обязательные заголовки ответа и рекомендуемый интервал (п. 4.7). Контракт состояний эндпоинта:
active, expired, traffic_exceeded, blocked, revoked_token — с указанием кода ответа и тела. Поведение
при нуле доступных серверов. Свойства токена: энтропия, TTL, авто-ротация, ответ на несуществующий
токен, порог защиты от перебора, запрет логирования пути в обратном прокси и в приложении. Зеркала
домена подписки. Требование включать в профиль автоселектор там, где формат это позволяет.

**Решение 10 — коэффициент.** Правило разрешения, когда нода входит в несколько тарифицируемых
групп: §4.8 задаёт пересекающиеся группы (Europe, Premium Europe, High Cost, Streaming), §4.4
разрешает менять группы во множественном числе, а иерархия §4.9 линейна. Поведение при отсутствии
коэффициента. Диапазон, шаг и правило округления `billable_bytes`. Момент фиксации коэффициента
при переносе ноды между группами внутри периода агрегации. Запрет ретроактивного пересчёта
списаний (П-5).

**Решение 11 — границы доверия.** Допущение «нода — недоверенная среда, может быть скомпрометирована,
изъята или снята снапшотом». Выбор «все пользователи на всех нодах» или «подмножества по группам» и
радиус поражения при компрометации. Свойства bootstrap-секрета из §4.5: одноразовость, TTL,
привязка к записи Node. Что именно проверяет администратор на шаге 8 §4.5. Запрет выдачи
credential ноде в статусах Pending и Provisioning. Поведение системы при недоступности Control
Plane: работает ли VPN, работает ли выдача подписки, буферизуется ли статистика, применяется ли
локально истечение подписки — в desired state §3.4 у пользователя нет ни срока, ни лимита, поэтому
нода физически не может это применить.

### 6.1 Что это меняет в постановке

**Коэффициент расхода трафика не является новым требованием.** В Remnawave это поле
`consumptionMultiplier` в таблице `nodes` (значение хранится в наноединицах, `1000000000` = 1.0,
диапазон 0.0–100.0 с шагом 0.1). Есть второй коэффициент `nodeConsumptionMultiplier` — для счётчика
трафика самой ноды. В Marzban и PasarGuard это поле `usage_coefficient` типа Float на ноде.

**Раздельное хранение raw и billable реализовано только в Remnawave.** История (`nodes_usage_history`,
`nodes_user_usage_history`) пишется без множителя, счётчики лимитов (`users.used_traffic_bytes`) — с
множителем. В Marzban и PasarGuard множитель применяется в момент записи (`int(value * coefficient)`),
поэтому сырой расход по пользователю не сохраняется.

Финальный комментарий документа утверждает, что раздельное хранение «потом сложно встроить без
миграции всей системы статистики». Утверждение верно и подтверждается тем, что две из трёх
реализаций коэффициента этого не сделали. Но как отличие от прайор-арта оно не работает.

**Ни в одной из шести панелей нет промокодов, купонов и приёма платежей.** Проверено поиском по
полным деревьям репозиториев: Marzban 556 путей, Marzneshin 890, PasarGuard 1018, 3x-ui 1937,
hiddifypanel 1063 — ноль совпадений по `coupon`, `promo`, `tariff`. Всё, что связано с продажами,
живёт во внешнем слое: Telegram-боты и отдельные биллинги.

**Направление соединения нода → Control Plane (§3.3) не реализовано ни в одной панели.** Во всех
шести панель или мастер подключается к ноде. У Remnawave нода поднимает HTTPS-сервер на
`NODE_PORT` и принимает запросы панели, защита — mTLS с TLS 1.3 плюс JWT. Требование §3.3 снимает
необходимость открывать порт на каждой ноде и допускает ноды за NAT.

### 6.2 Измеренная дельта

После проверки уникальными относительно прайор-арта остаются четыре позиции:

1. Исходящее соединение агента к Control Plane (§3.3).
2. Коэффициент на уровне группы серверов с иерархией «нода → группа → значение по умолчанию»
   (§4.9). В панелях коэффициент задаётся только на ноду; в Remnawave массовое назначение — это
   bulk-операция по списку нод, а не свойство группы.
3. Тарифный каталог, промокоды и Redeem-коды внутри ядра (§4.10, §4.14).
4. Экономическая модель ноды, отделённая от коэффициента списания (§5.10). Ближайший аналог —
   модуль Infra Billing в Remnawave, но он учитывает расходы на инфраструктуру, а не выручку.

Позиции 3 и 4 не связаны с управлением VPN-инфраструктурой. Они реализуемы поверх чужого API.

### 6.3 Что дописать в постановку

Раздел «0. Прайор-арт и решение build / adopt / fork» перед §1, содержащий:

- Таблицу «требование §4 и §5 × решение», с версией и датой проверки каждой строки.
- Явное решение с указанием владельца и условия пересмотра.
- Не более трёх требований в обосновании собственной разработки.
- Анализ лицензий. AGPL-3.0 обязывает раскрывать исходный код пользователям сетевого сервиса, что
  несовместимо с закрытой кодовой базой и с white-label из Phase 3. GPL-3.0 у ноды PasarGuard мягче:
  собственная панель, общающаяся с ней по сети, производной работой не становится. Код Hiddify для
  коммерческого использования исключён: ядро панели под CC BY-NC-SA 4.0 с явным условием
  NonCommercial.
- Третий вариант, не рассмотренный в документе: взять существующую панель как менеджер data plane и
  построить поверх её API собственный слой тарифов, промокодов и биллинга. Вся экосистема прайор-арта
  разделена именно так. При закладке тарифов прямо в модель Control Plane замена нижнего слоя
  становится невозможной.
- Timebox на проверку гипотезы и оценку трудоёмкости всех трёх вариантов. Слова «команда», «срок»,
  «бюджет» в документе отсутствуют, поэтому варианты сейчас несравнимы.

## 7. Что отсутствует полностью

Темы, не покрытые ни одним разделом документа.

1. **Тестовая стратегия.** Нет окружений, нет решения о постоянном стенде с реальными нодами, нет
   контрактных тестов Node API, нет матрицы «клиент × протокол × ОС». Дефекты этой системы —
   нерабочая ссылка, неверный учёт байтов, разрыв соединений при синхронизации — не воспроизводятся
   в модульных тестах.
2. **Релизный процесс и миграции.** §4.20 описывает развёртывание, но не обновление. Нет обратно
   совместимых миграций, нет отката, нет порядка обновления Control Plane и агентов.
3. **Патч-менеджмент парка нод.** Политика версий Xray и агента, реакция на уязвимости, обновление
   агента без ручного SSH, поведение при неуспешном обновлении.
4. **Эксплуатация.** Адресаты алертов, приоритеты, подавление и группировка, runbook, окно планового
   обслуживания, правило «Maintenance выключает алерты».
5. **Онбординг и первое подключение.** §8 обрывается на «пользователь получил URL». Нет инструкций
   по установке клиента, deep-link импорта, проверки соединения. Это основная точка оттока.
6. **Рабочее место поддержки.** Роль Support заведена в §5.11, инструментов у неё нет: не видно, что
   выдано подписке, обращался ли клиент к эндпоинту, каким клиентом, из какой страны.
7. **Доставляемость почты.** Почта названа минимальным каналом. Нет выбора отправителя, SPF, DKIM,
   DMARC, обработки возвратов, отдельного домена, запасного пути подтверждения.
8. **Часовые пояса и локализация.** Часовой пояс не упомянут ни разу при наличии «дата окончания»,
   «monthly limit», «traffic today», «hourly / daily records». Язык интерфейса не задан.
9. **Требования к интерфейсу.** Адаптивность, доступность, поддерживаемые браузеры. Личный кабинет
   открывают с того же телефона, на который ставят клиент.
10. **Совместимость с клиентами во времени.** Список из пяти клиентов дан как константа. Нет реестра
    версий, регулярной проверки, политики вывода клиента из списка.
11. **Коммуникация во время инцидента.** Кабинет, почта и домен подписки живут на той же
    инфраструктуре, которая отказывает. Нет внешней статус-страницы и независимого канала объявлений.
12. **Преемственность.** Домен, аккаунты провайдеров, платёжный аккаунт, ключи и бэкапы по умолчанию
    в одних руках. Нет реестра доступов и депонирования.
13. **Документация как артефакт.** При заявленном API-first нет требования публиковать
    OpenAPI-спецификацию и версионировать её. Нет пользовательских инструкций, нет журнала
    архитектурных решений.
14. **Юрисдикция размещения нод.** Страны фигурируют как названия. Нет проверки условий обслуживания
    провайдера, требований страны к хранению логов, критериев выбора, процедуры экстренного вывода
    ноды с уничтожением ключей.
15. **Политика данных и приватности.** Система хранит связку «кто, когда, на какой ноде и в какой
    стране потреблял трафик». §5.9 фиксирует почасовую разбивку. Не заданы перечень собираемых
    данных, сроки хранения, процедура удаления аккаунта и её согласование с §4.16 и §4.19.
16. **Правила допустимого использования и процесс abuse.** Исходящий трафик идёт с IP провайдера.
    Нет ограничений исходящих соединений, нет статуса «приостановлена провайдером», нет решения о
    минимальном наборе данных для ответа на жалобу.

   расхождение П-9.

| Замечание | Суть | Исправление |
| :--- | :--- | :--- |
| Ошибка вывода Н-17 | `connIdle` — таймаут бездействия, а не предельное время жизни соединения: активно передающее соединение им не прерывается. Вывод «60 с + 60 с = 1,5 ГБ» не учитывал время дожития сессии | §4.11 переписан: три кандидата механизма принудительного разрыва, выбор по результату PoC-1а; введены Н-17а и Н-17б; Н-17 объявлено предварительным до PoC |
| Автономный режим ноды | Н-7 допускает 24 часа без связи, при этом отзыв доступа выполняется только по команде: перерасход не ограничен ничем | В поток состава введено поле `quota_grant_bytes` — предоплаченный объём; агент локально отключает пользователя при исчерпании гранта |
