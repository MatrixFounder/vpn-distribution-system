# 9. Надёжность и отказоустойчивость

> Part of [docs/ARCHITECTURE.md](../ARCHITECTURE.md).


### 9.1 Обработка ошибок

| Ситуация | Поведение |
| :--- | :--- |
| Задача очереди завершилась ошибкой | повтор с экспоненциальной задержкой до `max_attempts`; затем `dead` и алерт |
| Control Plane недоступен для агента | обслуживание по последней конфигурации (Н-7); буфер отчётов (Н-8); грант квоты (Н-17в) — для тарифов с лимитом, у Unlimited грант не ограничен (В-6 а) |
| Redis недоступен | сессии недействительны; long-poll по таймауту; пользовательские эндпоинты с лимитом частоты отвечают 503 (fail-closed, перечень — §7.3); пределы Node API по identity ноды держат зоны прокси, от Redis они не зависят; алерт |
| PostgreSQL недоступен | C-01 отвечает 503; ноды работают автономно |
| SMTP-реле недоступно | доставки в `pending`, повтор; после порога — `failed`, алерт |
| Адрес получателя недоставляем | пометка `users.email_undeliverable_at` прекращает письма уведомлений этому адресу; её видят карточка пользователя в панели и кабинет. Пометку ставит постоянный синхронный отказ SMTP-реле (обратного канала у реле нет) и webhook отказов и жалоб выбранного провайдера: проверка подписи, жалоба ставит пометку и отключает уведомления; провайдер выбирается до начала 001.78, webhook реализует 001.78 (ОВ-13, В-37 в) |
| Отчёт с аномальным приростом | `held_anomaly`, алерт «Отложенный»; объём в пределах потолка канала списывается, превышение — нет (§5.9). Отдельного действия разбора нет: оператор снимает `Suspended` с ноды и корректирует баланс в обе стороны (001.50; В-4 а). 3 интервала с удержанной частью за скользящие 24 ч (`settings.held_reports_suspend`; счёт — интервалы, а не части; окно — не раньше снятия ручного статуса `nodes.manual_cleared_at`) переводят ноду в `Suspended` (001.30c; В-5 а) |
| Несовпадение `state_generation` | 409 `generation_mismatch` с текущим поколением в `details.generation`; агент сохраняет его, запрашивает снапшот (`full=1`) и применяет безусловно (§5.2; сервер — 001.75b, агент — 001.55) |
| Неуспешное обновление агента | откат, `Degraded`, алерт (§17.3); из `Degraded` по этой причине нода выходит после следующего успешного `update_agent` или действием администратора, а не по порогам §4.7 (В-15 а; отметка `nodes.update_failed_at` и выход — 001.30, действие администратора — 001.30b, приём результата команды — 001.76) |
| Ответ состояния без известного обязательного раздела | агент ответ не применяет: запись в журнал, повтор с выдержкой; `Degraded` не ставится — новый обязательный раздел вводит версия пути `/agent/v2` (§5.2, R-04; В-14 б) |
| Недоступность `reality_target` | проверяет агент раз в час (Н-30) и сообщает результат Control Plane; inbound в `error_state` в выдачу подписки не попадает, остальные профили ноды выдаются; алерт «Отложенный», нода `Degraded`; нода в `Provisioning` сначала становится `Active` по §4.6, затем `Degraded` (В-12 а) |

Агент: локальный watchdog systemd для `xray` и `node-agent`; при падении `xray` агент
перезапускает его, фиксирует новый `counter_epoch`; объём с последнего снятия счётчиков до сбоя
теряется в пределах бюджета Н-18 (§5.9, Н-19; без потерь — только плановый перезапуск; В-49);
сигнал для алерта — поле метрик агента (расширение тела метрик — 001.30, правило — 001.68; до
расширения агент пишет событие только в журнал). После каждого старта Xray (применение
конфигурации, `restart_xray`, перезапуск после сбоя, перезагрузка VPS; признак старта — сброс
времени работы процесса Xray) агент возвращает в inbound пользователей локального состава в
состоянии `active`, кроме исчерпавших грант, и переустанавливает правила маршрутизации 001.58 и
001.82 — последние, если PoC-1а (001.88) выберет `route_block` (001.80; тот же признак старта — в
учёте 001.56).

### 9.2 Резервное копирование

| Параметр | Значение |
| :--- | :--- |
| Инструмент | pgbackrest, репозиторий — S3-совместимый бакет у другого провайдера, чем хост Control Plane (ОВ-A1, В-44) |
| Полная копия | ежесуточно |
| Архив WAL | непрерывно, `archive_timeout = 900` (Н-9) |
| Шифрование | репозиторий pgbackrest; ключ — Docker secret на хосте, в копию не входит; его копия вне контура — в менеджере паролей оператора и у второго держателя доступов §17.12 (Н-12; ОВ-A1, В-44) |
| Хранение | 14 полных копий; WAL — до самой старой копии |
| Секреты конфигурации | копия файлов секретов и `tls/` (в том числе `ca_key`, `APP_ENCRYPTION_KEY`, пароли ролей и SMTP; ключ pgbackrest — вне копии, Н-12) и `.env` в том же хранилище, зашифрованная тем же ключом (001.67) |
| Журнал отзывов | каждый отзыв identity и аннулирование bootstrap-токена ставят в своей транзакции задачу очереди; она пишет строку «серийный номер листа, время» (у токена — «хеш токена, время») отдельным объектом в то же хранилище — вне базы и вне хоста (001.67; В-20 а). Окно потери ограничено: строка уходит в хранилище задачей после фиксации транзакции (секунды); при отказе хоста до выгрузки строки и без архива WAL, покрывающего отзыв, отзыв этого окна повторяет оператор по записи инцидента. Синхронная запись в хранилище не применяется: отзыв скомпрометированной ноды зависел бы от доступности S3 |
| Проверка | ежеквартальное восстановление на чистом хосте по инструкции (Н-11); результат в журнале эксплуатации |

Процедура восстановления (UC-10):

1. Развернуть Compose на чистом хосте и восстановить из копии секреты и `.env` (ключ шифрования
   копий — из менеджера паролей оператора или от второго держателя §17.12); постусловие —
   контейнеры запущены без базы.
2. Восстановить базу командой `pgbackrest restore`; постусловие — база на момент последнего WAL.
3. Запустить C-01; при старте он сравнивает пару «системный идентификатор кластера, линия
   времени» из `pg_control` и значение `state_generation` базы с меткой последнего запуска в файле
   `/var/lib/control-plane/generation` на хосте — вне резервируемого контура. Несовпадение или
   отсутствие метки ⇒ поколение увеличивается безусловно.
4. При обнаруженном откате C-01 до запуска `uvicorn` повторяет по внешнему журналу отзывов отзывы
   identity и аннулирования bootstrap-токенов, сделанные после точки копии
   (`check_generation_on_start`, 001.67; В-20 а); `restore.sh` открывает агентский порт прокси
   только после этого шага. Постусловие — отозванные после точки копии identity и токены
   недействительны и в восстановленной базе; исключение — отзывы, строка которых не была
   выгружена до отказа хоста (окно — строка «Журнал отзывов» выше): их повторяет оператор по
   записи инцидента.
5. Агенты обнаруживают новое поколение и запрашивают снапшот; окно приёма прежней identity
   продлевается на 7 суток в транзакции смены поколения (`extend_overlap_windows`, 001.31; §5.3;
   В-16 а); агент, получивший 401, повторяет запрос с сохранённой прежней identity (§7.1).

### 9.3 Мониторинг и алерты

Метрики Prometheus у C-01…C-03:

- латентность и коды ответов по маршрутам;
- глубина очередей по статусу и возраст самой старой задачи;
- число нод по статусам;
- возраст последнего принятого отчёта по каждой ноде;
- отчёты по статусам приёма (`rejected_time`, `held_anomaly`, `interval_closed`) по каждой ноде —
  ряд из `traffic_reports` (001.68);
- расхождения сверок;
- заполнение буфера отчётов на ноде — возраст `period_end` последнего принятого интервала больше
  порога из `settings` (правило — 001.68); полей буфера в метриках агента правило не требует;
- inbound в `error_state` по результатам проверки `reality_target`
  `control_plane_inbounds_error{node_id}` (001.27);
- ряд расхождения Desired/Applied по ноде `control_plane_node_applied_lag_seconds{node_id}` — время, в течение которого `applied_*` отстают от
  `desired_*`; ноды в ручных статусах в ряд не входят (001.75);
- переводы нод в `Suspended` по повторным удержаниям — счётчик
  `control_plane_node_held_suspensions_total{node_id}` (001.30c);
- кардинальность адресов ноды — число различных адресов в отчётах ноды за окно
  `control_plane_node_address_cardinality{node_id}` (001.38; §7.3 «Ложные адреса в отчёте»);
- ответы подписки с пустым списком серверов при активной подписке —
  `control_plane_subscription_empty_responses_total` (001.42);
- подряд идущие отказы исполнителя очереди `control_plane_worker_consecutive_failures` (001.68);
- доставки почты и webhook по статусам (001.78, 001.79).

Источник каждого алерта — ряд `/metrics`; запись ERROR в журнале служит разбору, а не правилам.

Правила алертов — по таблице §17.4 и по перечню ниже, который дополняет её алертами, требуемыми
разделами idea и решениями задач (В-42 а, заказчик 2026-10-25; правила — 001.68). Группировка по
ноде и типу; ноды в ручных статусах исключены, кроме алерта перевода в `Suspended` по повторным
удержаниям: его источник — сам перевод (001.30c). Доставка — Alertmanager → webhook оператора.

| Приоритет | Алерты |
| :--- | :--- |
| Немедленный — останавливает сервис, учёт или доступ | строки §17.4 с этим приоритетом (Control Plane и subscription-эндпоинт недоступны, расхождение сверки свыше Н-18, буфер отчётов заполнен); OOM или остановленный контейнер; база или Redis недоступны; неуспех копии или архива WAL; диск хоста больше 90 %; CA истёк или истекает через 30 дней и меньше; перевод ноды в `Suspended` по повторным удержаниям; ноль доступных серверов при активной подписке |
| Отложенный — остальное | строки §17.4 с этим приоритетом (нода Offline и Degraded, цель `reality_target` недоступна); DLQ больше 0; `held_anomaly`; `rejected_time`; `foreign_users`; `report_inconsistent`; интервалы длиннее 60 с; расхождение Desired/Applied больше 120 с; CPU или RAM ноды больше 90 % дольше 15 мин; отказ Xray; отказ SMTP; принудительное закрытие интервалов; кардинальность адресов ноды выше порога (001.38); ожидание задачи сверх порога; подряд идущие отказы исполнителя очереди; перезапуски контейнеров; CA истекает через 90 дней (срок листа) и меньше |

Операторские события §4.17, которые строятся по метрикам (нода недоступна и восстановлена,
расхождение сверки, буфер отчётов заполнен), доставляют те же правила; идентификатор события в
webhook — `groupKey` и `fingerprint` Alertmanager. Событие «Нода приостановлена провайдером» —
однократное событие ручного перехода, правилом алерта не является и доставляется webhook
приложения (001.79) с идентификатором события.
Плановое окно обслуживания — `silence` в Alertmanager по алертам приоритета «Отложенный» (§17.4).
Панель создаёт и снимает его через API Alertmanager (пункт «обслуживание» раздела Settings, §4.15;
001.85), действие пишется в Audit Log, ключа окна в `settings` нет (В-50 а). `inhibit` — только
для подавления зависимых алертов.

Логи: JSON в stdout (форматтер журналов C-01…C-03 — 001.68), ротация средствами Docker
(`json-file` 10 МиБ × 3 на службу), хранение не дольше 30 дней (§16.2); защита от вымывания —
внешний приёмник (001.68, §7.2). `access.log` Xray на ноде выключен (§16.3).

### 9.4 Внешний контроль доступности и объявления

C-10 стоит на хосте Control Plane и отказ всего хоста не видит. Внешний сервис мониторинга
доступности со своей страницей состояния вне инфраструктуры Control Plane (§17.11; ОВ-A2 закрыт,
В-43 а):

- раз в 1–5 мин проверяет `/healthz` и выдачу подписки по проверочному токену на обоих доменах
  подписки;
- уведомляет оператора своим каналом, независимым от Alertmanager: при отказе всего хоста алерты
  «Control Plane недоступен» и «Subscription-эндпоинт недоступен» даёт он, правила C-10
  покрывают частичные отказы — процесс, база, Redis (001.68);
- публикует инциденты на своей странице состояния; его данные — источник доступности за месяц
  для AC-21 (Н-5, Н-6).

Пробы, проверочный токен, уведомление оператора и данные доступности за месяц для AC-21 — 001.68
(R-47); страница состояния сервиса и публикация на ней объявлений — 001.70 (R-49).

Объявления (ОВ-15 закрыт, В-44): независимый канал — Telegram-канал сервиса; объявление
дублируется на странице состояния и в кабинете. Объявление о смене домена подписки подписывается
ключом объявлений; отпечаток открытого ключа кабинет показывает пользователю заранее, и по нему
пользователь проверяет подлинность нового адреса (§17.11). Закрытый ключ на хосте Control Plane
не хранится (security.md §7.2). Публикация объявлений в Telegram-канале и на странице состояния и
процедура смены домена — 001.70; сама замена домена — процедура развёртывания (deployment.md
§10.4; В-27 а).
