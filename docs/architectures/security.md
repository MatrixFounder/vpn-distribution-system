# 7. Безопасность

> Part of [docs/ARCHITECTURE.md](../ARCHITECTURE.md).


### 7.1 Аутентификация и авторизация

| Субъект | Механизм | Хранение |
| :--- | :--- | :--- |
| Пользователь | пароль argon2id; сессия — непрозрачный идентификатор в cookie `HttpOnly; Secure; SameSite=Lax` | Redis `sess:{id}`, TTL бездействия 30 суток (`USER_SESSION_TTL`, 001.14), набор `user_sessions:{user_id}` |
| Администратор | пароль + TOTP обязательно; резервные коды | Redis, TTL бездействия 12 часов (Н-27) |
| Node Agent | mTLS: клиентский сертификат внутреннего CA + токен identity в заголовке | `node_identities` |
| Клиент подписки | bearer-токен в пути, ≥ 128 бит | `subscription_tokens.token_hash` |
| Webhook-получатель | подпись HMAC-SHA256 тела | секрет в `settings` |

Инвалидация сессий: блокировка учётной записи удаляет все ключи из набора пользователя (Н-27);
смена пароля и перевыпуск второго фактора — все, кроме текущей; «выход везде» — все. Действие
«Заблокировать» карточки пользователя — одно действие (В-40 а): `users.status = 'blocked'`
(кабинет закрыт, сессии отозваны) и подписка `suspended_admin` (доступ к VPN снимается в срок
Н-14, эндпоинт подписки отвечает `blocked` с причиной; 001.50).

Учётные записи администраторов (В-33 в): первого Super Admin создаёт команда хоста
`python -m app.cli admin create` (001.47); остальные учётные записи Super Admin ведёт в разделе
панели `/admin/admins` — создание с обязательным TOTP, роль, блокировка с отзывом сессий, сброс
пароля (разрешение `admins.manage`, 001.89); свой профиль — смена пароля, перевыпуск TOTP, выход
везде — доступен каждому администратору (разрешение `admins.self`, 001.89).

Восстановление второго фактора администратора, потерявшего TOTP и резервные коды (§5.11,
В-35 в): при наличии другого активного Super Admin — его подтверждение в панели (001.89), иначе —
команда хоста `admin reset-2fa` (001.47): держатель доступа к хосту и есть второй держатель
доступов §17.12. Оба пути пишут запись в `audit_log` и отправляют служебное письмо всем активным
администраторам (путь `send_email`, не событие §4.17). Вход по резервному коду — самостоятельный
вход владельца второго фактора, сбросом не является.

Внутренний CA: ключ CA — Docker secret роли `api` (`ca_key`, P-256), сертификат CA — тот же файл
`tls/ca.crt`, которым nginx проверяет клиентов (§10.3; решение 001.25: nginx нужен сертификат CA
файлом раньше первого запроса, а зашифрованная копия ключа в базе защиты сверх файла
`APP_ENCRYPTION_KEY` не даёт и попадала бы в каждую резервную копию). Сертификаты нод выпускаются
при enrollment на срок 90 дней. Ротация автоматическая (В-16 а): C-03 ставит команду
`rotate_credentials`, когда до конца срока листа остаётся 30 дней и меньше; прежнее поколение
принимается 7 суток после выпуска нового (окно перекрытия Н-28), смена `state_generation` продлевает
окно на 7 суток от момента смены (сервер — 001.31, агент — 001.81). Лист решает CA, а не нода: из
CSR берётся только открытый ключ P-256 после проверки подписи, субъект — идентификатор ноды, профиль
`CA:FALSE`, `digitalSignature`, `clientAuth`. nginx проверяет сертификат по CA и передаёт его
целиком заголовком `X-Client-Cert` (`$ssl_client_escaped_cert`); C-01 считает отпечаток SHA-256 от
DER (у nginx есть только SHA-1 — `$ssl_client_fingerprint`), сверяет его с `node_identities` и токен
identity (`secrets.compare_digest` по хешам). Подпись ECDSA податлива: из листа `(r, s)` держатель
без ключа CA получает близнеца `(r, n − s)`, которого проверка по CA тоже принимает, — другие байты
и отпечатки, то же подписанное тело. identity близнеца C-01 не находит (401), а пределы прокси
ключуются серийным номером листа (`$ssl_client_serial`, внутри подписанного тела; номера CA выбирает
сам, 159 случайных бит) — у близнецов он общий (001.25, проверено на стенде). Подтверждение ноды
(UC-01 шаг 7) привязано к identity, которую сверил администратор: панель передаёт её отпечаток, и
если между сверкой и подтверждением прошёл новый обмен — 409 `identity_changed`. Отзыв identity
(Н-31) действует со следующего запроса: C-01 сверяет identity с базой на каждом запросе. Прокси
отозванный сертификат не отвергает (`ssl_crl` нет — решение 001.25, остаточный риск — §7.3):
держатель отозванного листа получает 401, но до ответа занимает пределы прокси своего сертификата —
до конца срока листа (не больше 90 дней); сократить это окно могут только отказ на прокси (001.66c)
или смена CA с перевыпуском всему парку. Повторное подтверждение после восстановления базы (§5.3,
UC-10 A2): агент хранит identity текущего и прежнего поколений и, получив 401, повторяет запрос с
сохранённой прежней; C-01 принимает прежнее поколение в окне перекрытия Н-28, продлённом сменой
`state_generation` на 7 суток (сервер — 001.31, агент — 001.54). Отозванная identity так не
восстанавливается — только новым bootstrap-токеном (§4.6). Отзыв identity и аннулирование
bootstrap-токена ставят в своей транзакции задачу очереди, которая пишет строку «серийный номер
листа, время» (у токена — «хеш токена, время») отдельным объектом во внешний журнал отзывов в
хранилище копий — вне базы и вне хоста; восстановление из копии повторяет записи, сделанные после
точки копии, до запуска `uvicorn` и открытия агентского порта (reliability.md §9.2; 001.67;
В-20 а). Строка уходит в хранилище задачей после фиксации (секунды); при отказе хоста до выгрузки
и без архива WAL, покрывающего отзыв, отзыв этого окна повторяет оператор по записи инцидента —
синхронная запись сделала бы отзыв скомпрометированной ноды зависимым от доступности S3.

Bootstrap-токен: 256 бит, хранится хешем, одноразовый, срок Н-24; обмен выполняется по HTTPS без
клиентского сертификата на отдельном `server` прокси, обслуживающем только `/agent/v1/enroll`.
Якорь доверия первого шага — сертификат внутреннего CA из bootstrap-команды: панель выдаёт его
вместе с токеном (ответ выдачи токена), администратор переносит на VPS своим каналом, и агент
проверяет им серверный сертификат enrollment-server (с именем) **до** того, как отдать токен;
`ca_pem` ответа обмена обязан совпасть с якорем. Иначе посредник на первом шаге прочёл бы токен,
обменял его сам и подсунул агенту свой CA — постоянный посредник на всём Node API. Серверные
сертификаты обоих портов агентов выпускает тот же CA с `extendedKeyUsage serverAuth` и SAN, листы
нод — только `clientAuth` без SAN: агент проверяет назначение и имя, и лист ноды не выдаст себя
за Control Plane. После 001.66d серверные сертификаты агентских портов подписывает отдельный
офлайн-CA, его сертификат — якорь bootstrap-команды; онлайн-CA в `api` подписывает только листы
нод, `ca_pem` ответа обмена — CA листов, с якорем он не совпадает, и агент сверяет его с выданным
листом (001.54, 001.61; §7.3 «Кража ключа CA»). После обмена агент печатает отпечаток своего
листа — его администратор сверяет на шаге 6 UC-01 (001.25; агент — 001.54, команда — 001.61).
Повторная выдача и отзыв identity аннулируют неиспользованный токен отметкой (`annulled_at`), а не
укороченным сроком: годность решают отметки — погашение, аннулирование, отзыв, — и шаг часов базы
назад её не вернёт.
Серийный номер каждого листа, выпущенного обменом, хранится (`node_identities.cert_serial`, форма
`$ssl_client_serial`) — по нему отказ на прокси (001.66c) найдёт и листы, выпущенные до него.
Исключения — стенд: `dev/dev-node.crt` из `deploy/scripts/dev-secrets.sh` выпущен тем же CA мимо
обмена, и строки identity у него нет (порт агентов его пропускает, C-01 отвечает 401); пробы
`control-plane/tests/stand/` выпускают листы обменом, но уборка удаляет их строки identity (ключи
нод пробы не сохраняет — предъявить такие листы некому); в промышленном контуре CA ничего мимо
обмена не подписывает (001.66c). Хранение номера держит код, а не схема: у `app_rw` есть DELETE на
`node_identities` (уборка тестов и проб), и удаление строки identity в коде приложения запрещено
только его дисциплиной.
Ключ ограничения частоты для enrollment — адрес источника и хеш предъявленного токена (§5.12 не
задаёт ключ для запроса без identity): на прокси стоят пределы соединений и частоты по адресу
источника и общий потолок частоты на всех клиентов (защита цикла событий C-01; 001.33), хеш
токена и распределённый источник — 001.72. Клиентский сертификат ноды проверяется по CA с
глубиной 0 — только листы, подписанные CA напрямую (в OpenSSL глубина считает промежуточных CA,
и 1 пропускала бы одного): лист, способный подписывать, множил бы серийные номера, по которым
ключуются все пределы прокси (первая линия — профиль листа, 001.25).

Авторизация: разрешения в коде, проверка декоратором на каждой операции; отказ пишется в `audit_log`
с результатом `denied`. Чтение журнала через `/admin/audit` регистрируется как действие с актором и
фильтром запроса (§4.16).

Матрица ролей §5.11 (R-35, ОВ-26; В-39 б; хранится в коде, 001.48; имена разрешений — 001.46,
001.48, 001.31, 001.89):

| Роль | Разрешения |
| :--- | :--- |
| Support | пользователи: поиск и карточка (`users.read`); действия карточки — блокировка, тариф, продление, трафик, сброс credentials, ручное подтверждение адреса (`users.write`); просмотр subscription URL (`users.view_subscription_url`), работа от лица пользователя (`users.impersonate`); дашборд (`dashboard.read`); список и подтверждение запросов второго подтверждения (`approvals.approve`); свой профиль (`admins.self`) |
| Operator | права Support; чтение нод (`nodes.read`: записи, доступность из стран, inbound, команды и их результаты); ручные статусы нод (`nodes.manual_status`, 001.30b); команда `restart_xray` (`nodes.restart_xray`, 001.31) |
| Admin | права Operator; остальные операции нод: запись (`nodes.write`: создание, изменение и вывод из эксплуатации — 001.87, bootstrap-токен, подтверждение, изменение inbound, обращение провайдера), отзыв identity (`nodes.revoke_identity`), `update_agent` (`nodes.update_agent`), команды `rotate_credentials` и `collect_diagnostics` (`nodes.commands`, 001.31); группы, тарифы, коды (экспорт — `codes.export`); журнал аудита (`audit.read`) |
| Super Admin | все разрешения: права Admin; настройки (`settings.read`, `settings.write`; окно обслуживания — `settings.write`); учётные записи администраторов (`admins.manage`, 001.89) |

Восстановление из копии — процедура на хосте (reliability.md §9.2), а не операция API: его
выполняет держатель доступа к хосту (§17.12), разрешения в матрице для него нет.

Политики §5.11:

- просмотр subscription URL — отдельное разрешение, каждый просмотр — запись в журнал;
- работа от лица пользователя (UC-13 шаг 6; В-36 б) — расширенная карточка в панели с данными
  `/me` пользователя, без входа в кабинет и без отдельного вида сессии, только чтение; начало и
  завершение — записи `audit_log` с `impersonated_user_id`, пользователь получает служебное
  письмо (001.48, экран — 001.64, шаблон — 001.78);
- второе подтверждение (ОВ-17; В-34 б): пороги начисления трафика и продления — ключи
  `settings` `approval.traffic_bytes` и `approval.renew_days`, по умолчанию выключены и
  включаются, когда появляется второй оператор; включение и изменение порога пишутся в журнал.
  Операция сверх включённого порога создаёт запрос (`approval_requests`), который подтверждает
  другая активная учётная запись с тем же разрешением; запрос живёт 24 ч (001.48).

### 7.2 Защита данных

| Данные | Защита |
| :--- | :--- |
| Пароли | argon2id: `m = 64 MiB`, `t = 3`, `p = 4` |
| Приватные ключи REALITY, credentials пользователей, секреты TOTP, коды, пароль SMTP | AES-256-GCM на уровне приложения; ключ `APP_ENCRYPTION_KEY` из файла секрета; `key_version` для ротации |
| Ключ CA | Docker secret `ca_key` роли `api` (файл вне репозитория, §10.3); в базу не попадает ни в каком виде (§7.1) |
| Токены подписки | хеш SHA-256 (`token_hash`) для поиска и шифротекст AES-256-GCM (`token_enc`, ключ `APP_ENCRYPTION_KEY`, `key_version`) для показа владельцу в кабинете, ролям Support и выше (каждый просмотр — запись `users.view_subscription_url` в `audit_log`) и в письме об активации (001.42) |
| Bootstrap-токены, ссылки писем | хеш SHA-256; исходное значение показывается однократно |
| Транспорт | TLS 1.2+ на nginx; mTLS для `/agent`; HSTS |
| Резервные копии | шифрование pgbackrest; копия ключа вне контура — в менеджере паролей оператора и у второго держателя §17.12 (Н-12; ОВ-A1, В-44); хранилище — у другого провайдера, чем хост |
| Ключ подписи объявлений | на хосте Control Plane не хранится; отпечаток открытого ключа кабинет показывает пользователю заранее, по нему пользователь проверяет объявление о смене домена подписки (ОВ-15, В-44; reliability.md §9.4, 001.70) |
| Персональные данные | перечень и сроки §16; автоудаление планировщиком; удаление аккаунта — см. ниже |
| Логи | путь `/s/` исключён из журнала nginx (по нормализованному `$uri` — на всех трёх `server`, и на 8443/8444, где пути `/s/` нет; у запроса, переведённого на 8443/8444 `rewrite` в служебный location, `$uri` к журналу — служебный путь, и у него решает путь сырой строки запроса `$request` до «?» и «#» в любой форме — метод с дефисом, второй пробел, absolute-form, `//s/`, `%73`/`%53`, косая `%2F` вокруг «s» (001.25, раунд 6); у остальных запросов сырой ключ не читается — в раунде 8 он читался у всех, и суффикс `#/s/` у любого пути (фрагмент nginx и приложение отбрасывают, маршрут срабатывает) прятал запрос из журнала целиком; строкой запроса, фрагментом или сегментом `/s/` пути, который маршрутизируется не в `/s/`, запрос из журнала не спрятать — спрятать можно только запрос, чей путь начинается с `/s/` в любом регистре (на публичном `server` — сама подписка или 404 приложения, на 8443/8444 — 404 nginx), и отказ на 8443/8444 по служебному пути, и только свой: карта служебных путей — по порту `server` (раунд 9: на публичном `/s/../__not_found` прятался); запрос, отвергнутый до разбора URI (пустой `$uri` при любом статусе — 400, 408, 414, 505: `$request` тогда — сырые байты строки), пишется форматом без строки запроса вовсе (раунд 9: 408, 414 и 505 писали токен); `$uri` меняют только переходы `rewrite` 8443/8444 в служебные location — `error_page` только в именованный location, `try_files` — в код, `X-Accel-Redirect` апстрима не исполняется, отдачи файлов и `index` нет: иначе внутренний переход увёл бы запрос подписки из его location на путь, который журнал пишет (стенд: `error_page 50x` на `/50x.html` при лежащем api — токен в access.log и error.log; раунд 9); все map без учёта регистра; `access_log` объявлен только на уровне http — ниже него только `off`, иначе строка уровня server заменила бы пару с фильтром; `error_log` не мягче `warn` — строки пределов с путём запроса пишутся на `notice`; location подписки пишет error.log в `/dev/null` — любая строка error.log в контексте запроса несёт строку запроса (ALERT исчерпания `worker_connections`, CRIT записи временного файла), — и временных файлов не создаёт; остаток — строки error.log до выбора location (разбор строки запроса и заголовков) идут в журнал уровня http со строкой запроса: сбой TLS-чтения соединения (CRIT — вызвать его может только сам клиент своим соединением) и нехватка памяти процесса (ALERT); путь `/s/` на 8443/8444 до апстрима не доходит; у переменных map писатель один — сама map) и из журнала приложения (access-log и WebSocket uvicorn выключены — журнал запросов ведёт nginx; конфигурация uvicorn — только строка запуска: `--log-level info`, а `UVICORN_*` из окружения точка входа снимает — уровень trace писал бы путь запроса; строки приложения с путём — 500, 503, сбой чтения тела — пишут путь без токена; Н-25, 001.25); тело запросов не логируется; тела Node API на диск хоста не попадают по конструкции: тело без известной длины на агентском и enrollment `server` не принимается (411 — сырой поток с обрамлением без верхней границы туда не доходит), буферы равны пределам тела (1 МиБ у отчёта, 64 КиБ у остальных), ответы апстрима (снапшот состава с credentials, панель; страница подписки — без временных файлов) сверх буферов прокси уходят во временный файл не больше 8 МиБ на ответ (`proxy_max_temp_file_size`; запрет файлов держал бы C-01 на скорости клиента и втащил бы её в норматив Н-4), а весь каталог временных файлов прокси смонтирован как tmpfs 64 МиБ внутри потолка памяти C-09 (восемь ответов по 8 МиБ — предел соединений одного сертификата, не потолок парка; каталог общий с телами публичного `server` больше 16 КиБ: анонимные медленные заливки могут его заполнить, и ответ Node API сверх буферов получит 500 — разделение каталогов и размер под парк 001.66b/001.75b, пределы публичного server — 001.66b); swap не выдаётся ни `nginx`, ни `api` (`memswap_limit` = `mem_limit`; на стенде cgroup `memory.swap.max` = 0); журналы контейнеров ограничены по размеру (10 МиБ × 3 на службу — внешний приёмник со сроком §16 и защитой от вымывания — 001.68; троттлирование прокси в error.log не пишется, а видно статусом 429 в access.log); ответ 422 тело не повторяет (не больше 50 ошибок, имена полей и сообщения усечены) |

Ротация ключа шифрования: новая версия ключа добавляется в конфигурацию; задача перешифровывает
записи по `key_version`; прежняя версия удаляется после завершения.

Удаление аккаунта (UC-14, §16.4) — модель без изменения журналов:

- персональные данные хранятся только в `users`, `email_tokens`, `auth_events`,
  `subscription_access_log`, `email_deliveries`, `user_online_ips`, `held_online_ips`,
  `user_blocked_ips` и в `node_user_state.blocked_ips`; при удалении `users.email`,
  `password_hash`, `timezone` стираются, `deleted_at` заполняется, строки остальных перечисленных
  таблиц удаляются (`email_deliveries` — по `events.user_id`, служебные письма без `event_id` — по
  `email_token_id` токенов пользователя и по `recipient`, равному `users.email` до стирания:
  своей колонки `user_id` у них нет), а `node_user_state.blocked_ips` очищается при переводе
  строк пользователя в `removed` (001.17);
- `user_id` в `traffic_lines`, `traffic_hourly`, `traffic_daily`, `balance_entries`, `audit_log`
  сохраняется как суррогат: после стирания он не связан ни с одним лицом;
- `audit_log` не хранит адресов почты и паролей в `old_value` и `new_value` (§4.4); для
  `actor_type = user` поля `ip` и `user_agent` не заполняются (001.48); ссылки на пользователя —
  по `user_id`.

**Why.** Замена идентификатора в журналах требует `UPDATE` на append-only таблицах ⇒ модель
сохраняет идентификатор и стирает то, что делает его персональным.

Ротация ключевого материала REALITY (§4.4): `short_ids` — окно перекрытия Н-33; ключевая пара —
при компрометации, с уведомлением пользователей ноды событием «Адрес или параметры ноды изменены»
(§4.17; В-41 б).

### 7.3 Защита от атак

| Угроза | Мера |
| :--- | :--- |
| Инъекции SQL | параметризованные запросы asyncpg; ORM нет |
| XSS | React экранирует по умолчанию; страница подписки — автоэкранирование Jinja2; CSP |
| CSRF | `SameSite=Lax` + заголовок `X-CSRF-Token` для изменяющих запросов |
| Перебор паролей и кодов | ограничение частоты по адресу и учётной записи, CAPTCHA (§5.12) |
| Перебор токенов подписки | отдельный порог для несуществующих токенов; ответ 404 без задержки |
| Подмена ноды | mTLS + одноразовый bootstrap; credentials только после `Active` (§11.3) |
| Компрометация ноды | credentials на пару «пользователь × нода»; отзыв identity Н-31; ротация Н-32, Н-33 |
| Ложные отчёты ноды | интервалы ноды монотонны и не перекрываются во времени (и через смену эпохи; `EXCLUDE` в схеме), `period_end` не позже часов сервера с допуском, первый интервал ноды — не раньше выдачи identity и не раньше суток назад (глубина буфера Н-8), новый — не старше 72 ч (сутки буфера плюс потолок возраста открытого): объявленное время не обгоняет стенное и отстаёт от него не больше окна приёма, поэтому порог прироста по полосе (полоса × длительность интервала на сумму uplink + downlink — байт пользователя проходит порт дважды — к нарастающим суммам частей интервала) ограничивает объём и по стенным часам, а слив буфера Н-8 после недоступности проходит; объявленное число частей только растёт, открытых интервалов у ноды не больше потолка, незавершённый интервал закрывается следующим интервалом, сроком или по возрасту (README `contracts/agent_v1/`, 001.34); потолок смен эпохи за скользящие сутки — против роста разрывов; удержание не освобождает от списания (объём в пределах потолка канала списывается сразу, удерживается превышение; часть сверх потолка открытых интервалов не списывается — отдельного действия разбора нет: оператор снимает `Suspended` с ноды и корректирует баланс в обе стороны (В-4 а); это путь, которым занижающая нода может уйти от списания, держа восемь удержанных интервалов открытыми, стопор — автоматический перевод ноды в `Suspended` при 3 интервалах с удержанной частью за скользящие 24 ч (порог — `settings.held_reports_suspend`; счёт — интервалы, а не части; окно — не раньше снятия ручного статуса; причина — в Audit Log и алерте «Немедленный»; событие «Нода приостановлена провайдером» не порождается; удержанные части и дальше списываются в пределах потолка, как в `Suspended` по матрице §4.6) — 001.30c, В-5 а) — иначе занижающая нода вызывала бы удержание намеренно; три сверки (§5.9), из которых независима только арифметическая — счётчики интерфейса тоже самоотчёт ноды |
| Ложные адреса в отчёте | вход лимита устройств (адреса и `last_seen`, §4.13) полностью под контролем недоверенной ноды: одна нода могла бы вытеснить настоящие устройства пользователя на всех его нодах — потолок различных адресов на пару «пользователь × нода» за окно, предпочтение адресов, подтверждённых строками трафика, алерт на кардинальность адресов ноды (ряд — 001.38, правило «Отложенный» — 001.68, reliability.md §9.3); `last_seen` не позже `period_end` интервала (с допуском часов) и не позже времени приёма, иначе приводится к `period_end` — адрес с меткой в будущем не остаётся «самым свежим» навсегда (001.38); принадлежность пользователей составу ноды (001.34) |
| Отказ учёта парка через прокси | принятый компромисс бюджета Н-4 против доступности: два слота одновременных отчётов на парк, и два держателя сертификатов CA медленными заливками занимают их до отказа на прокси (карта отказа по серийному номеру — 001.66c; 001.25 решила отзыв в C-01 без отказа на прокси); пороги приложения слоты не освобождают — тело дочитывает прокси до передачи в C-01 (`proxy_request_buffering on`), а 001.72 предела по identity в приложении не вводит, кроме порога `quota/request`; отказ на прокси закрывает риск лишь для отозванных сертификатов — медленная заливка держателем действующего остаётся, полное лечение — предел всей заливки: 411 убрал сырой поток без верхней границы, но предела на всю заливку у nginx нет — честный `Content-Length` в 1 МиБ по байту в 9 с (пауза между чтениями до 10 с) держит слот месяцами; нода за слотом получает 429 с `Retry-After` и повторяет с джиттером; два сертификата (одна нода в окне ротации Н-28: 2 × 5 r/s = 10 из 15 r/s парка) берут две трети частоты остальных операций парка, три сертификата — всю — остальные ждут в очереди прокси и получают 429 (тот же путь закрытия); признак рычага — рост `rt` при неизменном `urt` в access.log (задержки очереди в error.log не пишутся) — 001.68 |
| Отказ enrollment | enrollment — единственный анонимный вход: пределы соединений и частоты по адресу источника (один адрес не выбирает enrollment всему парку) и общий потолок частоты на всех (защита цикла событий) на уровне `server` — пути отказа 411, 413 и 404 тоже под ними (путь с управляющими символами — первым правилом server в служебный 404, на публичном server — 404 сразу, и C-01 сам отвечает на такой путь 404 до маршрутизации: иначе `%0A` в конце пути обходил точные `location`, а маршрут приложения с `$` его находил — 001.25, раунд 5): их решает `try_files` после фазы пределов (`return` исполняется до неё, а именованный `location` через `error_page` лишь задаёт формат ответа); отказов фазы FIND_CONFIG, тоже предшествующей пределам, конфигурация не допускает — `internal` нет, длина тела сверяется картой до проверки `client_max_body_size`, у prefix-location с `proxy_pass` есть точный сосед без косой черты (001.25, раунды 4–5); отказы, которые nginx выносит при разборе заголовков, — 400 (разбор, негодный `Host`, `Content-Length` вместе с `Transfer-Encoding`, сбой или отсутствие клиентского сертификата, HTTP без TLS на этот порт), 405 (`TRACE`, `CONNECT`), 408 (заголовки не дошли за `client_header_timeout`), 414, 494, 501 (неизвестный `Transfer-Encoding`) — пределов не знают (стенд: залпы без единого 429), поэтому пределы защищают приложение и цикл событий, а не журнал от анонимного залпа — сток, объём и срок журнала прокси — 001.68 (§7.2), предел соединений до запроса и `keepalive_requests` — 001.66b; распределённый источник и хеш токена — 001.72; обратная сторона ключа по адресу — несколько законных нод за одним адресом выхода делят один предел (NAT, один хостер) — 001.72; заголовки запроса ждутся не дольше 5 с и соединение по таймауту сбрасывается — полуоткрытое соединение не держит слот `worker_connections` (общий у трёх `server`) минуту; запас слотов от анонимных соединений — 001.66b |
| Кража ключа CA через уязвимость `api` | **принятый риск (решение заказчика 2026-09-25, 001.25)**: ключ онлайн-CA лежит в процессе `api`, открытом в интернет (панель, кабинет, страница подписки), а сертификат того же CA — единственный якорь агента для серверных сертификатов Control Plane (§7.1): чтение файлов или выполнение кода в любом публичном маршруте `api` дало бы ключ, а с ним — серверный сертификат для SAN Control Plane и подмену Control Plane перед нодами с позиции на их пути (identity листы с этим ключом не дают — её ищут по отпечатку и токену, — но дают TLS до C-01 с серийными номерами по выбору: номер чужой ноды занимает её пределы по сертификату — слот отчётов, и ей 429, — свежие номера дают бюджеты пределов без счёта, а карта отказа 001.66c по серийному номеру такой лист от листа жертвы не отличит). Сдерживание сейчас — только перевыпуск всему парку; снижение — отдельный офлайн-CA серверных сертификатов агентских портов как якорь bootstrap-команды, а онлайн-CA — только для листов нод (001.66d, 001.54) |
| Дорогой путь отказа до проверки identity | тело читается прокси и приложением до identity: тела без известной длины не принимаются (411 при `Transfer-Encoding: chunked` у любого метода — иное кодирование nginx отвергает 501 при разборе заголовков — и при отсутствии длины у любого метода, кроме GET и HEAD), пределы тела по классам операций с буферами, равными пределам, проверка формы **каждой** операции по байтам до разбора и до identity (пределы формы выведены из модели и публичны; путь отказа — единицы миллисекунд, а не тысячи ошибок pydantic), пределы одновременности и частоты по сертификату и на парк, пределы enrollment по адресу, потолки памяти, процессора и числа процессов, tmpfs временных файлов (001.33; C-09 правило границы 4) |
| Медленное чтение ответа | ответ апстрима прокси читает целиком без оглядки на клиента (`proxy_buffering on`) и отпускает C-01, остаток сверх буферов — во временном файле на tmpfs не больше 8 МиБ на ответ: медленный клиент держит соединение с прокси, не корутину api; ответ больше 8 МиБ обрывается (снапшот §5.7 — сотни КиБ). Исключение — страница подписки `/s/`: временных файлов у неё нет (Н-25), и ответ больше буферов прокси (умолчание nginx — 8 буферов по странице памяти, 32 КиБ на стенде) C-01 отдаёт со скоростью клиента — медленный клиент держит и запрос api (роаст 001.25, раунд 9); пределы соединений публичного `server` — 001.66b: по адресу источника (`limit_conn`, `limit_req`) — только для кабинета и панели, для `/s/` — общий потолок соединений с постоянным ключом и `send_timeout`, без ключа по адресу (§5.12) |
| Злоупотребление через ноду | nftables: порты 25/587, частные сети, метаданные, лимит соединений и частота новых входящих соединений с одного адреса клиента на порты inbound (meter; значение — поле ноды `new_conn_rate_per_ip` рядом с `max_conn_per_ip`, раздел `agent`, В-10 а) (§16.6) |
| Изменение журнала | `audit_log` без прав изменения у роли приложения; триггер |
| Утечка секретов в репозиторий | секреты только из файлов Docker secrets; проверка в CI |
| SSRF при доставке webhook | запрет частных диапазонов, адреса службы метаданных и перенаправлений; разрешение имени до запроса |
| Отказ Redis | fail-closed: `/s/{token}`, вход, восстановление, активация кодов отвечают 503 с `Retry-After` (§9.1); пределы Node API по identity держат зоны прокси, от Redis они не зависят |

Ограничение частоты реализовано счётчиками в Redis с ключами по §5.12: адрес, учётная запись,
токен. Ключ «identity ноды» §5.12 закрывают зоны прокси по серийному номеру клиентского
сертификата (`$ssl_client_serial`, §7.1), а не счётчики Redis (001.72). Агент применяет джиттер и
экспоненциальную задержку.

Реакции при превышении (колонка «реакция» §5.12), контракт для кода и для будущего сервиса
CAPTCHA (ОВ-A3):

- Отказ — 429 с `Retry-After` до освобождения скользящего окна; «отказ с задержкой» означает
  срок повтора, а не замедление ответа (удержание соединений — вектор отказа в обслуживании).
- CAPTCHA (вход по адресу источника и по учётной записи, регистрация по адресу и домену) — при
  настроенном сервисе CAPTCHA превышение порога даёт 429 `captcha_required`, верный ответ
  пропускает; без сервиса пороги по адресу и домену дают отказ, а порог по учётной записи **не
  действует**: блокировка учётной записи не применяется (§5.12), и без CAPTCHA нет способа
  отличить владельца от перебирающего — верные учётные данные проходят всегда, перебор одной
  записи сдерживает порог по адресу источника.
- Счётчик по учётной записи хранит только отказы: читается до проверки пароля, засчитывается
  после неверного пароля, обнуляется успешным входом. Иначе чужие попытки запирали бы владельца.
- Над порогом при настроенном сервисе ответ CAPTCHA проверяется **до** пароля (иначе порог —
  оракул пароля), и **один раз за запрос**: ответы сервисов CAPTCHA одноразовые, повторная
  проверка того же ответа отвечает «уже использован», а порогов, требующих ответа, в одном
  запросе несколько (адрес и учётная запись при входе; адрес, домен и настройка `captcha.enabled`
  при регистрации). Реализация — объект ответа запроса с однократной проверкой (`CaptchaAnswer`,
  задача 001.14); сервис CAPTCHA (ОВ-A3) реализует `CaptchaVerifier.verify` в расчёте на один
  вызов на ответ и без ответа не вызывается.
