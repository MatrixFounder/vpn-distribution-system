# 7. Безопасность

> Part of [docs/ARCHITECTURE.md](../ARCHITECTURE.md).


### 7.1 Аутентификация и авторизация

| Субъект | Механизм | Хранение |
| :--- | :--- | :--- |
| Пользователь | пароль argon2id; сессия — непрозрачный идентификатор в cookie `HttpOnly; Secure; SameSite=Lax` | Redis `sess:{id}` с TTL, набор `user_sessions:{user_id}` |
| Администратор | пароль + TOTP обязательно; резервные коды | Redis, TTL бездействия 12 часов (Н-27) |
| Node Agent | mTLS: клиентский сертификат внутреннего CA + токен identity в заголовке | `node_identities` |
| Клиент подписки | bearer-токен в пути, ≥ 128 бит | `subscription_tokens.token_hash` |
| Webhook-получатель | подпись HMAC-SHA256 тела | секрет в `settings` |

Инвалидация сессий: блокировка учётной записи удаляет все ключи из набора пользователя (Н-27);
смена пароля и перевыпуск второго фактора — все, кроме текущей; «выход везде» — все.

Внутренний CA: ключ CA — Docker secret роли `api` (`ca_key`, P-256), сертификат CA — тот же
файл `tls/ca.crt`, которым nginx проверяет клиентов (§10.3; решение 001.25: nginx нужен сертификат
CA файлом раньше первого запроса, а зашифрованная копия ключа в базе защиты сверх файла
`APP_ENCRYPTION_KEY` не даёт и попадала бы в каждую резервную копию). Сертификаты нод
выпускаются при enrollment на срок 90 дней с ротацией через `rotate_credentials` и окном
перекрытия (Н-28); лист решает CA, а не нода: из CSR берётся только открытый ключ P-256 после
проверки подписи, субъект — идентификатор ноды, профиль `CA:FALSE`, `digitalSignature`,
`clientAuth`. nginx проверяет сертификат по CA и передаёт его целиком заголовком `X-Client-Cert`
(`$ssl_client_escaped_cert`); C-01 считает отпечаток SHA-256 от DER (у nginx есть только
SHA-1 — `$ssl_client_fingerprint`), сверяет его с `node_identities` и токен identity
(`secrets.compare_digest` по хешам). Подпись ECDSA податлива: из листа `(r, s)` держатель без
ключа CA получает близнеца `(r, n − s)`, которого проверка по CA тоже принимает, — другие байты
и отпечатки, то же подписанное тело. identity близнеца C-01 не находит (401), а пределы прокси
ключуются серийным номером листа (`$ssl_client_serial`, внутри подписанного тела; номера CA
выбирает сам, 159 случайных бит) — у близнецов он общий (001.25, проверено на стенде).
Подтверждение ноды (UC-01 шаг 7) привязано к identity, которую сверил администратор: панель
передаёт её отпечаток, и если между сверкой и подтверждением прошёл новый обмен — 409
`identity_changed`. Отзыв identity (Н-31) действует со следующего запроса: C-01 сверяет identity
с базой на каждом запросе. Прокси отозванный сертификат не отвергает (`ssl_crl` нет — решение
001.25, остаточный риск — §7.3): держатель отозванного листа получает 401, но до ответа
занимает пределы прокси своего сертификата — до конца срока листа (не больше 90 дней); сократить
это окно могут только отказ на прокси (001.66) или смена CA с перевыпуском всему парку.

Bootstrap-токен: 256 бит, хранится хешем, одноразовый, срок Н-24; обмен выполняется по HTTPS без
клиентского сертификата на отдельном `server` прокси, обслуживающем только `/agent/v1/enroll`.
Якорь доверия первого шага — сертификат внутреннего CA из bootstrap-команды: панель выдаёт его
вместе с токеном (ответ выдачи токена), администратор переносит на VPS своим каналом, и агент
проверяет им серверный сертификат enrollment-server (с именем) **до** того, как отдать токен;
`ca_pem` ответа обмена обязан совпасть с якорем. Иначе посредник на первом шаге прочёл бы токен,
обменял его сам и подсунул агенту свой CA — постоянный посредник на всём Node API. Серверные
сертификаты обоих портов агентов выпускает тот же CA с `extendedKeyUsage serverAuth` и SAN, листы
нод — только `clientAuth` без SAN: агент проверяет назначение и имя, и лист ноды не выдаст себя
за Control Plane. После обмена агент печатает отпечаток своего листа — его администратор сверяет
на шаге 6 UC-01 (001.25; агент — 001.54, команда — 001.61). Повторная выдача и отзыв identity
аннулируют неиспользованный токен отметкой (`annulled_at`), а не укороченным сроком: годность
решают отметки — погашение, аннулирование, отзыв, — и шаг часов базы назад её не вернёт.
Серийный номер каждого листа, выпущенного обменом, хранится (`node_identities.cert_serial`, форма
`$ssl_client_serial`) — по нему отказ на прокси (001.66) найдёт и листы, выпущенные до него.
Исключения — стенд: `dev/dev-node.crt` из `deploy/scripts/dev-secrets.sh` выпущен тем же CA мимо
обмена, и строки identity у него нет (порт агентов его пропускает, C-01 отвечает 401); пробы
`control-plane/tests/stand/` выпускают листы обменом, но уборка удаляет их строки identity (ключи
нод пробы не сохраняет — предъявить такие листы некому); в промышленном контуре CA ничего мимо
обмена не подписывает (001.66). Хранение номера держит код, а не схема: у `app_rw` есть DELETE на
`node_identities` (уборка тестов и проб), и удаление строки identity в коде приложения запрещено
только его дисциплиной.
Ключ ограничения частоты для enrollment — адрес источника и хеш предъявленного токена (§5.12 не
задаёт ключ для запроса без identity): на прокси стоят пределы соединений и частоты по адресу
источника и общий потолок частоты на всех клиентов (защита цикла событий C-01; 001.33), хеш
токена и распределённый источник — 001.72. Клиентский сертификат ноды проверяется по CA с
глубиной 0 — только листы, подписанные CA напрямую (в OpenSSL глубина считает промежуточных CA,
и 1 пропускала бы одного): лист, способный подписывать, множил бы серийные номера, по которым
ключуются все пределы прокси (первая линия — профиль листа, 001.25).

Авторизация: разрешения в коде, проверка декоратором на каждой операции; отказ пишется в `audit_log`
с результатом `denied`. Чтение журнала через `/admin/audit` регистрируется как действие с актором и
фильтром запроса (§4.16). Политики §5.11: просмотр subscription URL и impersonation — отдельные
разрешения с записью в журнал; операции сверх порога — задача с подтверждением второй учётной
записью.

### 7.2 Защита данных

| Данные | Защита |
| :--- | :--- |
| Пароли | argon2id: `m = 64 MiB`, `t = 3`, `p = 4` |
| Приватные ключи REALITY, credentials пользователей, секреты TOTP, коды, пароль SMTP | AES-256-GCM на уровне приложения; ключ `APP_ENCRYPTION_KEY` из файла секрета; `key_version` для ротации |
| Ключ CA | Docker secret `ca_key` роли `api` (файл вне репозитория, §10.3); в базу не попадает ни в каком виде (§7.1) |
| Токены подписки, bootstrap-токены, ссылки | хеш SHA-256; исходное значение показывается однократно |
| Транспорт | TLS 1.2+ на nginx; mTLS для `/agent`; HSTS |
| Резервные копии | шифрование pgbackrest; ключ вне контура (Н-12) |
| Персональные данные | перечень и сроки §16; автоудаление планировщиком; удаление аккаунта — см. ниже |
| Логи | путь `/s/` исключён из журнала nginx (по нормализованному `$uri` — на всех трёх `server`, и на 8443/8444, где пути `/s/` нет; у запроса, переведённого на 8443/8444 `rewrite` в служебный location, `$uri` к журналу — служебный путь, и у него решает путь сырой строки запроса `$request` до «?» и «#» в любой форме — метод с дефисом, второй пробел, absolute-form, `//s/`, `%73`/`%53`, косая `%2F` вокруг «s» (001.25, раунд 6); у остальных запросов сырой ключ не читается — в раунде 8 он читался у всех, и суффикс `#/s/` у любого пути (фрагмент nginx и приложение отбрасывают, маршрут срабатывает) прятал запрос из журнала целиком; строкой запроса, фрагментом или сегментом `/s/` пути, который маршрутизируется не в `/s/`, запрос из журнала не спрятать — спрятать можно только запрос, чей путь начинается с `/s/` в любом регистре (на публичном `server` — сама подписка или 404 приложения, на 8443/8444 — 404 nginx), и отказ на 8443/8444 по служебному пути, и только свой: карта служебных путей — по порту `server` (раунд 9: на публичном `/s/../__not_found` прятался); запрос, отвергнутый до разбора URI (пустой `$uri` при любом статусе — 400, 408, 414, 505: `$request` тогда — сырые байты строки), пишется форматом без строки запроса вовсе (раунд 9: 408, 414 и 505 писали токен); `$uri` меняют только переходы `rewrite` 8443/8444 в служебные location — `error_page` только в именованный location, `try_files` — в код, `X-Accel-Redirect` апстрима не исполняется, отдачи файлов и `index` нет: иначе внутренний переход увёл бы запрос подписки из его location на путь, который журнал пишет (стенд: `error_page 50x` на `/50x.html` при лежащем api — токен в access.log и error.log; раунд 9); все map без учёта регистра; `access_log` объявлен только на уровне http — ниже него только `off`, иначе строка уровня server заменила бы пару с фильтром; `error_log` не мягче `warn` — строки пределов с путём запроса пишутся на `notice`; location подписки пишет error.log в `/dev/null` — любая строка error.log в контексте запроса несёт строку запроса (ALERT исчерпания `worker_connections`, CRIT записи временного файла), — и временных файлов не создаёт; остаток — строки error.log до выбора location (разбор строки запроса и заголовков) идут в журнал уровня http со строкой запроса: сбой TLS-чтения соединения (CRIT — вызвать его может только сам клиент своим соединением) и нехватка памяти процесса (ALERT); путь `/s/` на 8443/8444 до апстрима не доходит; у переменных map писатель один — сама map) и из журнала приложения (access-log и WebSocket uvicorn выключены — журнал запросов ведёт nginx; конфигурация uvicorn — только строка запуска: `--log-level info`, а `UVICORN_*` из окружения точка входа снимает — уровень trace писал бы путь запроса; строки приложения с путём — 500, 503, сбой чтения тела — пишут путь без токена; Н-25, 001.25); тело запросов не логируется; тела Node API на диск хоста не попадают по конструкции: тело без известной длины на агентском и enrollment `server` не принимается (411 — сырой поток с обрамлением без верхней границы туда не доходит), буферы равны пределам тела (1 МиБ у отчёта, 64 КиБ у остальных), ответы апстрима (снапшот состава с credentials, панель; страница подписки — без временных файлов) сверх буферов прокси уходят во временный файл не больше 8 МиБ на ответ (`proxy_max_temp_file_size`; запрет файлов держал бы C-01 на скорости клиента и втащил бы её в норматив Н-4), а весь каталог временных файлов прокси смонтирован как tmpfs 64 МиБ внутри потолка памяти C-09 (восемь ответов по 8 МиБ — предел соединений одного сертификата, не потолок парка; каталог общий с телами публичного `server` больше 16 КиБ: анонимные медленные заливки могут его заполнить, и ответ Node API сверх буферов получит 500 — разделение каталогов и размер под парк 001.66/001.75, пределы публичного server — 001.66); swap не выдаётся ни `nginx`, ни `api` (`memswap_limit` = `mem_limit`; на стенде cgroup `memory.swap.max` = 0); журналы контейнеров ограничены по размеру (10 МиБ × 3 на службу — внешний приёмник со сроком §16 и защитой от вымывания — 001.68; троттлирование прокси в error.log не пишется, а видно статусом 429 в access.log); ответ 422 тело не повторяет (не больше 50 ошибок, имена полей и сообщения усечены) |

Ротация ключа шифрования: новая версия ключа добавляется в конфигурацию; задача перешифровывает
записи по `key_version`; прежняя версия удаляется после завершения.

Удаление аккаунта (UC-14, §16.4) — модель без изменения журналов:

- персональные данные хранятся только в `users`, `email_tokens`, `auth_events`,
  `subscription_access_log`, `email_deliveries`; при удалении `users.email`, `password_hash`,
  `timezone` стираются, `deleted_at` заполняется, строки остальных перечисленных таблиц
  удаляются;
- `user_id` в `traffic_lines`, `traffic_hourly`, `traffic_daily`, `balance_entries`, `audit_log`
  сохраняется как суррогат: после стирания он не связан ни с одним лицом;
- `audit_log` не хранит адресов почты и паролей в `old_value` и `new_value` (§4.4); ссылки на
  пользователя — по `user_id`.

**Why.** Замена идентификатора в журналах требует `UPDATE` на append-only таблицах ⇒ модель
сохраняет идентификатор и стирает то, что делает его персональным.

Ротация ключевого материала REALITY (§4.4): `short_ids` — окно перекрытия Н-33; ключевая пара —
при компрометации, с уведомлением пользователей.

### 7.3 Защита от атак

| Угроза | Мера |
| :--- | :--- |
| Инъекции SQL | параметризованные запросы asyncpg; ORM нет |
| XSS | React экранирует по умолчанию; страница подписки — автоэкранирование Jinja2; CSP |
| CSRF | `SameSite=Lax` + заголовок `X-CSRF-Token` для изменяющих запросов |
| Перебор паролей и кодов | ограничение частоты по адресу и учётной записи, CAPTCHA (§5.12) |
| Перебор токенов подписки | отдельный порог для несуществующих токенов; ответ 404 без задержки |
| Подмена ноды | mTLS + одноразовый bootstrap; credentials только после `Active` (§11.3) |
| Компрометация ноды | credentials на пару «пользователь × нода»; отзыв identity Н-31; ротация Н-32, Н-33 |
| Ложные отчёты ноды | интервалы ноды монотонны и не перекрываются во времени (и через смену эпохи; `EXCLUDE` в схеме), `period_end` не позже часов сервера с допуском, первый интервал ноды — не раньше выдачи identity и не раньше суток назад (глубина буфера Н-8): объявленное время не обгоняет стенное и не уходит в прошлое дальше буфера, поэтому порог прироста по полосе (полоса × длительность интервала, по каждому направлению — к нарастающим суммам частей интервала) ограничивает объём и по стенным часам, а слив буфера Н-8 после недоступности проходит; объявленное число частей только растёт, открытых интервалов у ноды не больше потолка, незавершённый интервал закрывается следующим интервалом, сроком или по возрасту (README `contracts/agent_v1/`, 001.34); потолок смен эпохи за скользящие сутки — против роста разрывов; удержание не освобождает от списания (объём в пределах потолка канала списывается сразу, удерживается превышение; повторные удержания переводят ноду в `suspended`) — иначе занижающая нода вызывала бы удержание намеренно; три сверки (§5.9), из которых независима только арифметическая — счётчики интерфейса тоже самоотчёт ноды |
| Ложные адреса в отчёте | вход лимита устройств (адреса и `last_seen`, §4.13) полностью под контролем недоверенной ноды: одна нода могла бы вытеснить настоящие устройства пользователя на всех его нодах — потолок различных адресов на пару «пользователь × нода» за окно, предпочтение адресов, подтверждённых строками трафика, алерт на кардинальность адресов ноды (001.38); принадлежность пользователей составу ноды (001.34) |
| Отказ учёта парка через прокси | принятый компромисс бюджета Н-4 против доступности: два слота одновременных отчётов на парк, и два держателя сертификатов CA медленными заливками занимают их до `ssl_crl` (001.66: 001.25 решила отзыв в C-01 без отказа на прокси) и порогов приложения (001.72); `ssl_crl` закрывает риск лишь для отозванных сертификатов — медленная заливка держателем действующего остаётся, полное лечение — предел всей заливки: 411 убрал сырой поток без верхней границы, но предела на всю заливку у nginx нет — честный `Content-Length` в 1 МиБ по байту в 9 с (пауза между чтениями до 10 с) держит слот месяцами; нода за слотом получает 429 с `Retry-After` и повторяет с джиттером; два сертификата (одна нода в окне ротации Н-28: 2 × 5 r/s = 10 из 15 r/s парка) берут две трети частоты остальных операций парка, три сертификата — всю — остальные ждут в очереди прокси и получают 429 (тот же путь закрытия); признак рычага — рост `rt` при неизменном `urt` в access.log (задержки очереди в error.log не пишутся) — 001.68 |
| Отказ enrollment | enrollment — единственный анонимный вход: пределы соединений и частоты по адресу источника (один адрес не выбирает enrollment всему парку) и общий потолок частоты на всех (защита цикла событий) на уровне `server` — пути отказа 411, 413 и 404 тоже под ними (путь с управляющими символами — первым правилом server в служебный 404, на публичном server — 404 сразу, и C-01 сам отвечает на такой путь 404 до маршрутизации: иначе `%0A` в конце пути обходил точные `location`, а маршрут приложения с `$` его находил — 001.25, раунд 5): их решает `try_files` после фазы пределов (`return` исполняется до неё, а именованный `location` через `error_page` лишь задаёт формат ответа); отказов фазы FIND_CONFIG, тоже предшествующей пределам, конфигурация не допускает — `internal` нет, длина тела сверяется картой до проверки `client_max_body_size`, у prefix-location с `proxy_pass` есть точный сосед без косой черты (001.25, раунды 4–5); отказы, которые nginx выносит при разборе заголовков, — 400 (разбор, негодный `Host`, `Content-Length` вместе с `Transfer-Encoding`, сбой или отсутствие клиентского сертификата, HTTP без TLS на этот порт), 405 (`TRACE`, `CONNECT`), 408 (заголовки не дошли за `client_header_timeout`), 414, 494, 501 (неизвестный `Transfer-Encoding`) — пределов не знают (стенд: залпы без единого 429), поэтому пределы защищают приложение и цикл событий, а не журнал от анонимного залпа — объём журнала и предел соединений на уровне хоста — 001.66; распределённый источник и хеш токена — 001.72; обратная сторона ключа по адресу — несколько законных нод за одним адресом выхода делят один предел (NAT, один хостер) — 001.72; заголовки запроса ждутся не дольше 5 с и соединение по таймауту сбрасывается — полуоткрытое соединение не держит слот `worker_connections` (общий у трёх `server`) минуту; запас слотов от анонимных соединений — 001.66/001.72 |
| Кража ключа CA через уязвимость `api` | **принятый риск (решение заказчика 2026-09-25, 001.25)**: ключ онлайн-CA лежит в процессе `api`, открытом в интернет (панель, кабинет, страница подписки), а сертификат того же CA — единственный якорь агента для серверных сертификатов Control Plane (§7.1): чтение файлов или выполнение кода в любом публичном маршруте `api` дало бы ключ, а с ним — серверный сертификат для SAN Control Plane и подмену Control Plane перед нодами с позиции на их пути (identity листы с этим ключом не дают — её ищут по отпечатку и токену, — но дают TLS до C-01 с серийными номерами по выбору: номер чужой ноды занимает её пределы по сертификату — слот отчётов, и ей 429, — свежие номера дают бюджеты пределов без счёта, а карта отказа 001.66 по серийному номеру такой лист от листа жертвы не отличит). Реакции при превышении (колонка «реакция» §5.12), контракт для кода и для будущего сервиса
CAPTCHA (ОВ-A3):

- Отказ — 429 с `Retry-After` до освобождения скользящего окна; «отказ с задержкой» означает
  срок повтора, а не замедление ответа (удержание соединений — вектор отказа в обслуживании).
- CAPTCHA (вход по адресу источника и по учётной записи, регистрация по адресу и домену) — при
  настроенном сервисе CAPTCHA превышение порога даёт 429 `captcha_required`, верный ответ
  пропускает; без сервиса пороги по адресу и домену дают отказ, а порог по учётной записи **не
  действует**: блокировка учётной записи не применяется (§5.12), и без CAPTCHA нет способа
  отличить владельца от перебирающего — верные учётные данные проходят всегда, перебор одной
  записи сдерживает порог по адресу источника.
- Счётчик по учётной записи хранит только отказы: читается до проверки пароля, засчитывается
  после неверного пароля, обнуляется успешным входом. Иначе чужие попытки запирали бы владельца.
- Над порогом при настроенном сервисе ответ CAPTCHA проверяется **до** пароля (иначе порог —
  оракул пароля), и **один раз за запрос**: ответы сервисов CAPTCHA одноразовые, повторная
  проверка того же ответа отвечает «уже использован», а порогов, требующих ответа, в одном
  запросе несколько (адрес и учётная запись при входе; адрес, домен и настройка `captcha.enabled`
  при регистрации). Реализация — объект ответа запроса с однократной проверкой (`CaptchaAnswer`,
  задача 001.14); сервис CAPTCHA (ОВ-A3) реализует `CaptchaVerifier.verify` в расчёте на один
  вызов на ответ и без ответа не вызывается.
