### 5.1 Внешний API `/api/v1`

Стиль: REST, JSON, версия в пути. Спецификация OpenAPI генерируется FastAPI и публикуется
(R-50). Аутентификация — сессионная cookie (§7.1); входящий webhook `/hooks/*` — подпись HMAC,
без сессии и CSRF. Ошибки — единый формат
`{"error": {"code": "...", "message": "...", "details": {...}}}` с HTTP-кодами 400, 401, 403,
404, 409, 410 (истёкший одноразовый объект: `token_expired`, 001.14), 422, 429. Ответ 422
(`validation_error`) не повторяет тело запроса: в `details.errors` — не больше 50 ошибок,
остаток — числом в `details.truncated`, имена полей в `loc` усечены до 64 символов, сообщения
`msg` — до 200.

### 5.2 Node API `/agent/v1`

Транспорт: HTTPS с mTLS (§7.1), JSON. Версия в пути; `X-Agent-Version` в каждом запросе. Новый
обязательный раздел ответа состояния вводится только новой версией пути (`/agent/v2`): ответ, в
котором нет известного агенту обязательного раздела, агент не применяет — запись в журнал и
повтор с выдержкой (В-14; агент — 001.55).

| Операция | Метод и путь | Тело запроса | Ответ |
| :--- | :--- | :--- | :--- |
| Регистрация | `POST /agent/v1/enroll` | bootstrap-токен, CSR, версии | клиентский сертификат, токен identity |
| Heartbeat | `POST /agent/v1/heartbeat` | версии, время ноды, `applied_*`, состояние процесса Xray `xray_running` (001.30) | код 204 |
| Состояние | `GET /agent/v1/state?config_version=&users_seq=&generation=` и применённая версия раздела `agent` (имя параметра — README контракта, 001.26) | — | дельты, курсоры, контрольная сумма, раздел `agent`, команды |
| Снапшот | `GET /agent/v1/state?full=1` | — | полное состояние |
| Подтверждение | `POST /agent/v1/ack` | `applied_config_version`, `applied_users_seq` | 204 |
| Отчёт | `POST /agent/v1/reports` | ключ, период, строки по пользователям, адреса, счётчики интерфейса | `last_accepted_seq`, признак дубликата |
| Грант | `POST /agent/v1/quota/request` | `user_id`, израсходовано | `quota_grant_bytes`, `issued_seq` |
| Метрики | `POST /agent/v1/metrics` | CPU, память, диск, сеть, адреса, соединения; время работы ноды и агента `uptime_s`, `agent_uptime_s`, результат проверки целей `targets: [{inbound_tag, ok, reason}]` (Н-30) и накопительные счётчики агента (data-model §4.2.3 `node_metrics`) — поля вводит 001.30; счётчики соединений по адресам (conntrack) — поле вводит 001.39 | 204 |

Грант квоты (R-26):

- размер гранта пары «пользователь × нода» для тарифа с лимитом = `min(Н-17 в единицах списания,
  остаток периода) / N`, где N — число нод, на которых пользователь присутствует; отдельного
  размера по умолчанию нет, следующий грант агент запрашивает при расходе 50 % текущего
  (idea §4.11) — ОВ-A7 закрыт этим правилом;
- для Unlimited грант не ограничен (В-6): Н-17в действует для тарифов с лимитом, подключения при
  недоступности Control Plane не прерываются (Н-7); грант без ограничения — `quota_grant_bytes:
  null` в ответе `quota/request` и в строке состава (строка пользователя Unlimited несёт `null` и
  до первого гранта; в базе — `grant_bytes NULL`, data-model §4.2.5), в сумму непогашенных
  (AC-09) не входит; агент такого пользователя по гранту не отключает и следующего гранта не
  запрашивает (001.36, 001.57);
- новый грант выдаётся по запросу агента и заменяет остаток прежнего; прежний помечается
  `superseded_at`; агент остатки не суммирует;
- строка состава несёт `quota_issued_seq` рядом с `quota_grant_bytes`: грант из строки, как и из
  ответа запроса, агент применяет только с номером больше применённого — повтор строки
  (снапшот, дельта `blocked_ips`) остаток не сбрасывает (001.36, 001.57);
- грант и `consumed_bytes` — в единицах списания: агент считает расход по дельтам пользователя
  как `floor((uplink + downlink) × multiplier_milli / 1000)`, коэффициент — из раздела `agent`
  ответа состояния (001.36, 001.57);
- запрос гранта для пользователя вне состава ноды — 404 `user_not_on_node`, без повтора (001.36);
- суммарный непогашенный объём грантов пользователя с лимитом не превышает Н-17 (AC-09);
- расход гранта подтверждается отчётами и записывается в `consumed_bytes`.

Long-poll: C-01 удерживает запрос состояния до 30 с, ожидая сообщения в канале Redis `node:{id}`;
C-02 публикует в канал после записи в `node_user_state` или `node_config_versions`. Ответ без
изменений — код 204.

Поток конфигурации передаётся как полная конфигурация Xray без credentials пользователей. Поток
состава — список строк `node_user_state` с credentials из `node_user_credentials`. Расшифровка
выполняется на стороне C-01 для ноды, определённой по identity запроса (§4.4).

Параметры агента вне документа Xray — раздел `agent` ответа состояния рядом с `config`, вне
`config.json` и его контрольной суммы, со своим курсором версии: `max_conn_per_ip` (001.27),
`new_conn_rate_per_ip` — частота новых соединений с одного адреса клиента (001.27, В-10),
`multiplier_milli` (001.36), `disconnect_strategy` — константа со стратегией, выбранной PoC-1а
(001.40, 001.88; В-11). Смена раздела применяется без
перезапуска Xray (перезагрузка набора nftables, запись в хранилище агента); перезапуск — только
при смене контрольной суммы документа Xray: иначе каждая смена параметра рвала бы соединения и
открывала новую эпоху счётчиков. Форму раздела объявляет заглушка 001.26; агент принимает раздел
в 001.55 и применяет в 001.80. Применённую версию раздела агент передаёт параметром запроса
состояния (001.26); её отставание — повод ответить на удержанный запрос, как отставание
`config_version` (001.75c).

Вентиль по статусу (§4.6 источника — единственный источник правил):

| Статус ноды | Поток конфигурации | Поток состава | Команды |
| :--- | :--- | :--- | :--- |
| `pending` | отказ 403 | отказ 403 | нет |
| `provisioning` | да | нет; `users_seq` не продвигается | да |
| `active`, `degraded`, `maintenance` | да | да | да |
| `offline` | да, при первом обмене | да, при первом обмене | да |
| `disabled`, `suspended` | да | только строки со состоянием, снимающим доступ | нет |

При отфильтрованном ответе `users_seq` продвигается до наибольшего `updated_seq` выборки и ноде
выставляется `resync_required`; при выходе из фильтрующего статуса агент получает признак в
ответе и берёт полный снапшот. Для `provisioning` состав пуст: пробуждение по каналу `node:{id}`
не даёт немедленного ответа, удержание продолжается до таймаута.

Коды ошибок: 400 — тело не разобрано до проверки формы (негодный UTF-8, число длиннее 4 300
цифр, обрыв заливки; вложенность ограничена размером тела и проверкой формы, не пределом
разбора) — не повторять как есть (у операций без тела не объявляется); 401 — identity отозвана или неизвестна, у
регистрации — отказ по bootstrap-токену: `token_invalid` (не выдавался или нода выведена),
`token_used` (уже обменян), `token_expired` (истёк или аннулирован — новым токеном, отзывом identity
или установкой ручного статуса, 001.30b) — тем же токеном не повторять (001.25); 403 — нода не
подтверждена
(`node_not_approved`), отчёт содержит идентификатор другой ноды (`node_mismatch`), грант не
выдаётся ноде в этом статусе (`grant_unavailable`); 404 — грант для пользователя вне состава
ноды (`user_not_on_node`) — не повторять (001.36); 409 — несовпадение `generation`
(`generation_mismatch`; `generation` — `settings.state_generation` (§5.2 источника), а не
поколение identity, как в описании контракта 001.28, — описание приводит 001.75b; текущее
значение — в `details.generation`, с ним агент повторяет `full=1`: снапшот с чужим поколением
тоже получает 409) или курсор ноды опережает состояние Control Plane (`cursor_ahead`) —
требуется снапшот; 411 — тело без известной длины (`Transfer-Encoding: chunked` при любом
методе — иное кодирование nginx отвергает 501 ещё при разборе заголовков; отсутствие
content-length у любого метода, кроме GET и HEAD, — по HTTP/2 заголовка Transfer-Encoding нет)
прокси не принимает (`length_required`, единый формат) — не повторять (у операций без тела не объявляется; тип содержимого проверяет
приложение — без `Content-Type: application/json` 422); 413 — тело больше предела прокси
(64 КиБ у операций раздела, 1 МиБ у отчёта, у результата команды — по ширине формы с полем
`output`, В-18, 001.31; страница nginx без тела единого формата; прокси
сверяет `Content-Length` независимо от метода, поэтому объявлен и у GET; решается после пределов
прокси, как 404 и 411, — при их превышении раньше придёт 429); 422 — тело не
прошло проверку: `too_wide` — шире формы своей модели (скобки и запятые, а у модели без
строковых полей — и число длиннее `bigint`; сверяется по байтам до разбора и до identity у
каждой операции с телом; у плоских моделей это любое лишнее поле сверх полного набора, кроме
результата команды, где в предел входит бюджет свободного текста `error`), `json_invalid` —
синтаксически негодный JSON, остальное — ошибки модели; такие тела
чинятся на стороне агента, не повторяются и не делятся, кроме `too_wide` у отчёта: там это часть
шире пределов формы, она делится, как после 413; 426 — версия агента не
поддерживается; 429 — превышена частота или предел
одновременности (пределы по клиентскому сертификату и общие потолки парка стоят на прокси на
каждом проксирующем location агентского server, у enrollment-server — пределы по адресу
источника и общий потолок частоты — все на уровне `server`, пути отказа под ними; штатное
действие пределов частоты — задержка в очереди
прокси, 429 — сверх очереди; 429 прокси — в том же формате ошибки, `rate_limited`). Отказы 403,
409, 426 и 429 несут `Retry-After`. Поток состава несёт credentials
только у строк, выдающих доступ (`active`); строки, снимающие доступ, применяются по тегу
пользователя.

Повторное подтверждение identity (idea §5.3, UC-10 A2): отдельной операции нет — агент хранит
identity текущего и прежнего поколений и, получив 401, повторяет запрос с сохранённой прежней
(001.54); Control Plane принимает её в окне перекрытия Н-28, продлённом после смены
`state_generation` (001.31), если в базе она не отозвана. Отозванная identity возвращается
только новым bootstrap-токеном (§4.6 источника). Отзывы, сделанные после точки копии,
восстановление повторяет из внешнего журнала отзывов до открытия агентского порта (В-20,
data-model §4.2.3, 001.67): такая identity повторным подтверждением не возвращается.

Ротация identity (Н-28, В-16): планировщик C-03 ставит команду `rotate_credentials`, когда до
конца срока листа текущего поколения (90 дней) остаётся не больше 30 дней; агент подаёт CSR
операцией `POST /agent/v1/identity/rotate` и переходит на новое поколение, прежнее хранит; окно
перекрытия — 7 суток от выпуска нового поколения, смена `state_generation` продлевает его на
7 суток от момента смены (сервер — 001.31, агент — 001.81).

Отчёт о трафике: до 500 строк и 2 500 адресов в одной части (потолок — из Н-4: норматив
p95 ≤ 200 мс считается по времени апстрима, ни заливка тела при полосе ноды, ни отдача ответа
клиенту в него не входят — прокси буферизует тело целиком до передачи и ответ целиком после,
оба умолчания объявлены явно и закреплены; разбор в бюджете при двух частях, разбираемых
одновременно, плюс операции остальных видов и enrollment, прибывающие за это окно при своих
частотах, и резерв на транзакцию приёма; остальным операциям отведено не больше четверти
цикла событий процесса C-01 — решение, закреплённое гейтом; тело каждой операции сверяется
по байтам с формой её модели до разбора — путь отказа не дороже пути приёма); интервал
отчёта — штатно 60 с
(§5.9; длительность принятых интервалов наблюдается метрикой), не дольше часа (дельта после
перерыва снятия счётчиков; перерыв дольше часа — новая эпоха счётчиков, решение заказчика в
001.33; перезапуск Xray посередине интервала закрывает прежнюю эпоху последним
снятым интервалом, новая начинается с момента перезапуска, промежуток — разрыв; перезапуск
агента при живом Xray эпоху не меняет; смена эпохи для сверки — разрыв между концом
последней части прежней и началом первой части новой; смен эпохи за скользящие сутки — не
больше 48), задаётся `(counter_epoch, period_start, period_end)`, интервалы ноды монотонны и
не перекрываются во времени (и через смену эпохи), `period_end` не позже часов сервера с
допуском, первый интервал ноды — не раньше выдачи identity, первого назначения и суток назад
(глубина буфера Н-8), новый — не старше 72 ч (сутки буфера плюс потолок возраста открытого) —
так объявленное время не обгоняет стенное и отстаёт от него не больше окна приёма, и
порог §5.9 (полоса × длительность интервала на сумму uplink + downlink — байт пользователя
проходит порт дважды — к нарастающим суммам принятых частей) ограничивает объём и по стенным часам; интервал целиком относится к часу UTC
`period_start`; нода с большим составом шлёт за интервал несколько частей с последовательными
`report_seq` и объявленным `parts_total`, которое в пределах интервала только растёт
(деление отказанной части добавляет части; действует последнее принятое, применяется до
проверки диапазона; меньше прежнего — отказ 422 `report_inconsistent`) — пользователь в одной
части, счётчики интерфейса в первой (нарушения — тот же 422); интервал закрывается завершением, частью следующего интервала ноды,
сроком 25 часов после последней части (глубина буфера Н-8 плюс час) или потолком возраста от
первой части (48 часов — два буфера Н-8); часть к закрытому интервалу и часть вне диапазона
открытого — отказ 409 `interval_closed` без повтора (как и 409 `rejected_time`: отказ записан,
точка продолжения — в `details.last_accepted_seq`, `Retry-After` нет), недостающие части —
разрыв для сверки;
удержанная часть (`held_anomaly`) предыдущий интервал не закрывает: первая часть нового
интервала открывает его с признаком удержания, удержанное продолжение открытого ставит
признак на нём; открытых интервалов у ноды — не больше 8: удержанная часть сверх потолка
открывает свой интервал закрытым (`capped`), без списания, с алертом; удержание по порогу и
потолку смен эпохи не освобождает от списания — объём в пределах потолка канала списывается
сразу и входит в нарастающие суммы интервала, удерживается превышение; повторные удержания
(по умолчанию 3 различных интервала отчёта хотя бы с одной частью со статусом `held_anomaly`, в том
числе интервал с `close_reason = 'capped'`, за скользящие 24 ч по `received_at`, окно — не раньше
снятия ручного статуса `nodes.manual_cleared_at`; части одного интервала — одно удержание;
`settings.held_reports_suspend`)
переводят ноду в `suspended` — 001.30c, В-5: причина — в Audit Log и алерте, событие «Нода
приостановлена провайдером» не порождается, удержанные части и в `suspended` списываются в
пределах потолка канала (матрица §4.6); отдельного действия разбора нет — оператор снимает
`suspended` (001.30b) и корректирует баланс в обе стороны (001.50, В-4);
новый интервал не старше 72 ч (`too_old`); смена эпохи — соседние
интервалы с разными эпохами, возврат к прежней тоже;
состояние интервала — таблица `report_intervals` (data-model
§4.2.5); номер части, отказанной по размеру (413/422), переиспользуется после деления, номер
части, отказанной по времени или к закрытому интервалу, остаётся пропущенным — агент
продолжает с номера за последним отправленным; строки и адреса пользователей вне состава
ноды отбрасываются с алертом; identity и статус ноды приём перепроверяет под блокировкой её
строки (отзыв во время запроса — 401); один запрос отчёта в полёте на ноду
независимо от числа действующих сертификатов; значения — только в канонических формах (UUID
в 36 символов, метки RFC 3339 со смещением не длиннее 32 символов, адреса текстом без zone id,
целые без дробной части), тело — с `Content-Length` и `Content-Type: application/json`; тело
шире самого большого допустимого отвергается до разбора и до проверки identity (пределы формы
публичны); предел тела (1 МиБ — 413; без известной длины — 411), одновременности и частоты (по
сертификату и на парк) — на прокси. Каталог `contracts/agent_v1/` — зафиксированные запросы и
ответы.

### 5.3 Subscription-эндпоинт

| Путь | Ответ |
| :--- | :--- |
| `GET /s/{token}` | формат по `User-Agent` |
| `GET /s/{token}/base64` | принудительно `base64` |
| `GET /s/{token}/singbox` | принудительно `singbox` |
| `GET /s/{token}` из браузера | страница подписки (Jinja2, без SPA) |

Состояния и коды — по §5.6. Соответствие состоянию подписки (001.42): `active` → `active`;
`suspended_quota` → `traffic_exceeded`; `suspended_admin` → `blocked` (блокировка пользователя
ставит его вместе с `users.status = blocked`, В-40); `expired` → `expired`; токен отозван,
пользователь удалён (`deleted`) или подписки нет (`none`) → `unknown_token`, 404. Тексты
`announce` — по состоянию, у `blocked` — с причиной. Заголовки: `subscription-userinfo`,
`profile-update-interval`, `profile-title`, `announce`, `support-url`. Записывается
`subscription_access_log`. Соответствие `User-Agent → формат` — в `settings`; домены подписки —
окружение развёртывания (data-model §4.2.6, В-27).

Значения заголовков (001.42):

- `subscription-userinfo` (В-25): `total` — действующий лимит периода, лимит тарифа и начисления
  (`traffic_limit_bytes` − Σ дельт `bonus` и `adjustment` периода), у Unlimited — 0; `upload` и
  `download` — billable, списанный отчётами за период (`used_billable_bytes` − та же сумма),
  разложенный по направлениям пропорционально сырому трафику периода; `total − upload −
  download` равен остатку в кабинете; `expire` — `period_end` текущего периода, Unix-время;
- `profile-update-interval` — `settings.profile_update_interval_hours`, по умолчанию 1 ч
  (ОВ-18 закрыт, В-26): целевого значения восстановления base64-клиентов нет, оно ручное (Н-35).

### 5.4 Внутренние интерфейсы

| Интерфейс | Механизм | Гарантии |
| :--- | :--- | :--- |
| Постановка задачи | `INSERT INTO jobs` в транзакции бизнес-операции | at-least-once; идемпотентность по ключу |
| Выборка задачи | `SELECT ... FOR UPDATE SKIP LOCKED` по очереди; аренда выборки 5 мин | один исполнитель на задачу в каждый момент; брошенная (аренда истекла) выбирается снова, завершение фехтуется владельцем; выполнение — at-least-once |
| Пробуждение long-poll | Redis `PUBLISH node:{id}` | best-effort; страховка — таймаут удержания 30 с |
| Планировщик | `pg_advisory_lock` на запуск | один активный планировщик |
| Метрики | `/metrics` в формате Prometheus у C-01…C-03 | pull |
| Окно обслуживания | API Alertmanager v2 (`silence` на приоритет «Отложенный») из C-01 по действию в панели; другого обращения C-01 к Alertmanager нет | создание и снятие — в Audit Log; Alertmanager недоступен — 503 (001.85, В-50) |

Ключи идемпотентности задач: `notify:email:{event_id}`, `notify:webhook:{event_id}:{получатель}`
(почта и каждый получатель webhook — своя задача), `aggregate:{day}` (тип
`traffic.aggregate_day`, полезная нагрузка `{"day"}`), `publish_user:{user_id}:{xid}` (xid —
транзакция бизнес-операции: повторы внутри одной операции сливаются),
`publish_node:{node_id}:{xid}` (тип `composition.publish_node`, исполнитель и ключ — 001.29;
постановка при смене групп ноды — 001.87),
`rotate_node_credentials:{node_id}:{xid}` (тип `composition.rotate_node_credentials`: ключ по ноде
и транзакции отзыва identity, повтор отзыва в той же транзакции сливается — 001.29),
`revocation_log:identity:{cert_serial}` и `revocation_log:token:{token_hash}` (задача записи
строки внешнего журнала отзывов: одна на отозванную identity или аннулированный токен, имя
объекта в хранилище детерминировано, повтор перезаписывает тот же объект — 001.67, В-20),
`limits:{node_id}:{counter_epoch}:{report_seq}` (одна проверка лимитов на принятый отчёт со
списком пользователей), `limits:plan:{user_id}:{xid}` (переоценка квоты при смене тарифа: задача
`limits.check` в транзакции `change_plan` с полезной нагрузкой `{"user_ids": [user_id]}` без
`node_id` — обработчик читает только `user_ids`, 001.35). Уникальность действует для статусов
`pending` и `running` (§4.4), поэтому `aggregate:{day}` ставится повторно после позднего отчёта;
постановку, подавленную, пока задача суток в `running`, покрывает ночная агрегация 001.37c: она
пересчитывает сутки D−1…D−3 (окно приёма 72 ч).

Публикация состава — задача `composition.publish_user` очереди `critical`, поставленная в
транзакции бизнес-операции (переход подписки, перевод в `suspended_quota`, приём отчёта с
изменённым набором `blocked_ips`): исполнитель выделяет `updated_seq`, пишет `node_user_state` и
после коммита делает `PUBLISH node:{id}`. Прямой вызов публикации из приёма отчёта запрещён:
приём держит строку ноды, публикация ждала бы ту же блокировку. Принятая 001.22 публикует
напрямую после коммита; перевод на постановку — 001.29.

Пробуждение исполнителя: `LISTEN jobs_critical` / `LISTEN jobs_background`; постановка задачи
выполняет `NOTIFY` после коммита; страховочный опрос — раз в 1 с для критичной очереди и раз в
10 с для фоновой.

Раскладка бюджета Н-13 (p95 ≤ 10 с, максимум ≤ 60 с) для отзыва доступа:

| Шаг | Верхняя оценка |
| :--- | :--- |
| Приём отчёта, запись баланса, постановка `limits.check` (одна транзакция) | 1 с |
| Пробуждение исполнителя критичной очереди | 1 с |
| Проверка лимитов, перевод в `suspended_quota`, постановка `composition.publish_user` (одна транзакция) | 1 с |
| Пробуждение исполнителя критичной очереди | 1 с |
| Запись `node_user_state`, `NOTIFY`, `PUBLISH node:{id}` | 1 с |
| Пробуждение long-poll и ответ агенту | 1 с; без пробуждения — до 30 с таймаута |
| Применение агентом через `AlterInbound` | 1 с |

Итог без потери пробуждения — 7 с; при потере сообщения Redis — до 36 с, в пределах максимума.

### 5.5 Агент ↔ Xray

| Операция агента | Вызов Xray | Основание |
| :--- | :--- | :--- |
| Добавить или удалить пользователя | `HandlerService.AlterInbound` с `AddUserOperation` / `RemoveUserOperation` | Д-4 |
| Снять счётчики | `StatsService.QueryStats` без сброса, шаблон `user>>>*>>>traffic>>>*` | Д-3 |
| Адреса онлайн | `StatsService.GetStatsOnlineIpList` по пользователю | Д-5 |
| Блокировать адрес | `RoutingService.AddRule` с правилом по `source` на outbound `blackhole` | R-27 |
| Снять блокировку | `RoutingService.RemoveRule` | R-27 |
| Применить конфигурацию | запись файла, `systemctl restart xray` после финального чтения; затем возврат состава (ниже) | §5.2 |
| Распознать старт Xray | `StatsService.GetSysStats`: сброс `Uptime` | §5.9 источника; 001.56, 001.80 |
| Разорвать соединения пользователя | по ОВ-22: стратегию выбирает PoC-1а (001.88) — удаление и повторное добавление или правило `RoutingService` по адресам; реализуется только выбранная (`disconnect_strategy` раздела `agent`, §5.2; В-11); перезапуск inbound только замеряется и выбран быть не может (В-9) | R-25, Н-17а |

Агент хранит текущие правила маршрутизации в SQLite и переустанавливает их после каждого
перезапуска Xray (R-27).

Возврат состава: конфигурация Xray приходит без пользователей, поэтому после каждого старта Xray
(применение конфигурации, `restart_xray`, перезапуск systemd после сбоя, перезагрузка VPS)
агент добавляет через `AlterInbound` всех пользователей локального состава в состоянии
`active`, кроме исчерпавших грант локально, затем переустанавливает правила маршрутизации
(001.80). Старт распознаётся по сбросу времени работы процесса, а не по убыванию счётчиков: без
пользователей в inbound счётчиков нет (тот же признак эпохи — 001.56).
