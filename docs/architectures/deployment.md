# 10. Развёртывание

> Part of [docs/ARCHITECTURE.md](../ARCHITECTURE.md).


### 10.1 Окружения

| Окружение | Состав | Назначение |
| :--- | :--- | :--- |
| Разработка | Compose: postgres, redis; C-01…C-03 локально; нода в контейнере без REALITY | разработка, модульные и контрактные тесты |
| Стенд | Полный Compose на одном хосте; две реальные ноды в разных странах | приёмка §14, PoC |
| Промышленное | Полный Compose на одном хосте; ноды по §4.5 | обслуживание |

### 10.2 CI/CD

| Стадия | Control Plane | Node Agent | Web |
| :--- | :--- | :--- | :--- |
| Проверка | ruff, mypy, pytest | go vet, golangci-lint, go test | eslint, tsc, vitest |
| Контракты | контрактные тесты `/agent/v1` на зафиксированных запросах; эталонные ответы подписки побайтно | те же фикстуры со стороны агента | клиент из OpenAPI собирается без ошибок |
| Сборка | образ Docker | статический бинарный файл с контрольной суммой | статические файлы |
| Выпуск | тег версии; миграции применяются при старте C-01 с блокировкой | публикация бинарного файла; команда `update_agent` вручную (§17.3) | образ контейнера `web` (статический сервер за nginx, 001.66b) |

Стадия проверки поднимает пустую базу, поэтому применяет миграции перед тестами (`make migrate`):
сквозные тесты ходят в живую базу и ждут её мигрированной, а на стенде это делает роль `api` при
старте — предусловие, которого в CI иначе нет.

Стадия контрактов, наоборот, служебных контейнеров не требует: зафиксированные запросы
`contracts/agent_v1/*.json` воспроизводятся против приложения с подменённым пулом, и герметичность
проверяется, а не декларируется — любое обращение заглушек к базе валит прогон (`make
test-contract`). Тот же каталог фикстур читает сторона агента (`node-agent/internal/contracts`,
задача 001.53), поэтому расхождение сторон обмена видно до стенда.

Порядок выпуска: Control Plane, затем агенты (§17.2). Откат Control Plane — предыдущий образ;
миграции обратно совместимы в пределах одного выпуска.

### 10.3 Конфигурация

| Параметр | Источник |
| :--- | :--- |
| Адреса базы и Redis, домены подписки (`SUBSCRIPTION_DOMAINS`), режимы | переменные окружения из `.env` (права 600); домены подписки панель показывает только для чтения, в промышленном контуре (`APP_ENV=prod`) их не меньше двух — проверка валидатора настроек окружения при старте `api` (001.45), замена домена — процедура развёртывания (§10.4; В-27 а) |
| Пароли базы, `APP_ENCRYPTION_KEY`, ключ CA, пароль SMTP, ключ pgbackrest | Docker secrets из файлов вне репозитория |
| Настройки, изменяемые администратором | таблица `settings`; окно обслуживания — `silence` Alertmanager, который панель ставит через его API (адрес API — `ALERTMANAGER_URL` окружения; §9.3; 001.85) |
| Агент | `/etc/node-agent/config.yaml`: адреса enrollment и `/agent/v1`, пути к identity, путь к якорю доверия серверов — сертификату серверного CA из bootstrap-команды (§7.1; 001.53, 001.54, 001.66d); каталог `/var/lib/node-agent` (0600) |

### 10.4 Инструкция развёртывания

Control Plane:

1. Подготовить хост: Docker, Compose v2, DNS-записи для доменов кабинета, панели, двух доменов
   подписки и домена писем с записями SPF, DKIM, DMARC (R-41; 001.66e), сертификаты TLS
   (ACME HTTP-01: запрос `/.well-known/acme-challenge/` на порту 80 nginx передаёт (`proxy_pass`)
   в контейнер `certbot`, остальные запросы порта 80 — 301 на 443; nginx файлов не отдаёт;
   001.66b).
2. Создать файлы секретов и `.env`; сгенерировать `APP_ENCRYPTION_KEY` и ключ CA листов нод;
   ключ офлайн-CA серверных сертификатов создаётся и хранится вне хоста, на хост попадают его
   сертификат и подписанный им `tls/agent.crt` (001.66d).
3. `docker compose --env-file deploy/compose/.env -f deploy/compose/docker-compose.yml -f
   deploy/compose/<профиль>.yml up -d` — команда с явным списком файлов, своя у каждого профиля:
   стенд — базовый файл и `docker-compose.dev.yml`, промышленный контур — базовый файл и
   промышленный оверлей 001.66, оба оверлея вместе не применяются (Compose не подхватывает
   `compose.yaml`/`*.override.*` сам: список файлов — часть конфигурации, страж
   `control-plane/tests/unit/test_proxy_contract.py` читает команды из шапки базового файла,
   разбирает каждую отдельно и сверяет с `deploy/README.md`; вторую команду и разбор вводит
   001.66); C-01 применяет миграции при старте. Пределы ресурсов задаёт базовый файл и только он:
   `mem_limit` = `memswap_limit` (C-01 1 ГиБ, C-09 256 МиБ — без swap, страницы с адресами
   пользователей на диск хоста не уезжают), `cpus` и `pids_limit` (`worker_processes` nginx
   равен его квоте `cpus`), tmpfs каталога временных файлов nginx (64 МиБ — восемь ответов
   апстрима по 8 МиБ, предел соединений одного сертификата; каталог общий с телами публичного
   `server` — разделение и размер под парк 001.66b/001.75b; права точки монтирования 0711: мастер
   nginx создаёт подкаталоги рабочему процессу, которому нужен проход, — с 0700 он получал
   `Permission denied`, стенд), предел журналов контейнеров (`json-file` 10 МиБ × 3) — оверлеи
   их не переопределяют и не заводят своих томов nginx (001.33); потолки стоят у двух служб,
   которые держат тела запросов; потолки PostgreSQL, Redis, worker'ов и scheduler
   (`memswap_limit` = `mem_limit`) 001.66 добавляет в базовый файл. Промышленный оверлей несёт
   только политику перезапуска (в том числе после OOM) и службы `certbot` и `web` (001.66b);
   секретов и пределов в нём нет: секреты объявлены файлами в базовом файле (001.66).
4. Создать первого Super Admin командой `python -m app.cli admin create`; включить второй фактор.
   Остальные учётные записи администраторов создаёт Super Admin в разделе панели `/admin/admins`
   (001.89; security.md §7.1).
5. Настроить pgbackrest с бакетом у другого провайдера, чем хост (ОВ-A1); копию ключа шифрования
   записать в менеджер паролей оператора и передать второму держателю доступов (§17.12, Н-12);
   проверить первую полную копию.
6. Подключить внешний сервис мониторинга доступности: пробы `/healthz` и подписки обоих доменов
   и канал уведомления оператора (001.68), страница состояния (001.70) (§9.4).
7. Повторить шаги 3–5 на чистом хосте — критерий воспроизводимости AC-19.

Замена домена подписки (В-27 а): DNS-запись и сертификат нового домена, `server_name` nginx,
`SUBSCRIPTION_DOMAINS` в `.env`, пересоздание контейнеров `api` и `nginx` (`docker compose … up -d`:
подстановка `server_name` и чтение `.env` выполняются при старте контейнера, `restart` окружение не
перечитывает; 001.66); объявление о смене — подписанное ключом объявлений (§9.4). Шаги развёртывания
— `deploy/README.md` (001.66; DNS — 001.66e, сертификат — 001.66b); объявление о смене и способ
проверки его подлинности — 001.70.

Нода (§4.5):

1. Создать запись Node в панели; получить bootstrap-команду с адресами enrollment и `/agent/v1`
   и сертификатом серверного CA — якорем доверия (§7.1; 001.66d); команду из токена, адресов и
   `ca_pem` собирает 001.61 в ответе выдачи токена, показывает панель (001.64).
2. Выполнить команду на VPS: скрипт устанавливает Xray-core v26.10.21 с проверкой контрольной
   суммы, `node-agent`, systemd-юниты, базовые правила nftables.
3. Агент выполняет enrollment; нода в `Pending`; администратор подтверждает.
4. Нода переходит в `Active`; проверить подключение каждым клиентом §4.2.

Вывод ноды из эксплуатации (§4.6 «Удаление», UC-12 A2; В-21 а): в панели — операция вывода: статус
`disabled` с отметкой вывода (запись ноды сохраняется), отзыв identity без ротации ключевого
материала, запись в Audit Log (001.87); на VPS по SSH — локальная подкоманда `node-agent
decommission`: слив буфера отчётов, финальное чтение счётчиков, затирание identity и конфигурации
Xray (закрытый ключ REALITY, credentials пользователей), после успешного слива — состояния агента и
буфера (001.81). Канал команд для вывода не используется. Порядок шагов — инструкция оператора
(001.71).
