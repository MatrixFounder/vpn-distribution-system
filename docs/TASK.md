## 1. Описание задачи

### 1.1 Цель

Построить центральную систему управления парком VPN-серверов так, чтобы один оператор обслуживал
до 1 000 пользователей на 10 нодах из единой панели.

Пользователь при этом получает одну ссылку подписки на все доступные ему серверы.

### 1.2 Границы

**In scope.**

- Control Plane: пользователи, подписки, тарифы, коды, ноды, группы, учёт трафика, панель.
- Node Agent: регистрация, синхронизация, отчёты, команды, локальное принуждение.
- Три профиля подключения: `vless-raw-vision`, `vless-xhttp`, `trojan-reality` (§4.4).
- Subscription-эндпоинт в форматах `base64` и `singbox` (§5.6).
- Эксплуатационный контур: резервное копирование, аудит, алерты, развёртывание.

**Out of scope** — по `docs/idea.md` §10. Полный перечень там; ключевые позиции:

- приём платежей, рекуррент, скидочные промокоды — Phase 2;
- лимит одновременных подключений на пользователя как свойство тарифа — Phase 2;
- месячный и произвольный лимит трафика — вне MVP (§10);
- форматы Mihomo и Clash — вне MVP (§10);
- оркестратор поэтапного обновления парка — Phase 2;
- Telegram-бот, мобильные приложения, автоматическое создание VPS — Phase 2–3.

### 1.4 Решение build / adopt / fork

Принят вариант Build (решение заказчика 2026-10-25, `docs/reviews/wi-35-spec-review.md` В-11;
ОВ-1 закрыт). Настоящий документ описывает требования к собственным Control Plane и Node Agent;
требование ДЛ-1 (§0.2) действует. PoC-1, PoC-2 и PoC-3 служили выбору варианта и не выполняются.

PoC-1а (§0.3) выполняется отдельной ранней задачей 001.88 на VPS заказчика до задач логики
разрыва соединений 001.40, 001.60 и 001.82. Задача замеряет кандидатов R-25, закрывает ОВ-22 и
закрепляет Н-17; кандидат `restart_inbound` только замеряется и выбран быть не может (В-9).

Сквозной срез §7.2 (Redeem-код → подписка → подключение → учёт с коэффициентом → исчерпание →
отзыв) проверяется на стенде отдельной задачей 001.73b. Приёмка MVP по критериям раздела 5
требований приоритета M — задача 001.73; нагрузку (AC-20) проверяет 001.73c, учебное
восстановление с нодами (AC-18) — 001.73d (В-46). Механизм разрыва соединений (ОВ-22) и значение
Н-17 проверяет раньше задача 001.88 (решение заказчика 2026-10-25,
`docs/reviews/wi-35-spec-review.md` В-11, В-47).

### 3.1 Детали по идентификатору

**R-01** — Control Plane, источник истины (§2, §3.1, §5.1)

- Все сущности §4.4, §4.8–§4.11, §4.14, §5.9, §5.10 хранятся в Control Plane.
- Внешний API `/api/v1/` обслуживает кабинет и панель; иных клиентов API в MVP нет.
- Спецификация OpenAPI публикуется и версионируется вместе с API (§17.13).
- Секреты в базе хранятся зашифрованными (§5.13).

**R-02** — Bootstrap и регистрация (§4.5, Н-24)

- Токен одноразовый, срок жизни по Н-24, привязан к записи Node.
- Обмен токена на клиентский сертификат и токен identity (§5.3).
- В `Pending` нода не получает ни одного потока; в `Provisioning` — поток структурной
  конфигурации и канал команд, без состава пользователей (§4.6). Состав пользователей
  публикуется после перехода в `Active`.
- Администратор сверяет адрес источника, отпечаток сертификата, версии агента и Xray.
- Пересоздание использует ту же запись Node; при компрометации ключи REALITY заменяются.
- Отзыв identity переводит ноду в `Disabled` из любого статуса (Н-31); обмен нового
  bootstrap-токена — в `Pending` из любого статуса, кроме выведенной из эксплуатации; новая
  identity подтверждается заново (§4.6, решение заказчика 2026-09-24).

**R-03** — Inbound и профили (§4.4)

- Сущность Inbound: `node_id`, `profile`, `port`, `tag`, `enabled`.
- Поля REALITY по §4.4, включая `reality_min_client_ver`, `reality_xver`, `client_spider_x`.
  `reality_xver = 0` на всех нодах: цель не принимает PROXY protocol; на ноду рандомизируются
  только `reality_limit_fallback_*` (решение заказчика 2026-10-25, В-17).
- `reality_min_client_ver` = 1.8.1 (решение заказчика 2026-10-26, WI-36).
- `client_fingerprint` даёт в ядре клиента ClientHello с ключом X25519MLKEM768. Набор допустимых
  отпечатков — в `settings`, на v26.10.21 — `chrome`; перепроверяется по §17.3 (решение заказчика
  2026-10-26, WI-36).
- Поля XHTTP по §4.4 в именах версии v26.10.21: `session_id_placement`, `session_id_key`.
- Ключевую пару генерирует и хранит Control Plane; ротация по таблице §4.4 и Н-33.
- Требования к `reality_target`: TLS 1.3, HTTP/2, без перенаправлений; проверка при вводе и
  периодически (Н-30).

**R-04** — Контракт `/agent/v1/` (§3.4, §5.2, §5.4)

- Исходящее соединение агента; входящих портов управления на ноде нет.
- Потоки `config_version` и `users_seq`; long-poll с удержанием 30 с; контрольная сумма.
- Полный снапшот: первый запуск, расхождение суммы, раз в сутки, смена `state_generation`.
- Состав пользователей применяется горячо через API Xray; конфигурация — перезаписью с
  перезапуском после финального чтения счётчиков.
- Команды: `command_id` (в контракте — поле `id`), `type`, `expires_at`; статусы
  `issued`…`expired`; порядок по `issued_at`. `collect_diagnostics` возвращает в поле `output`
  результата версии, статус служб и хвост журнала агента без адресов пользователей, не больше
  64 КиБ (решение заказчика 2026-10-25, В-18).
- Версия API в пути; поддержка предыдущей версии ≥ 3 релиза. Новый обязательный раздел ответа
  состояния вводит новую версию пути; ответ без известного обязательного раздела агент не
  применяет: запись в журнал, повтор с выдержкой (решение заказчика 2026-10-25, В-14).
- Расхождение Desired/Applied дольше 120 с → алерт (§5.4).

**R-05** — Health monitoring и статусы (§4.6, §4.7, Н-15)

- Heartbeat с периодом §5.2; `Offline` и возврат в `Active` по порогам Н-15.
- Восемь статусов; переходы и матрица влияния по §4.6 — единственный источник правил.
- `Maintenance`, `Disabled` и `Suspended` не возвращаются в `Active` автоматически.
- Нода, после последнего подтверждения ещё не бывшая в `Active`, из `Offline` и после снятия
  ручного статуса переходит в `Provisioning`, а не в `Active` (решение заказчика 2026-10-25,
  В-13).
- Ручной статус меняется на другой ручной напрямую действием администратора; из `Pending` ручные
  статусы не ставятся (решение заказчика 2026-10-25, В-19).
- Повторные удержания отчётов (R-21) переводят ноду в `Suspended` автоматически: порог —
  настройка `held_reports_suspend`, по умолчанию 3 удержания за скользящие 24 ч. Удержание —
  интервал отчёта хотя бы с одной удержанной частью: части одного интервала дают одно удержание;
  удержания, принятые до снятия ручного статуса с ноды, не учитываются. Причина — в Audit Log и в
  алерте; событие «Нода приостановлена провайдером» не порождается; удержанные части списываются
  в пределах потолка канала, как у `Suspended` по §4.6 (решение заказчика 2026-10-25, В-5; счёт
  по интервалам — `docs/reviews/wi-35-spec-review.md` §5).
- Метрики: CPU, RAM, диск, сеть, уникальные адреса онлайн, соединения по данным ОС; состояние
  процесса Xray, время работы ноды и агента (§4.7).
- Ноды в ручных статусах алертов не порождают; исключение — алерт о самом переводе в `Suspended`
  по повторным удержаниям.

**R-06** — Пробы доступности (§4.7, Р-2) — приоритет S

- Проба из страны присутствия пользователей; признак доступности по стране.
- Недоступность из страны исключает ноду из выдачи пользователям этой страны без смены статуса.

**R-07** — Версии и обновление (§17.3, Н-26, Р-11)

- Xray-core v26.10.21, sing-box v1.14.4; Node Agent — семантические версии.
- Команда `update_agent`; неуспех → откат и `Degraded`. Нода выходит из `Degraded` после
  следующего успешного `update_agent` или действием администратора (решение заказчика 2026-10-25,
  В-15).
- Канареечная нода; проверка каждого клиента §4.2 до обновления остальных.
- Исправление уязвимости — не позднее 7 суток.

**R-08** — Регистрация и вход (§4.1, §5.12, Н-27)

- Режимы: открытая, по приглашению, закрытая. В режиме «по приглашению» регистрация возможна
  только с действующим Redeem-кодом; код сразу активирует подписку (решение заказчика 2026-10-25,

- CAPTCHA и ограничение частоты при открытой регистрации.
- Принятие правил использования при регистрации; версия принятия сохраняется (§16.5).
- Нормализация адреса, отклонение одноразовых доменов (§16.8).
- Сессии с серверным состоянием; «выход на всех устройствах».

**R-09** — Подтверждение и восстановление (§4.1, §17.7)

- Ссылка подтверждения и ссылка восстановления одноразовые; срок действия задан настройкой.
- Запасной путь подтверждения адреса при недоставке письма: повторная отправка письма с порогом
  частоты §5.12 и ручное подтверждение через Support с записью в Audit Log (решение заказчика
  2026-10-25, В-32).

**R-10** — Личный кабинет (§4.2)

**R-11** — Статистика (§4.12)

**R-12** — Первое подключение (§17.6)

- Показатель времени до первого подключения собирается с первого дня эксплуатации; целевое

**R-13** — Удаление аккаунта (§16.4)

**R-14** — Subscription-эндпоинт (§5.6, Н-25)

- Токен ≥ 128 бит, бессрочный, перевыпуск ротирует credentials на всех нодах.
- Выбор формата по `User-Agent` с конфигурируемым соответствием; суффиксы `/base64`, `/singbox`.
- Заголовки `subscription-userinfo`, `profile-update-interval`, `profile-title`, `announce`,
  `support-url`.
- `subscription-userinfo`: `upload` и `download` — billable периода, разложенный по направлениям
  пропорционально сырому трафику; `total` — действующий лимит (R-24); остаток в клиенте совпадает
  с кабинетом (решение заказчика 2026-10-25, В-25).
- `profile-update-interval` — настройка, по умолчанию 1 ч (ОВ-18 закрыт, решение заказчика
  2026-10-25, В-26).
- Состояния `active`, `expired`, `traffic_exceeded`, `blocked` → 200; `unknown_token` → 404.
  `suspended_quota` подписки → `traffic_exceeded`; блокировка пользователя (`suspended_admin`,
  R-34) → `blocked` с причиной в `announce` (решение заказчика 2026-10-25, В-40).
- Путь запроса не логируется; отдельный порог частоты для несуществующих токенов.
- Запись обращения: время, домен, формат, `User-Agent`, адрес источника и его страна; хранение
  30 дней.

**R-15** — Генераторы (§5.6, §17.1)

- `base64`: список `vless://` и `trojan://`; `singbox`: JSON по схеме v1.14.4.
- Профиль `vless-xhttp` выдаётся только в `base64`; генератор возвращает «неприменим».
- Эталонные ответы каждого формата сравниваются побайтно на приёмке.

**R-16** — Состав серверов (§4.3, §5.6, Н-34, Н-35)

- Фильтр: статус подписки, тариф, группы доступа, протоколы, статус ноды, доступность по стране,
  подтверждённый `users_seq` ноды, исправность inbound: inbound в состоянии ошибки (Н-30) не
  выдаётся, остальные профили ноды выдаются (решение заказчика 2026-10-25, В-12).
- Запись на каждую пару «нода × профиль»; имя содержит коэффициент, если он ≠ 1.0.
- `singbox`: автоселектор `urltest` → Н-34; `base64`: ручное восстановление → Н-35.

**R-17** — Домены и страница (§5.6, Р-1)

- Два домена в разных зонах, одинаковый контент, отдельно от административного API.
- Домены задаются окружением развёртывания; панель показывает их только для чтения; замена
  домена — процедура развёртывания: DNS, сертификаты, nginx (решение заказчика 2026-10-25, В-27).
- Обращение из браузера возвращает страницу подписки с инструкциями и кнопками импорта.

**R-18** — Группы (§4.8)

- Группа доступа: many-to-many с тарифами и нодами.
- Тарифицируемая группа: ровно одна на ноду; ограничение целостности в схеме.

**R-19** — Счётчики и отчёт (§5.9, Н-19, Н-20)

- Кумулятивное чтение без сброса; `counter_epoch` при каждом запуске Xray и после перерыва
  снятия счётчиков дольше часа (решение заказчика, 001.33): дельта перерыва не отправляется,
  объём оценивает сверка непрерывности; смен эпохи — не больше 48 за скользящие сутки.
- Отчёт с интервалом §5.9 (штатно 60 с, не дольше часа) и ключом `(node_id, counter_epoch,
  report_seq)`; отчёт интервала передаётся одной или несколькими частями; ответ несёт
  `last_accepted_seq`.
- Убывание счётчика внутри эпохи — ошибка: журнал, алерт, баланс не меняется.
- Финальное чтение перед плановым перезапуском Xray.
- Тег пользователя в Xray — устойчивый идентификатор, без credential.

**R-20** — Буфер и время (§5.9, Н-8)

- Персистентный буфер глубиной по Н-8; при переполнении — сброс старейших, алерт.
- Синхронизация времени; допуск §5.9 (5 с) проверяется по опережению: `period_end` позже часов
  Control Plane более чем на 5 с → отказ `rejected_time`, алерт. Интервалы ноды монотонны и не
  перекрываются.
- Окно приёма — 72 ч (сутки буфера Н-8 плюс потолок возраста интервала): интервал, начавшийся
  раньше, получает отказ `rejected_time`. Якорь проверяется только у первого интервала ноды
  (решение заказчика 2026-10-20): не раньше выдачи identity, суток назад и первого назначения
  тарифицируемой группе.
- Поздний отчёт в пределах окна относится к своему периоду; коэффициент и час записи — по
  `period_start` интервала, интервал не делится.
- Вывод ноды: принудительная отправка буфера и финальное чтение; интервалы недоучёта фиксируются.
  На ноде вывод выполняет локальная подкоманда `node-agent decommission` по SSH: отправка буфера,
  финальное чтение, затирание identity; в панели — операция вывода (задача 001.87; решение
  заказчика 2026-10-25, В-21).

**R-21** — Приём и сверки (§5.9, Н-18)

- Уникальность ключа; повтор → 200 с признаком дубликата, баланс без изменений.
- Порог прироста — полоса ноды × длительность интервала, к нарастающей по частям сумме
  `uplink + downlink` строк пользователей интервала; порог пользователя покрыт порогом суммы по
  ноде. Сверх порога часть удерживается (`held_anomaly`), алерт: доля в пределах порога
  списывается, превышение не списывается. Часть сверх потолка открытых интервалов (8) не
  списывается (решения заказчика 001.33 и 2026-10-20). Повторные удержания переводят ноду в
  `Suspended` (R-05).
- Отдельного действия разбора удержаний нет: оператор снимает `Suspended` с ноды и корректирует
  баланс вручную в обе стороны (R-38; решение заказчика 2026-10-25, В-4).
- В часовые агрегаты удержанной части входит только списанная доля, у части сверх потолка
  открытых интервалов (статус части `held_anomaly`, у интервала `close_reason = 'capped'`) — ноль;
  присланный объём остаётся в записях строк отчёта: `traffic_lines`, 14 дней (решение заказчика
  2026-10-25, В-2).
- Списание строки отчёта относится к периоду подписки, в который попадает `period_start`
  интервала: поздний отчёт после продления лимит нового периода не уменьшает. Если периода нет
  (подписки нет или `period_start` раньше первого периода), факты пишутся, запись баланса — нет,
  запись журнала ERROR (решение заказчика 2026-10-25, В-1).
- Сверки: арифметическая (Н-18), межисточниковая (коридор допуска), непрерывность `report_seq`.
- Каждое списание прослеживается до отчёта по ключу в пределах срока хранения записей (R-22).

**R-22** — Хранение (§5.9, Н-21, Н-22, §16.2)

- Поля записи по §5.9; сроки хранения по Н-21; партиционирование по Н-22.
- Записи баланса `report` и `late_report` хранятся 90 дней, как почасовые записи; дальше
  списание прослеживается до суточного агрегата; записи `adjustment` и `bonus` — 24 месяца
  (решение заказчика 2026-10-25, В-3).
- Два источника: пользовательские счётчики и сетевые счётчики интерфейса.

**R-23** — Traffic Multiplier (§4.9)

- Разрешение: переопределение ноды → тарифицируемая группа → 1.0.
- Диапазон 0.0–10.0, шаг 0.1, хранение в тысячных; `billable = floor(raw × m)`.
- Коэффициент фиксируется в записи; ретроактивный пересчёт запрещён.
- Перенос ноды между группами закрывает период агрегации принудительно.
- Изменение — в Audit Log с прежним и новым значением.

**R-24** — Лимиты и отзыв (§4.11, Н-13, Н-14)

- Типы: лимит на период подписки, Unlimited. База списания `uplink + downlink`.
- Пороги 80 %, 95 %, 100 % — от действующего лимита. Уведомления 80 % и 95 % — однократно за
  период; уведомление 100 % — при каждом новом отзыве доступа в периоде (решение заказчика
  2026-10-25, В-7).
- Состояния `active`, `suspended_quota`, `suspended_admin`, `expired` в потоке состава;
  `removed` — пользователь удалён из состава ноды, строка удаляется уплотнением после
  подтверждения.
- Отзыв применяется в сроки Н-14 (= Н-13) во всех статусах ноды, где идёт обмен (§4.6).
- Перерасход списывается полностью; его объём ограничен Н-17 (AC-08), поэтому списание за
  перерасход не превышает Н-17б: `Н-17 × traffic_multiplier` ноды.
- Восстановление при продлении, увеличении лимита, бонусе кода.
- Начисление (бонус кода, добавление трафика администратором) записывается в журнал баланса
  (`bonus`, `adjustment`) и увеличивает действующий лимит периода: лимит тарифа периода не
  меняется, действующий лимит — лимит тарифа плюс начисления периода; его показывает кабинет
  (механизм принят приёмкой 001.22).

**R-25** — Разрыв соединений (§4.11, Н-17а)

- Кандидаты: повторное добавление, правило маршрутизации по источнику, перезапуск inbound.
  Перезапуск inbound рвёт соединения всех пользователей inbound (нарушает AC-32): он только
  замеряется и выбран быть не может (решение заказчика 2026-10-25, В-9).
- Выбор по PoC-1а (задача 001.88, ОВ-22); до выбора Н-17 предварительно. Реализуется только
  выбранный механизм (В-11).

**Why.** Удаление из inbound не разрывает сессии (Д-2), а `connIdle` — таймаут бездействия
⇒ без отдельного механизма активная сессия живёт до закрытия клиентом.

**R-26** — Грант квоты (§4.11, Н-17в)

- `quota_grant_bytes` в записи пользователя потока 2, в единицах списания.
- Агент уменьшает грант, при исчерпании переводит в `suspended_quota` локально.
- Запрос следующего гранта при 50 %; без связи новый грант не выдаётся.
- Размер гранта ≤ Н-17 в единицах списания. Для тарифа Unlimited грант не ограничивается: Н-17в
  действует для тарифов с лимитом (решение заказчика 2026-10-25, В-6).

**R-27** — Лимит адресов (§4.13, Н-13)

- Агент опрашивает API статистики локально и передаёт адреса и время активности.
- Control Plane оставляет адреса с наиболее свежей активностью в пределах лимита. Окно
  наблюдения — настройка `device_window`, по умолчанию 1 ч (ОВ-23 закрыт, решение заказчика
  2026-10-25, В-8).
- `blocked_ips[]` в потоке 2; агент применяет через `RoutingService`; переустанавливает после
  перезапуска Xray.
- Вытеснение по времени активности снимает блокировку при смене сети.
- Ограничения механизма по §4.13: за CDN без `trusted_x_forwarded_for` адреса схлопываются (Д-14);
  в мобильных сетях возможны ложные срабатывания; лимит оценочный (§11.1).

**R-28** — Лимит соединений и egress (§4.13, §16.6, Н-29)

- Лимит одновременных соединений с одного адреса источника — межсетевой экран ноды.
- Блокировка исходящих портов 25 и 587, адресов частных сетей, службы метаданных.
- Ограничение частоты новых соединений с одного адреса клиента на порты inbound (межсетевой экран
  ноды). Значение — обязательное поле ноды `new_conn_rate_per_ip` в соединениях в секунду рядом с
  `max_conn_per_ip` (Н-29); значения по умолчанию нет (решение заказчика 2026-10-25, В-10).

**R-29** — Признаки перепродажи (§4.13, §8.5) — приоритет S

- Объём, частота новых соединений, круглосуточность активности — в карточке пользователя.
- Адреса назначения не собираются; §4.13 и §8.5 приведены к §16.3 по итогам ревью раунда 1.

**R-30** — Тарифы (§4.10)

- Поля: имя, `Price` (справочное), срок, лимит трафика, лимит устройств, группы доступа, протоколы.
- Валюта указывается в каждой записи (тариф, нода) кодом ISO 4217; единой валюты нет (ОВ-19
  закрыт, решение заказчика 2026-10-25, В-30).

**R-31** — Подписки (§4.11, О-2)

- Активация Redeem-кодом; период от активации.
- Продление: новый период, лимит тарифа, израсходованное обнуляется, остаток не переносится.
- Смена тарифа: замена срока и лимита, израсходованное переносится, без прорации.
- Блокировку администратора (`suspended_admin`) снимает только администратор: погашение кода
  при ней отклоняется (409 `subscription_blocked`); продление администратором и истечение
  периода блокировку сохраняют (решение заказчика 2026-10-25, В-24).
- `Order` и `Payment` в схеме; в MVP не используются.

**R-32** — Redeem-коды (§4.14, §16.8)

- Свойства: срок, максимум использований, максимум на пользователя, ограничение тарифом, бонусы.
- Тариф у Redeem-кода обязателен (код без тарифа — 422). Погашение: подписки нет — активация
  тарифа кода; тариф кода совпадает с текущим — продление; тариф другой — отказ 409
  `code_plan_mismatch`, смену тарифа выполняет администратор (UC-06 A1; решение заказчика
  2026-10-25, В-22).
- Одиночное создание, массовая генерация, экспорт, учёт использования.
- Контрольная сумма в коде; неверный код отклоняется без обращения к базе.

**R-33** — Promo-коды (§4.14) — приоритет S

- Бонус трафика увеличивает действующий лимит текущего периода записью журнала баланса (R-24).
- Бонус дней Promo-кода (`duration_bonus_days`) при `active` и `suspended_quota` переносит
  `period_end` текущего периода на N дней; лимит и израсходованное не меняются. Promo-код с
  бонусом дней при истёкшей подписке и без подписки отклоняется с кодом 409.
- Redeem-код с бонусом дней погашается по правилу R-32, в том числе при истёкшей подписке и без
  подписки; бонус добавляет N дней к периоду, открытому этим погашением (решение заказчика
  2026-10-25, В-23; правило Redeem-кода — `docs/reviews/wi-35-spec-review.md` §5).
- Ограничения использования те же, что у Redeem-кодов.

**R-34** — Панель (§4.15)

- Dashboard: пользователи, подписки, ноды онлайн и офлайн, трафик, алерты.
- Users: поиск, фильтр, профиль, блокировка, тариф, продление, трафик, сброс credentials.
- Блокировка пользователя — одно действие: учётная запись `blocked` (кабинет закрыт, сессии
  отозваны) и подписка `suspended_admin` (доступ к VPN снят в срок Н-14, эндпоинт отвечает
  `blocked` с причиной; решение заказчика 2026-10-25, В-40).
- Nodes: карточка по §4.15; изменение записи и вывод из эксплуатации (задача 001.87, В-21);
  Groups; Plans; Codes.
- Settings: режим регистрации, почта, CAPTCHA, домены подписки (только просмотр, R-17),
  пороги второго подтверждения (R-35, ОВ-17; решение заказчика 2026-10-25, В-34), обслуживание.
  Окно обслуживания панель ставит и снимает подавлением отложенных алертов в Alertmanager;
  действие записывается в Audit Log (решение заказчика 2026-10-25, В-50).
- Administrators (Super Admin): учётные записи администраторов (R-36).

**R-35** — Роли и политики (§5.11)

- Super Admin, Admin, Operator, Support; матрица «роль × операция» — этап проектирования.
- Operator — права Support плюс ручные статусы нод и `restart_xray`; отзыв identity ноды и
  `update_agent` — Admin и выше; восстановление из копии — доступ к хосту вне ролей, §17.12
  (ОВ-26 закрыт, решение заказчика 2026-10-25, В-39).
- Просмотр subscription URL регистрируется. Работа от лица пользователя — расширенная карточка в
  панели с данными кабинета (`/me`), только чтение, без входа в кабинет; пользователь получает
  письмо (решение заказчика 2026-10-25, В-36).
- Начисление трафика и продление подписки администратором сверх порога ОВ-17 — второе
  подтверждение другой активной учётной записью с тем же разрешением; запрос действует 24 ч.
  Пороги по объёму и по сроку продления — две настройки, по умолчанию выключены; включение
  записывается в Audit Log (ОВ-17 закрыт, решение заказчика 2026-10-25, В-34). Уменьшение
  баланса — с причиной.

**R-36** — Аутентификация администраторов (§5.11, Н-27)

- Второй фактор обязателен; резервные коды при включении; использование — в Audit Log.
- Срок бездействия сессии и срок инвалидации при блокировке — по Н-27.
- Сброс второго фактора подтверждает другой Super Admin в панели; если второго Super Admin нет —
  команда на хосте `admin reset-2fa`, её выполняет держатель доступа к хосту — второй держатель
  §17.12; письмо всем активным администраторам, запись в Audit Log (решение заказчика 2026-10-25,
  В-35).
- Учётные записи администраторов: первый Super Admin создаётся командой на хосте `admin create`
  (задача 001.47); остальных Super Admin создаёт в разделе панели `/admin/admins` с обязательным
  вторым фактором, назначает роль, блокирует, сбрасывает пароль; свой профиль ведёт каждый
  администратор (задача 001.89; решение заказчика 2026-10-25, В-33).

**R-37** — Audit Log (§4.16, Н-23)

- Запись: время, актор, роль, действие, сущность, прежнее и новое значение, адрес, результат.
- Append-only; недоступен для изменения из приложения; срок хранения по Н-23.

**R-38** — Данные поддержки (§17.5)

- Обращения к подписке, последнее подключение к каждой ноде, потребление с коэффициентом,
  состояние подписки и причина отзыва.
- Ручная корректировка баланса в обе стороны с обязательной причиной (R-21, В-4).

**R-39** — Пользовательские уведомления (§4.17)

- Семь событий по таблице §4.17; почта и webhook; язык профиля получателя.
- Повтор по одному событию в периоде подавляется, кроме «Лимит трафика исчерпан, доступ отозван»
  при новом отзыве доступа (R-24, В-7); webhook несёт идентификатор события.
- Смена адреса ноды и смена ключевого материала REALITY, в том числе после компрометации, порождают
  событие «Адрес или параметры ноды изменены»; отдельного события нет (ОВ-27 закрыт, решение
  заказчика 2026-10-25, В-41).
- «Подписка истекает» — за срок из настройки `subscription_expiring_notice_days`, по умолчанию
  3 дня (решение заказчика 2026-10-25, В-29).

**R-40** — Операторские уведомления (§4.17, §17.4)

- Пять событий; приоритеты «Немедленный» и «Отложенный»; группировка по ноде и типу.
- Доставка — Alertmanager → webhook оператора; «Нода приостановлена провайдером» — webhook
  приложения: правила алертов исключают ноды в ручных статусах (ревью WI-35, §4).
- Окно планового обслуживания отключает отложенные алерты; задаётся в панели (R-34, В-50).

**R-41** — Почта (§17.7)

- Отдельный домен; SPF, DKIM, DMARC; обработка отказов и жалоб; показатель доставки.
- До выбора провайдера — SMTP-реле без обратного канала: синхронный отказ помечает адрес
  недоставляемым (`users.email_undeliverable_at`), письма уведомлений на него прекращаются,
  пометку видят карточка поддержки и кабинет. После выбора провайдера — webhook отказов и жалоб;
  жалоба отключает уведомления (решение заказчика 2026-10-25, В-37).
- Провайдер — ОВ-13; выбирается до задачи 001.78 (§17.7).

**R-42** — Развёртывание (§4.20, §17.2)

- Состав: API, интерфейс, PostgreSQL, Redis с persistence, воркеры, обратный прокси.
- Backend API не хранит состояние в процессе: сессии, кеши и счётчики — во внешнем хранилище.
- PostgreSQL с архивацией журнала транзакций (основание Н-9).
- Одна команда из чистого состояния; воспроизводимость дважды подряд.
- Миграции expand/contract; сначала Control Plane, затем агенты.
- Процедура отката выпуска с критерием принятия решения об откате; проверка на стенде (§17.2).

**R-43** — Резервное копирование (§4.19, §5.3, Н-9…Н-12)

- Расписание, retention, удалённое хранилище, шифрование; ключ вне контура.
- Хранилище — S3-совместимое, у провайдера, отличного от провайдера хоста; ключ шифрования — в
  менеджере паролей оператора и у второго держателя §17.12 (ОВ-A1, решение заказчика 2026-10-25,
  В-44).
- RPO по Н-9, RTO по Н-10; учебное восстановление по Н-11.
- После отката: `state_generation` меняется; окно приёма прежней identity продлевается;
  отозванная identity возвращается только новым bootstrap-токеном (§4.6).
- Отзывы identity нод и аннулирования их токенов дополнительно записываются во внешний журнал
  отзывов вне базы и вне хоста (хранилище копий): серийный номер и время. Восстановление
  повторяет отзывы из журнала до открытия порта Node API (решение заказчика 2026-10-25, В-20).
  Строка журнала уходит в S3 задачей очереди после фиксации отзыва; при отказе хоста до выгрузки
  строки и без архива WAL отзыв этого окна (секунды) повторяет оператор по записи инцидента
  (В-20, `docs/reviews/wi-35-spec-review.md` §5).

**R-44** — Secrets (§5.13, Н-28)

- Секреты Control Plane зашифрованы.
- Ротация identity ноды автоматическая: планировщик выдаёт `rotate_credentials`, когда до конца
  срока сертификата ноды остаётся не больше 30 дней; окно перекрытия Н-28 — 7 суток, при смене
  `state_generation` продлевается на 7 суток (решение заказчика 2026-10-25, В-16).

**R-45** — Rate limiting (§5.12)

- Вход: по адресу и по учётной записи, CAPTCHA вместо блокировки.
- Подписка: по токену; отдельный порог для несуществующих. Node API: по identity ноды.
- Агент: джиттер heartbeat и экспоненциальная задержка.

**R-46** — Очереди (§5.8)

- Две очереди с раздельными пулами; идемпотентность по ключу задачи; ретраи; DLQ с алертом.
- Ожидание задачи критичного пути ≤ половины бюджета Н-13.

**R-47** — Observability (§5.14, §17.4)

- Логи приложения, агента, аудита; `access.log` Xray выключен (§16.3).
- Алерты по таблице §17.4 с инструкцией разбора на каждый тип. Таблица содержит полный перечень
  алертов с приоритетами: «Немедленный» — отказы, останавливающие сервис, учёт или доступ;
  остальные — «Отложенный» (решение заказчика 2026-10-25, В-42).
- Внешний сервис мониторинга: проба `/healthz` и подписки на обоих доменах раз в 1–5 мин,
  уведомление оператору; он обнаруживает недоступность Control Plane и подписки при отказе всего
  хоста, его месячная доступность — данные для AC-21 (решение заказчика 2026-10-25, В-43; 001.68).

**R-48** — Данные и правила (§16)

- Перечень данных §16.1; сроки §16.2; автоудаление.
- AUP: принятие при регистрации; запреты §16.5. Тексты правил использования и политики
  конфиденциальности (версия и URL) предоставляет заказчик до задачи 001.69 (В-45).
- Процесс реакции на обращение провайдера §16.7; статус `Suspended`. Жалоба сопоставляется по
  ноде и времени (адресов назначения нет, §16.3): оператору — пользователи с трафиком на ноде в
  интервале жалобы (идентификатор и объём по часам); провайдеру — только факт приостановки и
  принятые меры; жалоба хранится в `provider_complaints` со сроком хранения 12 месяцев (§16.2;
  решение заказчика 2026-10-25, В-45).

**R-49** — Вне контура (§17.11) — приоритет S

- Страница состояния вне инфраструктуры Control Plane; независимый канал объявлений.
- Страница состояния — страница внешнего сервиса мониторинга (R-47; решение заказчика 2026-10-25,
  В-43); объявления публикуются на ней и в канале объявлений (001.70).
- Канал объявлений — Telegram-канал, страница состояния и кабинет. Объявление о новом домене
  подписано ключом, отпечаток которого заранее показан пользователю (ОВ-15 закрыт, решение
  заказчика 2026-10-25, В-44).

**R-50** — Документация (§17.13)

- OpenAPI; руководство оператора с инструкциями по алертам; пользовательские инструкции; ADR.

**R-51** — Локализация (§17.8)

- Русский и английский: интерфейс, письма, страница подписки.
- Язык профиля → `Accept-Language` → английский; панель — независимо.
- Строки и шаблоны в файлах локализации; третий язык — без изменения кода.

**R-52** — Время (§17.8)

- Хранение и вычисление в UTC; отображение в поясе профиля; сутки агрегатов в UTC.

**R-53** — Интерфейс (§17.9)

- Кабинет под мобильное устройство; панель под настольный экран; QR читается с экрана.
- Браузеры: две последние версии Chrome, Firefox, Safari и Edge; iOS Safari 16 и новее; Android
  Chrome двух последних версий; кабинет — также встроенные браузеры мессенджеров (ОВ-14 закрыт,
  решение заказчика 2026-10-25, В-38).

## 4. Сценарии использования

Актёры: Пользователь, Администратор, Оператор, Support, Control Plane, Node Agent, Xray,
Клиентское приложение, Почтовый сервис, Хостинг-провайдер.

Правило назначения актёра: сценарий называет минимально достаточную роль §5.11. Операции,
инициатор которых закреплён в §4.6, выполняет Администратор: административная роль по матрице
R-35. Ручные статусы нод ставит роль Operator и выше; отзыв identity и `update_agent` — Admin и
выше (ОВ-26 закрыт, решение заказчика 2026-10-25, В-39). В UC-10 «Оператор» — держатель доступа к
хосту Control Plane (§17.12): восстановление из копии выполняется вне ролей панели.

### UC-01 Ввод ноды в эксплуатацию

**Актёры:** Администратор, Control Plane, Node Agent.

**Предусловия:** создан VPS с публичным адресом; администратор аутентифицирован со вторым фактором.

**Основной сценарий:**

1. Администратор создаёт запись Node: имя, география, провайдер, группы доступа, тарифицируемая
   группа, юридический профиль.
2. Control Plane создаёт три Inbound с ключевым материалом REALITY и одноразовый bootstrap-токен.
3. Control Plane выдаёт bootstrap-команду.
4. Администратор выполняет команду на VPS.
5. Node Agent обменивает токен на identity; нода переходит в `Pending`.
6. Администратор сверяет адрес источника, отпечаток сертификата, версии агента и Xray.
7. Администратор подтверждает ноду; нода переходит в `Provisioning`.
8. Node Agent запрашивает полный снапшот и применяет поток структурной конфигурации; поток
   состава пользователей в `Provisioning` пуст (§4.6).
9. Xray запущен, heartbeat получен; нода переходит в `Active`.
10. Control Plane публикует ноде состав пользователей; агент применяет его и подтверждает
    `users_seq`.
11. Нода появляется в выдаче подписок: статус `Active` и подтверждённый `users_seq` (R-16).

**Альтернативные сценарии:**

- **A1: токен просрочен (шаг 5).** Control Plane отклоняет обмен. Администратор выпускает новый
  токен; прежний аннулирован. Возврат к шагу 3.
- **A2: признаки не совпадают (шаг 6).** Администратор отклоняет ноду: identity отзывается,
  нода переходит в `Disabled`. Запись Node остаётся; выпускается новый токен, его обмен переводит
  ноду в `Pending`; далее с шага 6.
- **A3: `reality_target` недоступна (шаг 8).** Inbound переходит в состояние ошибки и в выдачу
  подписки не попадает; остальные профили ноды выдаются. Нода проходит `Provisioning → Active`
  по §4.6, затем переходит в `Degraded` (§4.7); алерт «Отложенный». Администратор меняет цель;
  после успешной проверки inbound выходит из состояния ошибки (решение заказчика 2026-10-25,
  В-12).
- **A4: пересоздание после компрометации.** На шаге 2 ключевой материал REALITY заменяется;
  пользователи ноды получают уведомление «Адрес или параметры ноды изменены» (§4.4, §4.17;
  ОВ-27 закрыт, решение заказчика 2026-10-25, В-41).
- **A5: связь потеряна до перехода в `Active` (шаги 8–9).** Нода переходит в `Offline`; после
  возобновления heartbeat возвращается в `Provisioning`, а не в `Active` (§4.6; решение заказчика
  2026-10-25, В-13). Возврат к шагу 8.

**Постусловия:** нода `Active`; Desired и Applied курсоры обоих потоков совпадают; до перехода в
`Active` нода не получала ни одного VPN-credential.

**Критерии приёмки:**

- От выполнения команды до `Active` проходит не более Н-16.
- Повторное использование bootstrap-токена отклонено.
- Токен старше срока Н-24 отклонён.
- В `Pending` запрос состояния отклонён; в `Provisioning` ответ не содержит ни одного credential.
- После перехода в `Active` состав пользователей применён и `users_seq` подтверждён.

### UC-02 Регистрация и активация подписки Redeem-кодом

**Актёры:** Пользователь, Control Plane, Почтовый сервис.

**Предусловия:** режим регистрации «открытая»; у пользователя есть Redeem-код.

**Основной сценарий:**

1. Пользователь открывает форму регистрации.
2. Control Plane показывает поля, правила использования и CAPTCHA.
3. Пользователь заполняет форму, принимает правила, проходит CAPTCHA.
4. Control Plane нормализует адрес, отклоняет одноразовый домен, проверяет уникальность.
5. Control Plane создаёт учётную запись со статусом «не подтверждена» и отправляет письмо.
6. Пользователь переходит по ссылке; статус меняется на «подтверждена».
7. Пользователь вводит Redeem-код.
8. Control Plane проверяет контрольную сумму, срок, число использований, ограничение тарифом.
9. Control Plane создаёт подписку: период от момента активации, лимит тарифа, состояние
   `active`.
10. Control Plane создаёт credentials на каждой доступной ноде и выдаёт токен подписки.
11. Пользователь видит ссылки на двух доменах, QR-код и мастер первого подключения.

**Альтернативные сценарии:**

- **A1: адрес занят (шаг 4).** Сообщение с предложением входа или восстановления. Конец.
- **A2: письмо не доставлено (шаг 6).** Пользователь запрашивает повторную отправку письма в
  пределах порога частоты §5.12; возврат к шагу 6. Если письмо не доходит, Support подтверждает
  адрес вручную; действие записывается в Audit Log (§17.7; решение заказчика 2026-10-25, В-32).
- **A3: неверная контрольная сумма (шаг 8).** Отклонение без обращения к базе; счётчик частоты
  увеличивается. Возврат к шагу 7.
- **A4: код исчерпан или просрочен (шаг 8).** Сообщение с причиной. Конец.
- **A5: превышен порог частоты (шаг 3 или 7).** Отказ с сохранением доступности остальным (§5.12).
- **A6: режим «по приглашению».** На шаге 2 требуется действующий Redeem-код; без него
  регистрация отклоняется. Код проверяется по шагу 8 и при регистрации сразу активирует подписку
  (шаги 9–10; решение заказчика 2026-10-25, В-31).
- **A7: режим «закрытая».** Форма недоступна; показано сообщение.

**Постусловия:** подписка `active`; событие «Подписка активирована» отправлено; версия принятых
правил сохранена.

**Критерии приёмки:**

- Повторная регистрация того же нормализованного адреса отклонена.
- Код активируется однократно; повторная активация отклонена с причиной.
- Письмо активации содержит оба домена подписки.
- Запись согласия содержит версию правил.

### UC-03 Получение подписки клиентом

**Актёры:** Клиентское приложение, Control Plane.

**Предусловия:** подписка `active`; у пользователя токен; хотя бы одна нода `Active`.

**Основной сценарий:**

1. Клиент запрашивает `https://{домен}/s/{token}`.
2. Control Plane проверяет токен и порог частоты.
3. Control Plane определяет формат по `User-Agent` или по суффиксу пути.
4. Control Plane отбирает пары «нода × профиль» по тарифу, группам, протоколам, статусу ноды,
   доступности по стране, подтверждённому нодой `users_seq` и исправности inbound (R-16).
5. Control Plane исключает пары, неприменимые для формата (§5.6).
6. Control Plane формирует ответ: записи с именами, содержащими коэффициент ≠ 1.0; для `singbox`
   — автоселектор `urltest`.
7. Control Plane добавляет заголовки `subscription-userinfo`, `profile-update-interval`,
   `profile-title`, `support-url`.
8. Control Plane записывает обращение: время, домен, формат, `User-Agent`, адрес источника и его
   страна.
9. Клиент импортирует профиль и подключается.

**Альтернативные сценарии:**

- **A1: токен не существует (шаг 2).** 404, пустое тело; счётчик несуществующих токенов.
- **A2: подписка `expired`, `traffic_exceeded` или `blocked` (шаг 2).** 200, пустой список,
  `announce` с причиной.
- **A3: ноль доступных серверов при `active` (шаг 4).** 200, пустой список, `announce`; алерт
  «Немедленный» (§17.4; решение заказчика 2026-10-25, В-42).
- **A4: обращение из браузера (шаг 3).** Страница подписки с инструкциями и кнопками импорта.
- **A5: неизвестный `User-Agent` без суффикса (шаг 3).** Формат `base64`.
- **A6: клиент sing-box (шаг 5).** Профиль `vless-xhttp` исключён; резерв — `trojan-reality`.

**Постусловия:** обращение записано; путь запроса в логах прокси отсутствует.

**Критерии приёмки:**

- Каждый клиент §4.2 импортирует ответ и устанавливает соединение по каждому профилю,
  применимому для его формата (§5.6).
- Ответ формата `singbox` не содержит записей профиля `vless-xhttp`.
- Ответ формата `base64` содержит по одной записи на каждый включённый inbound доступной ноды,
  кроме inbound в состоянии ошибки.
- Отключение одного inbound не изменяет записи остальных профилей той же ноды.
- Эталонный ответ каждого формата совпадает побайтно с зафиксированным (§17.1).

### UC-04 Учёт трафика и списание с коэффициентом

**Актёры:** Node Agent, Xray, Control Plane.

**Предусловия:** пользователь подключён к ноде с коэффициентом 3.0; связь с Control Plane есть.

**Основной сценарий:**

1. Node Agent читает счётчики Xray кумулятивно, без сброса.
2. Node Agent вычисляет дельты внутри текущего `counter_epoch`.
3. Node Agent формирует отчёт: `(node_id, counter_epoch, report_seq)`, `period_start`,
   `period_end`, дельты по пользователям, наблюдаемые адреса.
4. Node Agent сохраняет отчёт в буфер и отправляет.
5. Control Plane проверяет отклонение времени и уникальность ключа.
6. Control Plane проверяет прирост против полосы ноды.
7. Control Plane выбирает коэффициент на `period_start` интервала и вычисляет
   `billable = floor(raw × 3.0)`.
8. Control Plane записывает почасовую запись и увеличивает баланс пользователя.
9. Control Plane отвечает `last_accepted_seq`; агент удаляет отчёт из буфера.

**Альтернативные сценарии:**

- **A1: ответ потерян (шаг 9).** Агент повторяет отчёт; Control Plane отвечает 200 с признаком
  дубликата; баланс не меняется (Н-20).
- **A2: Xray перезапущен (шаг 1).** Агент генерирует новый `counter_epoch`; базовая точка 0.
  Перед плановым перезапуском выполнено финальное чтение (Н-19).
- **A3: счётчик убыл внутри эпохи (шаг 2).** Запись в журнал, алерт; баланс не меняется.
- **A4: `period_end` позже часов Control Plane более чем на 5 с (шаг 5).** Часть отклонена
  (`rejected_time`); алерт.
- **A5: прирост сверх порога (шаг 6).** Часть удержана (`held_anomaly`): доля в пределах порога
  списана, превышение не списано; алерт. Удержания по порогу R-05 за скользящие 24 ч переводят
  ноду в `Suspended` (решение заказчика 2026-10-25, В-5).
- **A6: Control Plane недоступен (шаг 4).** Отчёты копятся в буфере глубиной Н-8; при
  переполнении старейшие отбрасываются, алерт. После восстановления — отправка по порядку
  `report_seq`.
- **A7: отчёт за закрытый период (шаг 7).** Интервал, начавшийся не раньше 72 ч назад,
  принимается в свой период; суточный агрегат пересчитывается; коэффициент — тот, что действовал
  на `period_start`. Интервал старше — отказ `rejected_time`.
- **A8: перерыв снятия счётчиков дольше часа при работающем Xray (шаг 1).** Агент начинает новый
  `counter_epoch`; дельта перерыва не отправляется; разрыв оценивает сверка непрерывности.
- **A9: часть к завершённому или закрытому интервалу (шаг 5).** Отказ `interval_closed`; часть не
  повторяется, номер пропускается, разрыв фиксирует сверка непрерывности.
- **A10: части интервала противоречат друг другу (шаг 5).** Отказ `report_inconsistent`; ключ не
  записан; агент пропускает номер; алерт.

**Постусловия:** `raw_bytes` и `billable_bytes` записаны раздельно с зафиксированным
коэффициентом; списание прослеживается до отчёта.

**Критерии приёмки:**

- Передача 1 ГБ на ноде с коэффициентом 2.0 увеличивает `billable_bytes` на 2 ГБ, `raw_bytes` на
  1 ГБ.
- Повторная доставка отчёта не меняет баланс.
- Плановый перезапуск Xray во время передачи не даёт ни потери, ни повторного списания (Н-19);
  при внеплановом теряется объём с последнего снятия счётчиков, он входит в бюджет Н-18 (§5.9).
- Изменение коэффициента не меняет ранее записанные значения.
- Расхождение арифметической сверки ≤ 0,5 % (Н-18).

### UC-05 Исчерпание лимита и отзыв доступа

**Актёры:** Control Plane, Node Agent, Пользователь.

**Предусловия:** подписка `active` с лимитом на период; пользователь подключён.

**Основной сценарий:**

1. Баланс достигает 80 %; Control Plane отправляет уведомление.
2. Баланс достигает 95 %; второе уведомление.
3. Баланс достигает 100 %; Control Plane переводит пользователя в `suspended_quota` в потоке
   состава всех нод.
4. Node Agent получает изменение по long-poll и удаляет пользователя из inbound.
5. Node Agent применяет механизм принудительного разрыва (§4.11).
6. Control Plane отправляет уведомление «Лимит трафика исчерпан, доступ отозван».
7. Subscription-эндпоинт переходит в состояние `traffic_exceeded`.
8. Пользователь активирует код с бонусом трафика; начисление увеличивает действующий лимит
   периода (R-24); если остаток после бонуса положителен, состояние возвращается в `active`;
   ноды применяют изменение.

**Альтернативные сценарии:**

- **A1: нода без связи (шаг 4).** Агент расходует `quota_grant_bytes` локально; при исчерпании
  переводит пользователя в `suspended_quota` сам. Отзыв применяется при первом обмене.
- **A2: нода `Offline`, `Maintenance`, `Disabled`, `Suspended` (шаг 4).** Отзыв доставляется при
  первом обмене и до передачи трафика пользователя (§4.6).
- **A3: порог достигнут повторно в том же периоде (шаг 1, 2).** Уведомление подавлено.
- **A4: тариф Unlimited.** Пороги не применяются; `billable_bytes` записываются; грант квоты не
  ограничивается (R-26).
- **A5: лимит исчерпан повторно в том же периоде (шаг 8, затем шаг 3).** Доступ отзывается
  снова; уведомление «Лимит трафика исчерпан, доступ отозван» отправляется повторно (решение
  заказчика 2026-10-25, В-7).

**Постусловия:** пользователь отсутствует в inbound всех обменивающихся нод; перерасход в пределах
Н-17.

**Критерии приёмки:**

- Отзыв применён на всех обменивающихся нодах в сроки Н-14 (= Н-13).
- Установленные соединения разорваны не позднее Н-17а.
- Перерасход не превышает Н-17. Значение Н-17 предварительно до PoC-1а (задача 001.88, ОВ-22).
- Без связи перерасход не превышает грант (Н-17в) плюс полосу ноды × (период проверки гранта +
  Н-17а).
- Восстановление доступа выполняется в те же сроки, что и отзыв.

### UC-06 Продление и смена тарифа

**Актёры:** Пользователь, Администратор, Control Plane.

**Предусловия:** подписка существует в состоянии `active`, `suspended_quota`, `expired` или
`suspended_admin`.

**Основной сценарий (продление):**

1. Пользователь активирует Redeem-код продления с тарифом текущей подписки (R-32).
2. Control Plane определяет начало нового периода: от даты окончания при `active` и
   `suspended_quota`, от момента активации при `expired`.
3. Control Plane устанавливает лимит тарифа; израсходованное обнуляется; остаток не переносится.
4. Состояние становится `active`, кроме `suspended_admin` (A8); ноды применяют изменение.
5. Уведомление «Подписка активирована».

**Альтернативные сценарии:**

- **A1: смена тарифа администратором.** Срок и лимит заменяются значениями нового тарифа;
  израсходованное переносится; прорация не выполняется.
- **A2: новый тариф без части групп доступа (A1).** Пользователь удаляется из inbound нод
  исключённых групп в сроки Н-13; установленные соединения не разрываются; следующий ответ
  эндпоинта без этих нод.
- **A3: подписка истекает (по расписанию).** За срок из настройки
  `subscription_expiring_notice_days` (по умолчанию 3 дня) — уведомление «Подписка истекает»; в
  момент истечения — `expired`; ноды применяют; эндпоинт — `expired` (решение заказчика
  2026-10-25, В-29).
- **A4: администратор добавляет трафик.** Начисление записывается в журнал баланса и
  увеличивает действующий лимит периода (R-24); при `suspended_quota` и положительном остатке
  состояние возвращается в `active`.
- **A5: начисление сверх включённого порога ОВ-17 (A4).** Требуется второе подтверждение другой
  учётной записью (R-35).
- **A6: продление администратором сверх включённого порога ОВ-17.** Требуется второе
  подтверждение другой учётной записью (R-35).
- **A7: код другого тарифа (шаг 1).** Отказ 409 `code_plan_mismatch`; смену тарифа выполняет
  администратор (A1; решение заказчика 2026-10-25, В-22).
- **A8: подписка `suspended_admin` (шаг 1).** Погашение кода отклонено (409
  `subscription_blocked`). Продление администратором начинает новый период, состояние остаётся
  `suspended_admin`; истечение периода блокировку не снимает (решение заказчика 2026-10-25,
  В-24).

**Постусловия:** параметры подписки соответствуют таблице §4.11; запись в Audit Log.

**Критерии приёмки:**

- Пример §4.11: 100 ГБ на 30 дней, израсходовано 60 ГБ, до окончания 5 дней; после продления
  доступно 100 ГБ и 35 дней.
- Смена тарифа не обнуляет израсходованный объём.
- Продление истёкшей подписки начинает период от момента активации.
- Поздний отчёт за интервал до продления списывается с прежнего периода; лимит нового периода не
  уменьшается (R-21, В-1).
- Продление и истечение не снимают `suspended_admin`.

### UC-07 Отказ и возврат ноды

**Актёры:** Node Agent, Control Plane, Администратор, Клиентское приложение, Хостинг-провайдер.

**Предусловия:** нода `Active`; пользователи подключены.

**Основной сценарий:**

1. Heartbeat ноды прекращается.
2. После пропусков heartbeat по порогу Н-15 Control Plane переводит ноду в `Offline`.
3. Control Plane исключает ноду из выдачи подписок; алерт «Отложенный».
4. Клиент формата `singbox` переключается автоселектором на доступную ноду (Н-34).
5. Heartbeat возобновляется; после успешных heartbeat по порогу Н-15 нода возвращается в `Active`.
6. Node Agent отправляет буфер отчётов; Control Plane дедуплицирует.
7. Нода возвращается в выдачу; уведомление «Нода восстановлена».

**Альтернативные сценарии:**

- **A1: клиент формата `base64` (шаг 4).** Автоселектора нет; пользователь переключает сервер
  вручную или обновляет подписку (Н-35).
- **A2: нода в `Maintenance`, `Disabled` или `Suspended` (шаг 5).** Автовозврат не выполняется;
  нода возвращается только действием администратора.
- **A3: heartbeat прерывается однократно.** Порог не достигнут; статус не меняется; алерт не
  порождается.
- **A4: провайдер приостановил ноду.** Администратор переводит ноду в `Suspended` (§4.6);
  уведомление «Нода приостановлена провайдером»; при нуле доступных серверов — объявление (§17.11).
- **A5: пересоздание ноды.** Новый VPS, новый bootstrap, та же запись, тот же ключевой материал;
  обмен нового токена переводит ноду в `Pending`, администратор подтверждает её заново (UC-01
  шаги 6–9); при смене адреса — уведомление «Адрес или параметры ноды изменены» (R-39);
  изменение адреса в записи ноды — задача 001.87 (В-21).

**Постусловия:** статус ноды соответствует фактическому состоянию; статистика за период отказа
учтена из буфера.

**Критерии приёмки:**

- Остановка агента даёт `Offline`, восстановление даёт `Active` в сроки Н-15.
- Нода в `Maintenance` при живом heartbeat не выдаётся в подписке.
- Однократный пропуск не порождает алерт и не меняет статус.

### UC-08 Ограничение числа адресов и перепродажа доступа

**Актёры:** Node Agent, Control Plane, Администратор, Пользователь.

**Предусловия:** тариф с лимитом устройств 2; пользователь подключён с трёх адресов.

**Основной сценарий:**

1. Node Agent опрашивает API статистики локально и передаёт адреса и время активности в отчёте.
2. Control Plane считает уникальные адреса пользователя за окно наблюдения (R-27).
3. Control Plane оставляет два адреса с наиболее свежей активностью; третий попадает в
   `blocked_ips[]` потока 2.
4. Node Agent применяет правило маршрутизации по источнику через `RoutingService`.
5. Пользователь видит в кабинете число активных адресов и факт достижения лимита.
6. Пользователь меняет сеть; прежний адрес вытесняется по времени активности; блокировка снимается.

**Альтернативные сценарии:**

- **A1: перезапуск Xray (шаг 4).** Правило утрачено; агент переустанавливает его после
  перезапуска.
- **A2: один адрес, число соединений достигает Н-29.** Межсетевой экран ноды отклоняет соединения
  сверх предела.
- **A3: признаки перепродажи (R-29).** Объём, частота новых соединений, круглосуточность
  отображаются в карточке; администратор блокирует пользователя с причиной в Audit Log.
- **A4: тариф без лимита устройств.** Шаги 2–4 не выполняются; адреса сохраняются для поддержки.

**Постусловия:** число активных адресов ≤ лимита тарифа; блокировка обратима.

**Критерии приёмки:**

- Третий адрес блокируется правилом маршрутизации в сроки Н-13.
- Смена сети снимает блокировку прежнего адреса без действий администратора.
- Соединения с одного адреса сверх Н-29 отклонены на ноде.

### UC-09 Управление тарифами, группами и кодами

**Актёры:** Администратор, Control Plane.

**Предусловия:** администратор аутентифицирован со вторым фактором.

**Основной сценарий:**

1. Администратор создаёт тарифицируемые группы с коэффициентами.
2. Администратор создаёт группы доступа.
3. Администратор создаёт тариф: срок, лимит трафика, лимит устройств, группы доступа, протоколы.
4. Администратор генерирует партию Redeem-кодов с ограничением тарифом и сроком.
5. Администратор экспортирует партию.
6. Администратор назначает ноде тарифицируемую группу и переопределение коэффициента.
7. Control Plane записывает каждое изменение в Audit Log с прежним и новым значением.

**Альтернативные сценарии:**

- **A1: попытка назначить ноде вторую тарифицируемую группу (шаг 6).** Отклонено ограничением
  целостности.
- **A2: коэффициент вне 0.0–10.0 или не кратен 0.1 (шаг 1, 6).** Отклонено.
- **A3: изменение коэффициента при накопленной статистике (шаг 6).** Период агрегации закрыт
  принудительно; ранее записанные значения не меняются.
- **A4: удаление тарифа с активными подписками (шаг 3).** Отклонено; тариф переводится в
  архивный статус.
- **A5: роль без разрешения.** Операция отклонена; попытка записана в Audit Log.

**Постусловия:** сущности созданы; изменения прослеживаются.

**Критерии приёмки:**

- Добавление ноды в группу доступа делает её доступной тарифам с этой группой без изменения
  тарифов.
- Каждое действие сценария присутствует в Audit Log с актором, ролью и результатом.
- Экспорт содержит все коды партии.

### UC-10 Восстановление Control Plane из резервной копии

**Актёры:** Оператор, Control Plane, Node Agent.

**Предусловия:** резервная копия не старше Н-9; ключ шифрования доступен вне контура.

**Основной сценарий:**

1. Control Plane недоступен; ноды обслуживают пользователей по последней конфигурации.
2. Оператор восстанавливает Control Plane на чистом хосте из копии.
3. Control Plane изменяет `state_generation` и до открытия порта Node API повторяет отзывы
   identity нод и аннулирования их токенов из внешнего журнала отзывов (R-43; решение заказчика
   2026-10-25, В-20).
4. Агенты обнаруживают несовпадение поколения и запрашивают полный снапшот.
5. Control Plane принимает прежнее поколение identity нод в продлённом окне перекрытия.
6. Агенты отправляют буферы; повторы отбрасываются по ключу идемпотентности.
7. Сверка за период недоступности выполняется; расхождение сверх Н-18 порождает алерт.

**Альтернативные сценарии:**

- **A1: недоступность дольше 24 часов (шаг 1).** Буферы переполняются; старейшие отчёты
  отброшены; интервалы недоучёта зафиксированы.
- **A2: identity ноды выпущена после точки копии и восстановленной базе неизвестна (шаг 5).**
  Агент получает отказ аутентификации и выполняет повторное подтверждение по сохранённому секрету
  (§5.3) без ручного доступа к серверу. Повторное подтверждение принимается только в продлённом
  окне перекрытия после смены `state_generation` и только для identity, не отозванной ни в базе,
  ни во внешнем журнале отзывов. Отозванная identity повторным подтверждением не
  восстанавливается — только новым bootstrap-токеном (§4.6).
- **A3: выдача подписок во время недоступности.** Недоступна; установленные соединения работают.

**Постусловия:** все ноды на актуальном снапшоте; балансы не задвоены; восстановление в пределах
Н-10.

**Критерии приёмки:**

- Учебное восстановление на чистом хосте укладывается в Н-10 с потерей ≤ Н-9.
- Ни одна нода не потребовала ручного доступа по SSH.
- Повторно отправленные отчёты не изменили балансы.
- Identity, отозванная после точки копии, после восстановления отклоняется.

### UC-11 Обновление парка нод

**Актёры:** Администратор, Control Plane, Node Agent.

**Предусловия:** новая закреплённая версия Xray или агента; выбрана канареечная нода.

**Основной сценарий:**

1. Администратор выпускает команду `update_agent` для канареечной ноды.
2. Node Agent выполняет финальное чтение счётчиков и обновляется.
3. Администратор проверяет подключение каждого клиента §4.2 к канареечной ноде.
4. Администратор заносит результат в реестр клиентов (§17.10).
5. Администратор выпускает команду для остальных нод последовательно.

**Альтернативные сценарии:**

- **A1: обновление неуспешно (шаг 2).** Агент откатывается; нода `Degraded`; алерт; остальные
  ноды не обновляются. Нода выходит из `Degraded` после следующего успешного `update_agent` или
  действием администратора (R-07, В-15).
- **A2: клиент не подключается (шаг 3).** Администратор откатывает канареечную ноду; версия не
  закрепляется; риск Р-11 фиксируется.
- **A3: команда просрочена (шаг 1).** Агент возвращает `expired`; команда не выполняется.

**Постусловия:** все ноды на закреплённой версии либо парк остался на прежней.

**Критерии приёмки:**

- Повторная доставка команды с тем же `command_id` не выполняется повторно.
- Неуспешное обновление оставляет ноду работоспособной в `Degraded`.

### UC-12 Компрометация ноды

**Актёры:** Администратор, Control Plane, Node Agent, Хостинг-провайдер.

**Предусловия:** есть основания считать VPS ноды изъятым или снятым снапшотом.

**Основной сценарий:**

1. Администратор отзывает identity ноды (Н-31).
2. Control Plane исключает ноду из выдачи подписок.
3. Control Plane ротирует credentials пользователей, имевших доступ к ноде (Н-32).
4. Control Plane заменяет ключевой материал REALITY ноды — ключевую пару и `short_ids` (§4.4,
   Н-33).
5. Пользователи затронутой ноды получают уведомление «Адрес или параметры ноды изменены» (§4.17;
   решение заказчика 2026-10-25, В-41) и обновляют подписку.
6. Администратор пересоздаёт ноду с новым bootstrap; обмен нового токена переводит ноду в
   `Pending`, администратор подтверждает её заново (UC-01 шаги 6–9); прежний ключ не
   переиспользуется.

**Альтернативные сценарии:**

- **A1: нода продолжает слать heartbeat (шаг 1).** Запросы с отозванной identity отклоняются;
  статус `Disabled`.
- **A2: вывод ноды из эксплуатации без компрометации.** Администратор выполняет на VPS по SSH
  `node-agent decommission`: буфер отправлен, счётчики прочитаны, identity затёрта до уничтожения
  VPS; в панели нода выводится из эксплуатации (§4.6 «Удаление»; задача 001.87; решение
  заказчика 2026-10-25, В-21).

**Постусловия:** прежние credentials и ключ REALITY недействительны; доступ остальных нод не
затронут.

**Критерии приёмки:**

- Запрос с отозванной identity получает отказ.
- Ротация credentials для 1 000 пользователей укладывается в Н-32.
- Credentials остальных нод не изменились.

### UC-13 Поддержка пользователя

**Актёры:** Support, Control Plane, Пользователь.

**Предусловия:** обращение «не работает».

**Основной сценарий:**

1. Support открывает карточку пользователя.
2. Карточка показывает обращения к подписке: время, домен, формат, `User-Agent`, страна.
3. Карточка показывает последнее подключение к каждой ноде и потребление с коэффициентом.
4. Карточка показывает состояние подписки и причину отзыва.
5. Support просматривает subscription URL; просмотр записан в Audit Log.
6. Support открывает расширенную карточку с данными кабинета пользователя (`/me`) — только
   чтение, без входа в кабинет; пользователь получает письмо (R-35; решение заказчика 2026-10-25,
   В-36).

**Альтернативные сценарии:**

- **A1: обращений к подписке нет (шаг 2).** Support направляет пользователя в мастер первого
  подключения.
- **A2: корректировка баланса вручную.** Требует причины; уменьшение — с причиной в Audit Log;
  начисление сверх порога — второе подтверждение.
- **A3: письмо подтверждения адреса не доходит (UC-02 A2).** Support подтверждает адрес вручную;
  действие записано в Audit Log (R-09, В-32).

**Постусловия:** все действия Support прослеживаются в Audit Log.

**Критерии приёмки:**

- Просмотр subscription URL создаёт запись Audit Log с актором и ролью.
- Открытие расширенной карточки записано в Audit Log; пользователь получил письмо.

### UC-14 Удаление аккаунта

**Актёры:** Пользователь, Control Plane, Node Agent.

**Предусловия:** пользователь аутентифицирован.

**Основной сценарий:**

1. Пользователь запрашивает удаление и подтверждает его.
2. Control Plane аннулирует токен подписки и отзывает credentials на всех нодах.
3. Control Plane удаляет учётные данные и данные обращений.
4. Control Plane сохраняет `user_id` в записях потребления как суррогат: после шага 3 он не
   связан ни с одним лицом.
5. Записи Audit Log сохраняются; персональных данных они не содержат (ссылки — по `user_id`).

**Альтернативные сценарии:**

- **A1: нода без связи (шаг 2).** Отзыв применяется при первом обмене.

**Постусловия:** учётная запись не восстанавливается; агрегаты потребления сохранены без связи с
лицом; копии удаляются по сроку хранения копий.

**Критерии приёмки:**

- Вход по удалённому адресу невозможен; запрос подписки по прежнему токену возвращает 404.
- Записи потребления и Audit Log не позволяют установить личность удалённого пользователя.

### UC-15 Восстановление пароля

**Актёры:** Пользователь, Control Plane, Почтовый сервис.

**Предусловия:** учётная запись подтверждена; пользователь не аутентифицирован.

**Основной сценарий:**

1. Пользователь запрашивает восстановление, указав адрес.
2. Control Plane проверяет порог частоты по адресу электронной почты (§5.12).
3. Control Plane создаёт одноразовую ссылку со сроком действия из настройки
   `email_token_ttl_minutes` (по умолчанию 15 минут) и отправляет письмо.
4. Пользователь переходит по ссылке и задаёт новый пароль.
5. Control Plane аннулирует ссылку и инвалидирует все сессии пользователя.
6. Пользователь входит с новым паролем.

**Альтернативные сценарии:**

- **A1: адрес не зарегистрирован (шаг 2).** Ответ не раскрывает факт отсутствия адреса; письмо
  не отправляется.
- **A2: ссылка использована повторно или просрочена (шаг 4).** Отклонение с предложением
  запросить новую.
- **A3: превышен порог частоты (шаг 2).** Отказ; остальные пользователи обслуживаются.
- **A4: письмо не доставлено (шаг 3).** Пользователь запрашивает повторную отправку в пределах
  порога частоты.

**Постусловия:** пароль изменён; прежние сессии недействительны; событие `reset` в `auth_events`.

**Критерии приёмки:**

- Ссылка одноразовая; повторное использование отклонено (AC-31).
- Ответ на несуществующий адрес неотличим от ответа на существующий.
- Прежние сессии пользователя недействительны после смены пароля.

### UC-16 Работа в личном кабинете

**Актёры:** Пользователь, Control Plane, Node Agent.

**Предусловия:** пользователь аутентифицирован; подписка существует.

**Основной сценарий:**

1. Пользователь открывает кабинет и видит тариф, статус, дату окончания, лимит и остаток.
2. Пользователь открывает статистику: Raw Traffic по `uplink` и `downlink`, коэффициент по
   ноде, Billable Traffic, остаток, разбивка по ноде и стране, число активных адресов.
3. Пользователь копирует ссылку подписки на любом из двух доменов или показывает QR-код.
4. Пользователь запрашивает перевыпуск ссылки; Control Plane показывает предупреждение о
   разрыве всех устройств.
5. Пользователь подтверждает; Control Plane выпускает новый токен, аннулирует прежний и
   ротирует credentials на всех нодах.
6. Ноды применяют новые credentials в сроки Н-13; прежние конфигурации клиентов перестают
   работать.
7. Пользователь меняет язык и часовой пояс профиля; интерфейс и письма следуют профилю.

**Альтернативные сценарии:**

- **A1: подписка `suspended_quota` или `expired` (шаг 1).** Кабинет показывает причину и
  действие для восстановления.
- **A2: нода без связи (шаг 6).** Ротация применяется при первом обмене.
- **A3: пользователь запрашивает «выход на всех устройствах».** Все сессии кабинета
  инвалидированы, включая текущую; пользователь выходит.

**Постусловия:** прежний токен возвращает 404; статистика соответствует записям §5.9.

**Критерии приёмки:**

- Состав статистики соответствует §4.12 по каждой ноде за период (AC-34).
- Перевыпуск делает прежний токен недействительным и ротирует credentials (AC-35).
- Смена языка профиля меняет язык интерфейса и следующего письма (AC-22).
