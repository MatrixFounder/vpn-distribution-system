# Постановка задачи: централизованная VPN-платформа

## 1. Цель проекта

Необходимо разработать централизованную платформу для управления собственной распределённой VPN-инфраструктурой.

Платформа должна позволять управлять:

* пользователями;
* VPN-подписками;
* тарифами;
* VPN-серверами;
* группами серверов;
* VPN-протоколами;
* трафиком пользователей;
* промокодами;
* доступом пользователей;
* мониторингом инфраструктуры.

Основная цель — создать систему, позволяющую управлять большим количеством VPN-серверов из единой панели и предоставлять пользователям удобный личный кабинет с единой подпиской для подключения к различным VPN-серверам.

На первом этапе система ориентирована на использование:

* Xray-core;
* VLESS + REALITY;
* Trojan.

При этом архитектура не должна быть жёстко привязана к конкретному VPN-протоколу или реализации VPN-сервера.

# 2. Общая концепция системы

Система должна состоять из двух основных уровней:

```text
                    CONTROL PLANE
                         │
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
     VPN NODE         VPN NODE         VPN NODE
    Germany         Netherlands       Finland
```

## Control Plane

Центральная система управления.

Отвечает за:

* пользователей;
* аутентификацию;
* подписки;
* тарифы;
* доступ;
* промокоды;
* серверы;
* группы серверов;
* конфигурацию VPN;
* статистику;
* мониторинг;
* управление VPN-нодами.

Control Plane является единственным источником истины для всей инфраструктуры.

---

## VPN Nodes

Отдельные VPN-серверы, расположенные у различных VPS-провайдеров и в разных странах.

Каждая нода содержит:

```text
VPN Node
│
├── Xray-core
│
└── Node Agent
```

### Xray-core

Непосредственно обслуживает VPN/Proxy-подключения пользователей.

### Node Agent

Специальный агент управления, отвечающий за:

* регистрацию сервера;
* синхронизацию конфигурации;
* синхронизацию пользователей;
* обновление Xray;
* health checks;
* отправку heartbeat;
* сбор статистики;
* управление сервисами.

# 3. Архитектурные принципы

При проектировании необходимо соблюдать следующие принципы.

## 3.1 Control Plane является единственным источником истины

Все критические данные хранятся централизованно:

* пользователи;
* подписки;
* тарифы;
* права доступа;
* серверы;
* конфигурации;
* статистика.

VPN-нода не должна быть единственным местом хранения критической информации.

---

## 3.2 VPN-ноды являются disposable infrastructure

Любой VPN-сервер должен иметь возможность быть:

* выключен;
* удалён;
* полностью уничтожен;
* заново создан;
* автоматически возвращён в инфраструктуру.

При этом не должны теряться:

* пользователи;
* подписки;
* тарифы;
* права доступа.

Желаемый сценарий:

```text
Server destroyed
       ↓
New VPS created
       ↓
Bootstrap script executed
       ↓
Node Agent installed
       ↓
Node registered
       ↓
Configuration synchronized
       ↓
Node Active
```

---

## 3.3 Управление нодами через Node Agent

Control Plane не должен зависеть от постоянного SSH-доступа к VPN-серверам.

Основной канал взаимодействия:

```text
VPN Node
    │
    │ HTTPS / mTLS
    ▼
Control Plane
```

Node Agent самостоятельно устанавливает исходящее защищённое соединение с центральной системой.

---

## 3.4 Pull / Desired State модель

Control Plane хранит желаемое состояние инфраструктуры.

Например:

```text
Node DE-01

Desired configuration:

Protocols:
- VLESS Reality
- Trojan

Users:
- User A
- User B
- User C

Config version:
145
```

Node Agent получает актуальное состояние и приводит локальную инфраструктуру к нему.

Необходимо отслеживать:

```text
Desired configuration version
Applied configuration version
```

---

## 3.5 Разделение Control Plane и Data Plane

Центральная система управления и VPN-трафик должны быть логически разделены.

Control Plane:

```text
Users
Billing
Configuration
Management
Monitoring
```

Data Plane:

```text
Xray
VPN Traffic
Connections
```

Выход из строя отдельной VPN-ноды не должен приводить к потере Control Plane.

# 4.3 Автоматическое обновление серверов в подписке

Список серверов в subscription URL должен формироваться динамически.

При формировании учитываются:

* активность подписки;
* тариф пользователя;
* доступные Server Groups;
* доступные VPN-протоколы;
* статус сервера;
* ограничения доступа.

```text
Node → Offline
```

он автоматически исключается из выдаваемых пользователю конфигураций.

Если сервер возвращается:

```text
Node → Active
```


# 4.6 Статусы VPN-ноды

Минимальный набор:

```text
Pending
Provisioning
Active
Degraded
Maintenance
Offline
Disabled
```

### Pending

Сервер зарегистрирован, но ещё не готов.

### Provisioning

Идёт настройка.

### Active

Полностью доступен пользователям.

### Degraded

Есть проблемы, но сервер ещё работает.

### Maintenance

Сервер временно выводится из эксплуатации.

### Offline

Сервер недоступен.

### Disabled

Сервер отключён администратором.

# 4.9 Дифференцированная стоимость трафика для серверов

Это важное дополнительное требование.

Разные VPN-серверы могут иметь разную стоимость эксплуатации.

Например:

```text
Germany server
Traffic cost: normal

USA server
Traffic cost: normal

Premium Singapore server
Traffic cost: expensive

Japan server
Traffic cost: expensive
```

Поэтому необходимо реализовать механизм **Traffic Weight / Traffic Multiplier**.

---

## Концепция Traffic Multiplier

Для каждого Server Group и отдельного Node можно настроить коэффициент расхода трафика.

Например:

| Сервер / группа   | Реальный трафик | Списание с лимита |
| ----------------- | --------------: | ----------------: |
| Europe            |            1 GB |              1 GB |
| USA               |            1 GB |              1 GB |
| Japan Premium     |            1 GB |              2 GB |
| Singapore Premium |            1 GB |              3 GB |

Настройка:

```text
Traffic multiplier

Europe:
1.0

USA:
1.0

Japan:
2.0

Singapore:
3.0
```

Если пользователь использовал:

```text
10 GB
```

на сервере с multiplier:

```text
2.0
```

из лимита пользователя списывается:

```text
20 GB
```

---

## Иерархия коэффициентов

Необходимо предусмотреть следующую логику:

```text
Node Traffic Multiplier
        │
        │ highest priority
        ▼
Server Group Traffic Multiplier
        │
        ▼
Default Multiplier
```

Например:

```text
Default:
1.0

Group Asia Premium:
2.0

Node JP-Tokyo-01:
3.0
```

Для JP-Tokyo-01 используется:

```text
3.0
```

---

## Важно: хранить два типа трафика

Необходимо отдельно хранить:

```text
Raw Traffic
```

и:

```text
Billable Traffic
```

Например:

```text
User downloaded:
10 GB

Server multiplier:
2.0

Raw traffic:
10 GB

Billable traffic:
20 GB
```

Это критически важно для корректной статистики.

Пользователь должен видеть оба значения:

```text
Actual traffic used:
10 GB

Traffic charged:
20 GB
```

или более дружелюбное отображение:

```text
Used:
20 GB from subscription limit

Actual transferred:
10 GB
```

```text

Cost per GB

Profitability

Server utilization
```

Traffic Multiplier должен быть отделён от фактической стоимости сервера.


Это две независимые сущности.

## Мой комментарий по новому требованию с разной стоимостью серверов

Я считаю, что ты заметил очень важную вещь, и её стоит заложить **с самого начала**, потому что потом это сложно встроить без миграции всей системы статистики.

Я бы назвал сущность не просто `Traffic Multiplier`, а сделал более общую модель:

```text
Traffic Charging Policy
```

Для MVP она может состоять только из:

```text
multiplier: 1.0
```

Но архитектурно это позволит позже поддерживать:

```text
Fixed multiplier

Per-server multiplier

Per-group multiplier

Per-plan multiplier

Time-based multiplier

User-specific multiplier
```

И главное — с первого дня хранить отдельно:

```text
raw_bytes
```

и:

```text
charged_bytes
```

Это даст очень хорошую основу для будущей экономики VPN-сервиса и позволит гибко управлять дорогими регионами, например Японией, Сингапуром, Австралией или серверами с дорогим трафиком.
