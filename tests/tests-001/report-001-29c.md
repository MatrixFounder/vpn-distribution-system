## Что задача принесла

- `CompositionService.publish_config(conn, node_id) -> int` — в транзакции вызывающего (вне неё —
  `RuntimeError` до обращения к базе): версия `desired_config_version + 1` через `UPDATE nodes …
  RETURNING` (строка ноды заблокирована до коммита — версии одной ноды коммитятся по
  возрастанию), строка `node_config_versions` — документ `XrayConfigBuilder.build(read_node,
  stub_inbounds)` без закрытых ключей REALITY, `checksum` — по документу с ключами ноды; отказ
  источника ключа откатывает транзакцию вызывающего; ноды нет — `LookupError`.
- `wake_config(node_id, version)` — `PUBLISH node:{id}` с меткой `config:{версия}` после коммита
  вызывающего (`_wake` принимает метку: номер строки состава или `config:{версия}`).
- Выдача: `_read(…, config_after)` в том же снимке `repeatable read`, что и состав, читает
  `desired_config_version` и, если версия больше `config_after` (дельта — курсор ноды, снапшот — 0,
  вентиль закрыт — `None`), строку этой версии; `_issue_config` вставляет ключи ноды из identity
  запроса (`_keyed`: источник `reality_key` на подключении снимка) и сверяет сумму документа с
  ключами со строкой. Расхождение суммы, отказ источника (`InvalidTag`, `ValueError` — и ключ не в
  32 байта, `CipherMismatch`), отсутствие строки версии или её повреждение по форме
  (`MalformedConfig`, в том числе `null` на месте `streamSettings`/`realitySettings`; ключи тогда
  не запрашиваются) — раздела `config` нет, ошибка с `node_id` и
  версией в журнал приложения (без текста исключения), состав и команды выдаются; иное
  исключение источника не перехватывается. Курсор
  `config_version` впереди версии ноды — 409 `cursor_ahead` (вместо константы 1). Отказ выдачи сам
  по себе не повод ответить: на текущих курсорах состава и раздела — 204.
- Каркас `STUB_CONFIG_DOCUMENT`, `STUB_CONFIG_CHECKSUM`, `STUB_CONFIG_VERSION`, `stub_config`
  сняты; `StoredConfig` — форма строки версии; `NodeComposition` несёт `config_version` и
  выданный `config`.
- `xray_config`: документ `build` без `privateKey`; `RealityKeySource` — источник `(conn,
  node_id, tag) → 32 байта`; `stub_reality_key` — до 001.27; `reality_tags`; `with_reality_keys`
  — копия с ключом своего тега в каждом `realitySettings`, тег без ключа — `KeyError`; обе идут
  одним обходом формы, повреждённая форма — `MalformedConfig`.
- `inbounds.stub_private_key(node_id, profile)` — SHA-256 от ноды и кода профиля (у каждой ноды
  свой ключ); `stub_public_key(node_id, profile)` — пара к нему.
- `NodeService.approve` публикует версию в своей транзакции после записи статуса и будит ноду
  после коммита; `nodes.read_node(conn, node_id)` — карточка на подключении вызывающего.
- Фикстуры `state-*.json` с конфигурацией — по выдаче генератора с ключами заглушки
  `STUB_NODE_ID`; README контракта — ключ в `config.json`, сумма по документу с ключом, отказ
  выдачи (`config: null` или 204, снапшот при опережающем курсоре), ключ нодам `disabled` и
  `suspended` по вентилю.
- `data-model.md` (`node_config_versions`), `interfaces.md` §5.2 — хранение без ключа, вставка
  при выдаче, сверка суммы, исход отказа, владельцы `publish_config` и пробуждения;
  `system-architecture.md` — версию конфигурации пишет транзакция той операции, что меняет
  конфигурацию: C-01 (подтверждение, операции панели над inbound) или C-02 (ротация по отзыву
  identity, снятие прежнего `short_id`).

### Решения

Решения заказчика 2026-11-04 (хранение без ключа, вставка при выдаче; расхождение суммы — без
`config`) и 2026-11-05 (отказ источника ключа — без `config`) записаны в файле задачи до кода;
решения 2026-11-20 по находкам раунда 1 (L2 — опережающий курсор конфигурации при отказе выдачи:
поведение не меняется, описано в README; L4 — ключ нодам `disabled` и `suspended` по вентилю) —
там же. Правила, записанные по находкам раунда 2 без нового выбора поведения: конфигурацию из
снапшота нода применяет и при меньшей версии (по образцу раздела `agent`, N2); версию пишет
транзакция той операции, что меняет конфигурацию, — C-01 или C-02 (N1).
Технические заметки реализации (поведение не меняют) — там же, раздел «Технические заметки
реализации (2026-11-20)»: пробуждение после коммита делает вызывающий; источник ключа читает на
подключении вызывающего и в снимке выдачи; отказ выдачи на текущих курсорах — 204; версия без
строки или с повреждённой строкой — исход расхождения суммы, иное исключение источника не
перехватывается; повторное подтверждение — следующая версия; документ до 001.27 —
по `stub_inbounds`; импорт `xray_config` и `inbounds` в `composition` — на месте (цикл `plans`).

  описании случая нет; повреждение — раунд 1, L1) — техническая заметка в теле задачи.
