## Что задача принесла

- `CompositionService.enqueue_rotate_node(conn, node_id)` — постановка
  `composition.rotate_node_credentials` в транзакции отзыва, ключ
  `rotate_node_credentials:{node_id}:{xid}`, очередь `critical`.
- `rotate_node_credentials(node_id)` / `rotate_node_credentials_on(conn, node_id)` — исполнитель на
  подключении вне транзакции: одна транзакция — строка ноды `FOR NO KEY UPDATE`, новые ключи всех
  пар ноды по возрастанию `user_id` (`_fresh_credentials`: UUID VLESS и пароль Trojan из CSPRNG,
  контейнеры с привязкой пары, `version + 1`, `rotated_at`), постановка `composition.publish_node`;
  шифр берётся до транзакции (`CipherMismatch` — ничего не записано, задача повторяется).
- `rotate_user_credentials(conn, user_id)` — в транзакции вызывающего: блокировка публикации
  пользователя (`pg_advisory_xact_lock(PUBLISH_LOCK_CLASS, …)`, до коммита вызывающего), затем по
  парам пользователя по возрастанию `node_id` строка ноды `FOR NO KEY UPDATE` и новые ключи; затем
  постановка `composition.publish_user`. Вне транзакции — `RuntimeError`. Предусловие
  вызывающего: до вызова транзакция не держит строк нод и блокировок публикации других
  пользователей, в одной транзакции — один пользователь (докстринг, 001.42, 001.50).
- Обработчик `composition.rotate_node_credentials` (`{"node_id"}`, негодная нагрузка —
  `NonRetryableError`) зарегистрирован в `HANDLERS`.
- `NodeService.revoke_identity`: отзыв, отозвавший хотя бы одну identity, ставит ротацию в своей
  транзакции; повторный — только если у ноды есть отозванная identity, а последняя по `id` задача
  ротации этой ноды отказала (`dead`, `failed`) или её нет
  (`CompositionService.rotation_unfinished`; решение заказчика 2026-11-21, H-1). `enroll` сбрасывает
  `applied_config_version`, `applied_users_seq`, `applied_at`, `last_heartbeat_at` (решение
  заказчика 2026-11-21, M-1), `missed_heartbeats`, `ok_heartbeats`; `desired_*` не трогает.
- `_fresh_credentials` — одна функция новых ключей пары для создания, замены непригодных
  контейнеров (001.29) и ротации.
- `data-model.md` (`node_user_credentials.version`; сброс колонок ноды при обмене токена; §4.5 —
  хранение последней задачи ротации ноды в `done`), `interfaces.md` §5.4 (задача ротации,
  повторный отзыв, перезапуск до пересоздания ноды), `system-architecture.md` (задача ротации по
  отзыву — credentials пар и ключевая пара 001.27).

### Решения

Решения заказчика 2026-11-20 записаны в задаче до кода: `version` пары — как есть (после снятия
пары и повторной выдачи — снова 1, нода применяет ключи по значению); ротацию ставит любой первый
отзыв identity, в том числе отклонение ноды в `pending` (UC-01 A2); повторный — только для
недовершённой ротации (уточнено 2026-11-21, H-1). Там же —
разбор сценария на 1 000 пар (постановка, исполнение, отказ, повтор, поздняя часть, время) и
техническое решение: писатель credentials пары берёт строку её ноды раньше записи (общий первый
шаг публикации и обеих ротаций — иначе ротация ноды по `user_id` и ротация пользователя по
`node_id` могли бы ждать друг друга по кругу). Решения заказчика 2026-11-21 по находкам раунда 1:
повторный отзыв перезапускает отказавшую ротацию (H-1); обмен токена сбрасывает и
`last_heartbeat_at` (M-1). По находкам раунда 2 выбора поведения не было; уточнения реализации
записаны в теле задачи с датой: решает последняя задача ротации этой ноды; очистка очереди
(001.37) последнюю задачу ротации ноды хранит; перевыпуск берёт блокировку публикации
пользователя раньше чтения его пар. Решения заказчика 2026-11-21 по раунду 3 (правки без 4-го
раунда): очистка хранит последнюю задачу ротации ноды только в `done` (`failed`, `dead` — по своему
сроку, тревога DLQ не горит бессрочно); перезапуск после пересоздания ноды — как есть: повторный
отзыв отзывает и новую identity, перезапуск — до обмена нового токена.

## Тесты

Сквозные на живой базе:

- TC-E2E-01 (`test_nodes.py::test_tc_e2e_01_29d_…`): после обмена нового токена `applied_*`,
  `last_heartbeat_at`, `missed_heartbeats`, `ok_heartbeats` сброшены, `desired_*` прежние, нода —
  `pending` (сброс проверяется строкой ноды); подтверждённый новый агент с нулевыми курсорами
  получает 200 — свойство правила 409 (оно сравнивает курсоры запроса с `desired_*`), не сброса.
- TC-E2E-02 (`test_credentials_rotation.py`): нода с 1 000 парами во всех состояниях доступа
  (`active`, `suspended_quota`, `suspended_admin`, `expired`), каждый седьмой пользователь
  заблокирован (`users.status = 'blocked'`); отзыв identity — одна задача
  ротации, `xmin` задачи = `xmin` отозванной identity, хвост ключа — номер транзакции отзыва;
  исполнение — у всех 1 000 пар `version + 1`, новые VLESS и Trojan (расшифровка привязкой своей
  пары), пары тех же пользователей на другой ноде не изменились; ключи всех пар и постановка
  публикации ноды — одна транзакция (`xmin`); после публикации все строки ноды с номерами больше
  прежнего курсора; повторный отзыв после `done` новой задачи не ставит. Время ротации 1 000 пар
  на стенде — **0,025 с** (вывод `pytest -s` теста после раунда 2), предел Н-32 — 4 ч.
- Отклонение ноды в `pending` (UC-01 A2) ставит ротацию.
- TC-E2E-03: `rotate_user_credentials` — 3 пары пользователя на трёх нодах, в том числе `offline`,
  `version + 1`, новые VLESS и Trojan — каждый, сосед не тронут; публикация пользователя — в
  транзакции ротации (`xmin`); дельта ноды после публикации несёт новые ключи и версию.
- Блокировка строки ноды (×2): пока строку ноды держит конкурирующий писатель (оператор
  `_LOCK_NODE`), ротация ноды и ротация пользователя ждут, ничего не пишут и строку пары не
  занимают (`for update skip locked` её видит); после отката — записывают.
- Отказ сверки ключа процесса (×2): `checked_cipher` отказывает `CipherMismatch` — ротация ноды и
  ротация пользователя отказывают исключением; у ротации ноды пары не записаны и публикация не
  поставлена (у ротации пользователя откат делает транзакция теста, поэтому проверяется только
  исключение). Через обработчик: `CipherMismatch` выходит из него как есть, решение очереди
  `decide` по нему — `retry`, а не `failed` или `done`.
- Перезапуск: стоящая ротация повторным отзывом не дублируется, отказавшая (`dead`)
  перезапускается, завершённая не повторяется; решает последняя задача ротации этой ноды (×4:
  `failed`, `running`, `done` после `dead`, `dead` после `done`; `done` соседней ноды не
  закрывает отказ этой); отозванная identity без задачи ротации — перезапуск; новая компрометация
  (identity поколения 2) после завершённой ротации ротирует снова; завершённая позже публикация
  той же ноды (задача другого типа) отказавшую ротацию не закрывает; отзыв ноды без identity
  (`insert_node`) и ноды только с выданным токеном (`test_nodes.py`) ротацию не ставит.
- Порядок: пары созданы в обратном физическом порядке; ротация ноды шифрует их по возрастанию
  `user_id`, ротация пользователя — по возрастанию `node_id`. Порядок блокировок строк нод мерится
  в базе: старшую ноду держит другой писатель — младшая к этому моменту уже взята ротацией
  пользователя (`skip locked` с третьего подключения).
- Перевыпуск (AC-35 «на всех нодах»): пары в каждом из четырёх состояний с credentials
  (`active`, `suspended_quota`, `suspended_admin`, `expired`; ×4) на нодах всех восьми статусов —
  ключи заменены на каждой. Блокировка публикации пользователя: пока её держит публикация,
  перевыпуск ждёт, не держа ни строку ноды, ни строку пары; пара, созданная публикацией на второй
  ноде за время ожидания, ротирована (`version` 2, новый ключ). Блокировка — уровня транзакции:
  после коммита перевыпуска на открытом подключении вне пула её берёт другое подключение.

Модульные: тип и обработчик ротации; негодная нагрузка (×6); исполнитель ротации ноды отказывает
подключению в транзакции, постановка ротации и ротация пользователя — подключению вне транзакции.
